# PART A: AMAZON / AWS

## A1. Code review, ownership, COE, and deployment safety (Builders' Library, Well-Architected, Amazon writing)

### Takeaway
Amazon's documented model puts one small team in charge of each service from code to production, makes peer code review the last human gate, and then lets a fully automated pipeline deploy slowly (one box, then one region wave at a time, with "bake time" and automatic rollback). Incidents feed a blameless "Correction of Error" write-up whose action items flow back into readiness checklists.

### Cited Findings
- **Code review is mandatory and pipeline-enforced (2020).** "All changes going to production start with a code review and must be approved by a team member before merging into the mainline branch." The pipeline "will block any unreviewed commits from being deployed." — [Clare Liguori, "Automating safe, hands-off deployments", Amazon Builders' Library, 2020 (PDF)](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf); [AWS What's New, June 2020](https://aws.amazon.com/about-aws/whats-new/2020/06/new-abl-article-automating-safe-hands-off-deployments)
- **Review is the last human check.** With fully automated pipelines, code review is "the last manual review and approval" before production. Reviewers judge correctness and whether the change is safe to deploy: tested, instrumented for monitoring, and safely roll-back-able. Some teams auto-attach a checklist to every review (new unit tests? new integration tests? commands run locally?). — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Config and infrastructure go through the same safety.** Runtime configuration such as feature flags and rate limits is deployed via dedicated pipelines with the same automatic rollback, "because a bad feature flag configuration change can have an impact on production just as a bad application code change can." Dependencies such as AMI IDs are auto-upgraded at least weekly. — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Staged rollout numbers (2020).** One-box stage first (a single VM/container or a small % of Lambda invocations), typically serving at most 10% of a Region/AZ's requests. A typical pipeline waits at least 1 hour after each one-box stage, at least 12 hours after the first regional wave, and 2 to 4 hours after each later wave. Default pipelines reach all Regions in "about four or five business days." Bake time also requires a minimum number of data points (example: at least 100 requests to the Create API). — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Stated #1 objective:** prevent negative impact to multiple Regions at the same time, and to multiple AZs in the same Region. — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Automatic rollback.** Aggregate high-severity alarms (all of a team's microservice alarms plus canaries) trigger rollback of all that team's in-flight deployments in the Region. One-box stages also roll back on one-box-scoped metrics. The deploy system can also roll back on anomalies in standard metrics from Amazon's internal web-service framework. Some teams deploy 5% of boxes at a time but roll back 33% at a time. — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Emergency speed-ups need senior scrutiny.** Bake time can be dialled down for urgent fixes, but only with review by the organization's Principal Engineers. — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Correction of Error (COE).** Well-Architected describes the COE as "a closed-loop mechanism" for post-incident analysis of any significant event, "even if customers don't see an impact." It aims to prevent recurrence in that workload and to stop the same known risk in other workloads. It is explicitly "not to blame or punish." Triggers include customer-impacting events, missed test cases and missed use cases. — [AWS Well-Architected Tool, "Correction of Error (COE)" concept, 2020](https://wa.aws.amazon.com/wellarchitected/2020-07-02T19-33-23/wat.concept.coe.en.html); [re:Invent 2022 ARC308, "Improving resiliency with the correction of error process" (slides)](https://d1.awsstatic.com/events/Summits/reinvent2022/ARC308_Improving-resiliency-with-the-correction-of-error-process.pdf)
- **COE feeds readiness reviews.** The COE process is "a major driver" of Operational Readiness Review (ORR) checklist items; Well-Architected tells customers their own post-incident analysis should evolve their ORR. — [AWS Well-Architected, Operational Readiness Reviews](https://docs.aws.amazon.com/wellarchitected/latest/operational-readiness-reviews/wa-operational-readiness-reviews.html); [OPS07-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/ops_ready_to_support_const_orr.html); [REL12-BP02 post-incident analysis](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_testing_resiliency_rca_resiliency.html)
- **Two-pizza teams and single-threaded ownership.** AWS describes two-pizza teams as small (10 or fewer), decentralized teams with single-threaded ownership of one service and its customers, with their own metrics and charter. — [AWS Executive Insights, "Amazon's two-pizza team"](https://aws.amazon.com/executive-insights/content/amazon-two-pizza-team/); [AWS eBook "Powering Innovation and Speed with Amazon's Two-Pizza Teams"](https://d1.awsstatic.com/executive-insights/en_US/two_pizza_teams_eBook.pdf)
- **"You build it, you run it" (2006).** Werner Vogels coined the phrase in a 2006 ACM Queue interview: developers operate their own services, which puts them in daily contact with customers and creates a feedback loop. (The ACM page returned 403 to the fetcher; content confirmed via secondary summaries.) — [ACM Queue, "A Conversation with Werner Vogels", 2006](https://queue.acm.org/detail.cfm?id=1142065); summary in [koder.ai](https://koder.ai/blog/werner-vogels-you-build-it-you-run-it-operational-philosophy)

### Inferences
- In this model, technical debt is mostly handled locally. The owning team carries the operational pain (pages, COEs), so it has a direct reason to pay the debt down. There is no central "debt office" in the public material.
- The pipeline treats review as necessary but not sufficient. Slow, metric-gated rollout is the real backstop. That matters for AI code: if review quality drops, the 2020 design still expects bake time and rollback to catch problems.

### Gaps
- builder.aws.com (the new home of the Builders' Library) would not render through the fetch tool, so the newer online version was not compared against the 2020 PDF.
- No public Amazon figure was found for how many COEs are written per year or how many pipelines exist.

## A2. Shared code and dependencies (SOA, API mandate, Brazil)

### Takeaway
Amazon runs a "many-repo" world: each team owns its packages and services, and teams depend on each other through service APIs or versioned packages. The public description of the Brazil build system and its "version sets" comes almost entirely from former employees, not from Amazon.

### Cited Findings
- **Brazil and version sets (secondary, ex-employee accounts).** Brazil is Amazon's internal multi-repo build and dependency system. A "version set" is a pinned set of package versions that has been shown to build together; it records the full transitive dependency closure. Teams can merge in upstream version sets. Dependencies are typed as runtime, build or test, so deployment can strip all but runtime ones. — [DoltHub, "Building at Scale, Amazon style", 2024](https://www.dolthub.com/blog/2024-11-06-brazil-on-dolt/); [DoltHub, "Enterprise Git - The Amazon Story", 2024](https://www.dolthub.com/blog/2024-10-18-git-at-amazon/); [Andreas Zwinkau, "Pondering Amazon's Manyrepo Build System"](https://beza1e1.tuxen.de/amazon_manyrepo_builds.html); [HN comment on version sets](https://news.ycombinator.com/item?id=30946947)
- **Internal deployment packages.** Amazon's own Builders' Library confirms "internal deployment packages" that behave like container images (immutable, rolled back by switching to the prior package). — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Pipelines as code with inheritance.** Amazon's internal pipeline tool lets teams define shared settings (which Regions in each wave, bake times) in a parent class and have every microservice pipeline inherit them. This is how standard safety rules are applied once across many services. — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- **Backward compatibility across services.** Gamma and one-box stages exist partly to catch new code writing data that old code cannot read, and to catch ordering problems when a change spans microservices. — [Builders' Library PDF, 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)

### Inferences
- Version sets explain how a 2024 mass Java upgrade was mechanically possible: a transformation tool can rebuild a package against a new JDK inside a version set and let the normal pipeline prove it.

### Gaps
- The "API mandate" (Bezos memo requiring all teams to talk only through service interfaces) is known publicly only through Steve Yegge's 2011 "platforms rant", a secondhand memoir. I did not retrieve it in this session and found no Amazon-published copy. Treat it as folklore unless a primary source is found.
- Amazon has not published an official description of Brazil.

## A3. AI on existing code: Amazon Q code transformation, Kiro, AI-DLC, and measured quality

### Takeaway
Amazon's headline claim (Aug 2024) is that Amazon Q's code transformation upgraded much of its internal Java fleet and saved 4,500 developer-years. In 2025 it pushed "spec-driven" development through Kiro and an AI-Driven Development Lifecycle (AI-DLC) with humans approving each step. In 2025–2026 it mandated Kiro internally, then faced outages that press reports linked to AI-assisted changes. Amazon disputed that AI-written code caused them, but did add review friction.

### Cited Findings
- **The 4,500 developer-years claim (CLAIM, Aug 2024).** Andy Jassy: average time to upgrade an application to Java 17 fell "from what's typically 50 developer-days to just a few hours." Amazon estimates this saved 4,500 developer-years. More than 50% of production Java systems were upgraded in under six months. Developers shipped 79% of auto-generated code reviews without further changes. Amazon estimates $260M in annualized efficiency gains from security and infrastructure-cost improvements. — [Andy Jassy on X, Aug 2024](https://x.com/ajassy/status/1826608791741493281?lang=en); quoted in [Simon Willison, 24 Aug 2024](https://simonwillison.net/2024/Aug/24/andy-jassy-amazon-ceo/); [Amazon on X](https://x.com/amazon/status/1826741062142230994?lang=en)
- **Application count (reported).** Secondary coverage reports more than 30,000 Java applications migrated in a few months. — [Digiday, 2024](https://digiday.com/media/how-amazons-genai-tool-for-developers-is-saving-4500-years-of-work-260-million-annually/); [Slashdot, Aug 2024](https://developers.slashdot.org/story/24/08/25/0049230/amazon-ceo-ai-assisted-code-transformation-saved-us-4500-years-of-developer-work)
- **What "79% shipped unchanged" does and does not measure.** It is an acceptance rate of AI-generated change sets by reviewers. Amazon published no defect, rollback or incident rate for the transformed code. Skeptical commentary at the time questioned how reviews of that volume were done. — [Slashdot discussion, Aug 2024](https://developers.slashdot.org/story/24/08/26/1559222/amazon-and-aws-developers-may-not-want-to-invite-their-ceos-to-java-code-reviews)
- **Kiro and spec-driven development (2025–2026).** Kiro is AWS's agentic IDE, launched in summer 2025. Its "Specs" follow requirements → design → tasks. Requirements are written in EARS notation ("WHEN [condition] THE SYSTEM SHALL [behavior]"). Kiro later added a design-first variant and a "Bugfix Spec" for working on existing apps. — [Kiro docs, Specs](https://kiro.dev/docs/specs/); [Kiro docs, Feature Specs](https://kiro.dev/docs/specs/feature-specs/); [Kiro blog, "New spec types: fix bugs and build on top of existing apps"](https://kiro.dev/blog/specs-bugfix-and-design-first/)
- **AWS guidance on agentic coding: AI-DLC (Jul 31, 2025).** AWS's "AI-Driven Development Life Cycle" says AI plans, asks clarifying questions, and implements, while humans supply context and approve each step. It renames sprints "bolts" (hours or days) and uses "Mob Elaboration" and "Mob Construction" where the whole team validates AI proposals. The post gives no quantitative results. — [AWS DevOps Blog, Raja SP, 2025](https://aws.amazon.com/blogs/devops/ai-driven-development-life-cycle/)
- **Internal Kiro mandate (Nov 2025, reported).** An internal memo signed by SVPs Peter DeSantis and Dave Treadwell made Kiro Amazon's "recommended AI-native development tool," said existing third-party tools would stay supported but no new ones would be approved, effectively steering staff away from Codex, Claude Code and Cursor. — [Reuters via Yahoo Finance, Nov 2025](https://finance.yahoo.com/news/amazon-pushes-engineers-toward-house-114020167.html). Secondary sources add an 80% weekly-usage target tracked as an OKR and pushback from about 1,500 engineers; I could not confirm these details in a primary or wire source. — [AI CERTs News](https://www.aicerts.ai/news/inside-amazons-kiro-mandate-and-the-future-of-ai-coding/)
- **Dec 2025 Cost Explorer outage: FT report vs Amazon rebuttal (Feb 2026).** The Financial Times reported, citing anonymous sources, that Kiro and Amazon Q had caused at least two production outages, including a 13-hour Cost Explorer outage in a mainland China region after an agent deleted and recreated an environment. Amazon responded that it was one brief interruption to one service in one of 39 Regions, caused by "user error—specifically misconfigured access controls—not AI." Amazon said "the same issue … could occur with any developer tool," called a second AWS event "entirely false," and said it had added mandatory peer review for production access. — [Amazon, "Correcting the Financial Times report about AWS, Kiro, and AI", Feb 2026](https://www.aboutamazon.com/news/aws/aws-service-outage-ai-bot-kiro); [TechTarget, 2026](https://www.techtarget.com/searchsoftwarequality/news/366639129/AWS-Kiro-user-error-reflects-common-AI-coding-review-gap); [AI Incident Database #1442](https://incidentdatabase.ai/cite/1442/)
- **March 2026 retail outages and "controlled friction".** After early-March retail site outages, Amazon made a normally optional engineering meeting mandatory (Mar 10, 2026). Internal documents reviewed by CNBC/FT quote SVP Dave Treadwell on "temporary safety practices" adding "controlled friction" to changes in the most important retail systems, plus investment in "deterministic and agentic safeguards." Amazon's spokesperson called the meeting a normal availability review. Amazon told Fortune only one incident involved AI tools, "none of the incidents involved AI-written code," and the AI-linked one was an engineer following "inaccurate advice that an agent inferred from an outdated internal wiki." — [Fortune, Mar 12, 2026](https://fortune.com/2026/03/12/amazon-retail-site-outages-ai-agent-inaccurate-advice); [CNBC, Mar 10, 2026](https://www.cnbc.com/amp/2026/03/10/amazon-plans-deep-dive-internal-meeting-address-ai-related-outages.html)
- **Senior sign-off on AI-assisted changes (reported, Mar 2026).** Multiple outlets report that junior and mid-level engineers now need a senior engineer's sign-off on AI-assisted production changes. Some reports add a 90-day "code safety reset" over about 335 Tier-1 retail systems and order-loss figures (6.3M orders on Mar 5; 120,000 on Mar 2). These specific numbers come from secondary write-ups of leaked documents; I could not verify them in a primary source. — [Slashdot, Mar 10, 2026](https://slashdot.org/story/26/03/10/212214/after-outages-amazon-to-make-senior-engineers-sign-off-on-ai-assisted-changes); [TechRadar, 2026](https://www.techradar.com/pro/amazon-is-making-even-senior-engineers-get-code-signed-off-following-multiple-recent-outages); [Yahoo/Fortune syndication](https://finance.yahoo.com/news/amazon-puts-humans-back-loop-181403771.html); unverified figures in [openclawai.io](https://openclawai.io/blog/amazon-90-day-code-safety-reset-ai-outages)

### Inferences
- Amazon's AI story has two sides. The 2024 Java claim is a narrow, mechanical, well-bounded upgrade with an existing review-and-pipeline safety net, and Amazon reports high acceptance. The 2025–2026 problems involved agents acting on production access and on stale documentation, which the 2020 pipeline controls do not cover.
- Amazon's official line puts the cause on access controls and human judgment, not on code quality. Either way, the fix it chose is more human review (peer review for production access, senior sign-off), not less.
- An outdated wiki leading an agent astray is a documentation-debt problem. Stale docs become a direct production risk once agents read them.

### Gaps
- No Amazon-published defect, rollback or incident rate for Q-transformed or Kiro-written code was found. The only quality metric is the 79% unchanged-acceptance figure (2024).
- No primary source for the 80% Kiro usage target, the 335-system reset, or the order-loss numbers.
- I did not find an Amazon statement updating the 4,500 developer-years number after 2024, or AWS Transform (the 2025 successor to Q transformation) internal results.

# PART B: ORACLE

## B1. Oracle Database, Java/OpenJDK process, and secure coding guidelines

### Takeaway
Oracle publishes almost nothing about how the Oracle Database codebase itself is maintained. Its best-documented engineering process is OpenJDK, where Oracle leads: formal JEPs for any significant change, a strict deprecate-before-remove rule, at least one Reviewer per change enforced by tooling, and GitHub-based review bots (Skara). Its Java secure coding guide (v11.0, June 2025) adds design rules that double as anti-debt rules.

### Cited Findings
- **JEP process (JEP 1, created 2011, last updated 2018).** A JEP is required for any "nontrivial change to the JDK code base" whose goals and results are "worth communicating broadly." States run Draft → Posted → Submitted → Candidate → Funded → Completed (or Withdrawn/Rejected). The OpenJDK Lead decides what joins the roadmap, informed by Reviewers, Group Leads and Area Leads; reviewer approval is recorded in a "Reviewed-by" line. Owner: Mark Reinhold (Oracle). — [JEP 1](https://openjdk.org/jeps/1)
- **Deprecation policy (JEP 277, 2014, shipped Java 9 in 2017).** Adds `@Deprecated(forRemoval=true, since=...)`. Rule: an API element "should not be removed from the Java SE specification unless" it was marked `forRemoval=true` in a previous version. Terminal deprecation produces stronger "removal warnings." — [JEP 277](https://openjdk.org/jeps/277)
- **Review enforced by tooling.** The JDK repository's jcheck configuration (current master, targeting JDK 28) fails a commit unless it has `reviewers=1` (at least one Reviewer), plus checks for author, committer role, linked JBS issue, whitespace, problem lists and Oracle copyright headers. — [openjdk/jdk `.jcheck/conf` on GitHub](https://raw.githubusercontent.com/openjdk/jdk/master/.jcheck/conf)
- **Skara and the move to GitHub (JEP 369, 2019, delivered JDK 16 in 2021).** Moved OpenJDK from Mercurial to GitHub. Motivations: faster clones, better uptime, APIs for review automation, and a larger contributor pool. Skara bots check and integrate PRs (`pr`), mirror comments to mailing lists (`mlbridge`), and update the JBS tracker (`jbs`). Authors run `/integrate` once "all reviewers are satisfied"; the bot squashes and adds Reviewed-by trailers. Contributor roles (Author, Committer, Reviewer) come from the OpenJDK Census. — [JEP 369](https://openjdk.org/jeps/369)
- **OpenJDK Developers' Guide.** It covers reviewer and sponsor responsibilities and how to review on GitHub, and says newcomers need a sponsor and "a few friends that agree with your change." — [OpenJDK Developers' Guide](https://openjdk.org/guide/)
- **Secure Coding Guidelines for Java SE (v11.0, last updated June 2025).** Sections: 0 Fundamentals, 1 Denial of Service, 2 Confidential Information, 3 Injection and Inclusion, 4 Accessibility and Extensibility, 5 Input Validation, 6 Mutability, 7 Object Construction, 8 Serialization and Deserialization, 9 Access Control, plus a JNI appendix. FUNDAMENTALS-0: "Prefer to have obviously no flaws rather than no obvious flaws" (write code that needs no clever logic to see it is safe). FUNDAMENTALS-2: "Avoid duplication," because duplicated code and data get changed inconsistently. FUNDAMENTALS-3: restrict privileges. The guide now treats the Security Manager as a legacy case. — [Oracle, Secure Coding Guidelines for Java SE](https://www.oracle.com/java/technologies/javase/seccodeguide.html)

### Inferences
- OpenJDK manages debt mostly through process at the API boundary: changes need a public proposal, removals need a release of warning, and every commit needs a named reviewer. This suits a codebase with millions of downstream users that cannot be changed in lockstep.
- The secure coding guide's "obviously no flaws" and "avoid duplication" rules are useful review criteria for AI-generated Java too, though the guide itself does not mention AI.

### Gaps
- I found no Oracle-published description of how the Oracle Database server codebase is reviewed, tested or refactored. Oracle's public testing material (Real Application Testing, Database Replay) is about customers testing their own upgrades, not Oracle's internal process. — [Oracle docs, Introduction to Oracle Database Testing](https://docs.oracle.com/en/database/oracle/oracle-database/21/ratug/introduction-to-oracle-database-testing.html)
- The OpenJDK guide's exact wording on review wait times and HotSpot reviewer counts did not come through the fetch tool. Only the `reviewers=1` jcheck rule is confirmed here.

## B2. The 2018 Hacker News anecdote about Oracle Database (ANECDOTE, unverified)

### Takeaway
This is an anonymous Hacker News comment from November 2018 by a user claiming to be a former Oracle Database developer. It describes Oracle Database 12.2 as roughly 25M lines of C, held together by millions of tests and a slow, flag-driven bug-fix cycle. No Oracle source confirms or contradicts it.

### Cited Findings
- **What it says (ANECDOTE, 2018).** User "oraguy" wrote that Oracle Database 12.2 is "close to 25 million lines of C code." Code is controlled by thousands of interacting flags; fixing a bug can mean understanding 20 or even hundreds of flags. Changing a line breaks thousands of tests. The product survives because of "literally millions of tests." Tests run on a farm of about 100 to 200 servers and take 20 to 30 hours per run. A typical bug takes weeks of submit-and-wait cycles; features take 6 months to 2 years; code review adds 2 weeks to 2 months. Developers juggle several bugs while tests run. — [Hacker News, item 18442941, Nov 2018](https://news.ycombinator.com/item?id=18442941); thread: [Ask HN: largest amount of bad code you have seen work](https://news.ycombinator.com/item?id=18442637); archived copy: [GitHub gist](https://gist.github.com/cam8001/ca334c6e389e006156bf589b3f132e06)
- **Follow-up by the same user (Nov 15, 2018).** The 25M lines is only the C source. Tests are written in an internal DSL called OraTst and add an estimated 25M to 50M more lines. — [Hacker News, item 18456117](https://news.ycombinator.com/item?id=18456117)
- **Replies.** Others described similar setups at enterprise storage vendors and debated whether the pain reflects inherent domain complexity or management choices. None offered Oracle-side evidence. — [Hacker News thread](https://news.ycombinator.com/item?id=18442941)
- **Spread.** The comment keeps recirculating (e.g. on X in 2024), often stripped of its anonymous, unverified status. — [Phil Eaton on X, 2024](https://twitter.com/eatonphil/status/1823105782491091081); [brandur.org Nanoglyph 029](https://brandur.org/nanoglyphs/029-path-of-madness)

### Inferences
- If accurate, the anecdote shows a pattern where tests become the only safety net for a codebase too entangled to reason about, and feedback loops measured in days slow every change. That is the classic shape of high technical debt.
- It is one anonymous person's account of one release (12.2, about 2017). It should not be presented as Oracle's current practice.

### Gaps
- No Oracle statement, engineering blog, paper or talk was found that confirms or disputes the 25M-line figure, OraTst, or the test farm size. I searched Oracle blogs and documentation without success.

## B3. Oracle and AI-assisted coding (2024–2026)

### Takeaway
Oracle's AI-coding story is mostly about products for customers. It announced Oracle Code Assist in 2024 (Java-optimized, used internally first), and by July 2026 it openly supports third-party agents like Claude Code and Codex for building on Fusion. I found no Oracle figure on internal productivity or quality, and no Oracle equivalent of Amazon's Java-upgrade claim.

### Cited Findings
- **Oracle Code Assist beta (Sept 10, 2024).** Announced at CloudWorld as an "AI code companion" available through the Oracle Beta Program, delivered as an IntelliJ IDEA or VS Code plugin. It is Java-optimized and also supports Python, JavaScript, SuiteScript, Rust, Ruby, Go, PL/SQL, C# and C. A customer quote (NRI) cites "thousands of Java applications in production" and hopes to update legacy ones. — [Oracle press release, Sept 10, 2024](https://www.oracle.com/news/announcement/ocw24-oracle-announces-new-ai-capabilities-to-help-accelerate-application-development-2024-09-10/); [Oracle blog, Code Assist beta and NetSuite SuiteScript](https://blogs.oracle.com/ai-and-datascience/announcing-oracle-code-assist-beta-and-netsuite-suitescript-support)
- **First announced May 2024; internal use first (CLAIM).** Oracle said Code Assist would help "quickly update code written in older Java versions." Coverage reports that Oracle deployed it to its own developers before external release, with thousands of Oracle engineers using it for boilerplate, unit tests, documentation and Q&A. — [Oracle press release, May 7, 2024](https://www.oracle.com/europe/news/announcement/oracle-code-assist-can-help-developers-build-applications-faster-with-ai-2024-05-07/); [VentureBeat, 2024](https://venturebeat.com/ai/oracle-code-assist-revealed-ai-powered-coding-assistant); [The New Stack, 2024](https://thenewstack.io/oracle-code-assist-java-optimized-now-in-beta/)
- **Availability status.** Oracle's product page and community posts describe Code Assist as limited availability or beta. I found no general-availability announcement. — [Oracle Code Assist page](https://www.oracle.com/apac/application-development/code-assist/); [Oracle community thread](https://community.oracle.com/products/oracleanalytics/discussion/28522/is-oracle-code-assist-currently-available-for-use-in-oci-and-are-the-plugins-for-ides-released)
- **Fusion AI Studio Skill (Jul 14, 2026).** Oracle lets developers use VS Code, CLIs, Git and "AI coding agents or assistants including Codex and Claude Code" to build Fusion agentic applications "within the same Fusion-native framework for governance that Oracle uses," with local validation, debugging and CI/CD. Generated apps "inherit Fusion security and governance controls." — [Oracle press release, Jul 14, 2026](https://www.oracle.com/news/announcement/oracle-introduces-ai-native-builder-experience-2026-07-14/); [SiliconANGLE, Jul 14, 2026](https://siliconangle.com/2026/07/14/oracle-opens-fusion-agentic-applications-pro-code-developers-coding-agents/); [InfoWorld](https://www.infoworld.com/article/4196667/oracle-expands-ai-agent-studio-for-fusion-applications-with-pro-code-tools.html)
- **Java platform positioning (Mar 2026).** At JavaOne 2026 Oracle released Java 26 (10 JEPs) and pitched Java for AI workloads (Vector API, AOT object caching, the "Java Verified Portfolio", Helidon with LangChain4j).
