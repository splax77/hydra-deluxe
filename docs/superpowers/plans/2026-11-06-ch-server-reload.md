# Reloading the `ch` server mid-session (2026-11-06)

## The plain version

Today the `ch` MCP server loads its Python once, when Claude Code starts it, and keeps that code until someone reconnects it from `/mcp`. Seven sessions since 2026-10-15 lost time to this (the cards are listed under "What was checked"), and the user has now said: "why dont we develop a way to reconnect it mid-session instead of accepting this limitation?" and then "plan it".

The fix is to split the server in two. A small front process is what Claude Code starts and talks to, and it almost never changes. Everything real (the game launch, Frida, the kit, the Star Power watch) stays in `tools/ch_mcp/server.py`, which now runs as a child of the front, called the worker. The front asks the worker for its tool list at start and forwards every call to it, so the tool text keeps its one home in `build_server()`. One new tool, `ch_reload`, stops the worker and starts a fresh one, so merged code is live a few seconds later with nobody touching `/mcp`. `ch_reload` refuses while anything is open (a run, a backup, a Frida agent, the kit, a play session, a watch) and says to call `ch_stop` first, so a reload can never leave the user's files unrestored.

Reloading the Python in place (`importlib.reload`) was rejected, and the code says why: the foreground watch, the Star Power watch, the play session and the method watch each run on a daemon thread, and Frida calls the agents back on threads of its own, so a reload would rebind the module names while every live object and thread kept the old classes. A fresh process is the only clean slate.

One thing nobody can settle by reading: whether Claude Code acts on the `tools/list_changed` notification from a stdio server mid-session, so that a brand-new tool shows up without a reconnect. Claude Code's own docs say it does, and two bug reports from June 2026 say it does not for stdio servers. So the plan makes it a live step and builds a fallback: `ch_call(tool, args)` in the front, which can reach any worker tool by name. Because the key lock in `percall.py` refuses `ch_key`, `ch_press` and `ch_play_chart` with route keys by tool name, `ch_call` would walk past it; the hook learns to look inside `ch_call` before the front merges.

The switch-over costs the user one last `/mcp` reconnect, so Claude Code picks up the new `.mcp.json` entry. After that one, no more.

## The design, point by point

### 1. Two processes, one home for the tools

`tools/ch_mcp/front.py` is new and is what `.mcp.json` runs: `py tools/ch_mcp/front.py -- py tools/ch_mcp/server.py`. Everything after `--` is the worker's command line, so the tests can start a fake worker and nothing in the front names `server.py`. `server.py` keeps `Helper`, `build_server` and `main` unchanged in shape and stays runnable on its own, which is how the tests and the old `.mcp.json` ran it. The front owns no tool text: at start it sends `initialize` to the worker, keeps the `instructions` string from the reply, sends `tools/list`, and serves that list to Claude Code as its own. Its own low-level `Server` gets the worker's `instructions`, plus one sentence the front appends naming `ch_reload` and `ch_call`. A tool's description, schema and name are copied as the worker sent them; a test compares the front's list to the fake worker's list field by field.

### 2. What `ch_reload` does and refuses

`ch_reload` (front) first asks the worker `ch_open_items` (worker, new in R3). That tool returns one line per thing open: the run and its backup folder, an adopted backup, the Frida state agent, the kit, a running play session, a running Star Power watch, a running method watch, a running trace. With any line present, `ch_reload` refuses: "refused: <the lines>; call ch_stop first, then ch_reload". With none, and no other call in flight (the front counts forwarded calls that have not replied), it closes the worker's stdin, waits up to `WORKER_EXIT_CAP_S` for it to exit, terminates it if the cap ends the wait and says so, starts a new worker, waits up to `WORKER_START_CAP_S` for its `initialize` reply, fetches the new tool list, and replies with the old and new process ids, the seconds each step took, the tool counts before and after, the names added and removed, the protocol version the worker and Claude Code negotiated, and whether it sent `tools/list_changed`. The `ch_open_items` check is the worker's, because only the worker knows its own state; the refusal text is the front's.

### 3. Who restores the user's files in each failure

The rule is that the user's files are always put back, and each case names an owner.

The worker exits on its own, by an uncaught exception or because its stdin closed: the worker's own `atexit` runs `Helper.shutdown`, which is `ch_stop`, as today. Owner: the worker.

The worker is killed hard, by the front's `WORKER_EXIT_CAP_S` or by anything else: no `atexit` runs. So the worker writes a marker file, `OPEN_RUN_MARKER` in `game_tools.py` (one constant, the path under the temp root), holding its pid and the backup folder, the moment a run or an adopted backup opens, and deletes it after a successful restore. A fresh worker reads the marker at start. Three outcomes, each with its line in `ch_status` and in the worker's first reply to the front. The folder is gone: the marker is deleted and the line says so (a stuck adoption would make every `ch_stop` fail). The marker's pid is still running: the worker does not adopt, because that process may be a second session's worker with a live run, and restoring under it would corrupt its game; the line names the pid and the folder and gives the by-hand restore, `py tools/ch_mcp/bot_run.py --restore "<folder>"` (`bot_run.py` `_restore_hint`). Otherwise the worker adopts the folder as `_adopted_backup` and says "a previous worker (pid N) left a backup open: <folder>, <age> old; ch_stop restores ..." (the age comes from the folder's own time, and the line names the files `ch_stop` restores and the ones it leaves). Nothing restores a backup adopted from a marker without an explicit `ch_stop`, the user's answer to question 9 ("Yes, take all nine"): the worker's `atexit` leaves that backup and its marker in place and says so; `ch_start` refuses while it is pending, naming the folder and its age and telling the user to call `ch_stop`; and the backup still counts as open in `ch_open_items`, so `ch_reload` refuses. An ordinary adopted backup, taken by `ensure_backup` for a game the server did not start, behaves as before. `ch_stop` restores a marker backup through `bot_run.restore_only` and leaves a game it did not start running, but with the user's ruling "Leave score files": it puts back `settings.ini`, `scorestats.json` and the Rewired registry key, and leaves `scoredata.bin`, `scoresext.bin`, `user.bin`, `profiles.ini` and `profiles.bin` as they are, printing one line for each file it left, saying the backup may be older than the user's play. That kept set is `game_files.KEPT_FILES`, its one home; `restore_only` takes it as a `leave` argument, and with none (a live run's `ch_stop`, and `py tools/ch_mcp/bot_run.py --restore`) every file is restored as before. Owner: the next worker, through the marker. The front's part is to start that next worker at once when the old one dies and to put the worker's adoption line in `ch_reload`'s or the failed call's reply.

The front dies, hard or soft: the worker's stdin reaches end of file, its `run` returns, its `atexit` restores. Owner: the worker, as today. The front holds no game state at all, so nothing is lost with it.

Claude Code exits: on Windows it closes the front's stdin and ends the whole process tree 300 ms later (row P22, from Claude Code's MCP page, "How Claude Code stops a stdio server"; before v2.1.296 it ended the tree at once). The tree includes the worker and a game the worker started, so a worker with a run open never gets its 40 s `ch_stop`, today or under this plan. With nothing open the worker's `atexit` prints "nothing to restore" at once and loses nothing. With a run open, the owner is the marker: no `atexit` completes, the game dies with the tree, and the next worker (next session) adopts the folder as above. The front still closes the worker's stdin on its own end of file and waits up to `FRONT_EXIT_CAP_S`; that wait serves a launcher that does wait (a test, another client), and under Claude Code on Windows it will usually be cut off by the tree's end. LS-R5 reads the log for the nothing-open case only.

A worker that crashes mid-call: the front's wait ends when the worker process exits, and the reply names the tool, the exit code and the new worker's adoption line. The game, if one was running, is an orphan the next `ch_stop` leaves running after restoring the files, which is the behaviour the adopted-backup path already has.

### 4. Tool list changes and the fallback

After a reload the front compares the tool lists. When they differ it sends `tools/list_changed`, if the negotiated protocol let it declare `listChanged` (design point 6). Whether Claude Code then shows the new tool is row P12, settled by LS-R3a. Whatever the answer, `ch_call(tool, args)` in the front reaches any worker tool by name: it refuses a `tool` that is not a string, an `args` that is not an object (so the hook and the front read the same shape and nothing is coerced between them), a name not in the worker's current list (naming the list), and `ch_call` and `ch_reload` as the inner tool, and otherwise forwards `tools/call` and returns the text unchanged. `ch_call` is the fallback for a brand-new tool and for a changed schema; for a tool whose name Claude Code already knows, the direct call goes to the new worker anyway, because the front forwards by name.

### 5. The link to the worker and its caps

The front starts the worker with `subprocess.Popen`, `stdin` and `stdout` as pipes, `stderr` inherited so the worker's lines reach Claude Code's MCP log as they do today, and `CREATE_NO_WINDOW`. The framing is MCP's own stdio framing, JSON-RPC 2.0 with one JSON object per line in UTF-8, the same thing `mcp/server/stdio.py` reads, so the worker needs no change to be spoken to. The front writes four kinds of message (`initialize`, the `initialized` notification, `tools/list`, `tools/call`) and reads replies by id on one reader thread. No Job Object is used, for the reason "What was checked" gives; a game the worker starts belongs to the worker, and the worker's own `ch_stop` and `atexit` are what close it.

The waits, each with a cap and a reply. A worker that does not start: `WORKER_START_CAP_S` on the `initialize` reply; the reply names the command, the exit code if it exited, and that its stderr is in the MCP log. A forwarded call: the front waits for the reply or for the worker process to exit, checking the process every `FRONT_POLL_S`; there is no fixed cap on top of the worker's own, because the worker's caps follow the song's length (`run_cap_s`) and a fixed number would either cut a long legitimate `ch_wait_stats` or be too large to mean anything (question 4 offers a backstop). A reload's stop: `WORKER_EXIT_CAP_S`, then terminate, and the reply says the cap ended it. The front's own exit: `FRONT_EXIT_CAP_S`. The numbers are question 3 and question 5.

`REPLY_CAP_CHARS` stays one home: the worker cuts, the front forwards text as is, and a test pushes a 12,000-character reply through a fake worker and gets it back byte for byte.

### 6. Declaring `listChanged`

The front prints the protocol version Claude Code offers in `initialize` (when it sends one) and the version the connection runs to stderr, and keeps the running version for `ch_reload`'s reply. An `initialize` that offers `2026-07-28` is answered with `2025-11-25` (`_negotiate_initialize`, `mcp/server/runner.py` line 425), a handshake connection that does declare `listChanged`; only a real `2026-07-28` connection, which has no `initialize` and opens with the per-request `_meta` keys, does not. `create_initialization_options` takes no protocol version and is called before any client connects, so the front always passes `NotificationOptions(tools_changed=True)` to it; the package uses that flag on a handshake-era connection and, on `2026-07-28`, recomputes the flag per connection from whether `subscriptions/listen` is served (`server/lowlevel/server.py` line 685, row P28). The version is therefore known only from the handshake, and it decides only whether the front sends. On `2026-07-28` the front does not serve `subscriptions/listen`, so it says so in `ch_reload`'s reply ("list_changed not declared on protocol 2026-07-28; use ch_call for a new tool") and sends nothing. Which version this install negotiates is row P13, read in LS-R2.

### 7. The Hydra server stays out

`tools/hydra_ui_mcp.py` is a second `MCPServer` of the same shape: a `Helper` with state, `atexit` shutdown, `run("stdio")`. The front could serve it later with two changes it does not get now: a `--prefix` argument so the reload tool is `hydra_reload` rather than `ch_reload`, and an open-state tool on that server (its sessions and detached windows) for the refusal. The user asked for `ch`; Hydra is in Out of scope.

### 8. The switch-over and LS-O2

Once the front merges, the running `ch` server is still the old `server.py` as a direct child of Claude Code. The user reconnects `ch` from `/mcp` once (LS-R1); Claude Code reads the new `.mcp.json` entry and starts the front. From then on `ch_reload` replaces that step. LS-O2 of `docs/superpowers/plans/2026-11-06-optimal-score-run.md` has not run and needs `ch_run_chart`, which merged as b009b591 after the current server started, so LS-O2 already needs one reconnect whatever this plan does. Question 6 asks which order the user wants: LS-O2 first on a plain reconnect, then the front; or the front first, LS-R1 and LS-R2 passing, then LS-O2 through the front. In the second order LS-O2's one never-tried call stays `ch_run_chart`, because LS-R1 has shown forwarding and LS-R2 has shown a reload.

### 9. What the worker's `instructions` cannot do

Claude Code reads a server's `instructions` at connect. A reload that changes `build_server`'s instructions string changes what the next `initialize` would say, not what Claude Code already holds; the new text is live at the next reconnect. `ch_reload`'s reply says "instructions changed; live at the next reconnect" when the string differs, so nobody wonders.

## Questions

Each has the recommended side first. The user took all nine recommended sides on 2026-11-06, in session f1fabefd: "Yes, take all nine".

1. **The link to the worker.** Recommended: plain `subprocess.Popen` and the front's own forty lines of JSON-RPC over the pipes (design point 5). The other side: the mcp package's `stdio_client` and `ClientSession`, which are already installed and tested, but which put the worker and the game in a Job Object that is hard-killed two seconds after stdin closes, so a front exit with a run open could kill the game before the worker's restore finished.
2. **The key lock and `ch_call`.** Recommended: `_key_call` in `percall.py` learns to read `mcp__ch__ch_call`'s `tool` and `args` as the inner call (so `ch_call(tool="ch_key")` and `ch_call(tool="ch_play_chart", args={"route": "keys"})` are refused exactly as the direct calls are), and the front merges only after that hook change is on `main`. The lock keeps one home and the user's rule about chokepoints holds. The other side: the front refuses those three names inside `ch_call` itself, which needs no hook change but copies the list.
3. **`WORKER_START_CAP_S`.** Recommended: 30 s. The worker imports frida and six tool modules. The front cannot answer Claude Code's `initialize` until the worker has answered its own (the front serves the worker's `instructions` and tool list), so this cap sits inside Claude Code's connect wait, not behind it. Claude Code's startup limit is set by `MCP_TIMEOUT` and its default is not read here (row P30, unchecked; the MCP page's 10-second hold applies to calls on a resumed session, not to connecting). LS-R1 times the connect, and the number is revisited if it is near the limit. The other side: 10 s, closer to the real import time on a quiet machine, at the cost of a false "did not start" on a busy one.
4. **The front's wait on a forwarded call.** Recommended: no fixed cap; the wait ends at the reply or when the worker process exits, polled every `FRONT_POLL_S` of 0.5 s. The other side: a backstop `FRONT_CALL_CAP_S` of 1,800 s as well, after which the front reports the call as hung and leaves the worker alone; a song longer than 29 minutes would trip it.
5. **`WORKER_EXIT_CAP_S` and `FRONT_EXIT_CAP_S`.** Recommended: 10 s for a reload's stop, because `ch_reload` runs only with nothing open and the worker's `atexit` then prints "nothing to restore" and exits at once; and 90 s for the front's own exit, because a worker with a game and a kit open needs about 40 s for `ch_stop` (`EXIT_CHECK_S` 30 plus `KIT_SETUP_CAP_S` 10 plus the registry compare) and the cap should hold twice that. This 90 s serves a launcher that waits; Claude Code on Windows waits 300 ms and ends the tree (row P22), so for it the marker, not this wait, restores a run left open. The other side: one number for both, 90 s, which makes a stuck reload wait longer than it needs.
6. **LS-O2 and the switch-over.** Recommended: the front first, if its merge lands before the user is ready to give LS-O2 its go; LS-R1 and LS-R2 pass, then LS-O2 runs through the front with `ch_run_chart` its one never-tried call. The other side: LS-O2 first on a plain `/mcp` reconnect, and the front's switch-over after it; one reconnect more in total.
7. **Out of scope.** The list at the end needs the user's yes.
8. **Two new tools the user did not ask for.** `ch_open_items` (R3) is needed by the refusal and stays. `ch_worker_info` (R5) exists only so LS-R3a has a new tool to look for. Recommended: remove it in a small commit after LS-R3a, so the tool list holds only what a user would call. The other side: keep it, since "which worker am I talking to, and since when" is a fair thing to ask after a reload.
9. **A run left open when Claude Code exits.** Today, and under this plan, Claude Code on Windows ends the process tree 300 ms after closing stdin (row P22), so a run open at that moment is never restored by the exiting server; the game dies, and the user's settings and Rewired key stay as the run left them. The other side: the next worker restores at its own start when the marker's pid is dead and no Clone Hero process runs, so the user's keyboard bindings come back without anyone asking; it is a small addition to R3 and it changes what the user sees at the start of a session (a restore, with its lines, before any call).
