# Plan: a hook rule that refuses Bash commands that fail on Windows

Date: 2026-11-06. Planner: a59fd5a52518d5b92 (Fable). Task: bash-windows-rule-plan. Status: waiting for the user's yes. Nothing here is built.

## What the user asked for

The user wants a hook that stops Claude attempting Bash tool commands that will fail on Windows. Their ruling, typed word for word, was "length over 1000 and backslashes". When asked whether three more shapes should go in the hook as well, they typed "yes block those too". The main session reads those two answers as the five parts below. This plan states that reading plainly so the user can correct it at approval.

Only the Bash tool is read. Parts 2 to 5 come from the handoff to Git Bash, which the PowerShell tool does not go through (backslashes are plain characters there, and `cmd /c` runs as typed), so the rule never looks at a PowerShell call. Part 1, the length limit, is the exception: the PowerShell tool's own length limit was not measured (question 3), so this plan does not claim it is free of that problem.

## The rule in one paragraph

A new module, `gates/bash_windows_rule.py`, has one function `check(data)` that returns a refusal reason or `None`. `percall.py` calls it for every Bash call, in the main session and in every subagent, the same way it already calls `delete_rule.check`. There is no second `*` registration (the README's "How a hook is registered" says a new per-call rule becomes a module `percall.py` calls). The module runs with the other refusals, so a crash in it denies the call with the error in the reason: that is the README's `closed` mode, and `common.run` already does it for `percall.py`. The refusal always ends with an `Instead:` line that says what to do instead. The five parts:

1. **Length.** `len(command) > MAX_CHARS`, with `MAX_CHARS = 1000` as the first constant in the module. Raw character count, no weighting: 1,000 passes, 1,001 is refused. The user saw the measured 7,600 option and chose 1,000, so nobody swaps in a higher number. Instead: put the content in a file with the Write tool and run that file (`python -I <file>`, `bash <file>`), or split the command. A long `git commit` is refused like anything else; the agent writes the body to a scratch file with Write and commits with `git commit -F <file> --trailer ...` (a file, not stdin; the preamble forbids `-F -`). In the extract (T2) no `git commit` call passed 1,000 characters, and only 12 `git` calls of any kind did, so this bites almost never. An agent that is already over budget cannot call Write, but it also cannot have written a 1,000-character commit yet; it shortens the body.

2. **Doubled backslashes.** A `\\` pair whose quoting is single quotes, a heredoc body, or a bare word is refused. In those three places the pair is halved somewhere in the handoff to Git Bash, before bash runs the text, so the text is silently changed (users' reports blame MSYS2 re-reading the command line; the plan does not claim to know which program does it, row P9): `'x\\y'` reaches bash as `x\y`, a heredoc line `b:\\` is written as `b:\`, and bare `a\\b` becomes `ab`. A pair inside double quotes passes (open question 1). Instead: write the text to a file with the Write tool, or use forward slashes in paths.

3. **`cmd` with a slash flag.** A piece of the command whose first word is `cmd` or `cmd.exe` (by its last path part, lower-cased, as `delete_rule._word` reads a command word) and that has a later word starting with `/`, unless that same piece holds `MSYS_NO_PATHCONV=1`. Git Bash rewrites `/c` as a Windows path, `cmd` gets no command to run and opens an interactive prompt that sits until the tool's 120-second timeout. Measured today: `cmd.exe /d /c "echo hi"` printed the cmd banner and never `hi`; with `MSYS_NO_PATHCONV=1` in front it printed `hi`. Instead: run it from the PowerShell tool, or put `MSYS_NO_PATHCONV=1` before it. Only `cmd` is listed; open question 2 asks about other slash-flag tools.

   What counts as "a later word starting with `/`": a word that starts with one slash and not two. `cmd //c "echo hi"` is the form Git Bash passes through untouched (measured today: it printed `hi`), so it passes. The text-based figure first measured for this part, 13, and a plain "any word starting with `/`" test would both have refused 10 working `cmd //c` calls. The scanner decides what a piece and a first word are. A piece ends at an operator (`&&`, `||`, `;`, `|`, `&`, a newline) that the scanner labels bare, and the first word is the first word of the piece that is neither a leading `NAME=value` word (so `MSYS_NO_PATHCONV=1 cmd /c x` has `cmd` as its first word and the `MSYS_NO_PATHCONV=1` word is seen) nor anything with a quote character in it. So `cmd /c` inside a quoted string (a `python -c "..."` body, a list of test strings, a search term passed to a shell function), inside a heredoc body, or as an argument of `find -exec` or `bash -c "..."` is not a command word and passes. That is a deliberate gap: such text is not the `cmd /c` the user named, and listing wrappers is the pattern the user called a losing battle (open question 2 covers the same ground).

4. **A `<ref/with/slash>:.dotpath` argument.** A whole shell word, with its quotes taken off, that matches `<word>/<...>:.<letter>`, such as `origin/main:.gitignore`, bare or in single or double quotes. Git Bash rewrites it as a Windows path: measured today, `git show 'origin/main:.gitignore'` and the same word in double quotes both failed with `fatal: ambiguous argument 'origin\main;.gitignore'` while `main:.gitignore` worked. Only a word that is the whole argument counts: the same text inside a longer quoted string (a `python -c "..."` body, say) is not a word of its own and passes. Words inside a heredoc body are not read for this part. Instead: name a ref with no slash (`main:.gitignore`), or run the git command from the PowerShell tool.

5. **A Windows path ending in a backslash before a closing double quote.** A double quote that opens a drive-letter path and never closes, because the path ends `\"`, as in `ls "C:\Users\Patrick\"`. Bash reads `\"` as an escaped quote, so the quote stays open; measured today it failed with `unexpected EOF while looking for matching`. Instead: drop the trailing backslash, or write the path with forward slashes.

   The scanner reads `\"` as an escaped character, so the "word" never ends in its eyes and the test cannot be "a word that ends `\"`". It is three conditions, all of which must hold. One: a double quote that the scanner labels as opening (the previous character is in bare state) is followed at once by a drive letter, `:` and `\`. Two: the first `"` character after that opening is preceded by `\` (so the path run, spaces allowed, ends `\"`). Three: the scanner ends the command still inside that same double quote. Any one missing means pass. That gives these answers. A `\"` inside a longer double-quoted string that does not itself open with a drive letter passes, because the opening quote fails condition one: `python -c "REPO = r\"C:\Users\...\hydra-test\" ..."` and `powershell -Command "... \"$g\target\" ..."` are valid bash. A drive-letter opening quote that does close later, as in `"C:\foo\" bar"`, passes, because the scanner reaches the end outside the quote (condition three fails); bash reads that as the one word `C:\foo" bar`, which is valid bash even if it is not what the writer meant. A command that holds later quotes can end balanced, or leave a different quote open, and pass too (bash may still fail on it); the rule refuses only when the drive-letter quote itself stays open, since only that is the named shape. A drive-letter path in single quotes, a heredoc or a bare word is not a double quote opening and passes.

Each refusal reason starts with a fixed tag naming its part (`[length]`, `[backslashes]`, `[cmd]`, `[ref]`, `[path quote]`), so the proof step can count refusals per part by that tag and the refusal log keeps it in its first 300 characters.

## How the quoting check stays small

Two rulings bear on this. The user said on 2026-10-31 that "trying to ban specific command patterns is a losing battle because there will always be another pattern nobody thought to check." The harness plan of the same day says a hook "never parses free text when a chokepoint exists." The old path gate (session 2026-10-06) matched path-looking text without knowing how it was quoted, and it would have refused 39 ordinary commands.

Here there is no chokepoint: the command string is the only place the fact exists, so the rule reads it. It keeps that reading small in three ways. First, it looks for five fixed shapes and nothing else; the user named each one. Second, parts 2 to 5 all need to know the quoting, and one scanner answers for all four (part 3 asks it where the bare operators and bare words are). It is a small state machine (about forty lines) that walks the command once and labels each character as bare, single-quoted, double-quoted or heredoc body, reading `\x` as one escaped character outside single quotes and a heredoc as starting at `<<WORD` and ending at a line that is exactly `WORD`. Part 2 asks it where each `\\` sits, part 4 asks it for the bare and quoted words, part 5 asks it which double quotes open in bare state and whether the command ends inside one. Nobody writes a second scanner. Third, the scanner has one fixed answer for every input, so there is no "cannot read" case: a quote that never closes means the rest of the command is inside that quote, and a heredoc whose end word never comes means the rest is heredoc body. Bash itself reads an unclosed quote the same way, then refuses the command. A crash anywhere in the module denies the call, per `closed`.

The status helper call is never read: `percall._subagent` already skips every shell rule for a call `progress.is_status_call` recognises, and the new call sits inside that same `if`. The main session makes no status calls.

### T1: the module and its tests

In a worktree of `C:\Users\Patrick\.claude` under `C:\Users\Patrick\.claude\worktrees\bash-windows-rule` (a folder `delete_rule.WORKTREE_FOLDERS` allows), on branch `bash-windows-rule`, one executor writes `gates/bash_windows_rule.py` with `MAX_CHARS`, the scanner, the five parts and `check(data)`, and wires it into `percall.py`: in `_subagent`, into the existing `reason = delete_rule.check(data) or ...` chain; in `_main_session`, into the `reason = _library_refusal(...) or _key_refusal(...)` line, which sits outside the `stall` try so a crash denies. - `test_backslashes_double_pass`: `"a\\b"` passes (open question 1 may change this test's expected value, and the test says so in its name only).
- `test_unclosed_quote_is_inside`: a pair after an unclosed single quote is refused; a pair after an unclosed double quote passes.

- `test_crash_denies`: a `tool_input.command` that is not a string makes `percall.body` deny through `common.run` in `closed` mode, in the main session and in a subagent.
- `test_scanner_is_the_one_reader`: the module defines exactly one function that walks quoting, and `check` reaches each part through it (a structural test: parts 2 to 5 are called with the scanner's output, never the raw string).

## Questions for the user (all open)

1. **Backslash pairs in double quotes.** The rule's real test for part 2 is: refuse when the scanner labels any `\\` as single, heredoc or bare. Double is left out. In double quotes bash itself turns `\\` into `\`, so the usual result is what Claude meant: `"a\\b"` prints `a\b`. But two cases came out wrong in this session's probes: `"\\$HOME"` printed the literal `$HOME`, and `"\\\\srv"` printed `\srv` (bash would print `\\srv`). In the extract (see T2), 104 past calls had pairs only in double quotes, and none of them showed a real failure. Adding double quotes would have refused 269 calls instead of 165. Recommendation: leave double quotes out, because bash's own reading of a pair in double quotes is usually what Claude meant, and revisit if a real failure appears in the refusal log or a transcript.

2. **Other slash-flag tools.** Part 3 lists `cmd` only, as the user's words did. Other Windows tools take slash flags too (`reg`, `tasklist`, `taskkill`, `findstr`), and Git Bash rewrites their `/x` words the same way, though they fail with an error rather than hanging. Past calls to them were not counted. Recommendation: keep `cmd` only. A list of tools is the pattern the user called a losing battle, and the preamble already says to run Windows tools from the PowerShell tool.

3. **The PowerShell tool as a second suggestion in the length refusal.** Today's check shows the PowerShell tool starts `pwsh.exe` with the command in an environment variable (`CLAUDE_CODE_SHELL_LAUNCHER_SCRIPT`) and runs it with `Invoke-Expression`, so it does not pass the text on the command line the way the Bash tool does. Its own ceiling was not measured. Recommendation: leave PowerShell out of the length refusal in this change; the refusal names the Write tool only. If wanted, a one-call probe of an 8,500-character PowerShell command can be added to T3.

4. **Citing the GitHub issues.** The reasons for the halving and the long-command cut-off come from users' reports on `anthropics/claude-code` (#85856, #97409, #93618, #85111), none confirmed by a maintainer, and this planner did not open them. Recommendation: the preamble cites the user's ruling and the measured results in `probe_results.md`, not the issues.

5. **The hook line budget is already over.** `replay.py` fails a run when the hook code is over `LINE_BUDGET = 3100`, a number its comment says only the user changes. Counted with the replay's own `line_total` rule on the hooks repo's committed `main` today, the hook code is 3,679 lines, 579 over, before this change adds a line. So the replay's exit code cannot show that this change keeps the code under budget, and the new module and tests add more (a scanner of about forty lines plus five parts). This plan will not raise the number. Recommendation: you either raise `LINE_BUDGET` or say what to trim; until you do, T2's executor reports the line count before and after and the lines this change added, and the exit code of the replay is expected to be 1 for that reason alone (the executor tells it apart from a crash by the replay's own output lines).
