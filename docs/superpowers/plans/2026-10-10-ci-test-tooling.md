# CI and test tooling: run what nobody runs, run it faster, and add three new kinds of check

Written 2026-10-10 by planning agent TP-4 (session c39f32f3). Source: the test-suite audit (`docs/audit/2026-10-10-test-suite-audit.md`), the W2 tools and C structure scout reports, the code named below, and the web pages cited inline. Every claim from the scouts was checked against the code before it went in here; where I could not check something, the step that would check it is in the plan and the fact is marked unconfirmed.

## What this plan changes and why

Today CI builds Hydra and runs the one C++ test program and the GUI runner. That is all. The Python and PowerShell tool tests (14 Python files, two `.ps1` self-tests) run only when someone remembers. The 42-second C++ run is one process. The GUI suite has two run modes that can disagree, and its doc has the wrong test count (it says 85; `hydra_uitest --list` prints 88). And the suite only checks what the tests assert: nothing looks for memory errors, nothing feeds the file parsers bad input, and nobody knows which lines no test runs.

This plan adds seven things, in value-per-cost order. First, a CI job that runs the tool tests, because that is one small YAML step and stops a slow rot. Second, one run mode for the GUI suite, so a test cannot pass locally and fail in CI. Third, the C++ suite split into a few parallel slices under CTest, which roughly halves the run today and cuts it to about 7 seconds once the 18-second case another session is trimming lands. Fourth, an AddressSanitizer job, which finds memory bugs in code whose tests already pass; it needs a build switch that turns mimalloc off. Fifth, a coverage report, published as a build artifact first and to Codecov only if you want it. Sixth, fuzzing the six file parsers on a schedule with a time box you choose. Seventh, one property-based test with RapidCheck on the replay's "window order does not matter" rule, as a trial.

Nothing here changes what the app does. The ASan and coverage builds never ship. Where a step adds a number (a shard count, a time box, a seed), it is a question in the decisions section, not a choice I made.

## Facts I checked first

The repo `splax77/hydra-deluxe` is public (`gh repo view --json visibility` says PUBLIC). On GitHub, Actions minutes on standard hosted runners are free for public repositories (https://docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions). So extra CI jobs cost wall time only when they are on the critical path, and these all run beside the existing job. The last six CI runs took 6.9 to 10.8 minutes each (`gh run list`), almost all of it the two cold builds; the tests are under a minute.

The C++ tests already keep out of each other's way across processes. `tests/temp_util.h` builds every scratch path as `<temp>hydra_test_<tag>_<pid>`, so two processes never share a file; the single-owner scan enforces that it is the only temp-path lookup under `tests/`. The one HTTP test (`tests/test_dm_report.cpp:511-519`) binds port 0 and reads back the port it got, so there is no fixed port. Only one test opens the audio device (`tests/test_audio_device.cpp`), and CI already skips it. I found no test that writes into `testdata/` or the source tree; the 22 test files that write at all go through `temp_util`, `ScopedFile` or `temp_dir` in the ones I read. The executor of the sharding task confirms the rest (step 3 says how).

The per-case durations (`scratchpad\suite-durations.txt`, 1,250 cases, 41.9 s summed, 78 files) show no single warm-up spike early in the run: the first cases over 0.1 s are the work-pool and CLI tests at 0.1 to 0.4 s. So splitting into processes does not make every shard pay a big shared cache cost; each shard pays only for the charts its own tests touch.

Microsoft's AddressSanitizer for MSVC is supported, not experimental; it is incompatible with `/RTC`, incremental linking and precompiled headers built without it, and the docs warn that another library's `operator new`/`delete` override can make ASan miss or misclassify heap errors (https://learn.microsoft.com/en-us/cpp/sanitizers/asan-known-issues). mimalloc's redirect DLL hooks the same heap calls, so the ASan build must turn mimalloc off. MSVC's libFuzzer (`/fsanitize=fuzzer`) is experimental, available since VS 2022 17.0, recommended together with `/fsanitize=address`, and the two flags must be given separately, never as `/fsanitize=address,fuzzer` (https://learn.microsoft.com/en-us/cpp/build/reference/fsanitize). CMake has no first-class switch for it; flags are passed by hand (https://gitlab.kitware.com/cmake/cmake/-/issues/23725).

`Microsoft.CodeCoverage.Console` ships inside Visual Studio under `Common7\IDE\Extensions\Microsoft\CodeCoverage.Console`, collects coverage for C++ by instrumenting the binary on disk, and needs the exe linked with `/PROFILE`. In VS 2022 it is Enterprise-only; in the current VS it is in every edition (https://learn.microsoft.com/en-us/visualstudio/test/microsoft-code-coverage-console-tool). Its `merge` command (shared with `dotnet-coverage`) writes `coverage`, `xml` or `cobertura`; the docs show Cobertura output only for .NET and say plainly that `dotnet-coverage collect` does not support native modules, so whether the Cobertura conversion keeps C++ line data is still unconfirmed and step 5 checks it before anything is built on it (https://learn.microsoft.com/en-us/dotnet/core/additional-tools/dotnet-coverage). The GitHub `windows-2025` image carries Visual Studio Enterprise with the `Microsoft.VisualStudio.Component.VC.ASAN` component, Python 3.12 by default, .NET SDKs and CMake (https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md). CI uses the `windows-2025-vs2026` label; I could not fetch that image's own readme (the guessed file name 404s), so the ASan job's first run is also the probe that the component is there.

doctest's `doctest_discover_tests` registers one CTest test per case and discovers them at build time with a post-build `--list-test-cases` step (https://raw.githubusercontent.com/doctest/doctest/master/scripts/cmake/doctest.cmake). That would mean 1,250 process starts, which is more overhead than it saves here; the plan slices by source file instead. Codecov's action v5 lets a public repo upload without a token only when the Codecov organisation has turned the token requirement off or the commit is on a fork branch; existing organisations default to "required" (https://docs.codecov.com/docs/codecov-tokens). RapidCheck is BSD-2-Clause, builds as a CMake subdirectory, names Visual Studio 2015 in its CI with "later versions should work", and has adapters for Boost.Test and GoogleTest but not doctest (https://github.com/emil-e/rapidcheck).

## The tasks, in order of value per cost

### 1. Run the tool tests in CI (small; independent of everything else)

Add a second job to `.github/workflows/ci.yml`, `tool-tests`, that runs beside `build-and-test` with no C++ build. It checks out the repo, installs pytest (`py -m pip install pytest`; the runner's default Python 3.12 is enough, the tests use only the standard library plus pytest), and runs `py -m pytest tools/ch_probe/tests tools/test_compare_db.py -q` from the repo root. Naming the two paths matters: `tools/ch_probe/experiments/key_delivery_test.py` and `pad_flash_test.py` match pytest's default pattern and would try to drive Clone Hero, so the job never points pytest at `tools/` as a whole. None of the 12 ch_probe tests needs the game or a window: `test_process.py` and `test_analysis.py` say so in their docstrings, `test_debugger.py` swaps in a fake `_Win32`, and the modules that import `ctypes.wintypes` import fine on a Windows runner. `test_compare_db.py` runs `compare_db.py` as a child process with `sys.executable`, so it needs nothing extra.

The same job then runs the two PowerShell self-tests: `pwsh -NoProfile -File tools/test_mutation_probe.ps1` (builds a throwaway git repo in temp, fakes the build, touches nothing in the checkout) and `pwsh -NoProfile -File tools/test_derive_once_precheck.ps1`. The second one's Part 2 runs the precheck on two real commit ranges (`c6debcd` and `11b9d44`) and skips with a note when they are not in the clone. `actions/checkout` fetches one commit by default, so the job either sets `fetch-depth: 0` for the full history (recommended; decision 1) or accepts that Part 2 is skipped in CI. Neither script reads `~/.claude`, the hooks or `build-cpp` (checked by grep).

`docs/development.md` gets the three commands in its testing section so a developer can run them locally the same way. Proof: the executor runs each command locally and records the pass counts, then the first CI run shows the same counts. A deliberate `assert False` is not needed; if pytest reports fewer tests than the local count, the job is wrong. Files: `.github/workflows/ci.yml`, `docs/development.md`.

### 2. One run mode for the GUI suite, and the right count (small to medium; independent)

Today `hydra_uitest --all` runs every test in one process on one ImGui context, in a hand-kept order (`kRunOrder` in `tests/ui/uitest_tests.cpp:25-33`) because state leaks from test to test. `--jobs N` starts a fresh process per test (`tests/ui/uitest_main.cpp:118-206`). CI uses `--jobs 4`; `ctest` and a plain `--all` use the shared context. A test that passes only thanks to leftover state passes in one and fails in the other, and no run checks both.

The fix is to keep only the fresh-process mode. `main` routes every run that names more than one test, and every `--all`, through `run_parallel`, with a default job count (decision 3). A single `--test <name>` and `--script <file>` still run in-process, because a script needs the engine in the same process and a single test is the debugging case. `kRunOrder` and the ordering loop go away; `register_tests` simply registers each area's table. `ctest`'s entry stays `hydra_uitest --all` and now means the same as CI's command. The comment block at `uitest_main.cpp:11` already describes the fresh-process mode, so it needs no change. The `WaitForMultipleObjects(..., INFINITE)` at lines 167-168 belongs to another session; this task edits `main` and `register_tests`, not the wait, and lands after that session's cap if both are in flight at once.

For the count: `docs/agents/ui-testing.md:32` says "has 85 now (`hydra_uitest --list`)". The exe prints 88 today. The paragraph also quotes 14 s and 22 s timings from 2026-09-27 that it admits are stale. Recommended: drop the standing count and the stale timings from that paragraph, keep the `--list` pointer, and record one fresh timing of the new single mode with its date and run count (decision 3). The `kRunOrder` paragraph at line 137 and the two-row table at lines 21-22 are rewritten to describe the one mode. The doc change is gated by doc review like any `docs/` edit.

Proof: the executor runs three named tests through the new path (`--test scan --test analyze --test dynamics`), which now spawns three processes, and one `--script` run, and shows both still print `[PASS]` lines and the "N of M passed" footer. The main session's merge run of `--all` is the full proof (rule 1). Files: `tests/ui/uitest_main.cpp`, `tests/ui/uitest_tests.cpp`, `docs/agents/ui-testing.md`, `CMakeLists.txt` only if the ctest line changes.

### 3. Shard `hydra_tests` under CTest (medium; after task 2 is merged if both touch `CMakeLists.txt`, otherwise independent)

Replace the single `add_test(NAME hydra_tests COMMAND hydra_tests)` at `CMakeLists.txt:576` with a handful of entries that each run the same exe on a slice of source files. doctest's `-sf=` takes comma-separated wildcard patterns, and `-sfe=` excludes patterns. The slices are: the heavy files on their own (`test_track_state.cpp`, `test_single_owner.cpp`), a few mid-weight groups (`test_preview_controller`, `test_app_state`, `test_store`, `test_search`, `test_cli`, `test_replay` spread so no group is heavier than the heaviest single file), the audio-device test as its own entry `hydra_tests_audio_device`, and a last catch-all entry that runs with `-sfe=` of every file named above. The catch-all is the safety: a new test file lands in it automatically, so no test can fall between shards. One more CTest entry, `hydra_tests_shards_cover_all`, runs a short PowerShell script that lists test cases per shard with `-ltc` and checks that the shards' lists together equal the whole exe's list, once, with no overlap. That script is the only place the shard patterns are written twice, so it reads them from a small list file the CMake entries also read.

CI then runs `ctest --test-dir build-cpp -C Release -j 4 -E audio_device --output-on-failure` instead of the exe directly, and the `-tce=` exclusion line goes away: the audio device test is excluded by its CTest name, and a developer's local `ctest` still runs it. `hydra_uitest` gets the CTest property `PROCESSORS 4` so `ctest -j` does not start four shards beside a runner that itself starts four children.

What it buys, from the durations file: with whole-file slices and four shards, the longest shard today is 19.7 s (that is `test_track_state.cpp` alone, 18.2 s of it one case), against 42 s serial, so about 2.1 times faster. Once the trim of that case to about 1.5 s lands (another session owns it), four shards give a longest shard of about 7.4 s and six or eight shards about 5.9 s, with the single-owner scan at 4.2 s as the floor. So four shards is the right count until that scan is also faster (decision 2). Each shard is a fresh process, so a shard pays its own chart parsing; the durations show that cost is spread thin, not a single spike, so the estimate holds within a second or two.

How this fits agent rule 1: nothing changes for agents. They still run `hydra_tests.exe -tc=` or `-sf=` for their own tests and never the suite. The main session's one full run at merge becomes `ctest -j 4` instead of one exe call; it is still one run. Two free extras come with CTest entries: `ctest --rerun-failed` to rerun only the shard that failed, and `--repeat until-fail:N` for the forced-repro step of a flaky test (the project rule is to force the repro, not loop and hope, so this is a diagnosis aid, never a retry in the pipeline).

Proof: the executor runs the cover-all script and shows the counts agree (1,250 cases, 0 overlap), runs two shards by hand with `--duration=true` and shows each shard's summed time matches the file sums above, and the main session's merge run uses `ctest -j 4` with the wall time recorded. Files: `CMakeLists.txt`, a new `tools/check_shards.ps1` and `tests/shards.txt` (or the list inline in CMake if the executor finds a way to read one list from both; the list must live in one place), `.github/workflows/ci.yml`, `docs/development.md` (the ctest command).

### 4. An AddressSanitizer job (medium; independent of 1 to 3, but lands after 3 so it can call `ctest`)

Two CMake options. `HYDRA_MIMALLOC` (default ON) decides whether `hydra_use_mimalloc()` at `CMakeLists.txt:674-691` runs and whether `third_party/mimalloc` is added at all. `HYDRA_ASAN` (default OFF) forces `HYDRA_MIMALLOC` off and adds `/fsanitize=address` to every target's compile and link options, third-party included, because Microsoft's docs say a process that is only partly sanitised misses errors. Release already compiles with `/Zi` and links with `/DEBUG` (`CMakeLists.txt:65-70`), so ASan has symbols; the option also sets `/INCREMENTAL:NO` explicitly, since incremental linking is unsupported. A new configure preset `asan` in `CMakePresets.json` (binaryDir `build-asan`, `HYDRA_ASAN=ON`) and the matching `buildPresets` entry let `build_cpp.ps1 -Preset asan` build it locally; `build_cpp.ps1`'s `ValidateSet` gains the name.

Turning mimalloc off needs three small code changes. `src/app/allocator.cpp` includes `mimalloc.h` and calls `mi_is_redirected` and `mi_process_info`; with `HYDRA_MIMALLOC` off it compiles against the Windows heap instead: `malloc_redirected()` returns false, the committed-bytes figure comes from `GetProcessMemoryInfo`, and the purge call does nothing. The two tests that require mimalloc (`tests/test_library_jobs.cpp:291` and `:320`) and the GUI harness check that refuses to start without it (`tests/ui/uitest_harness.cpp:188-192`) are compiled behind a `HYDRA_MIMALLOC` define so the ASan build skips the tests and lets the harness start. Shipping builds keep mimalloc exactly as D88 decided; only the sanitizer build differs, and it never ships.

One runtime detail: with the `/MD` runtime, ASan's `clang_rt.asan_dynamic-x86_64.dll` sits beside `cl.exe`, not beside the exe. `tests/test_cli.cpp` copies the CLI tools and "every DLL beside them" into a scratch box and runs them as child processes, so the job runs inside a Visual Studio developer shell (the `Launch-VsDevShell.ps1` that ships with VS, or the `ilammy/msvc-dev-cmd` action), which puts that folder on `PATH` for the children too.

The job `asan` in `ci.yml` builds `hydra_tests` and `hydra_uitest` with the `asan` preset and runs `ctest -j 4 -E audio_device` (task 3) and `hydra_uitest --all --jobs 4`, on every push to main and every PR (decision 4). Expected time: the build is the same length as today's (5 to 7 minutes cold); ASan runs the 42-second suite roughly two to three times slower, so 1.5 to 3 minutes, and the GUI suite about a minute. Total 10 to 15 minutes, in parallel with the existing job, so the wall time of a CI run does not move. Memory: ASan's runtime never returns memory to the OS during a run, so the 300 MB Opus test and the corpus tests may look like leaks in Task Manager; that is documented behaviour, not a finding.

Proof: the first run on the runner proves the `VC.ASAN` component is on the `windows-2025-vs2026` image. Locally, the executor builds the `asan` preset, confirms `MIMALLOC_VERBOSE=1` prints nothing (no mimalloc loaded) and that a one-line deliberate heap overflow in a scratch test makes `hydra_tests` abort with an ASan report, then removes that line. The suite green under ASan is the deliverable; any red is a real finding and goes to the user as a bug, not a reason to weaken the job. Files: `CMakeLists.txt`, `CMakePresets.json`, `build_cpp.ps1`, `src/app/allocator.cpp`, `tests/test_library_jobs.cpp`, `tests/ui/uitest_harness.cpp`, `.github/workflows/ci.yml`, `docs/development.md`. The mimalloc link-order memory note still applies to the normal build; the ASan build has no mimalloc to misorder.

### 5. Coverage report (medium; lands after 3 and 4 share their CMake option pattern; needs decision 5)

A CMake option `HYDRA_COVERAGE` (default OFF) links every exe with `/PROFILE`, which the Microsoft tool needs for native instrumentation. A `coverage` job in CI builds with it, then runs `Microsoft.CodeCoverage.Console instrument` on `hydra_tests.exe`, `hydra_batch.exe` and `hydra_fillcompare.exe` (the CLI tests run the last two as children), starts a collection session in server mode, runs `ctest -j 1 -E audio_device` and `hydra_uitest --all --jobs 1` inside it, shuts the session down, and converts the `.coverage` file. A settings XML excludes `third_party\` and `tests\` sources so the report shows only `src/`.

Before any of that is wired in, one probe step decides the conversion. The executor runs `Microsoft.CodeCoverage.Console merge -f cobertura` on the native `.coverage` file and opens the result: if it contains `src/search/pather.cpp` with line hits, Cobertura works for C++ and the job uses it. If not, the fallback is `-f xml` (Microsoft's own format) fed to ReportGenerator (`dotnet tool install dotnet-reportgenerator-globaltool`, which reads Visual Studio coverage XML and writes HTML, Cobertura and a Markdown summary; https://github.com/danielpalme/ReportGenerator). Either way the job publishes the HTML report as a workflow artifact and writes the line-coverage summary to the job summary page, so the number is visible on every run without a third-party account. Uploading to Codecov is a separate, optional step that needs a Codecov account for the repository and a `CODECOV_TOKEN` secret (the public-repo tokenless path only works if the Codecov organisation setting allows it); that is decision 5.

No threshold. Coverage is a map of what no test reaches, not a score to defend, and a gate would be a new number with no decision behind it. The job runs on pushes to main only, not PRs, because it informs rather than blocks (also decision 5). Expected time: instrumented runs are slower; 15 to 20 minutes in parallel is a fair guess until measured.

Proof: the probe above, then the artifact from the first run, opened by the executor, showing per-file percentages for `src/` and nothing from `third_party/`. Files: `CMakeLists.txt`, `CMakePresets.json` (a `coverage` preset), `.github/workflows/ci.yml`, a new `tools/coverage.settings.xml`, `docs/development.md`.

### 6. Fuzz the file parsers on a schedule (medium to large; after 4, because it needs the no-mimalloc ASan build; needs decision 6)

Hydra reads six kinds of untrusted bytes, and every one has a bytes-in entry point already: `load_songbytes_chart`, `load_songbytes_mid`, `load_songbytes_sng` and `load_songbytes_srb` in `src/parse/song.h:304-320`, `decode_audio` in `src/audio/decode.h:50` with `sniff_format` in `src/core/audio_sniff.h:38` in front of it, and `decode_image` in `src/image/decode.h:31`. Each gets a tiny harness in a new `tests/fuzz/` folder: one `.cpp` per target with `extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size)` that copies the bytes into a `std::vector`, calls the entry point at default settings, catches `std::exception` (a bad file that is reported properly is the expected outcome) and returns 0. Anything else, a crash, an ASan report, a hang past the fuzzer's `-timeout`, or an `abort()`, is a finding. The audio and image targets mostly exercise third-party decoders (miniaudio, stb_vorbis, opus, stb_image), so a finding there is a report upstream or a local patch in `third_party/`, which is a user call when it happens.

CMake gets `HYDRA_FUZZ` (default OFF, requires `HYDRA_ASAN`), which adds one `add_executable` per target, with `/fsanitize=fuzzer` and `/fsanitize=address` as two separate compile and link options; libFuzzer supplies `main`. A `fuzz` preset builds them into `build-fuzz`. Seed corpora come from what is already checked in: every `notes.chart` and `notes.mid` under `testdata/input` for the chart and MIDI targets, `testdata/audio/sine220.{wav,ogg,mp3,opus}` for audio, `testdata/preview/golden_onyx.png` for images. There is no checked-in `.sng` or `.srb`; `tests/test_sng.cpp` and `tests/test_srb.cpp` build their fixtures in code, so a small script `tools/fuzz_seeds.ps1` writes those fixtures once into the seed folder (the executor reuses the tests' fixture builders rather than writing new ones). A short dictionary file for `.chart` (`[Song]`, `[SyncTrack]`, `N `, `S `, `E `, `=`) helps the fuzzer find structure faster; libFuzzer's `-dict=` takes it (https://llvm.org/docs/LibFuzzer.html).

A separate workflow `fuzz.yml` runs on a schedule (weekly, decision 6) with a six-way matrix, one target per job, each with `-max_total_time=<time box> -timeout=10 -rss_limit_mb=2048`, the grown corpus cached between runs with `actions/cache` keyed per target so coverage accumulates the way OSS-Fuzz does it (https://google.github.io/oss-fuzz/). A crash writes a `crash-<hash>` file; the job uploads it as an artifact and fails. The same exes run locally for a long session when wanted; the user's machine is much faster than a runner and has no 6-hour job limit.

Crashes become regression tests this way: the crash file is copied into `testdata/fuzz/<target>/` with a short name, and one table-driven doctest case per target, "fuzz regressions: every file under testdata/fuzz/<target> is rejected without crashing", walks that folder and runs each file through the same entry point and catch block the harness uses (the harness body lives in a header both include, so the rule is written once). A new crash file then needs no code to become a permanent test. The fix for the parser follows the normal path (failing test first, fix, review).

Proof: the executor builds the `fuzz` preset, runs each target for 60 seconds locally on its seeds and shows the fuzzer's `cov:` counter climbing and no crash, then plants a deliberate out-of-bounds read in a scratch copy of one parser and shows the fuzzer finds it inside a minute and the crash file replays through the regression test. Files: `tests/fuzz/*.cpp` and `tests/fuzz/harness.h`, `CMakeLists.txt`, `CMakePresets.json`, `build_cpp.ps1`, `tools/fuzz_seeds.ps1`, `testdata/fuzz/`, `.github/workflows/fuzz.yml`, one new doctest file `tests/test_fuzz_regressions.cpp`, `docs/development.md`. MSVC's fuzzer is experimental; if it does not build or does not report coverage on VS 2026 within one working session, the executor stops and reports, and the fallback is the same harness under `clang-cl` from the LLVM that ships with Visual Studio.

### 7. One RapidCheck trial (small; independent)

The candidate is the replay rule at `tests/test_replay.cpp:1815`, "window order does not matter and SP points add up window by window". Today a hand-rolled LCG at lines 1487-1522 makes 2,000 synthetic windows on the longest corpus chart, and the test checks that reversing the list gives identical rows, that the disc follows SP's payment, and that the first 120 windows' SP points add up one window at a time, for five leeway variants. It is already a property test; what it lacks is shrinking. When it fails, the report is 2,000 windows and a row number. RapidCheck would hand back the smallest window set that still breaks the rule, often two or three windows, which is the whole point of the trial.

Vendor RapidCheck as `third_party/rapidcheck` (BSD-2-Clause; its licence text goes into `THIRD_PARTY_NOTICES.txt` like every other vendored library), `add_subdirectory` with `EXCLUDE_FROM_ALL`, linked only into `hydra_tests`, and kept out of the `hydra_warnings` `/W4 /WX` sweep the way `stb_image.h` is. There is no doctest adapter, so the test calls `rc::check(...)` inside a `TEST_CASE` and `CHECK`s the bool it returns; RapidCheck prints the shrunk counterexample and its seed on failure. The new case sits beside the old one, generates windows with `rc::gen` (an activation index in `[0, n)`, a length in `[1, 60]`, an optional tick offset, an optional squeeze-out index), and checks the same three things. The seed is fixed through `RC_PARAMS` so the suite stays deterministic (decision 7), and the case count stays at RapidCheck's default 100 so the run time matches the 120-window sum the old test already limits itself to (its comment records 5.6 s for 2,000).

Proof: the case passes; then the executor plants a one-character change in `replay_path`'s squeeze-out branch in a scratch build, shows RapidCheck's shrunk counterexample is a handful of windows while the old test prints a wall of rows, and reverts. The trial's write-up (five lines in the handoff) says whether the shrunk output was worth the dependency. Stop condition: if RapidCheck does not compile under VS 2026 with C++17 within an hour, stop and report; do not patch the library. Files: `third_party/rapidcheck/`, `THIRD_PARTY_NOTICES.txt`, `CMakeLists.txt`, `tests/test_replay.cpp` (one added case).

## What can run in parallel

Tasks 1, 2 and 7 touch disjoint files and start together. Task 3 is also independent of 1 and 2 in code, but it and task 2 both edit `CMakeLists.txt` near line 576; the simplest order is 2 then 3, or one executor for both. Task 4 builds on 3 (it calls `ctest`) and task 5 and 6 build on 4 (they share the option pattern and the no-mimalloc path), so 4, then 5 and 6 in parallel. Three waves: {1, 2, 7} and {3}; then {4}; then {5, 6}.

## User decisions

**1. Tool tests: full history for the precheck self-test?** Its Part 2 checks two real commit ranges and skips without them. Options: `fetch-depth: 0` (full clone, a bit slower, Part 2 runs) or the default shallow clone (Part 2 skipped in CI). Recommendation: `fetch-depth: 0` on the `tool-tests` job only; measure the checkout time on the first run and drop back if it is over a minute.

**2. How many shards?** Options: 4, 6 or 8. From the durations: today 4 and 8 give the same 19.7 s (one file bounds it); after the 18-second case is trimmed, 4 gives about 7.4 s and 6 or more about 5.9 s. Recommendation: 4, matching the runner's cores and `--jobs 4`; revisit when the single-owner scan gets faster.

**3. GUI suite: one mode, and what the doc says.** Options for the default job count when `--all` runs: 1 (strictly serial, slowest, simplest) or 4 (what CI uses). Options for the doc: keep a count and refresh it to 88, or drop the standing count and keep only the `hydra_uitest --list` pointer. Recommendation: default 4; drop the count and the two stale timings, and write one fresh timing with its date and run count instead.

**4. ASan on every push and PR, or nightly?** Recommendation: every push and PR. Minutes are free on this public repo, the job runs beside the existing one so wall time does not change, and a memory bug is cheapest to find in the PR that adds it. Fall back to nightly only if it proves flaky.

**5. Coverage: where does the report go, and how often?** Options: a workflow artifact plus the job summary (no account, no secret); Codecov as well (needs a Codecov account for the repo and a `CODECOV_TOKEN` secret, gives PR comments and trend graphs). And: pushes to main only, or PRs too. Recommendation: artifact plus summary first, main only; add Codecov later if you find yourself wanting the graphs. No threshold either way.

**6. Fuzzing: time box and schedule, and where crashes live.** Options for the time box: 5, 10 or 30 minutes per target per run. Schedule: weekly or nightly. Crash files: checked into `testdata/fuzz/` (recommended; that is the regression mechanism) or kept only as artifacts. Recommendation: weekly, 10 minutes per target (six targets in parallel, so about 12 minutes of wall time a week), crash files checked in. A long local run on your machine whenever a parser changes is the better use of fuzzing time than more CI minutes.

**7. RapidCheck: vendor it, and fix the seed?** Options: vendor it (one more third-party dependency and licence notice; it lives only in the test exe) or skip the trial. Seed: fixed (deterministic suite, same as today's LCG) or random per run (finds more, but a red run is not reproducible without the printed seed). Recommendation: vendor it for the trial and decide after seeing one shrunk counterexample; fixed seed.

**8. The runner label (outside this plan's scope, but it affects every new job).** CI pins `windows-2025-vs2026`. GitHub's changelog says that label was a pre-migration test label and that `windows-2025` and `windows-latest` moved to Visual Studio 2026 by 15 June 2026 (https://github.blog/changelog/2026-05-14-github-actions-upcoming-image-migrations). I could not confirm the label's current status. Recommendation: a one-line follow-up that tries `windows-2025` on a branch; if it builds, switch, so the workflow does not depend on a label GitHub called temporary.

## Risks

ASan and mimalloc are the main one, and the plan removes it by never building both into one exe. The second is MSVC's fuzzer being experimental: it may not build on VS 2026 or may report no coverage; the task has a stop condition and a clang-cl fallback. The third is the Cobertura conversion silently dropping C++ data; the probe step comes before any wiring. Fourth, the GUI runner's `main` is also where another session is capping the `INFINITE` wait; two edits to one function need an order, and task 2 names it. Fifth, sharding can hide a test if a slice pattern is wrong; the cover-all CTest entry exists for exactly that and fails the run when the lists disagree. Sixth, the ASan and coverage jobs each add a cold build on a shared runner; on a public repo that costs nothing in minutes, but if GitHub's concurrency limit for the account queues them behind the main job, the wall time grows; the first week of runs shows whether that happens.

## Rough size

Task 1 is an hour. Task 2 is two to three hours plus the doc review. Task 3 is half a day, mostly the cover-all script and the first balanced slice list. Task 4 is half a day to a day, most of it the allocator stub and the first CI run. Task 5 is half a day plus the probe. Task 6 is one to two days including seeds, the regression test and the workflow. Task 7 is two to three hours. About four to five executor-days in all, three waves, with reviews after each merge as rule 5 says.

## What done looks like

A push to main runs four jobs beside each other: the existing build-and-test (now `ctest -j 4` over shards, under a minute of tests), tool-tests (Python and PowerShell, no C++ build, a few minutes), asan (the same tests, slower, finding what the asserts cannot), and coverage (a report artifact and a line in the job summary). A weekly fuzz run keeps six parsers honest and turns any crash into a checked-in file that a doctest case replays forever. `hydra_uitest --all` and CI's run mean the same thing, and the doc stops quoting a count that drifts. One RapidCheck case sits in `test_replay.cpp`, and a five-line note says whether shrinking earned its keep.
