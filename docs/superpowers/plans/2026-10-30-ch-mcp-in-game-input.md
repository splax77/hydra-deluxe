## The plain version

The `ch` server drives Clone Hero so an agent can test it. Today it presses keys with Win32 `SendInput` (`tools/ch_probe/input_driver.py`), and `SendInput` only reaches the window in front. So a run takes the keyboard and the screen, and the user cannot use the machine while it runs. The user ruled that this is wrong: "yes we need to do autonomous runs. that waws the whole point of this", after asking "why does the game need to be focused? hydra doesnt need to be focused when you test it". A run must go on while the user keeps working, with the game window never in front.

The probe of this session showed the way. The game keeps running minimized at about 160 frames a second (Unity's frame count rose from 2,168 to 4,909 between two reads, 16 frames in 100 ms). Its input library, Rewired, has a switch that drops input when the window is not focused; set it off, and the game listens again. Rewired also lets a script create a virtual controller from the game's own "SLInputDrums" definition and hand it to Player 1 with the game's default drum map. Writing a button or an axis on that virtual kit from inside the game, through Frida, made the game react: Start opened "Choose a Profile", and the Green pad read as Green one frame later. None of that touched the keyboard or the window.

So the plan is: build a Frida agent that sets up that virtual kit, presses its pads and buttons on request, and takes it away at the end. The auto-player keeps its schedule in Python and sends each chord to the agent instead of to `SendInput`. The menu driver presses kit buttons instead of keys and reads which screen is on screen through Frida instead of looking. The game is launched minimized and never shown. The user's own keyboard and mouse are taken away from every Rewired player for the run, so their typing cannot reach the game. Two new things get backed up and restored: the registry key Rewired saves its bindings in, and the `pause_on_focus_lost` line of `settings.ini`. Every live step checks the restores the way `ch_stop` checks files today.

Two things the kit cannot do by itself, and the plan says how each is handled. It cannot type, so the song search is out; the song is reached by the start method the old plan's LS-M study finds, with a field set as the fallback. And it cannot scroll with arrows; the user's `settings.ini` has `drum_pad_scrolling = 1`, which by its name lets drum pads scroll menus, but no manual page read says which pads, so the live steps find out.

## The design

### One agent for the kit, loaded beside the state agent

A new Frida agent, `tools/ch_mcp/agent/kit.ts` (built to `kit.js` by a `build:kit` script), stays loaded like `state.ts` and answers four messages, each with an id: `setup`, `press`, `status` and `teardown`. `frida_attach.LiveAgent` gains `request(message, cap_s)`, which posts a dict that has a text `type` and no `id` of its own with the next id, and waits for the reply carrying that id; `read(cap_s)` goes through the same code and every existing test passes unedited. The server keeps a second `LiveAgent` for the kit, attached by `ch_kit_setup`, with its own log `kit-<n>.jsonl` in the session folder. The alternative, one agent for everything, would put thirty Rewired calls into `state.js` and change a file every read goes through; two agents keep the state read as it is.

`setup` runs on the game's main thread (`Il2Cpp.perform(fn, "main")`, as the probe's `--main` did for `q6`): it records the switch's value, sets `ignoreInputWhenAppNotInFocus` false, records for every player whether it has the keyboard and the mouse, takes both away from every player (every player means `ReInput.players.AllPlayers`, which includes Rewired's System player; the registry export shows the System player holds its own keyboard map, so `Players`, which leaves it out, is not enough), finds or creates the custom controller with the tag `KIT_TAG = "hydra-kit"` from definition `KIT_DEFINITION_ID = 6`, adds it to the player named in the message (`KIT_PLAYER`, Player1), loads the default custom maps, and reads the bindings back. The tag, the definition id and the player come in the `setup` message; the agent holds none of the kit's numbers. A second `setup` in the same agent keeps the first one's record of the switch and the flags, because by then the values it would read are the ones the first `setup` set. It replies with everything it recorded and the map it read, so the Python side can check the ten bindings against the list it expects (by the game's action id, in enabled maps) and refuse to go on if one differs. `press` takes a list of element ids with a value each, a hold in frames and a `rewrite` flag: it sets every element, then watches `UnityEngine.Time.frameCount` until the hold has passed (rewriting the values each 2 ms while `rewrite` is true, the probe's way), clears every element, and replies with the frame it went down on, the frame it came up on, and the wall times of both. It runs on Frida's own thread first (no hop to the main thread, so less delay); LS-K1 settles whether that is enough, and the Python side sends `on_main: true` if not. `status` replies with the frame count, `Application.isFocused`, the switch's value, whether the kit exists, and each player's keyboard and mouse flags. `teardown` clears every element a press wrote, removes the kit from its player, destroys it with `DestroyCustomController`, gives every player back exactly the keyboard and mouse flags `setup` recorded, puts the switch back, and replies with one check per step (`what`, `ok`, `detail`) and `all_ok`. A step that throws is a failed check, and the steps after it still run.

Every call the agent makes is a name in one list. `tools/ch_mcp/kit_methods.json` lists each class and method the agent may call, with the dump line it was read from (the Rewired classes are in `dump.cs` under the `Rewired_Core` image: `ReInput`, its `ConfigHelper`, `ControllerHelper` and `PlayerHelper`, `Player`, `Player.ControllerHelper`, `CustomController`, `Controller`, `ControllerMapHelper`, plus `UnityEngine.Time` and `UnityEngine.Application`). K2's executor read the exact names and overloads out of the dump (35 names, each with its dump line; `get_Count` and `get_Item` carry the `List<T>` line because the dump types the three lists they are called on only as `IList`). The teardown's destroy call is `ReInput.ControllerHelper.DestroyCustomController`, dump line 309953.

### Where the schedule runs, and how a press is timed

The schedule stays in Python, in `play_chart.play_chords`, which is already the one owner of "when is this chord pressed". Only the `press` seam changes: `kit_tools.kit_press(agent)` returns a callable that sends `{"type": "press", ...}` with the chord's element ids and waits for the agent's reply (cap `KIT_PRESS_CAP_S`), so by the time it returns the pads have been down for the hold and the game has run at least one input update with them down; `play_chords`'s 5 ms sleep and score read then work as before. The other side, holding the whole chord list in the agent and pressing against `GameManager.songTime` on a 1 ms timer, would remove the Python round trip but would be a second home for the schedule rule (first note, jump back, frozen clock, the lead), in TypeScript, with no fake-clock tests; it is not built unless LS-K4 shows the round trip costs hits.

A press registers once per frame: Rewired reads the kit at its update step, so a press lands up to one frame late (about 6 ms at 160 fps, 17 ms at 60 fps), and a press and release inside one frame is never seen. That is why the hold is counted in frames, not milliseconds, and why the release is a separate frame. Whether the frame grain matters is measured, not guessed: each press row gains `down_frame`, `up_frame` and the agent's wall times, `ch_kit_status` reports the frame rate (frames over one second), and LS-K4's pass line is the same hit count L2 got with keys (142 on Window Map) and a `ch_compare` pass of the game's `scorestats.json` against Hydra's score file. If the compare fails on dynamics only, the velocity is the cause (next paragraph); if hits are missing, the rows' frame numbers show whether the press came late.

The pads are axes, and an axis value is a velocity. The probe pressed with 1.0. Whether the game reads a custom kit's axis as a velocity and grades accents and ghosts by it is unknown; `play_chart.load_dump_chords` reads only each gem's `color` and `cymbal`, so the chords carry no dynamics today. K3 checks whether `hydra_replay score` writes a per-gem accent or ghost field and reports the line; the press message carries one value per element, so a later task can send a lower value for a ghost if LS-K4's compare says the game grades velocity. This plan does not pick velocity numbers.

### Menus without seeing

`menu.ts` gains, for every live instance of every menu class, `active`: the result of `get_gameObject()` then `get_activeInHierarchy()` on it, the documented Unity flag for "is this object shown". `PlayerProfileMenu` joins the menu classes, so the profile screen reads apart from the main menu. From the first live `PlayerSelectionMenu`, the agent reads the two enums by the names a data file gives them (`tools/ch_mcp/menu_fields.json`: class, field name, dump line, enum table), and sends `instrument` and `difficulty` as numbers; `frida_tools.menu_lines` prints them with the enum words. `menu_tools.EXPECT` gains `profile_screen_active`, `main_menu_active`, `song_select_active` and `player_screen_active`, each true when some live instance of that class reads `active` true, and keeps the old words. `menu_steps.json` is rewritten with `kit:` items (`kit:start`, `kit:green`, `kit:yellow`, `kit:blue`, `kit:red`, `kit:select`, `kit:kick`) and no `lane:` or key item: Start then Green on the profile screen, Green on the main menu, then the song list. There the plan does not search. The song is started by `ch_start_song` (the old plan's T8, built after LS-M names the method), which needs no list walk; until then, the walk presses Green on whatever song the list has selected and Ready after it, which is enough for LS-M to watch the start. The fallback if LS-M fails twice is a field set allowed by ruling 5: `SongSelect.currentSong` set to the `SongEntry` whose `folderPath` matches the target (found with `Il2Cpp.gc.choose`), then Green; it is tried in LS-K3's third run only, and the reply shows what the list did. The player screen's instrument and difficulty are read before Ready; the pass line needs `ProDrums` (9) and `Expert` (3) to match the score files, and a different read stops the step and goes to the user with the two numbers. The old method study LS-M stays, driven by the kit; T8 stays and becomes the main song-start route, as the old plan said.

### Launch without focus, and nothing ever shown

`bot_run._real_launch` passes a `STARTUPINFO` with `STARTF_USESHOWWINDOW` and `wShowWindow = SW_SHOWMINNOACTIVE` (7: minimized, not activated), the documented way to ask a new process to open minimized without taking focus. Whether Unity honours it is for LS-K0. The module `tools/ch_mcp/foreground.py` watches `GetForegroundWindow` every `FOREGROUND_POLL_S` on a daemon thread from `ch_start` to `ch_stop`, counts each time the game's window (found by `input_driver.find_game_window`) becomes the front one, and `ch_status`, `ch_kit_status` and `ch_stop` print "foreground went to the game N times"; the count is the pass line of every live step. No tool calls `focus_window` or `SetForegroundWindow` on the kit route, and `ShowWindow` is never called.

### Restore

`game_files` gains the registry: `REGISTRY_KEY = r"HKCU\Software\srylain Inc.\Clone Hero"`, exported with `reg.exe export <key> <file> /y` into the backup folder as `rewired.reg` beside the five files, with a manifest entry. `restore_registry` (called by `restore_all`, which `bot_run`'s restore uses) exports the key again, compares the text with the saved export, and on a difference deletes the key and imports the saved file, then exports once more and compares, raising `RestoreError` named `rewired.reg` if the texts still differ or `reg.exe` fails; the reply line reads "rewired registry: unchanged" or "rewired registry: restored", the way the file lines do. The `reg.exe` runner is an argument (`run_reg`, default `game_files.run_reg` through `bot_run.Env`) so the tests use a fake, and every `reg.exe` call is capped at `REG_CAP_S = 30`. `set_game_setting(path, key, value)` rewrites exactly one `key = value` line inside the `[game]` section of a `settings.ini` and raises `SettingNotFound` when the key is not there, or is there more than once; `ch_start` calls it for `pause_on_focus_lost = 0` after the backup and before the launch (a file without the line launches with a warning), and the restore of `settings.ini` from the backup puts the user's line back. `ch_kit_setup` refuses when the live `settings.ini` does not read `pause_on_focus_lost = 0`, naming `ch_start` as the way to get it. The kit is removed by `ch_kit_teardown`, which also runs as a stop hook before the game is stopped; its reply lists each check (kit gone, players' keyboard and mouse flags back, switch back) as "ok" or the mismatch, and a mismatch makes `ch_stop` print it the way a failed file restore is printed.

## Prior art

Rewired's Custom Controllers page says values are set with `SetAxisValue` and `SetButtonValue` and read during the input update step, and that they "must be updated on the Custom Controller each frame" ([Custom Controllers](https://guavaman.com/projects/rewired/docs/CustomControllers.html)); the probe's `SetButtonValueById` and `SetAxisValueById` are the by-id forms of those, and LS-K1 settles whether one write is kept. A GameDriver support article drives a Rewired game through a custom controller made in the Rewired editor ([GameDriver and Rewired](https://support.gamedriver.io/support/solutions/articles/69000848109-using-gamedriver-with-the-rewired-input-system)), the same idea from a test tool's side. Unity's own Input System does not receive keyboard input while unfocused on desktop ([Unity discussion](https://discussions.unity.com/t/not-receiving-input-while-focus-lost/858982)), which is why the kit, not a fake keyboard, is the route; a Roblox bot's FAQ says the same about `SendInput` ([pyrobloxbot FAQ](https://pyrobloxbot.readthedocs.io/en/stable/faq.html)). The Clone Hero manual says a profile is picked with Start, Strum and Green ([Keyboard and Gamepads](https://wiki.clonehero.net/books/guitars-drums-controllers/page/keyboard-and-gamepads)). frida-il2cpp-bridge's `Il2Cpp.perform(fn, "main")` is how the probe ran setup on the game's main thread ([frida-il2cpp-bridge](https://npmjs.org/package/frida-il2cpp-bridge)). `SW_SHOWMINNOACTIVE` is Windows' "minimized, do not activate" show command for a new process's `STARTUPINFO` ([ShowWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindow)). No Clone Hero bot or in-process input tool was found on the web.
