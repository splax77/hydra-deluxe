## The plain version

The user built the `ch` server so an agent could test Clone Hero with nobody at the keyboard. Two things stop that today, and this plan adds both.

First, the server cannot read Star Power. It needs the meter amount, the full-bar size, whether Star Power is on, when it ends, and the multiplier, both as one read and as a watch over a whole run. The overlay spike already found and proved those five fields from outside the game on 2026-10-28: `sp_watch.py` logged 40,922 rows of them during one song, and `sp_compare.py` checked them against Hydra's path with 31 PASS and 3 FAIL (`tools/ch_probe/experiments/results/overlay-spike/run1_cal0_sp_compare.txt`). The three FAIL lines all come from one split, read in the sitting handoff as: the game did not offer Hydra's third fill (tick 34,944) and activated at the next one (tick 38,016), and the later lines follow from that. That is a difference in where the game offers a fill, not a wrong field. So this plan does not find anything new about the fields. It moves the proven watcher into the server as tools, and gives it one place to live. The server plan listed "Combo, multiplier and Star Power in the snapshot" as out of scope (`docs/superpowers/plans/2026-10-28-ch-mcp-server.md` (removed; `git show ec91f8d1:docs/superpowers/plans/2026-10-28-ch-mcp-server.md`), "Out of scope"); the user's "yes write that plan" brings the Star Power part in scope, and combo stays out.

Second, the server cannot start a song that keys can play. A command-line launch always adds a bot, and the bot never uses Star Power. The only way a key-played song has ever started is the user picking it in the menu. This plan builds two routes. The first drives the menus by key presses through the same `SendInput` path `ch_press` already uses, with a state read after every press so the server knows where it is. The second calls the game's own start method through Frida, so a song starts in one step. The first route is built first and stays the fallback, because the keys the menus take are documented and the start method is not yet known: the dump names it only by a scrambled name among several candidates (below), and a live hook study is what settles which one it is. Once that study has run, the one-step method route becomes the main way, and the key route stays for the day the method stops working. The user's rulings of 2026-10-30 made both routes allowed; the "Rulings" section quotes them.

The first use is a fill check on the Senri Kawaguchi chart: its written fills skip a drum solo from 114.6 s to 166.5 s, Star Power comes ready inside it, and the question is whether the game offers a fill there anyway. Hydra says no (`Song::check_activations` in `src/core/song.cpp` generates no fills when a chart has any). Live step LS3 is that check, with pass and fail lines and a cap.

Does this still need the user? No. After this plan, an agent can start a song, play it and read Star Power with the user pressing nothing, and the user ruled that nobody has to be at the keyboard (ruling 6 below). The standing line "every live run needs the user present and watching" in `docs/agents/clone-hero-mcp.md` was written by an agent, and nobody had quoted the user picking it; T5 replaces it. Two facts still hold. The keys go to whichever window has focus, so nobody can type or click elsewhere on that machine during a run. And `ch_stop` restores `settings.ini` and the four profile and score files, so a run that goes wrong in a menu is undone (`game_files.py`, the five files). The user says in chat when a run may start.

## What exists today (checked in the files)

The Star Power fields are read from outside the game. `tools/ch_probe/constants.py` holds `OFF_SP_AMOUNT = 0x68`, `OFF_SP_MAX = 0x1B0`, `OFF_SP_ACTIVE = 0x42`, `OFF_SP_MULTIPLIER = 0x48`, `OFF_SP_END_TIME = 0x120` and `OFF_SP_OVERFLOW = 0x130`, each still commented "not yet confirmed live". `engine.decode_snapshot` turns one `SNAPSHOT_SIZE` read of the engine object into a `Snapshot` with `sp_amount_u32`, `sp_amount_u64`, `sp_max_u32`, `sp_max_u64`, `sp_active_byte`, `sp_active_u32`, `sp_mult_byte`, `sp_mult_u32`, `sp_end_s` and `sp_overflow_u32`, beside `clock_s` and `score`. `EngineModel.snapshot()` does that read. The Il2Cpp dump settled the widths (`il2cpp-fields.md`, "The six Star Power offsets"): the amount and the maximum are 8-byte `long`s, the flag at `0x42` is one byte with three other flags right after it, the multiplier a 4-byte `int`, the end time a `double`. `sp_compare.DEFAULT_WIDTH = 64` and it reads the flag from `sp_active_byte` for that reason.

`sp_watch.watch(snapshot, write_row, *, now, sleep, poll_s=0.004, cap_s=240.0)` is pure: it polls every 4 ms, writes a row only when a logged field changed, and stops on a frozen or backward clock (`live.StoppedCheck`), a failed read, Ctrl-C or the cap, returning a `WatchSummary` with the reason. `sp_watch.run` is the command line around it: open read-only, `verify_targets`, `engine_finder.find_live_engine_capped` (120 s, `ENGINE_SEARCH_CAP_S`), then `watch`. Run 1 of the sitting ran it beside `play_chart.py`, each with its own engine search, and the presser still hit 857 of 857 (`run1_cal0_play_chart.txt`), so two scans at once did not hurt the presses.

`sp_compare.compare(rows, score, *, resolution, sp_bar_ticks=None, width=64) -> Report` is pure and prints PASS and FAIL lines; `_find_activations(rows)` finds each 0-to-1 flip of the flag; `--resolution` is required only to print Hydra's full meter beside `sp_max`. Run 1 proved the fields: 11 phrase ends each raised the amount by 1,438 to 1,440; `sp_max` held at 5,760 (30 times the chart's resolution of 192, where Hydra's meter is 32 times); each activation set the flag, doubled the multiplier 4 to 8, and set an end time at which the flag cleared; the two activations on the path ended within 2.9 and 1.2 ms of Hydra's deactivation (`run1_cal0_sp_compare.txt`, lines 2 to 27). The write-up `docs/research/2026-10-28-overlay-spike-results.md` is still the empty template, so the result file and the sitting handoff (`docs/handoffs/2026-10-28-overlay-spike-sitting-handoff.md`) are the record.

The server's Frida side reads `GameManager` by field name only (`agent/state.ts`: `songTime`, `isPaused`, `isSongOver`, `isSongPlaying`, `songLoaded`), finds it on every read with a heap walk that L1 timed under 0.1 s, and `frida_tools.state_words` turns the fields into one word. `ch_snapshot` adds the score after the play session's last press. Nothing in the server reads the engine object. No agent today calls `.invoke(` or `.method(` (grep of `agent/*.ts`, 0 hits). The trace agent `trace.ts` already hooks every method of a class by walking `klass.methods` and attaching `Interceptor.attach` at each distinct `virtualAddress` (`targetsOf`, lines 218 to 249), decodes arguments by Il2Cpp type (`decoderFor`), and sends each call with the song time in `args` mode; the method-watch agent of T7 reuses that shape for the menu classes.

The menus are readable by name, and the dump names the classes. `SongSelect : BaseMenu` (dump.cs line 20595) has `currentSong` (`SongEntry`, 0x190), `mainMenu`, `playerSelection` and `onlineMenu` (all `GameObject`, 0x198 to 0x1A8), `songSelectSearch`, `songOptions`. `MainMenu : BaseMenu` (line 42723) has `songSelect`, `settingsMenu`, `onlineMenu` (`GameObject`s), `songScan`, `controlMapper`. `PlayerSelectionMenu : BaseMenu` (line 72822) has `playerIndex`, `confirmSelection`, `instrumentSelection`, `difficultySelection`, a `PlayerSelectionCanvas playerSelectionCanvas` (0x1C8), a private `SongEntry` at 0x238, a private instrument enum at 0x240 and a difficulty enum at 0x241. `PlayerSelectionCanvas : MonoBehaviour` (line 25710) holds `PlayerSelectionMenu[] players` (0x30), `GameObject songSelect` (0x38) and a `TextMeshProUGUI loadPhrase` (0x28). `GlobalVariables : MonoBehaviour` (line 55801) has the static `instance` (0x8), `currentSongEntry` (`SongEntry`, 0x28), `selectedSong` (0x20), `gameMode` (0x50), `playerCount` (0x54), `playerList` (0x38), `isPracticeEnabled` (0x72), `returnToSongSelect` (0x75), `promptRescan` (0x78) and `replayPath` (0xF0). ## Every way to start a song without a person at the menu

**The command line with a bot.** Proven (Test 1 of the feasibility study): the game plays the chart with a bot and writes `scorestats.json`, and "the bot never uses Star Power. In both Trippin runs (11 phrases) it earned 0 phrases, with 0 activations". The manual says `--player` "adds a bot player" and `--profile` is "a template for all of the bot players" ([the command-line page](https://wiki.clonehero.net/books/clone-hero-manual/page/chart-previews-via-the-command-line)). So it cannot answer any Star Power question, and its results screen took no keys in L1.

**The command line with `--song` and no `--player`.** Untried. The manual does not say what the game does with a song and no players, and `CliGameLauncher` (dump.cs line 17909) has no readable method name, so the dump does not say either. It costs one launch to find out, so LS0 tries it once. I rate it unlikely, because the page describes the feature as a preview by bots, but a guess is not evidence.

**`--replay`.** A flag in the string table and a `replayPath` field on `GlobalVariables`. A replay plays back recorded inputs, not live keys, so even if it loads a song it does not give a key-played run. Left out.

**Key navigation of the menus, checked by reads.** The game opens at its main menu with `ch_start()` (proven, L2 and L3). The manual documents the menu keys (Enter for Start, A as Green, arrows to move, a short Blue press for the search tool; "Prior art" says which page says what), and the song list can be searched by name. Three of the driver's states are readable fields: which `SongEntry` is `currentSong` and its `folderPath`, whether a live `GameManager` exists, and its `songLoaded`. Whether a menu is on screen is readable too, now that method calls are allowed: `GameObject.get_activeInHierarchy()` on `SongSelect.onlineMenu` and `MainMenu.onlineMenu` says whether that object is shown. **Built first (T3, T4, T6), and kept as the fallback.**

**The game's own methods through Frida.** Allowed by ruling 2. The dump gives candidates but not the answer, because every name on the start path is scrambled. **Built second (T7 finds it live, T8 calls it), and becomes the main route once LS-M names the method.** The next section lists the candidates.

**The results screen.** A song started from the menu ends on a results screen that takes keys (L2 run 1: the user went back to the main menu by hand), so `ch_open_song` can be called again for a second song in one game process; after a bot launch the results screen took no keys (L1), so that route still ends with `ch_stop`.

## The design

### Where the Star Power read lives, and who calls it

The read lives outside the game, in `ch_probe`: `engine.decode_snapshot` says where each field is and how wide (through `constants.OFF_SP_*`), `EngineModel.snapshot()` reads it, and `sp_watch.watch` polls it. Nothing new reads memory. The server gets one new module, `tools/ch_mcp/sp_tools.py`, with a class `SpTools` beside `GameTools` and `FridaTools`. It runs `watch` in a daemon thread, keeps every row and the latest `Snapshot` in memory, writes the CSV live in the session folder, and formats the fields in one function, `sp_lines(snapshot)`. `ch_sp` prints the latest row the watcher read (at most one poll old), so the single read never touches the process from a second thread and never blocks on an engine search. The alternative was reading the fields inside the game through the Frida agent; it is possible but unproven live, it would run a 4 ms timer inside the game, and it would add a second home for "where the Star Power fields are". The outside read is proven and already has one home.

The watcher finds the engine the way `sp_watch.run` does today, with its own capped search. It does not share the play session's engine address, because the play session's `EngineModel` lives inside `live_play` and exposing it would make the watcher depend on a presser. Two searches at once are proven harmless (run 1).

Registers the tool (thirty names).

Tests: a fake agent records the `invoke` message with the file's class, RVA, `sets` and the decoded arguments; the refusals each name their reason; the wait ends at the cap with the last read; the allowed-calls test passes with the data file naming one method and counts exactly two `.invoke(` sites in `menu.ts`, so a third fails it; a file with a `sets` entry reaches the fake agent in the message and a file without one sends an empty list; `TOOL_NAMES` is thirty. ## Prior art

Clone Hero's command line is documented only as a bot preview ([chart previews via the command line](https://wiki.clonehero.net/books/clone-hero-manual/page/chart-previews-via-the-command-line)); the game's string table adds `--replay` and `--lbsToken`, undocumented. The manual's keyboard defaults are Enter for Start, A for Green and the arrows for Strum Up and Down ([Keyboard and Gamepads](https://wiki.clonehero.net/books/guitars-drums-controllers/page/keyboard-and-gamepads)), and it says "You need to press Start and select a profile using Strum Up/Down and Green before you can navigate the menus"; the short Blue press for the search tool is on [How to Play](https://wiki.clonehero.net/books/clone-hero-manual/page/how-to-play). Neither page says which key the search box takes text from or what the Ready press is; those are the data file's guesses. Unity UI automation from outside a stock build has no general tool: AltTester drives menus and keys but only in an instrumented build of the app ([overview](https://alttester.com/docs/desktop/v.2.0.0/pages/overview.html)). frida-il2cpp-bridge reads instance fields as `object.field(name).value`, calls methods as `object.method(name).invoke(...)`, and finds live objects with its choose call ([README](https://npmjs.org/package/frida-il2cpp-bridge)); the server already uses the field read and the choose in `state.ts` and `gamemanager.ts`, and T4 and T8 add the static-field read and the two calls the same way. Unity's `GameObject.activeInHierarchy` is the documented "is this object active in the scene" flag ([Unity manual](https://docs.unity3d.com/ScriptReference/GameObject-activeInHierarchy.html)), and il2cpp exposes it as `get_activeInHierarchy`.
