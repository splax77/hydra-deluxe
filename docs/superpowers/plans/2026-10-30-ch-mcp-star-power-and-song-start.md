# Plan: Star Power reads and a song start without the user, for the `ch` MCP server (2026-10-30)

Task id `CHSP-PLAN`, session `9a82ff65-26fd-45d5-8f6c-5766bbb06a37`. Plan only; no code changed. Every path, number and claim below was checked today against the files named beside it, on main's tip 9f007234, unless it says otherwise.

## The plain version

The user built the `ch` server so an agent could test Clone Hero with nobody at the keyboard. Two things stop that today, and this plan adds both.

First, the server cannot read Star Power. It needs the meter amount, the full-bar size, whether Star Power is on, when it ends, and the multiplier, both as one read and as a watch over a whole run. The overlay spike already found and proved those five fields from outside the game on 2026-10-28: `sp_watch.py` logged 40,922 rows of them during one song, and `sp_compare.py` checked them against Hydra's path with 31 PASS and 3 FAIL (`tools/ch_probe/experiments/results/overlay-spike/run1_cal0_sp_compare.txt`). The three FAIL lines all come from one split, read in the sitting handoff as: the game did not offer Hydra's third fill (tick 34,944) and activated at the next one (tick 38,016), and the later lines follow from that. That is a difference in where the game offers a fill, not a wrong field. So this plan does not find anything new about the fields. It moves the proven watcher into the server as tools, and gives it one place to live. The server plan listed "Combo, multiplier and Star Power in the snapshot" as out of scope (`docs/superpowers/plans/2026-10-28-ch-mcp-server.md`, "Out of scope"); the user's "yes write that plan" brings the Star Power part in scope, and combo stays out.

Second, the server cannot start a song that keys can play. A command-line launch always adds a bot, and the bot never uses Star Power. The only way a key-played song has ever started is the user picking it in the menu. This plan surveys every real way to start one without a person at the menu, and recommends driving the menus by key presses through the same `SendInput` path `ch_press` already uses, with a state read after every press so the server knows where it is. That breaks one written rule ("no tool opens any menu"), so question 1 puts it to the user.

The first use is a fill check on the Senri Kawaguchi chart: its written fills skip a drum solo from 114.6 s to 166.5 s, Star Power comes ready inside it, and the question is whether the game offers a fill there anyway. Hydra says no (`Song::check_activations` in `src/core/song.cpp` generates no fills when a chart has any). Live step LS3 is that check, with pass and fail lines and a cap.

Does this still need the user? Partly, and the plan says where. After this plan, an agent can start a song, play it and read Star Power with the user pressing nothing. The user still has to be at the machine, for two reasons. The standing rule in `docs/agents/clone-hero-mcp.md` says every live run needs the user present and watching, because the game changes the user's files. And the keys go to whichever window has focus, so the user cannot type or click elsewhere during a run. Three things can still put the user back at the keyboard: question 1 answered no (they start songs by hand), the first menu key sequence failing in LS1 (it is a guess until then), and the menu read being unable to tell an open menu from a hidden one (question 1, last case). Each is named with its own stop line below.

## Questions for the user

Each has my recommendation first, then the strongest case against. Say "go with the recommendations" to approve them all. Questions 1 to 4 change what gets built.

**1. Tools that open menus.** `docs/agents/clone-hero-mcp.md` says, under "Safety rules": "Play stays offline. The server launches the game only with the command line `bot_run.launch_command` builds, and no tool opens any menu. The user picks songs in the menu by hand." The server plan's question 1 set that because nothing had proved another way to reach a key-played song. The only non-bot route this plan found is the game's own menus (see "Every way to start a song"). Recommendation: change the rule to "no tool opens the Online menu; `ch_open_song` drives only the main menu, the song list and the player screen, by keys, and refuses to press anything while the menu read says the Online menu is open". The offline guarantee stays what it was: the server plan's words are "the network adapter off is the only hard guarantee and stays the user's choice". Both ends: `ch_open_song("C:\Clone Hero\songs\Hydra Probe\Window Map")` presses Enter, types "Window Map" into the search, confirms, and the song starts with the user watching but not touching anything; a run where the menu read says the Online menu is open stops at once with "refused: the Online menu is open", and presses nothing. The case against: a key sequence that goes wrong in a menu could change a setting or a profile; the answer is the read after every press, the per-step cap, and `ch_stop`'s restore of `settings.ini` and the four profile and score files, which already undoes any such change (`game_files.py`, the five files). The weaker point, which the recommendation has to carry: the Online guard rests on a read that may not work. `facts.json` types `SongSelect.onlineMenu` and `MainMenu.onlineMenu` as `GameObject`, a reference to a scene object. Reading it by field name says the object exists; it does not say the menu is on screen, and telling a shown object from a hidden one takes a method call (`activeInHierarchy`), which the no-writes rule forbids (question 2). So `onlineMenuLive` may read true on every screen. That has not been looked at; LS1 looks at it first (its stop line). If it reads true when the Online menu is not open, the guard cannot tell, `ch_open_song` would refuse every time, and the plan comes back to you with that fact before LS2 or LS3 runs. If you keep the rule as written, the song-start half of this plan is dropped and the user keeps starting songs by hand; the Star Power half still goes ahead.

**2. Calling the game's own methods.** The same page says "The Frida agents only read and trace. They never write game memory, set a field or call a game method", and `tools/ch_mcp/tests/test_frida_attach.py` refuses any agent that matches `.invoke(` or `new NativeFunction`. The feasibility study imagined "pick a song and difficulty for a human-style player through `SongSelect`" (`docs/research/2026-10-28-clone-hero-mcp-feasibility.md`, "Song control"). Recommendation: do not do it, and keep the rule and its test unchanged. Two reasons: the rule comes from the EULA ruling, and this plan reads the user's "Proceed, my call" (2026-10-28) as covering reading and hooks only, which is a reading, not a quote of what it covered; and `SongSelect` has 72 methods of which 5 besides the constructor have readable names (`Start`, `OnEnable`, `OnDisable`, `Update`, `Awake`, from `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\6142\facts.json`; they are Unity's own lifecycle names), so nobody knows which one starts a song, and finding it is a hooking study of its own. Both ends: with the rule kept, a song starts only through key presses the game treats like a player's; with the rule dropped, an agent could call an obfuscated method that starts the song in one step, but the first wrong guess could do anything from changing the selection to crashing the game. The case for dropping it: it would be faster and would not depend on the menu layout. I recommend against.

**3. Four new numbers for the menu driver, and one changed cap.** (a) `MENU_STEP_CAP_S = 10`: after the last key of a step, the menu read must show the change the step expects within 10 s, else the driver stops and reports the step and the read. The clock starts after the last key, so typing time is not under this cap. 10 s is a guess. The only menu timing on record is run 1 of the spike: its log watcher printed "GO" at 20:36:10.974 and the "Loading Song" line appeared at 20:36:15.244 (`run1_cal0_log_tail.txt`), 4.3 s later. That 4.3 s includes the time the user took to react to "GO", so it is an upper bound on one transition, and no other transition was timed. (b) `MENU_KEY_GAP_S = 0.25`: the pause between two presses inside one step (typing a name, or Down several times), a guess with no measurement behind it; LS1 records whether a shorter gap drops keys. Typing takes the name's length times this gap: "Window Map" is 10 characters, 2.5 s; "Ladies Talk [Kiyo Sen] (Drumeo Performance)" is 43, 10.75 s. (c) `SEARCH_DOWN_CAP = 10`: when the search result the read shows is not the target folder, the driver presses Down at most 10 times before it stops with "the target is not among the first 11 results". (d) `MENU_POLL_S = 0.5`: how often the driver reads the menu while it waits for a step's change; a guess, and each read is three heap walks (`MainMenu`, `SongSelect`, `PlayerSelectionMenu`), so a shorter poll would mostly measure the walks. (e) The run cap. `play_chart.RUN_CAP_S` and `sp_watch.RUN_CAP_S` are both 240 s of wall time, and the Senri song is 260,504 ms long (`song_length` in `C:\Clone Hero\songs\Hydra Probe\Ladies Talk fill check\song.ini`), so both would stop 20 s before its end. The solo question is settled by 166.5 s, so LS3 would still work, but a full run needs the longer cap. Recommendation: the server passes a cap of the song length plus `bot_run.POLL_CAP_EXTRA_S` (60 s, approved in the server plan's question 5 for the stats wait) when it knows the song folder, and the modules keep 240 s as their default for the command line. That reuses an approved number for two more waits and adds no new number; the one rule (length plus 60 s) already sits in `bot_run.start_run`, and T3 moves it into a function there so the server and `start_run` call the same code. The case against: 240 s was an approved number and raising it means a stuck run waits longer before it stops; the stall check (`live.STALL_S`, 5 s of frozen clock) still ends a run whose song stopped.

**4. The first menu key sequence, and what the menu read can see, are guesses until LS1.** The Keyboard and Gamepads page ([wiki](https://wiki.clonehero.net/books/guitars-drums-controllers/page/keyboard-and-gamepads)) lists Enter as Start, A as Green, S as Red and the up and down arrows as Strum Up and Down, and says "You need to press Start and select a profile using Strum Up/Down and Green before you can navigate the menus." The second guess is the menu read: that an object being alive means its menu is on screen. Question 1 gives the reason it may not. Recommendation: T6 writes the sequence as data (`tools/ch_mcp/menu_steps.json`) from the manual, marked unverified, and LS1 walks it one press at a time with the user watching and corrects the file in a one-file data commit (reviewed like any other). ## What exists today (checked in the files)

The Star Power fields are read from outside the game. `tools/ch_probe/constants.py` holds `OFF_SP_AMOUNT = 0x68`, `OFF_SP_MAX = 0x1B0`, `OFF_SP_ACTIVE = 0x42`, `OFF_SP_MULTIPLIER = 0x48`, `OFF_SP_END_TIME = 0x120` and `OFF_SP_OVERFLOW = 0x130`, each still commented "not yet confirmed live". `engine.decode_snapshot` turns one `SNAPSHOT_SIZE` read of the engine object into a `Snapshot` with `sp_amount_u32`, `sp_amount_u64`, `sp_max_u32`, `sp_max_u64`, `sp_active_byte`, `sp_active_u32`, `sp_mult_byte`, `sp_mult_u32`, `sp_end_s` and `sp_overflow_u32`, beside `clock_s` and `score`. `EngineModel.snapshot()` does that read. The Il2Cpp dump settled the widths (`il2cpp-fields.md`, "The six Star Power offsets"): the amount and the maximum are 8-byte `long`s, the flag at `0x42` is one byte with three other flags right after it, the multiplier a 4-byte `int`, the end time a `double`. `sp_compare.DEFAULT_WIDTH = 64` and it reads the flag from `sp_active_byte` for that reason.

`sp_watch.watch(snapshot, write_row, *, now, sleep, poll_s=0.004, cap_s=240.0)` is pure: it polls every 4 ms, writes a row only when a logged field changed, and stops on a frozen or backward clock (`live.StoppedCheck`), a failed read, Ctrl-C or the cap, returning a `WatchSummary` with the reason. `sp_watch.run` is the command line around it: open read-only, `verify_targets`, `engine_finder.find_live_engine_capped` (120 s, `ENGINE_SEARCH_CAP_S`), then `watch`. Run 1 of the sitting ran it beside `play_chart.py`, each with its own engine search, and the presser still hit 857 of 857 (`run1_cal0_play_chart.txt`), so two scans at once did not hurt the presses.

`sp_compare.compare(rows, score, *, resolution, sp_bar_ticks=None, width=64) -> Report` is pure and prints PASS and FAIL lines; `_find_activations(rows)` finds each 0-to-1 flip of the flag; `--resolution` is required only to print Hydra's full meter beside `sp_max`. Run 1 proved the fields: 11 phrase ends each raised the amount by 1,438 to 1,440; `sp_max` held at 5,760 (30 times the chart's resolution of 192, where Hydra's meter is 32 times); each activation set the flag, doubled the multiplier 4 to 8, and set an end time at which the flag cleared; the two activations on the path ended within 2.9 and 1.2 ms of Hydra's deactivation (`run1_cal0_sp_compare.txt`, lines 2 to 27). The write-up `docs/research/2026-10-28-overlay-spike-results.md` is still the empty template, so the result file and the sitting handoff (`docs/handoffs/2026-10-28-overlay-spike-sitting-handoff.md`) are the record.

The server's Frida side reads `GameManager` by field name only (`agent/state.ts`: `songTime`, `isPaused`, `isSongOver`, `isSongPlaying`, `songLoaded`), finds it on every read with a heap walk that L1 timed under 0.1 s, and `frida_tools.state_words` turns the fields into one word. `ch_snapshot` adds the score after the play session's last press. Nothing in the server reads the engine object. `test_frida_attach.py`'s `NO_WRITE_PATTERNS` refuses, in every `agent/*.ts`, writes, `.value =`, `.invoke(`, `new NativeFunction`, `Interceptor.replace` and `add(0x` (reads by offset).

The menus are readable by name. `facts.json` lists `SongSelect` with readable fields `currentSong`, `mainMenu`, `playerSelection`, `onlineMenu`, `songSelectSearch`, `songOptions`; `MainMenu` with `songSelect`, `settingsMenu`, `onlineMenu`, `songScan`, `controlMapper`; `PlayerSelectionMenu` with `playerIndex`, `instrumentSelection`, `difficultySelection`, `confirmSelection`; `GlobalVariables` with a static `instance` and `currentSongEntry`, `selectedSong`, `gameMode`, `playerCount`, `isPracticeEnabled`; `SongEntry` with `folderPath`, `chartName`, `songLength`, `checksum`. Every field entry in `facts.json` carries `name`, `type`, `static` and `offset`.

Keys reach the game. `input_driver.InputDriver.send_key(vk, key_up)` is the one `SendInput` call, `press_chord` presses lanes, `find_game_window` and `focus_window` are the window owners, and `play_chart.live_press` is "focus, then press". `ch_press` takes lane names only; there is no way to send Enter, an arrow or text. L3 proved `SetForegroundWindow` and `SendInput` work from the server.

The command line is `launch_command`: `[exe]` for the menu, else `--song`, `--player` and an optional `--profile`. The game's string table (`stringliteral.json` from the 2026-10-28 Il2CppDumper run, in session f756d547's scratch) holds exactly these game flags: `--song`, `--player`, `--profile`, `--instrumentNames`, `--versus`, `--replay`, `--lbsToken`, and the short forms `-i`, `-p`, `-r`; everything else starting with `--` is Unity UI style-class text. `--replay` and `--lbsToken` are not in the manual and nobody has tried them.

## Every way to start a song without a person at the menu

I looked for every route and checked each against the evidence. The recommendation follows.

**The command line with a bot.** Proven (Test 1 of the feasibility study): the game plays the chart with a bot and writes `scorestats.json`, and "the bot never uses Star Power. In both Trippin runs (11 phrases) it earned 0 phrases, with 0 activations". The manual says `--player` "adds a bot player" and `--profile` is "a template for all of the bot players" ([the command-line page](https://wiki.clonehero.net/books/clone-hero-manual/page/chart-previews-via-the-command-line)). So it cannot answer any Star Power question, and its results screen took no keys in L1.

**The command line with `--song` and no `--player`.** Untried. The manual does not say what the game does with a song and no players. The game's `CliGameLauncher` class has no readable method, so the dump does not say either. It costs one launch to find out, so LS0 tries it once: if the game opens the song for the keyboard profile and `is_bot` is false in the stats, this is the simplest route of all and `ch_open_song` is never needed for charts that are installed. I rate it unlikely, because the page describes the feature as a preview by bots, but a guess is not evidence.

**`--replay`.** A flag in the string table and a `replayPath` field on `GlobalVariables`. A replay plays back recorded inputs, not live keys, so even if it loads a song it does not give a key-played run. Left out.

**The game's own methods through Frida.** Question 2. Not recommended; it breaks the no-writes rule and the dump does not name the method.

**Key navigation of the menus, checked by reads.** The game opens at its main menu with `ch_start()` (proven, L2 and L3). The manual documents the menu keys (Enter for Start, A as Green, arrows to move, and for the search tool a short Blue press; question 4 says which page says what), and the song list can be searched by name. Three of the driver's states are readable fields: which `SongEntry` is `currentSong` and its `folderPath`, whether a live `GameManager` exists, and its `songLoaded`. Which screen is showing is not proven readable: a `SongSelect` or `MainMenu` object can exist while hidden (question 1). No public tool does this for Clone Hero; the general Unity UI drivers (AltTester, for one) need an instrumented build of the app ([AltTester overview](https://alttester.com/docs/desktop/v.2.0.0/pages/overview.html): "The instrumented build opens a communication protocol which gives you programmatic access to objects inside your Unity App"), which a shipped game is not, and the community Frida servers expose raw JavaScript, which the no-writes rule forbids. What the server already has, `SendInput` to a focused window plus a Frida read of named fields, is the same shape AltTester uses from the inside. **This is the recommendation**, with question 1's rule change.

**The results screen.** A song started from the menu ends on a results screen that takes keys (L2 run 1: the user went back to the main menu by hand), so `ch_open_song` can be called again for a second song in one game process; after a bot launch the results screen took no keys (L1), so that route still ends with `ch_stop`.

## The design

### Where the Star Power read lives, and who calls it

The read lives outside the game, in `ch_probe`: `engine.decode_snapshot` says where each field is and how wide (through `constants.OFF_SP_*`), `EngineModel.snapshot()` reads it, and `sp_watch.watch` polls it. Nothing new reads memory. The server gets one new module, `tools/ch_mcp/sp_tools.py`, with a class `SpTools` beside `GameTools` and `FridaTools`. It runs `watch` in a daemon thread, keeps every row and the latest `Snapshot` in memory, writes the CSV live in the session folder, and formats the fields in one function, `sp_lines(snapshot)`. `ch_sp` prints the latest row the watcher read (at most one poll old), so the single read never touches the process from a second thread and never blocks on an engine search. The alternative was reading the fields inside the game through the Frida agent, resolving the scrambled field names from `facts.json` by offset the way the trace resolves method names; it is possible (the fields are listed with offsets, and `BasePlayer.engine` is a readable path to the object) but unproven live, it would run a 4 ms timer inside the game, and it would add a second home for "where the Star Power fields are". The outside read is proven and already has one home.

The watcher finds the engine the way `sp_watch.run` does today, with its own capped search. It does not share the play session's engine address, because the play session's `EngineModel` lives inside `live_play` and exposing it would make the watcher depend on a presser. Two searches at once are proven harmless (run 1).

### Safety rules kept

Backups: `ch_sp_watch_start`, `ch_key` and `ch_open_song` call `game.ensure_backup()` before they touch the game, like `ch_press`. `ch_stop` restores as today. Offline: `ch_open_song` reads the menu before every step and refuses to press when the read says the Online menu is live (if question 1 and LS1 show that read works), and `launch_command` is untouched. Frida: `state.ts` gains reads by name only; the no-writes grep covers it with no change. Caps: every new wait has one and names it in its reply. No whole-library anything: every tool takes one folder. The user is present and watching every live step, as the standing rule requires; they press nothing, which is the point.

### T2: the pure Star Power checks (no blockers)

## Prior art

Clone Hero's command line is documented only as a bot preview ([chart previews via the command line](https://wiki.clonehero.net/books/clone-hero-manual/page/chart-previews-via-the-command-line)); the game's string table adds `--replay` and `--lbsToken`, undocumented. The manual's keyboard defaults are Enter for Start, A for Green and the arrows for Strum Up and Down ([Keyboard and Gamepads](https://wiki.clonehero.net/books/guitars-drums-controllers/page/keyboard-and-gamepads)); the short Blue press for the search tool is on [How to Play](https://wiki.clonehero.net/books/clone-hero-manual/page/how-to-play). Unity UI automation from outside a stock build has no general tool: AltTester drives menus and keys but only in an instrumented build of the app ([overview](https://alttester.com/docs/desktop/v.2.0.0/pages/overview.html)). frida-il2cpp-bridge reads instance fields as `object.field(name).value` and finds live objects with its choose call ([README](https://npmjs.org/package/frida-il2cpp-bridge); [a field-reading gist](https://gist.github.com/eybisi/28f05a3d0bfd7d12de3c5c947ea0e80f)); the server already uses both in `state.ts` and `gamemanager.ts`, and T4 adds the static-field read the same way.
