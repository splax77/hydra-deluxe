## What this plan does, in plain terms

A fold is the same fact worked out in two places. The engine knows whether a chord comes after the Star Power end, and the replay works it out again by hand. A test rebuilds a formula the production code already has. A GUI test retypes a label the app builds. Phase 6 gives each of those facts one owner and points the copies at it. Where the second copy is a test oracle that re-implements production, the oracle goes and the test pins a literal from one run instead (D42).

Nothing here changes a score, a path or a stored record, and almost nothing changes what a player sees. Every merge proves that with byte-identical corpus scores. The four things that could show are the questions in the questions sheet: a database slot nothing reads, half a pixel on the Score range box, a fill lane colour in a case no chart reaches, and a known Preview gap we propose to leave.

## How it runs

The rules carry over from phases 3 to 5.

Planning runs on Fable. Each task is one Opus implementer in its own worktree, about 15 minutes of work. The light per-task answer check and the derive-once reviewer run on Sonnet. Each task's brief lives in `docs/superpowers/plans/tasks/p6-<id>.md`, written after approval, with the shared preamble `docs/agents/brief-preamble.md`. No code listings anywhere in this plan or the briefs: a brief names owners, files, test cases and the literals the tests pin, and the implementer writes the code.

Agents never run the full suite. Each brief names its `-tc=` and `-sf=` filters, its `hydra_uitest` scripts, or its `pytest -k` selection. The main session runs the full suite once per merge to main, plus the corpus-scores check: every phase 6 change is code-only, so byte-identical scores are the proof.

Every agent writes a status line every 10 calls or 5 minutes. A blocked agent stops and reports the exact error; it never waits. Helpers run in the foreground. Agents commit before 110 calls.

There is one merge to main per wave, M6-J1 to M6-J4. Each goes the same way: merge main into the wave branch, run `tools/derive_once_precheck.ps1` if phase 0's M0 has landed (it is not on main yet; if not, say so and go on), get a Sonnet derive-once review, run one sweep fix round of two fresh agents (production findings and test findings), run the full suite once, check the corpus scores are byte-identical, merge. The integrator also joins `tests/test_single_owner.cpp`: every task appends its scan rows there, and it is the one file every task shares.

Decisions: the questions sheet's answers and the recorded-as-recommended list below get the next free D numbers in `docs/audit/2026-10-03-fix-decisions.md` when you answer. Other sessions are numbering decisions too (D52 is already phase 3's), so this plan names them by question, not by number.

## What others do

Three outside practices back the shape of this plan. Feathers' characterization tests say to pin a system's current behaviour before refactoring it, so that a refactor that changes behaviour fails a test rather than a user ([bssw.io](https://bssw.io/items/working-effectively-with-legacy-code)); our byte-identical corpus scores at every merge are that test. ArchUnit-style architecture tests turn "this rule lives in one place" into a test that reads the source and fails on a second copy ([archunit.net](https://www.archunit.net/)); `tests/test_single_owner.cpp` plays that role, and every task adds its rows there. And the DAMP-versus-DRY discussion of tests, with the literature on test oracles, is why D42 forbids an oracle that re-implements production while allowing a literal pinned from a run: a second implementation cannot tell you which copy is wrong, a literal can ([enterprisecraftsmanship.com](https://enterprisecraftsmanship.com/posts/dry-damp-unit-tests/), [aipatternbook.com](https://aipatternbook.com/correctness_testing_and_evolution/test_oracle.html)).
