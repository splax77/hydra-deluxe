### 6a. The risky gate: blank quoted text and here-doc bodies, in the scanner

What is wrong today. For the Bash tool the gate reads real `rm` commands through the scanner (lines 163 to 181), which is right, but then runs its backstop regexes over the whole raw text whenever the scanner found no recursive rm (lines 187 to 192). For the PowerShell tool the rm rules and the `Remove-Item`, `DROP TABLE`, `TRUNCATE` and `del /f /s /q` rules are regexes over the raw text for both tools (lines 202 to 208). Scout G's samples in `G_samples.json` are cut to 260 characters, so for most I cannot show the matched phrase, but the shape is plain in the ones that fit: sample 47 is `for p in "rm -rf / rm -r is blocked" "sed is blocked" ...`, a list of quoted phrases; sample 52 is a Python here-doc whose text holds the same phrase as a dictionary key; samples 2, 3 and 11 are `status_append.ps1 ... "<status text>"` calls denied for `DROP TABLE` inside the quoted status text; sample 14 is a plan written through a PowerShell here-string, denied for `TRUNCATE`; samples 10, 13 and 46 are `grep -rn "DROP TABLE..."` searches of the repo. Scout G's own two denials that day were the same kind. Every one of these is a quoted argument or a here-doc body.

What changes. The scanner already knows which words are quoted (`.Quoted` on each word, header line 91) and holds each here-doc's body (`.Heredocs`, line 69) with positions in the command's `.Source`. Add one function to `lib\shell_scan.ps1`, say `Get-ShellBareTexts -Scan $scan`, that returns, for every distinct `.Source` string in the scan (the top-level text and the script of each inner shell), that text with every quoted argument word and every here-doc body blanked to spaces, keeping the verb word of each command even when it is quoted. The risky gate's `Get-BackstopText` (lines 129 to 143) already does this positional blanking for one case (the subcommand word of `git rm --cached`); the new function generalizes it, and the gate's copy goes. The gate then runs its backstop and PowerShell-tool regexes over the bare texts instead of the raw text. In a loose scan (unbalanced quotes) nothing is blanked and the gate judges the raw text as today, because quotes could not be read and the gate must over-read.

Why this cannot hide a real delete inside a wrapper. The scanner reads the script handed to `bash -c "..."`, `sh -c`, `powershell -Command "..."`, `pwsh -Command`, `cmd /c`, `eval`, `Invoke-Expression`, `-EncodedCommand`, and a shell fed on stdin, as its own commands (`Get-ShellInnerScripts`, lines 275 to 365; the header lists them at lines 31 to 39). Those inner commands appear in `.Commands` with `.Via = 'inner-shell'` and their own `.Source` (the unquoted script text). So `bash -c "rm -rf /c/src"` gives two sources: the top-level text, in which the quoted script is blanked, and the inner script `rm -rf /c/src`, in which `rm` is a verb with its words, so `Read-RmWords` catches it on the Bash tool and the bare-text regex catches it on the PowerShell tool (`powershell -Command "Remove-Item -Recurse -Force C:\src"` works the same way). A quoted verb (`"rm" -rf x`) keeps its word because verbs are never blanked. Launchers the scanner does not look into (wsl, ssh, docker, Start-Process; header lines 104 to 107) keep the words of their arguments unquoted in the top-level text (`docker exec c rm -rf /` has no quotes), so the backstop still sees them; `docker exec c "rm -rf /"` would hide, and the deny text's existing sentence ("a wrapper the scanner does not look into") should be extended with a test case pinning that `kubectl exec pod -- rm -rf x` is still caught, which test_h24 lines 93 to 102 already do for the unquoted form. The one true gap is a quoted script given to a launcher outside the scanner's list; that gap exists today too (the scanner cannot read a script file either), and is the same size.

The `DROP TABLE` and `TRUNCATE` patterns. SQL always reaches a program inside quotes (`sqlite3 db "DROP TABLE x"`), so once quoted text is blanked these two patterns can never match a real command, only an unquoted bare word, which is not SQL. Keeping them on the raw text keeps the false denials; keeping them on the bare text makes them dead. Scout A and the audit both say they can go. This is a user question (below); my recommendation is to drop them.

### 6c. The attribution gate's patch-script rule: scratch files are not source

What is wrong today. Rule 3 at `git_attribution_gate.ps1:568-582` denies any command whose text matches `patch\w*\.py`, and any Python here-doc that writes a file (`open(..., 'w')` or `write_text`) when the text anywhere holds `.py`, `.ps1`, `.cpp`, `.h` or `.md`. It never asks where the file is. The samples are helpers like `cat > <scratch>/mark.py <<'E'` and `cd <scratch> && python - <<'EOF' ... p='review-lb1-draft.md' ... open(p,'w')`: scratch files, which the preamble lets agents write freely.

## Open questions for the user

1. How are the 20 lines counted? The rule today (`lib\doc_review_rules.ps1:40`) is a different quantity: `$DocReviewEditLineLimit = 20` counts changed lines, added plus removed, as `git diff --numstat` does, and it is dead code (task 2 removes it). The new rule counts the lines of the whole text. Two choices. Count every line of the normalized text (BOM dropped, CRLF to LF): a gh comment of 19 sentences separated by blank lines is 37 lines and needs a review. Count non-blank lines: the same comment is 19 lines and passes; a 21-line plan with no blank lines needs a review either way. I recommend non-blank lines, because blank lines carry nothing for a reviewer to read. A trailing newline at the end of a file is not a line under either choice.

2. Does the 20-line rule also apply to commits that change the four gated pages? The code gates `README.md`, `docs/README.md`, `docs/UserGuide.md` and `docs/differences-from-public-hydra.md` (`lib\doc_review_rules.ps1:53`). Their sizes today: 59, 8, 343 and 133 lines (38, 5, 197 and 93 non-blank), counted with Get-Content on the main checkout. Reviewed-once already lets every later edit of a signed-off page through (line 936), so the body-line rule would only ever change the treatment of `docs/README.md`, the one page under 20 lines, and of a brand-new short page. Applying it uniformly keeps one function for all three gates; not applying it means `Get-DocReviewPublishRefusal` takes a flag. I recommend applying it uniformly.

3. Drop the `DROP TABLE` and `TRUNCATE` patterns from the risky gate? Today (`bash_risky_gate.ps1:48-49`) they match those words anywhere in the text, so `grep -rn "DROP TABLE" src` and a status line saying "dropped the table" are denied, while `sqlite3 x.db "DROP TABLE t"` would also be denied and that is the intended catch. Once quoted text is blanked (task 6a) the intended catch cannot match either, because SQL always arrives quoted; keeping the patterns on the raw text keeps the false denials. The three sampled real matches (scout A: two in an agent's Python test of a scratch database copy, one in a plan here-string) were all harmless. I recommend dropping both.

4. The PowerShell tool's rm reading. On 2026-10-05 the user put the PowerShell tool out of the risky gate's scanner change, so its rm and `Remove-Item` rules are regexes over the whole text (`bash_risky_gate.ps1:33-36`). Task 6a would run those regexes over the bare text (quotes blanked) for PowerShell too, which is still a regex, not a scanner reading. Example both ways: `& status_append.ps1 "id" "done: Remove-Item -Recurse -Force test green"` is denied today and would pass; `Remove-Item -Recurse -Force "C:\src"` is denied today and stays denied (the verb and flags are unquoted). Is extending the blanking to the PowerShell tool within the 2026-10-05 decision, or does the user want PowerShell left exactly as it is?

5. The suite gate and filters in a loop. Rule 1 today (`suite_run_gate.ps1:122-136`) looks for a filter in the statement around the run; scout G's sample `foreach ($f in '-tc=activation timeline*','-tc=scrub marks*') { & $exe $f }` was denied because the filters are quoted literals in the loop header, not words of the run. Under the scanner rewrite the loop header's literals are words of the foreach statement. Should a run whose only filter arrives through a loop over literal filter strings count as filtered (it runs five named tests, one per pass) or stay denied (the gate cannot prove `$f` is one of them without reading the loop)? I recommend counting it when every literal in the loop header is a valid filter value, and denying when any is a variable.

## Prior art

One web search (query: Claude Code PreToolUse hook, rm -rf false positive on quoted strings and here-docs). I found no issue reporting this exact failure. The guides agree on the cause and the fix: grepping the raw command text matches the words wherever they are, and the remedy is to tokenize the command and judge only command words. Sources: the Anthropic hooks reference (https://code.claude.com/docs/en/hooks), which says only exit 2 blocks and so a parser crash must fail closed, the point task 3 and P2's dispatcher work make; a hook catalog that advises validating patterns against real command logs (https://agentpatterns.ai/tool-engineering/hook-catalog/), which is what the 2026-10-05 corpus replay does; and a hooks guide that shows the plain `grep -q 'rm -rf'` pattern and its misfires (https://israynotarray.com/en/ai/2026/05/31/claude-code-hooks-complete-guide/). Our scanner already does the tokenizing those sources suggest; task 6a only makes the regex layer use it.
