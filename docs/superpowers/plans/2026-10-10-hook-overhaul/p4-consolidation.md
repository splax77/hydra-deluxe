## What this section assumes

It plans for the hooks that remain after the user's retirements. On the shell dispatcher that means nine gates stay (bash_risky, bash_windows_path, git_attribution, derive_once_review, merge_precheck, doc_review_submit, suite_run, library_run, doc_review_gh) and four leave (shell_read, rerun, fanout_track, fable_delegate). The media guard that P2 lifts out of `fable_delegate_gate.ps1` becomes a tenth shell gate. On the star dispatcher the two gates stay (agent_progress, stall_inject). The Stop gate is gone, so there is nothing to consolidate on Stop. I checked today's registrations in `settings.json` lines 17 to 231 and the project's `settings.local.json`.

Two facts shape the whole section. First, Anthropic's docs say every hook matching one event runs in parallel (hooks reference, "All matching hooks run in parallel"). So for wall time the user feels roughly the slowest hook on an event, not the sum; consolidation saves CPU and process starts, and wall time only where the slowest hook itself gets faster. Second, today the slowest hook on a shell call is `dispatch_bash_ps.ps1` at about 1.0 s against a 0.245 s bare PowerShell start (both from scout H's timed runs). Once it drops, `dispatch_star.ps1` at about 0.6 s (scout H) becomes the floor, and `stall_inject.ps1` is most of that (scout E measured 398 ms for stall_inject alone and 629 ms with a real transcript holding ten subagents). That is why stall_inject caching is in this section.

Version ceiling: `claude --version` prints 2.1.275. The desktop app's own `claude.exe` (`AppData\Local\AnthropicClaude\app-2.31226.1\claude.exe`) prints the app version, 2.31226.1, not a Claude Code version; the Claude Code builds it runs live in `~\.local\share\claude\versions`, and the newest there is 2.1.275. So 2.1.275 is the ceiling for both the terminal and the app until the user updates.

## Where the time goes today (the mechanism, before any change)

`dispatch_bash_ps.ps1` reads stdin once (line 32), then for each of 13 gates points `[Console]::In` at a fresh StringReader and runs the gate file with `&` (lines 72 to 75). Every gate then does the same four things on its own: dot-sources `lib\hook_input.ps1`, calls `Read-HookInput`, runs `ConvertFrom-Json` on the whole input, and, if it reads the command, dot-sources `lib\shell_scan.ps1` (48,905 bytes) and calls `Get-ShellScan` on the same text. My grep of every `Get-ShellScan` call in the hooks folder finds eight of the nine remaining gates scan (all but suite_run, which has its own regex scanner that P3 moves onto the shared one). Four of them skip the scan on most commands through a cheap pre-check (merge_precheck line 35 exits unless the text mentions "merge"; doc_review_submit line 64 exits unless it names a helper; bash_risky line 145 scans only Bash-tool calls or text mentioning git; library_run and doc_review_gh load the scanner later in their flow). Two always scan: `git_attribution_gate.ps1` line 516 and `derive_once_review_gate.ps1` line 82. So a plain PowerShell command today is scanned about 3 to 5 times and JSON-parsed 13 times; a Bash git command is scanned up to 8 times. Seven of the eight scan calls use the same arguments, `-Tool $toolName -TryOtherDialect`. The one exception is `bash_windows_path_gate.ps1` line 148, which always scans with `-Tool 'Bash'` and no other dialect, because it only runs for the Bash tool (line 40) and needs the Bash reading of backslashes. Those two readings differ only when the text is unbalanced (the `-TryOtherDialect` reading may then switch to PowerShell rules; `shell_scan.ps1` header lines 41 to 44).

One caution for the executor. Scout H's claim that "each `&` call to a gate reparses the lib file" is plausible but unmeasured; PowerShell keeps a compiled-script cache for files, so the re-parse may be cheaper than it looks. The first step of task 1 is therefore to measure per gate before changing anything (memory: measure small, explain first).

## Task 1: parse once in the shell dispatcher, and one shared gate loop

Why: the dispatcher does the same decode, JSON parse and shell scan up to 13, 13 and 8 times per call. The cost is paid on every Bash and PowerShell call, about one second each (scout H).

What changes. Step one adds a timing switch: when the environment variable `HOOK_TIMING` is set, the dispatcher writes one stderr line per gate with its milliseconds. The executor runs it three times by hand on two made-up payloads (a plain `Get-ChildItem` and a `git commit -m x` in a Bash call), the way scout H did, and records the numbers in its report. That tells us which gates and which loads cost the most, and that measurement sets the target below rather than a guess.

Step two moves the shared work into the dispatcher. `lib\hook_input.ps1` gains two functions beside `Read-HookInput`. `Get-HookInput` returns the parsed object: when a dispatcher has stored one in `$global:HookInputObject` it returns that, otherwise it parses `Read-HookInput` itself. `Get-SharedShellScan -Text -Tool [-TryOtherDialect]` returns the dispatcher's stored scan from `$global:HookShellScan` when the text, tool and dialect flag match, otherwise it calls `Get-ShellScan`. The dispatcher parses the JSON once, loads `lib\shell_scan.ps1` and `lib\git_words.ps1` once, scans once with `-Tool $toolName -TryOtherDialect`, and stores all of it in those globals before the gate loop. This lives in `hook_input.ps1`, not `shell_scan.ps1`, on purpose: P3 is changing the scanner's word matching, and two tasks never own one file at the same time. The dispatcher keeps pointing `[Console]::In` at a StringReader per gate, so a gate nobody edited still reads correctly.

Step three edits each of the nine shell gates in the same three small ways: its `ConvertFrom-Json` line becomes `Get-HookInput`; its dot-source of `shell_scan.ps1` and `git_words.ps1` is guarded with "load it only if `Get-ShellScan` (or `Get-GitInvocations`) is not already defined", because a function defined in the dispatcher's scope is visible to a script run with `&`; and its `Get-ShellScan` call becomes `Get-SharedShellScan` with the same arguments. `bash_windows_path_gate.ps1` keeps its own Bash reading only when the shared scan's `.Dialect` is not `Bash`, which happens only on unbalanced text. Every gate still runs standalone exactly as before, because each helper falls back to doing the work itself; that matters because tests h5, h20, h24, h25, h30 and h35 run the gates standalone on stdin.

Step four lifts the gate loop (missing file, thrown error, empty or non-JSON output, each turned into a deny by P2's rule) out of the two dispatchers into `lib\dispatch_lib.ps1` as one function, `Invoke-GateList`, so the two new dispatchers in tasks 2 and 3 cannot drift from it. P2 puts the validity check in `lib\verdict_merge.ps1`; `Invoke-GateList` calls it and adds no rule of its own.

Files owned: `dispatch_bash_ps.ps1`, `dispatch_star.ps1`, `lib\hook_input.ps1`, `lib\dispatch_lib.ps1` (new), the nine shell gates named above (input and scan lines only), `tests\test_h39_parse_once.ps1` (new), and the existing `tests\test_h27_verdict_merge.ps1` where its stub folder needs `dispatch_lib.ps1` copied in.

## Prior art

I searched once for a single-process hook dispatcher that parses stdin once. The closest is captain-hook, a Python hook framework whose dispatch flow parses stdin once into a typed event, matches hooks, runs them and merges results ("Parse: JSON from stdin is parsed into a typed event object", https://captain-hook.readthedocs.io/en/latest/guide/hooks-and-events/); that is the shape of task 1, in another language. General hook guides (https://www.claudelog.com/mechanics/hooks/) recommend one entry point over many processes but give no measurements, and I found nothing on PowerShell hook cost specifically. Anthropic's own pages (https://code.claude.com/docs/en/hooks, https://code.claude.com/docs/en/sub-agents, https://code.claude.com/docs/en/env-vars) are the sources for every version and setting named above.

## Open questions for the user

1. Nesting: the depth setting is stricter than today's gate. `no_recursive_delegation_gate.ps1` denies an Agent call only when the running subagent's model matches `sonnet` or `haiku` (lines 19 to 22) and prints `{}` for every other model. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` denies Agent calls from every subagent. Example that changes: an Opus executor dispatching a Sonnet helper is allowed today and refused after. Example that does not: a Sonnet reviewer dispatching anything is refused both ways. The preamble already tells every agent "you have no helper agents", so I recommend the setting. Yes, or keep the gate?

2. Named agents: the four `.claude/agents` files only bind when a dispatch says `subagent_type: executor` (and so on). A dispatch written as `Agent(model: "sonnet", prompt: ...)` with no type gets no file. Should the posture require the four names for every dispatch, or is a model per call still acceptable?
