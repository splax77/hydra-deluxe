## T1. The dispatchers fail closed

Why. Both dispatchers let a call through when a gate breaks, in four ways, and the user already approved the rule that fixes it: a gate that prints nothing is broken and gets denied (`docs/handoffs/2026-10-10-dispatcher-fail-closed-handoff.md`).

I checked the handoff's line numbers against today's files and they hold. `dispatch_bash_ps.ps1` skips a missing gate at line 68, turns a thrown error into "no output" at line 75 and skips it at line 76. `dispatch_star.ps1` does the same at lines 45, 49 and 50. `lib\verdict_merge.ps1` drops any line it cannot parse at line 38, and its header comment at lines 14-15 still says empty lines mean "no opinion". The fourth hole is the dispatcher itself crashing: Claude Code treats any exit other than 2 as non-blocking, so the call runs. The web confirms this is a known trap, not something odd about our setup: a GitHub issue reports a PreToolUse hook that exited 2 and still let `git push` run ([anthropics/claude-code#23284](https://github.com/anthropics/claude-code/issues/23284)), a second reports exit 1 being ignored ([claudeissues 21988](https://claudeissues.com/issue/21988-bug-pretooluse-hooks-exit-code-ignored-operations-proceed-after-hook-failure)), and a docs issue asks for a warning that exit 1 is silently non-blocking ([claudeissues 44707](https://claudeissues.com/issue/44707-docs-hook-exit-codes-exit-1-silently-non-blocking-needs-prominent-warning)). The lesson every one of them draws is the same: never rely on an exit code for enforcement; print the decision. The built-in `onFailure: "block"` setting would close the fourth hole natively, but the audit says it arrived in v2.1.295 and the installed CLI is v2.1.275, so this fix cannot use it yet.

One correction to the handoff. It counts seven gates whose main logic runs with no outer `catch`, and names `agent_progress_gate` among the four with no try at all. That is wrong: `agent_progress_gate.ps1` line 292 wraps its whole main function in `try { Invoke-Main } catch { '{}' }`. So the no-catch list is six, not seven: `bash_risky_gate`, `bash_windows_path_gate` and `shell_read_gate` have no outer try; `fanout_track`, `fable_delegate_gate` and `suite_run_gate` have a try with only a `finally`. After T5 retires four of those, only `bash_risky_gate`, `bash_windows_path_gate` and `suite_run_gate` remain, and T1 covers all three. That last one is open question 5 below.

Both dispatchers call it, so the rule has one owner.
