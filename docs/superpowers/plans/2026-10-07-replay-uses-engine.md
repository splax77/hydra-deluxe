# Track R: hydra_replay uses the engine

Planned 2026-10-07 from the Track R section of `2026-10-07-summary-only-storage.md`, section 6 of `docs/handoffs/2026-10-06-storage-audit-handoff.md` and D87 item 8. Baseline on main bc48742: `hydra_replay selfcheck` passes 382 of 382 paths over 97 charts in 1.5 s; `dump` on blink-182 "Discography" takes 0.6 s and its best path has 522 activations; `target --ticks` with those 522 ticks was still running at 60 s and was killed.

## What is wrong today, in plain words

**Score.** The handoff called `hydra_replay score` a second derivation of the window rules. Most of that was already fixed by the 2026-09-24 derivation work: the replay prices every chord's doubling through `core::paid_by_sp` and `core::backend_row_value`, the same functions the engine calls, so the window's inclusive end, the backend leeway and the squeeze-out reduction each have one owner already. Three copies remain. First, the chord-by-chord walk that carries the combo and calls `category_scores` and `solo_bonus` exists twice: once in `ScoreGraph::build` (where it is summed onto edges and thrown away) and once in `replay_path`. Second, the graph already keeps a per-chord row for Star Power (`all_backends`: tick, chord, SP value, squeezed-out value) and the replay rebuilds that row from scratch. Third, the header comment of `src/core/replay.h` spells out the three rules in prose, which `docs/agents/brief-preamble.md` forbids: a comment names the owner, it never restates the rule.

One rule stays in the replay on purpose: which chords a window covers. In the graph that is structural (the activation edge carries the fill chord's own doubling, and the SP track runs from there to the deactivation node). In the replay it is a tick comparison. There is no third place that could own it, and the corpus self-check is exactly the test that the two agree.

**Target.** `search_target` pins only where activations start. Every way of ending each activation (squeeze in, squeeze out, end plainly) survives, and the widest possible band keeps them all, so the frontier doubles at every squeeze choice. That is why blink never finishes. The engine also re-runs the whole search once per prefix to name the failing activation, which is just as slow. The comment at `tools/replay.cpp:507` ("Each run is milliseconds") is wrong for long charts.

## Fix 1: one chord-score table

One function, `chord_score_table`, walks the chart once and returns one row per chord: base, combo, SP value, squeezed-out SP value, accent, ghost, solo, the multiplier before and after the chord, and the combo before and after. It lives in `src/core/scoring.h` and `.cpp`, beside `category_scores` and `solo_bonus`, and `ScoreGraph::build` reads its sums from that table instead of calling `category_scores` itself. The multiplier-squeeze list reads the combo off the same row.

`replay_path` reads the same table. Its per-chord points come straight off the row, and the only path-dependent term, the doubling, is still asked of `core::backend_row_value` with the window's deactivation node and squeezed-out chord. The per-note detail the full replay prints (each note's SP share, multiplier and dynamics bonus) is a flag on the table function, so the graph pays nothing for it and the Preview's scores-only replay pays nothing either. Nothing in the replay calls `category_scores` or `solo_bonus` any more.

Hand-typed windows (`--acts`) need no engine path. The table has no path in it, and a typed window is priced by the same `backend_row_value` call as a stored one, with the squeeze-out resolved by `resolve_sqout_note` as today. So a typed window is priced by exactly the functions a stored window is, and no rule gets a second copy.

The replay.h header is rewritten to say what the module does and where each rule lives, not what the rules are.

**Proof that no number changes.** Before the first edit, the executor runs the baseline exe over every testdata chart (`dump`, then `score --path <dump> --index 0`) and keeps the JSON in its scratch folder. After the change the same commands must produce byte-identical JSON. `hydra_replay selfcheck` must still pass 382 of 382. The Preview reads five fields off each replay row (`src/app/preview_view.cpp` build_score); four are in that JSON and the fifth, `multiplier_shown`, is pinned by the corpus test "replay: on every corpus path the disc follows SP's payment and windows add up". Speed: `category_scores` is the hottest function in analysis, and this moves its call, it does not add one. The main session's one timing run at the join (the perf memory's warm redo, 9.7 s baseline) catches any regression.

## Fix 2: target pins the whole path

**Why the deactivation tick is the whole pin.** Every squeeze choice the engine faces is binary: at an SP-end node the path either ends Star Power here (plain end, or a squeeze-out that gives the phrase back) or keeps going (a squeeze-in that moves the end). So one fact per activation, the tick its Star Power ended on, answers every choice: before that tick keep going, on it end, past it the path has already diverged. The stored record and the dump JSON carry that tick (`deact_tick`, stamped by the engine, ADR 0011), and so does a typed `--acts` window. Which phrase gets squeezed out is then the engine's own answer; when the pin names one too (`sqout_tick` from a dump, or a typed offset resolved by `resolve_sqout_note`), the returned path is checked against it after the search, the way `keep_target_paths` checks activation ticks today. A mismatch means the pinned path is not one the engine produces, and target says so.

**Engine.** `EngineOptions` gets a pinned-window list beside `target_act_ticks` (one line in `src/search/engine.h`, which the brief does not list: see the questions). In the run loop's target block, an SP node looks up the running activation's pinned end by its activation tick. Before the pinned end only the continuing parent survives; on it only the ending child survives; a running path past its pinned end dies. With every choice pinned the frontier holds one path, so the search is linear in the graph's nodes, and the normal search and the tick-only target are untouched.

**Pather and CLI.** `search_target` keeps its signature (the single-owner scan test pins it) and gains an overload that takes the pinned windows; both call one inner function over an already-built graph. `cmd_target` accepts `--path <dump-or-target.json> [--index N]` and `--acts "act:deact[:sqoutMs]"` through the same readers `cmd_score` uses, and `--ticks` stays the activation-only pin that returns every squeeze variant, which the FC video workflow reads. When a set is unrealizable, the graph is built once and the failing prefix is found by binary search over the prefix length, because realizability is monotone: a path that takes the first k+1 windows and nothing else is, with the last one declined, a path that takes the first k. That is at most ten runs for blink instead of 522, in both modes. For a pinned run the JSON adds `failed_reason`, "activation" or "window_end", found by one more run that pins the failing window's activation only. The comment at `tools/replay.cpp:507` is replaced by one that says the cost is a graph build plus one linear walk per run.

`check_chart` gains a second check, so one `selfcheck` command proves both halves: each stored path is handed back as a full pin, and target must return exactly that path, alone, with the same facts. At about 2 ms per run that adds roughly a second.

**Proof that no number changes.** The app never calls `search_target` (only `tools/replay.cpp` and the tests do), so no stored record or app display can move. The engine change sits inside the `if (target...)` block; the diff shows it. The existing search tests run unchanged.

## What others do

Scoring a known path without re-searching is the usual shape. torchaudio's `forced_align` takes the network output and a target sequence and returns a per-step score for that one path ([docs](https://docs.pytorch.org/audio/stable/generated/torchaudio.functional.forced_align.html)). CTranslate2 scores a fixed hypothesis through `score_batch`, a separate entry point from its beam search ([docs](https://opennmt.net/CTranslate2/python/ctranslate2.Translator.html)). Marian offers `force_decode` for a given prefix ([PyMarian paper](https://arxiv.org/pdf/2408.11853)). Hugging Face's `prefix_allowed_tokens_fn` is the closest match to the engine change here: a callback that, at each beam step, leaves only the allowed children alive, so a fully specified target keeps the beam at one ([docs](https://huggingface.co/docs/transformers/v4.21.1/en/main_classes/text_generation), [example](https://discuss.huggingface.co/t/example-of-prefix-allowed-tokens-fn-while-text-generation/6635)). On exposing per-step values instead of re-scoring, MEME's dynamic program writes each cell's decision into a trace matrix during the fill and reads it back, never re-pricing ([source](https://mitra.stanford.edu/kundaje/marinovg/oak/programs/meme-5.0.5/src/dp.c)); HMMER's traceback re-scores instead and has to repeat the fill's exact order of operations to stay right ([source](https://mitra.stanford.edu/kundaje/marinovg/oak/various/programs/hmmer-3.2.1/src/generic_vtrace.c)), which is the trap the chord table avoids. CHOpt, the other Clone Hero path tool, finds optimal paths only and has no "price my path" mode ([repo](https://github.com/genericmadscientist/chopt)).
