A few terms used throughout, glossed once. An RVA is an address counted from the start of `GameAssembly.dll`, so it is the same on every machine. Il2Cpp is Unity's way of compiling C# to native code; its "dump" is a text listing of every class, member and RVA that the game's metadata still names. A TypeDefIndex is the number the dump gives each class, which is the only stable name an obfuscated class has. Capstone is a disassembler library (it turns machine code into instruction text); Ghidra is a decompiler (it turns machine code into C-like text). `earlyStart` on a task means it may fork from another task's branch tip as soon as that task commits, without waiting for the merge.

## The plain version

Hydra models Clone Hero, and what we know about Clone Hero is scattered. There are 53 session cards tagged `clone-hero` (a grep of the cards' `index.md` today), 114 sessions once the squeeze, fill and hit-window sessions are counted in (the history survey's cut), 26 memory notes (listed in question 3) and about a dozen docs. Each piece answers one question. Nobody can see the whole, so a session started a bot run to test Star Power without knowing the bot never uses it.

The fix is one folder, `docs/clone-hero/`, with one page per area of the game in the game's own order: reading a chart, building the note list, timing, fills, Star Power, scoring, internals. Beside them sit an index, a questions page, a live-checks page and a `code/` folder of annotated listings. Every rule on a page says what the game does, which function decides it (class, method, RVA, annotated file), how sure we are under exactly four labels, which Hydra function owns the same rule, and which session found it. Where Hydra differs on purpose, the row cites the ruling. Where Hydra differs and no ruling exists, the row goes on the questions page for the user.

The work runs in waves. First, read-only scouts on Sonnet mine the record four at a time. Each takes one area's sessions and docs and returns a claim table with evidence and a label. In the same round, the first reverse-engineering scouts re-list the functions whose listings were lost with old scratch folders (most of the record's addresses, as the docs survey found); a second round goes after rows nobody has read. Then four writers on Opus assemble the pages from the claim tables, and one join task generates the fact tables from the finished pages and runs the docs test over them. Then the old documents are cut to one-line pointers and, once the user approves the list, the memory notes are emptied down to the user's own rulings. The five pattern tasks make this folder the model for later knowledge bases: an index, a one-home rule, a line in `CLAUDE.md`, a write-back rule with a card-writer flag, and a test that checks every Hydra name and every game fact on the pages at every merge. Each writer branch and each code change gets one fresh reviewer.

This plan starts no live run. ### 2. The single home for game facts

The request: "Give each one a single home (today the RVAs sit in tools/ch_probe/constants.py, and the dumps hold the rest). In the plan, say how a page's copy is checked against that home. If you see no clean way, ask me."

Today `tools/ch_probe/constants.py` holds 28 named values (lines of the form `NAME = 0x...`, counted today: 14 `RVA_*` and 14 `OFF_*`) and 8 more inside its two `RVA_FORMULA_*` tables (`"c1": 0x...` entries), and says of itself "This is the ONE place the numbers live" (its lines 5 and 6). Of the `RVA_*` names, `RVA_CONST_*`, `RVA_FORMULA_*` and `RVA_HITCHECK_THRESHOLD` (lines 159 to 191) are data addresses in the DLL's `.rdata` section (read-only constants), not methods, so no dump line names them. The dumps hold everything else: for 6142, `dump.cs` is 36,453,454 bytes and `facts.json` 19,792,675 bytes (folder listing today), outside the repo in `hydra-data\ch-dumps\`, so no test in CI can read them. Docs already carry hex addresses on 342 lines in 50 files, 651 addresses in all, none checked by anything (a grep today of `0x` plus five or more hex digits over the tracked `docs/**/*.md`, leaving out this plan; the game survey, with its own pattern, got 327 lines in 42 files).

Recommendation: a committed extract that holds only the facts the pages cite. `tools/ch_mcp/dump_facts.py`, which already parses the `// RVA:` lines (its line 45), gains a `--tsv` mode (TSV is a plain-text table with tab-separated columns) that reads the pages folder and `constants.py`, looks each cited fact up in the dump, and writes `docs/clone-hero/code/facts-6142.tsv` and `facts-4045.tsv`. One row per fact: build, kind (method, field, class, enum), TypeDefIndex, class name (blank when obfuscated), member, RVA (blank for 4045, whose dump has no addresses), field offset. The header carries the build's version string and the MD5 of `GameAssembly.dll` computed from the file on disk when the table is written (not copied from a log). The docs test then checks every game fact on a page against those tables, and checks every `RVA_*` method address and `OFF_*` offset in `constants.py` against the 6142 table, so the two homes cannot drift apart. Tasks K5a (the test), K5b (the tool) and J1 (the tables, generated once the pages exist) own that. `dump_facts.py --check` diffs an existing table against the dump and exits 1 on a difference; it is run by hand on this machine, so the one gap left is that a page is checked against the extract at every merge, but the extract is checked against the dump only when someone runs the tool. The MD5 header makes a stale extract visible but not automatic.

What each kind of fact looks like on a page, and how it is checked. A method or field of a readable class: `GameManager.songTime`, checked by name. A member of an obfuscated class: `#8255.sp_amount` (TypeDefIndex, then the member), checked by index and name. A field known only by its offset: `#8255+0x68`, checked by index and offset. An RVA: `0x20F6800`, checked by address. A `.rdata` constant: its `constants.py` name, `RVA_CONST_NORMAL_BACK`, which the existing docs test already checks against `tools/` because it has an underscore; the hex is never written on a page. What stays unchecked, and says so on `README.md`: enum values and `_TypeInfo` addresses from `il2cpp-fields.md` (they are cited by name with "not checked" in the evidence line), and the `.rdata` hex values themselves, whose only home is `constants.py`. The check also cannot tell whether a real address is the right one for the rule it is cited under: a page that gives a real method's address for the wrong rule passes, because the test proves only that the fact exists in the dump. That part is the reviewer's job and the annotated listing's (the listing shows the instructions that decide the rule), and `README.md` says so.

Both ends: a page that cites `0x20DEEC0` passes because the 6142 table has that method; a page that cites `0x20DEEC1`, or `GameManager.songTimer`, fails the merge with the page and line. The strongest case against: it is a third copy (dump, extract, page), and the table is regenerated by hand. The alternative with no new file is to check pages only against `constants.py`, which covers its 28 named values and 8 table entries and leaves every other fact unchecked; the request forbids that unless the user says so.

## The page template

Every rule is one block with a stable id, so a card, a test or a pointer can name it. The block is a `###` heading and seven fixed lines, in this order, because a fixed shape is what the test and the card writer can grep for.

```
### SP-07 Star Power ends when the meter reaches zero, checked per frame

Rule: <the rule in plain words, one or two sentences>
Label: <exactly one of: Proven in the game's code | Proven in a live run | Hydra assumes it, never checked | Unknown>
Evidence: <for code: the annotated file under code/ and the lines; for a live run: the run, its date, its result file; for assumed: the Hydra code that holds it; for unknown: where we looked>
Game code (6142): <Class.member or #<TypeDefIndex>.member>, RVA `0x20F6800`, `code/6142/sp_update_20F6800.asm` lines 41 to 58; or "not found: looked in ..."
Hydra: <owner function or constant, file:line, e.g. `activation_initial_end_times` in src/search/graph.h; or "no owner: <where we looked>">
Ruling: <D-number or ADR with the user's quoted words, or "open split: see questions page Q-nn", or "none needed: same rule">
Found: <date>, session <id>; <or "this plan's wave 1 scout <slice>" for a fact assembled from several sessions>
```

Game names are written as the dump writes them, `Class.member`, never `Class::member` or `method()`, because the docs test treats a span with `::` or `()` as a Hydra name and would fail it. An obfuscated class is written `#<TypeDefIndex>.member`, or `#<TypeDefIndex>+0x<offset>` when only the offset is known (question 2). An RVA is always backticked `0x` plus at least five hex digits. A `.rdata` constant is written by its `constants.py` name, never as hex. A 1.0 fact writes `Game code (4045): Class.Method, code/4045/<file>.cs lines ...` with no RVA. Hydra names are the ones the C++ or Python code holds: write `kLegacyFillsFlag`, not `legacy_fills` (which passes today only through a local variable in `src/cli/batch.cpp` line 73), and never a name that lives only in a `.js` agent file, which the docs test does not walk.

Each page opens with three lines: what the page covers, which build it describes, and the date of the last write-back. Then the rule blocks, grouped under `##` headings in the order the request gives for that area. Each page ends with "Rows waiting on a live run" (ids only, pointing at the live-checks page) and "Open splits" (ids only, pointing at the questions page).
