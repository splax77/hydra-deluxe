# Plan: a controlled test of agent effort (high, medium, and low where it fits)

Written 2026-11-07 by a planner agent (task `EFFORT-PLAN`, session `43eecb1c-c046-4595-b33c-4b483bdcbdc8`). Nothing in this plan has run. The test spends real money, so it waits for the user's yes, and that yes must name a budget (agent rule 3; the handoff's "What is next").

## The question in one paragraph

Agents here run at whatever effort their session has, which has mostly been high. The handoff found that medium-effort agents cost about half as much as high-effort ones, but those agents did different work in different sessions, so the gap mixes effort with task difficulty. This plan runs the same work at each level, scores it blind, and counts rework, so the user can decide per role whether to lower effort. The honest limit up front: an affordable test can show the cost gap is real and can catch a large quality drop. It cannot see a small one. Section "How big the test is, and what it can and cannot show" says the numbers.

## What the docs say about setting effort (read 2026-11-07, both pages cut off at 100,000 characters)

From `https://code.claude.com/docs/en/sub-agents`: the frontmatter `effort` field "Overrides the session effort level, but not the `CLAUDE_CODE_EFFORT_LEVEL` environment variable. Options: low, medium, high, xhigh, max". The per-call parameter: "When you ask Claude to run a non-fork subagent at a specific effort level, it can also pass an `effort` parameter for that invocation. The parameter overrides the `effort` field ... The per-invocation parameter requires Claude Code v2.1.292 or later." And: "On the main conversation's model, the subagent runs at the level you pick in the session ... On another model, that level doesn't apply. To choose its level, set the `effort` field."

From `https://code.claude.com/docs/en/model-config`: the session's level resolves in this order: the environment variable, a level picked in the session, `--effort`, saved settings, then "The model's default effort: `high` on every model that supports effort, except that Opus 5.5, Sonnet 5.5, and Haiku 5.5 default to `medium`". Fable 5.1 and the 5.5 models all support `low`, `medium`, `high`, `xhigh`, `max`.

So the priority the main session relayed is right as far as the docs go: environment variable, then per-call parameter, then frontmatter, then session level (on the same model) or the model's default (on another model). The test uses the per-call parameter, because it changes no file and a user-approved plan naming each agent's level counts as the instruction the Agent tool's text asks for. If the user later adopts a level for a role, the permanent form is the `effort:` frontmatter line in that role's agent file, which is a gated change to `C:\Users\Patrick\.claude\agents\` and needs its own review.

One web result (a blog, unchecked) says Claude Code 2.1.316 added `CLAUDE_CODE_SUBAGENT_EFFORT` and stopped subagents inheriting the session level. This machine runs 2.1.310. If Claude Code updates during the test the ground moves, so every live step records `claude --version` and stops if it differs from the version LS-0a recorded.

## Prior art, and what I take from it

I searched the web for measurements of reasoning-effort levels in coding agents. The usable sources are an arXiv preprint, "Prompt-Induced Waste in Coding Agents: Reasoning, Effort, Harness Design, and End-to-End Cost" (`https://arxiv.org/pdf/2608.01347`), which reports that going from low to xhigh raised billed cost 2.4 to 4.5 times while success on Opus 5 barely moved, and that every timeout and empty patch happened at high or xhigh; a Latitude blog post, "reasoning effort only matters without tests" (`https://latitude.so/blog/reasoning-effort-only-matters-without-tests`), which found effort made no difference when the agent could run tests and a large difference when it could not; and a single-run Sonnet 5.5 bug-fix comparison (`https://wmedia.es/en/tips/claude-code-subagents-cheaper-low-effort`) where medium was cheapest ($0.076) because low took 12 turns instead of 4 and cost more ($0.094) than medium, with every level passing all hidden tests. All three are `unchecked` premises in the map; none is load-bearing for a result, only for the design.

Three design choices follow. Our executors can run their task's tests, so the prior art predicts a small quality gap there; the test must be able to see a gap of a few failures or it proves nothing new, and the size section is honest about that. Low effort can cost more than medium through extra turns, so the test measures cost, not just the level, and never assumes lower is cheaper. Single runs are noise, so every cell has repeats.

## Global constraints

Every test agent stays on its role's model (agent rule 2): executors on Opus, reviewers and scouts on Sonnet, planners on Fable. No run touches the full test suite, `hydra_uitest --all` or any library run (rules 1 and 8); an executor runs only the test file its brief names, on `testdata/input`. Every test branch is cut by hand from one pinned base commit into a worktree directly under `C:\Users\Patrick\Downloads\Hydra\hydra-test\.claude\worktrees\`, and no executor is launched with `isolation: worktree`, because the docs say that cuts from the default branch, not the session's `HEAD` (P6b), and `origin/main` is hundreds of commits behind `main` (P6); the task's base is an older commit than either. `.claude/worktrees/` is also the one place the delete rule trusts. No test branch is ever merged into `main`; the check in T4 proves it. The scorer never learns an agent's level. Every step has a dollar cap, a run cap and a time cap, and says what to report when a cap is hit. The whole test has a hard stop cap. `CLAUDE_CODE_EFFORT_LEVEL` must be empty for the whole test, because it would override every per-call level.

Two branches carry the test's own files, and neither name starts `claude/eff-`, so T4's guard never mistakes them for test branches. `claude/effort-test-tools` holds the scripts from T1, T3 and T4, and goes through one code review and onto `main` before LS-0a. `claude/effort-test-results` holds T2's fixtures and later `runs.csv` and `results.md`, goes through one document review at the end (LS-5), and the main session cuts it from `main` after the tools branch merges. Both are made by hand, in worktrees under `.claude\worktrees\`. The main session runs every script from the main checkout, never from a worktree cut at a task's old base.

Reviewers are launched as `docs/agents/derive-once-review.md` step 4 says for real reviews: `subagent_type: reviewer`, `isolation: worktree`, and a brief that names the fault branch's key and the run's own hand-made worktree, where the reviewer commits. The isolation copy is only a scratch checkout cut from `origin/main`; `git merge-base --is-ancestor` shows none of the five merges T2 considers (`32973b96`, `735d2daa`, `8ad1fc65`, `60f7a5b3`, `be54d7bc`) is in `origin/main`, so that copy holds no finished solution. The hook that checks a reviewer dispatch (`review_dispatch.py`) needs only the type and one 40-character key. Executors are launched without `isolation`.

Test agents must not read the finished solution. Worktrees share git's objects and the main checkout sits on the same disk, so an executor or reviewer could read the merged work from `main`, from the merge commits of the four tasks, from another run's branch or from `claude/effort-test-results`. Every test brief carries this rule: "Do not read the main checkout, `main`, `origin/main`, any other branch or worktree, or any commit other than your own base and branch. The one allowed use of `main` is the range `main...<your key>`, for a reviewer." The check is a script (T3), run over the transcripts of each wave after it ends. It lists every tool call that names `main` or `origin/main` outside that range form, any `claude/` branch other than the run's own, any path under `C:\Users\Patrick\Downloads\Hydra\hydra-test` outside the run's own worktree, `git log --all`, `git branch -a`, and the first eight characters of each of the four merge hashes. The main session reads each listed call and rules on it: a call that read the finished solution or a sibling's work makes the run **tainted**. A tainted run, and a run the progress hook stopped while its first build was still running (the transcript's last call is a build), are both **void**. A void run counts in neither level's pass count or rework cost, is charged to the spend, and is re-run once at the same level in a fresh worktree. A second void run in one cell leaves that cell with no result, and a role needs every cell for a verdict. The test cannot prevent a read, only find it; a read the script does not list is not found, and the results note says so.

## The work before any run

### T1: rebuild the accounting as a committed script

The handoff's scripts were scratch and are gone. T1 writes `tools/agent_cost.py` in the Hydra repo, on `claude/effort-test-tools`, following the handoff's recipe: walk every `*.jsonl` under `C:\Users\Patrick\.claude\projects\<project>\<session>\subagents\`, read `agentType` from the `.meta.json` beside each, take the last `message.usage` per `requestId`, price it by `message.model` with the price table from the handoff (Fable 5.1 $10 / $50 / $0.25 per million input / output / cache read, Opus 5.5 $4 / $20 / $0.20, Sonnet 5.5 $2 / $10 / $0.20, Haiku 5.5 $0.10 / $0.50 / $0.01, and for a Haiku request whose context (input plus cache read plus cache write tokens) is over 100,000 tokens $0.50 / $2.50 / $0.05), read the `effort` key on each assistant record, and count `tool_use` blocks.

Cache writes are priced by their length, read from the usage record's `cache_creation` object: `ephemeral_5m_input_tokens` at 1.25 times input and `ephemeral_1h_input_tokens` at 2 times input (the handoff's "Prices used" paragraph). The two kinds are not the same on this machine. A scan of the Hydra project's transcripts on 2026-11-07 found 191.8 million cache-write tokens in 1,618 agent transcripts, all of them 5-minute; and 37.9 million in 144 main-session transcripts, all of them 1-hour. So an agent's cost is nearly all 5-minute writes, and the main session's own cost (the orchestration the budget counts) is 1-hour writes, which a flat 1.25 would under-count by 37.5% of their price. When a record has no `cache_creation` object, the script prices its `cache_creation_input_tokens` at 1.25 times input and prints how many records it did that for.

The script takes `--session <id>` to report only one session's agents, `--agent <id>` for one agent, and `--since <date or date-time>`. It prints one row per agent (agent id, type, model, effort values seen, cost, calls, first timestamp) and a summary per type and effort, and writes the rows as CSV to a path given with `--out`. It also prints the main session's own cost for `--session`, so the orchestration overhead is measured, not guessed. The main session's cost is read from `<project>\<session>.jsonl` the same way.

### T3: the blind scorer's brief and the scoring script

The scorer is a Sonnet scout at high effort, launched once per executor task after that task's runs finish. It gets the task's checklist, the reference diff, and the six runs' diffs and test output labelled R1 to R6 in an order a script shuffled and recorded in a key file the scorer never reads. It fills one line per run per checklist item (done, partly, missing) and lists anything a run changed outside the task. It never sees transcripts, costs, levels or agent ids. Scoring for reviewers needs no scorer: a script reads each reviewer's commits after the handed tip and checks each planted fault's file and line against the fault key (fixed, named in the review but not fixed, or missed), and counts edits to lines with no planted fault as false findings. Rework is counted in dollars. A run that fails (an executor whose named tests do not pass, or that hit the progress cap or reported unfinished; a reviewer that missed any one of its three planted faults; a scout whose answer does not match) is charged its own cost plus the median high-effort cost of its role for a redo. That is the "rework-adjusted cost" the decision rule reads. A void run (Global constraints) is not a failure and is not charged this way. For executors and scouts the charge is a fair stand-in for doing the job again. For a reviewer it is not: a second review would not necessarily catch the fault, and the real cost of a missed fault is a defect reaching `main`, which dollars do not show. So the results note reports, beside each reviewer's pass count, how many of the 36 planted faults each level caught (12 runs times 3 faults), and the question list asks the user to rule on reviewers (question 8).

## How big the test is, and what it can and cannot show

Each cell (one role, one task, one level) gets 3 repeats. Runs of the same task at both levels launch in the same wave, alternating levels, so time of day and machine load fall on both sides alike (rule 6 says to run in parallel anyway).

Executors: 4 tasks x 2 levels x 3 repeats = 24 runs. Reviewers: 4 fault branches x 2 levels x 3 repeats = 24 runs. Scouts: 4 questions x 3 levels (high, medium, low) x 3 repeats = 36 runs. Planners: 0 unless question 2 says yes (then 2 tasks x 2 levels x 2 repeats = 8 runs, scored by a plan reviewer on a fixed checklist).

What this can show. The cost gap: the rebuilt data puts the executor interquartile range at $1.47 to $3.15 at high and $0.79 to $1.68 at medium. Within one task the spread is narrower than across tasks, and a paired comparison of 12 runs per level per role can tell a 40% cost gap from noise; the observed gap is about 45%, so if it is real the test will see it. A large quality drop: 12 of 12 passing at high against 7 of 12 at medium is a difference a two-sided Fisher test calls real at about p = 0.04. A small quality drop: 12 of 12 against 11 of 12 is p = 1.0 and against 10 of 12 is p about 0.48 (both computed with the same two-sided Fisher test), which is no evidence either way. Said plainly: if medium fails one or two more runs than high out of 12, this test cannot tell whether that is real. The decision rule below then treats two extra failures as "inconclusive, keep high". It does not do that for one extra failure: with a saving of 25% or more it lowers the role, so the rule accepts a one-failure drop (about 8 percentage points more failures) that this test cannot see. Question 9 asks the user to rule on that.

Two limits make the numbers above optimistic. First, a reviewer run fails if it misses any one of three planted faults, so even a good reviewer can fail often: at 90% per fault it fails 27% of runs, and high may score well below 12 of 12. A pass count near 8 of 12 at high leaves little room to see a drop, so the results note gives the per-fault catch counts beside the pass counts. Second, the Fisher numbers treat 12 runs per level as independent, but they are 4 tasks times 3 repeats, and repeats of one task resemble each other. The real evidence is closer to 4 paired comparisons than to 12 independent runs, so the p-values read as best cases and the results note says so. Doubling the repeats to 6 per cell would roughly halve the smallest detectable gap and double the cost; that is question 5.

### LS-0a: does the guard script pass, and what version are we on?

The main session runs `tools/effort_test_guard.ps1 -Record` from the main checkout. It prints one line for each of its four checks, writes `claude-version.txt` from `claude --version`, and exits 0 only when the other three checks pass. ## The decision rule, fixed before any run

For each role, compare the 12 high runs with the 12 medium runs (or the 12 low runs for scouts).

Lower the role's effort to the cheaper level when both hold: the cheaper level has at most one more failure than high out of 12 (failures as T3 defines them), and its rework-adjusted cost is at least 25% below high's. Keep the role at high when either holds: the cheaper level has three or more failures than high out of 12, or its rework-adjusted saving is under 15%. Anything between is inconclusive, and inconclusive means keep high; the results note says what a larger test would cost to settle it. For scouts, low is chosen over medium only if low passes the same two tests against medium. A role whose step was stopped by a cap before 12 runs per level finished, or that has a cell with no result after a second void run, gets no verdict. For reviewers the results note also reads the per-fault catch counts; a level that catches fewer of the 36 planted faults than high by a margin the user would not accept is the user's call (question 8), not a thing the rule decides alone.

If LS-0b fails, no verdict exists for any role and nothing changes.

## Questions

1. **Budget.** Approve a core test at about $159 with a hard stop of $200, or with planners about $231 and a hard stop of $290. Both figures include building the scripts and fixtures (T1 to T4, about $18 of the $159) and the main session's own orchestration (a 25% guess, about $32, replaced by a measured figure at LS-0b). The hard stop is checked before each wave, and can be overshot by about $16 at most. Recommendation: the core test without planners. You will see about 96 agent launches over roughly a day of wall clock, and nothing else changes.

2. **Planners in or out.** Planners are 9.6% of spend and the hardest role to score (a plan's quality is a judgement, not a test result), and the handoff's own numbers show the smallest effort gap for them. Recommendation: out for now, as a second test if the core test lowers any role. You will see no planner runs and no planner verdict.

3. **Low effort for scouts.** Adding `low` to the scout step costs about $8 more (12 scouts at the rebuilt $0.55 mean is $6.60, with 25% orchestration $8.25). The prior art warns low can take more turns and cost more than medium, which is exactly what the measurement would show. Recommendation: include it; scouts are read-only and the user asked whether some agents need only low. Reviewers do not get a low arm, because they are the safety gate and a missed fault there costs more than the test saves.

4. **The four executor tasks.** The four named in T2 are my pick for being small, tested, non-UI and needing no live game: three Python tooling merges and one C++ merge (`be54d7bc`). The verdict covers that kind of work and says little about C++ alone, because C++ has one task and six runs. A second C++ task would add six executor runs and six reviewer runs, about $26 with orchestration, plus its fixture work, and its cold builds are slow. Recommendation: accept the four; or name others, with the same properties (small, own test file, non-UI, no live game). You will see those four tasks redone 6 times each on throwaway branches.

5. **Repeats.** Three per cell is the smallest size that can see the cost gap and a large quality drop. Six per cell would roughly halve the smallest detectable gap and double the cost of the runs (the core estimate would be about $295: the fixed $24 of building and checking, with orchestration, stays and the other $135 doubles). Recommendation: three, and read the inconclusive verdict as keep high. You will see the limits written into the results note.

6. **Fault branches and review verdicts.** Test reviewers leave CLEAN or BLOCKED records for fault-branch tips in `reviews.jsonl`. Those branches are kept out of `main` by the guard, and the records only matter if someone merges them. Recommendation: after the results are committed, you delete the `claude/eff-*` branches and worktrees yourself, or type a yes for the main session to do it. You will see about 52 extra branches and worktrees until then (24 executor runs, 24 reviewer copies, 4 fault branches), plus any re-run of a void run.

7. **If LS-0b fails.** If the per-call level does not land, the only other route the docs give is the `effort:` frontmatter line in each agent file, which is a gated change to the agents folder for the test's duration. Recommendation: stop and ask before trying it. You would see one reviewed commit in `C:\Users\Patrick\.claude` adding and later removing those lines.

8. **How a reviewer's miss is judged.** A reviewer run fails if it misses any one of three planted faults, and the rework charge (its cost plus a redo) does not capture what a missed fault in a safety gate costs. The results note will show pass counts and per-fault catch counts out of 36 per level. Recommendation: reviewers stay at high unless medium's per-fault catch count matches high's, and you read both counts before deciding; the decision rule alone does not lower the reviewer. You will see both counts side by side in the results note.

9. **A one-failure drop the test cannot see.** The decision rule lowers a role when the cheaper level has at most one more failure than high out of 12 and saves at least 25%. One extra failure in 12 has p = 1.0 on the same Fisher test, so the test cannot tell it from luck: the rule accepts a possible quality drop of about 8 percentage points in exchange for the saving. Two extra failures (p about 0.48) already count as inconclusive, which keeps high. Recommendation: keep the rule as written for scouts and executors, and let question 8 govern reviewers; or tighten it to "no more failures than high", which makes a verdict harder to reach and so likelier to end as keep high. You will see the verdict for each role, and the rule's threshold quoted beside it.
