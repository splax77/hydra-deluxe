# The press schedule comes from Hydra: hydra_replay plans every press, the player only sends it

Date: 2026-11-08. Planner: Fable, tasks PL-REPLAY-SCHEDULE and PL-REPLAY-SCHEDULE-2 (this revision), session 6341c618. Follows `docs/superpowers/plans/2026-11-08-player-freak-fixes.md` (T1 merged; T2 held on `claude/pl-freak-t2`) and `docs/superpowers/plans/2026-11-07-player-limits.md`.

## The plain version

Today the auto-player reads two files Hydra writes (`hydra_replay dump` and `hydra_replay score`) and then works the Star Power timing out again in Python: which chord's press moves each end, how far to press it early, the planned end, the per-note hit window, the frame delays. The user's words: "the solver re-deriving everything hydra's engine already knows ... this never should have been an isue", and on the first draft of this plan, "why is the python still doing its own thing? the whole point of this plan is to hand off all the starpower planning to hydra which already knows what to do".

So this revision hands all of it over. A new `hydra_replay schedule` command takes the chart, the dump and a path index, and writes one file: for every chord, each press's aim time, the window side the game gives that chord, the latest clock at which the press may still be sent, which chord leads each squeeze and by how much, the end the game should store after each press, what to do if the end the game actually stores crosses a threshold, and whether the game can make each squeeze at 100% speed. Every number in that file comes from the engine's own `Activation` and from constants that live in the schedule code with their sources. The Python keeps only what happens live: sending each press at its time, reading the end the game stored after the chord the schedule names, shifting the later presses by the difference, picking the fallback the schedule wrote when the read crosses its threshold, not sending a press the clock has already passed, and the logs.

One number in the first draft was wrong, and the move fixes the cause. The draft said chord 263 on Get Ur Freak On, the overfill chord whose press moves the first end, has the widest window on the chart (85.72 ms a side) because its neighbours are 2.4 and 7.8 s away. That came from the test fixture `freak_limits_score.json`, which keeps 109 of the chart's 1,605 chords and not chords 262 or 264. In the real chart they are 56.18 ms away on each side, so 263's side is the narrowest the game gives, 48.15 ms. The equal-room split still works (both presses keep 23.3 ms), but the aims change: 263 at 24.82 ms early and 387 at 24.27 ms late, not 43.61 and 5.48. Once the C++ computes the windows from the whole chart, no pruned fixture can do this again.

Seven questions are left for the user. Five are about the schedule: how a squeeze is split between its two presses (the numbers are in design point 4), where the frame period comes from, what to do when a timed squeeze-in's read end comes too early, how the decline mode reaches the schedule, and what to do with a squeeze the game cannot make at 100%. The `ch_run_chart` arguments and the held T2 branch are two smaller ones. Which notes are a chord's neighbours is no longer a question: the game's code answers it (TM-51 on page 03), and chord 1062 gets 73.76 ms a side.

## Prior art

A search (2026-11-08, "rhythm game bot precomputed input schedule from chart analysis engine hit window") found no bot that takes its press schedule from the game's own path analysis. The nearest patterns are a browser rhythm game's scheduler, which fills a short lookahead from one audio clock ([Mintlify, Funkin gameplay](https://www.mintlify.com/FunkinCrew/Funkin/systems/gameplay)); the osu!mania bot RhythmSharp, which reads the notes first and runs them through a scheduler ([RhythmSharp](https://github.com/rwdkor/RhythmSharp)); and the Sonolus guide, which judges a press by the window around its note's time ([Sonolus play guide](https://wiki.sonolus.com/sonolus.py-guide/play/11)). All three keep the timing in one place and leave the sender to send. ADR 0030 in this repo is the same shape: the Python helper is transport, Hydra owns every rule.

## The design, point by point

### 1. One new command: `hydra_replay schedule`

`hydra_replay schedule --chart <chart> --path <dump> --index <n> --out <schedule.json>`, plus the decline mode as question 4 settles it. It loads the chart as `score` does, takes the path's activations off the dump the way `windows_from_file` does, and runs the same `replay_path` so every chord's gems, multipliers and Star Power payment are the engine's. Then it writes one file the player reads and nothing else needs. The writer is a new file, `tools/replay_schedule.cpp` with `tools/replay_schedule.h`, in the `hydra_replay_json` library, so `tests/test_replay_schedule.cpp` can call it. There is no `player.json` and no other input: every constant the schedule uses lives in `tools/replay_schedule.cpp`.

### 2. The constants, and where each comes from

Each is one `constexpr` in `tools/replay_schedule.cpp`, with a comment naming its source and a test pinning its value. None is read from a file, and none has a Python copy once TP1 lands.

- The window clamps: front 37.5 ms and back 85 ms (TM-18 on `docs/clone-hero/03-timing.md`), the half-gap rule (TM-19: half the gap to each neighbour, held between front and back; a missing neighbour or one at the same time gives the back), the formula (TM-21: whole window = (x × 0.0110924369747899 − x² × 2.628539e-05) × 170 − 20, x the summed gap in ms) and the note's half (TM-20). The schedule holds the formula's constants as its own; TP1 deletes the Python copies `WINDOW_FORMULA_NORMAL_*` from `tools/ch_probe/constants.py`, whose only readers were `play_chart.py` and its test. `EXPECT_NORMAL_FRONT_S` and `EXPECT_NORMAL_BACK_MS` stay in `constants.py`: the probe reads them to check a live engine's fields, which is a different question. `kHitWindowMs` (85) and `kSqueezeWindowMs` (500) in `src/core/model.h` are not touched and are not read by the schedule; nothing under `src/` includes `tools/replay_schedule.h`. This per-note window code is where the user's "new feature" would start, by moving it under `src/core` and giving the screens a reader; this plan does not do that.
- The neighbours of a chord are the chords before and after it in the chart, by time; gems of the same chord are not each other's neighbours. That is the game's rule: its two neighbour lookups return the nearest note strictly later and strictly earlier by tick, so a gem at the same tick is never returned (TM-51 on `docs/clone-hero/03-timing.md`, read from `code/6142/note_after_lookup_5DD8D0.asm` and `code/6142/note_before_lookup_5DDED0.asm`; row P35). `window_sides` uses the same rule today. So chord 1062 (kick and green cymbal, 84.27 ms after chord 1061 and 340.91 ms before chord 1063) gets 73.76 ms a side.
- The frame period `kFrameMs` 3.0: one frame at the game's `framerate = 330` cap (TM-49) and the 2.98 to 3.03 ms the four live activations showed (SP-47). A press is judged between one and two frames after the clock the player read when it sent it (TM-27, SP-47): `kJudgeEarlyMs` = 1 × `kFrameMs`, `kJudgeLateMs` = 2 × `kFrameMs`. Question 2 asks whether the period must follow the machine.
- `kPressLeadMs` 2 (D51), `kSpEndLeadMs` 15 (the 2026-11-06 optimal-score plan's question 3), `kSpOutLagMs` 15 (the 2026-11-07 refinements plan's question 2), `kChordOrderGapMs` 8 (the same plan's amendment, "8 ms", "Only where it matters") and `kRoomMarginMs` 3.0 (the freak-fixes plan's question 2, the user's "Yes, start it"): each keeps the meaning its Python comment gives today; the comment moves with it.
- The order of the pads for a declined chord's kept gem, Green, Blue, Yellow, Red (FL-09 on `docs/clone-hero/04-fills.md`; today's `_TOP_PAD_ORDER`).

### 3. The geometry, read off the engine

For each activation, in path order: the activation chord's index, the nominal end in ms (`nominal_end()`), the final end (`deact_tick()`), and every SP-end step as the engine stored it: the chord that moved it, its kind (activation, collected, clamped, squeeze-in), the end in force after it, and that step's anchor chord (`end_anchor_tick(step)`). The activation also names `read_end_after`: the chord whose press the live player reads the game's end after. That is the anchor of the final end: 263 for Freak's 232, 1062 for 1062. The end is also read right after the activation's own press, because the nominal end there checks the frame model (SP-47).

For each squeeze (`sqinouts`): its chord, its kind, its `offset_ms` as stored, the end it is measured against (`squeeze_end_tick(k)`), the chord whose press moves that end (`squeeze_anchor_tick(k)`), the ratios on that end (`transfer_post` for a SqOut, the SqIn's own `transfer` for a SqIn, never recomputed), the steady spans on the anchor and the end (`steady_spans`), and `needs_no_timing` (`SPSqueeze::needs_no_timing`). A squeeze-out's chord is `sqout_tick`.

For each chord: index, tick, ms, `side_ms` (its window side from point 2), its gems in `Chord::note_list(true)` order with multiplier and dynamic, `ends_sp` (its tick is a final end), `declined` (its tick is in some activation's `skipped_fill_ticks`) with the gems the decline mode sends, and `paid_by`: the activations whose Star Power paid it, with its offset from each one's end. `paid_by` comes from the one loop in `src/core/replay.cpp` that already decides `in_sp` per window; `ReplayChord` gains the list and the loop fills it where it counts `sp_paid`. Nothing else works that out again.

### 4. The aims: which press leads a squeeze, and by how much

The schedule writes, per chord, one or more presses. Each press has its gems, `aim_ms` (relative to the chord's time: negative is early, positive is late), `after_ms` for a later order group, `timed_from_end` (the activation whose end it is measured against, when it is), `room_ms` (how far inside the chord's side its judged press stays in the worst frame case) and `last_send_ms` (the latest song clock at which it may still be sent: the chord's time plus its side less `kJudgeEarlyMs`, so that a press judged one frame later still lands inside; the TM-27 rule T1's drop check applies today, worked out once here). The rules, each stated once in `tools/replay_schedule.cpp`:

- A plain chord is pressed `kPressLeadMs` early.
- A chord on a final end, or paid inside near an end a lead moved earlier, is pressed `kSpEndLeadMs` before that end (the limits plan's design point 3, unchanged in meaning).
- A squeeze that needs no timing (Freak's 717, 84.27 ms inside its end) gets the plain press and the line says so.
- A squeeze that needs timing is split between its two presses: the anchor chord's press (the chord `squeeze_anchor_tick` names, which is the overfill chord when the cap clamped, else the activation) and the squeeze chord's press. Question 1 sets the split rule; the recommended rule is equal room. For a squeeze-out with anchor side `side_a`, squeeze side `side_s`, `gap` ms between the squeeze chord and the end, ratio `r`, lag `kSpOutLagMs` and `jl` = `kJudgeLateMs`: the anchor lead is `L = (side_a − side_s + gap + lag) / (1 + r) + jl`, the squeeze aim is `gap + lag − r × (L − jl)` late, the anchor room is `side_a − L` and the squeeze room is `side_s − aim − jl`. Both rooms are equal by construction. A squeeze-in after the end is the mirror: the anchor goes late, the squeeze press `kSpEndLeadMs` before the moved end.
- The split uses the ratio on the side it moves (`end_scale_early` for an early anchor, `end_scale_late` for a late one) and refuses a lead that crosses a steady span, as today.
- A chord with several gems is pressed in groups `kChordOrderGapMs` apart: an activation's flagged gem first (row P27 says who names it), then by multiplier, lowest first; a squeeze-out's late gem last, after every inside group. The refusals today's `_squeeze_out_inside_groups` makes stay, in C++.
- The planned end per activation, and per `read_end_after` chord: the end the game should store once that chord's press is judged `kJudgeEarlyMs` after its aim. For a plain activation press that is the nominal end moved by `r × (kJudgeEarlyMs − kPressLeadMs)`, 1 ms later; for a led anchor it is the stored end moved by `r × (L − kJudgeEarlyMs)`. The live reply's "later than planned" line then reads 0 to one frame when the game does what the model says.
- Each press that an end times (the squeeze press, the inside group of a squeeze-out) also carries `aim_end_ms`: the end its aim assumed, which is the stored end moved by `r × (L − kJudgeLateMs)`, the latest the end can be when the anchor press is judged one to two frames after its send. It is `kJudgeLateMs − kJudgeEarlyMs` (times `r`) later than the planned end above, because the aim and room figures are worked out for the worst frame. The player shifts such a press by the read end minus `aim_end_ms`, never minus the status line's planned end: the read can only land 0 to `r × 3` ms before `aim_end_ms`, so a retimed press moves earlier or stays and is never later than its `aim_ms` and `room_ms` say. (Shifting by the planned end instead would add up to 3 ms to an aim that already assumed the late frame, and would break the fallback threshold of point 5, which assumes the retimed press goes at `read + kSpOutLagMs`.)

Every refusal that today raises `ValueError` in Python is a `refusals` list in the file, each naming the chords and the rule in plain words: an activation that would need both directions, a lead that leaves its window, a steady span crossed, a press that reaches another note on its pad (today's `_refuse_far_presses`, moved whole, TM-50's rule included), a squeeze-out whose late gem pays less than an inside gem. A squeeze also carries `feasible`: true when every press of it has `room_ms >= kRoomMarginMs` at 100% speed. Hydra's own 500 ms horizon is untouched: the schedule may list a squeeze Hydra's screen shows as Insane+ and say `feasible: false`; that is the user's second reason for the horizon, now in the file.

### 5. The live fallback, written ahead of time

A squeeze press whose room depends on the end the game actually stores gets a `fallback` block, so the Python decides nothing: it compares one read with one threshold and does what the block says.

- A squeeze-out's late gem: `if_end_after_ms` is the read end past which the late press, at `read + kSpOutLagMs` and judged up to `kJudgeLateMs` later, would leave the chord's side: `chord.ms + side_ms − kSpOutLagMs − kJudgeLateMs`. The action is `join_group`: the gem goes down with the chord's last inside group (pressed `kSpEndLeadMs` before the read end), and the row says `retimed=inside`. That is the freak-fixes plan's question 3 (a), which the user approved. On Freak 1144 the threshold is 141,571.98 + 53.59 − 15 − 6 = 141,604.57 ms; run 1's read of 141,608.66 would have crossed it, and the read the new lead should give (about 141,598.6 to 141,601.7) does not.
- A squeeze-in pressed before a moved end: `if_end_before_ms` is the read end before which the press at `read − kSpEndLeadMs`, judged as early as `kJudgeEarlyMs` later, would land before the chord's side: `chord.ms − side_ms + kSpEndLeadMs + kJudgeEarlyMs`. Question 3 asks what the action is; until it is answered the schedule writes `drop` and TP2 sends nothing for that press.
- Every press still carries `last_send_ms`, and the Python never sends a press once the clock has passed it (T1's drop, now one comparison against the file).

### 7. What the Python player keeps, and what it does with the schedule

`play_chart.py` keeps `play_chords`, `retime_from_end`, `press_messages`, `with_axes`, `live_play`, `live_press`, `main`, the press-log writers (`write_press_log`, `append_press_row`, `_press_log_writer`), `find_normal_engine`, `load_score_times` (which `tools/ch_mcp/trace_hits.py` reads), `_KEY_FOR_PAD` (the gem colour to kit key map, which is transport), `RunResult`, `RunCapReached`, `StopAsked`, `DECLINED`, `DROPPED`, `NO_ACTIVATION_READ`, `SCORE_READ_DELAY_S`, `RUN_CAP_S`, `STOP_NO_ENGINE` and `_SAME_MS` (the 1e-6 ms equality tolerance `press_messages` uses to pair a press with its group head; it feeds no Star Power number). It gains `load_schedule(path)`, which reads the chords and presses as written, builds `Press` rows from `aim_ms`, `after_ms`, `last_send_ms`, `timed_from_end`, `read_end`, `planned_end_ms` (the status line's, on the chord read after), `aim_end_ms` and `fallback`, and refuses to start when `refusals` is not empty or any squeeze is not `feasible` (question 5), quoting the file's words. `press_plan(chords)` keeps its name and returns the schedule's presses in firing order; it computes nothing.

`play_chords` changes in three places. The drop check becomes `raw_ms > press.last_send_ms`. After a press of a chord the schedule marks `read_end` (the activation's own chord and its `read_end_after` chord), it reads the game's end once, writes `end_read_ms`, and `retime_from_end` shifts every later press with `timed_from_end` equal to that activation by the read end minus the press's `aim_end_ms` (design point 4): one subtraction per press, as today. Then, for each shifted press with a `fallback`, it compares the read end with the block's threshold and applies the block's action (join the inside group, or drop), and the row says `retimed=late`, `retimed=inside` or `dropped`.

`prep_inputs.py` chains the third command: dump, score, then `hydra_replay schedule`, and dry-loads the schedule the way `ch_run_chart` will. `ch_run_chart` and `ch_play_chart` take `schedule_json` in place of `dump_json`; `score_json` stays for `ch_compare`. The reply's squeeze lines come off the schedule: "chord 263 pressed 24.8 ms early for the squeeze-out at chord 387 (end planned 60,551.5 ms, ratio 1.0000, room 23.3 ms both presses)", and `activation_end_lines` keeps its planned-against-read form, now keyed by the chord read after.

## Questions

1. **How a squeeze is split between its two presses.** The code's rule after TC2 is one formula in `tools/replay_schedule.cpp`. Sides: (a) equal room: the anchor press and the squeeze press keep the same distance inside their own windows in the worst frame case. Freak 387: 263 at 24.82 ms early, 387 at 24.27 late, 23.32 ms of room each; Freak 1144: 1062 at 65.72 early, 1144 at 39.55 late, 8.04 each; Rescued 6.58 and 5.86 each; Ghost 4.87 each. `kRoomMarginMs` 3.0 is then the floor each room must clear for `feasible`. (b) the user's literal "-45/+45" on Freak 1144: 1062 at 45 early (room 28.76) and 1144 at 45 late, judged 48 to 51 late against a side of 53.59 (room 2.59); on a 100 ms squeeze such as Rescued 931 the same aims leave the note 7.9 to 12.8 ms inside the end, so the squeeze fails: -45/+45 is not a rule for every chart. (c) the minimal lead, T2's rule: move the anchor only as far as the squeeze needs plus 3 ms, so the squeeze press always has 3.0 ms of room and the anchor the rest (13.08 on Freak 1062; on Freak 263 the anchor would lead by 3.09 + 3 and keep 42 ms). Recommended: (a); it is what "tons of room" means on Freak's squeezes (both presses well inside), and it gives the most room on the chart where room is scarcest (Ghost, 4.87 each, against (c)'s 3.0 on one side).

2. **Where the frame period comes from.** `kFrameMs` is 3.0 in the schedule code, from the user's `framerate = 330` cap (TM-49) and the 2.98 to 3.03 ms of SP-47. Sides: (a) the constant alone; the main session's pre-run check reads `machine_report`'s "settings.ini: framerate = 330" line (`tools/ch_mcp/machine_report.py`, `SETTINGS_KEYS`) and refuses to run on another value until the constant is changed and TC2's pin test with it. (b) `hydra_replay schedule --frame-ms <n>`, with the Python reading `settings.ini` and passing the number: the Python then owns a number again, against the ruling. Examples from both ends: at 3.0 ms Freak 1144's room is 8.04; at a 4.0 ms frame (250 a second, seen only under a build in TM-49) the bounds become 4 and 8 and the equal-room split gives 1062 at 67.72 early with 6.04 ms of room; at 3.03 (1000/330) the rooms move by less than 0.1 ms. Recommended: (a).

3. **The fallback for a timed squeeze-in whose read end comes too early.** The rule is in design point 5: the press at `read − 15` would land before the chord's side. Sides: (a) press the chord plain at `kPressLeadMs` early instead, so it scores (outside Star Power) and the combo holds, and the row says `retimed=plain`; (b) drop it, as the schedule writes until this is answered: the chord is missed and the combo breaks. No fixture chart has a timed squeeze-in (Freak 717 needs none), so the example is hand-built: a chord 60 ms after a planned end with a 50 ms side, read end 20 ms earlier than planned: (a) presses it 2 ms early and loses the squeeze's bar; (b) loses the chord and the combo too. Recommended: (a), the mirror of the approved squeeze-out answer: keep the chord's score and combo over the squeeze.

4. **How the decline mode reaches the schedule.** The mode says what a declined chord sends (`kick_only`, `nothing`, `all_but_top_pad`); it is the user's pick per run. Today's rule (`_kept_gems` in `play_chart.py`): `nothing` sends no gem of a declined chord, `kick_only` sends its first kick and nothing else, `all_but_top_pad` sends every gem but its highest pad (Green, then Blue, Yellow, Red), a chord with no pad gem sends nothing, and a chord with two gems of its highest pad's colour is refused. The user's words asked for a schedule from the chart, the dump and a path index; this flag is one input more, so it is a question. Sides: (a) `hydra_replay schedule --decline <mode>`, one more flag, the Python passes the string through untouched and the mode names' one home is the C++; (b) the schedule writes every mode's gem list per declined chord and the Python picks the list by the mode's name. Examples from both ends: Freak chord 162 (declined; kick, blue cymbal, green cymbal): under (a) with `all_but_top_pad` the file holds kick and blue cymbal for it; under (b) it holds three lists and the Python chooses. Freak chord 51 (declined; kick, blue tom): `all_but_top_pad` keeps the kick, `kick_only` keeps the kick, `nothing` keeps none; under (b) the Python must also decide what an unknown mode name does, which under (a) is `hydra_replay`'s refusal. Recommended: (a); one file, one plan, and a stale or mixed file cannot happen.

5. **A squeeze the game cannot make at 100% speed.** The schedule marks it `feasible: false`. Hydra still lists it, because the user gave a second reason for the 500 ms horizon. Examples from both ends: Freak 387 has 28.09 ms to cover and both presses keep 23.32 ms (feasible); a squeeze whose gap exceeds both windows together (a made-up 200 ms gap against two 53.59 ms sides) has negative room on both presses (not feasible). Sides: (a) the player refuses the whole chart, naming the squeeze; (b) it plays the chart, presses that squeeze's chords plain, and prints a line naming it and its room; the run's score then falls short by that squeeze and `ch_compare` says so. Recommended: (a), because a run that cannot match Hydra's score is a failed run and the refusal says why before the game starts.

6. **`ch_run_chart`'s arguments.** `dump_json` is replaced by `schedule_json`; `score_json` stays for `ch_compare` and the trace. Sides: (a) replace, so one file carries the plan and a stale dump cannot be passed by habit; (b) keep both for a while. Examples from both ends: under (a) a call that still passes `dump_json=<dump>` fails at once with an unknown-argument error, so a habit shows on the first call; under (b) the same call loads, the player reads the dump for nothing, and a schedule made from another chart's dump can sit beside a matching dump without anything noticing. Recommended: (a).

7. **The T2 branch.** Sides: (a) do not merge; TP2 re-makes the `retimed` column and the room check against the schedule's `fallback`; the branch is deleted after TP2 merges. (b) merge T2 first, then let TP1 delete its solver. Examples from both ends: under (a) T2's `retime_from_end` room check never lands in its own form, and its `SqueezeOutDropTest` is written again against the `fallback` block (same cases, new inputs); under (b) T2's solver, which leads chord 232 and so cannot solve the clamped case, reaches `main` for one merge and is then deleted whole by TP1, with its tests.
