# Plan: with "1.0 fills" ticked, generated fills follow old Clone Hero 1.0's own code

Written 2026-11-21 by a planning agent (session 63088e3d, task plan-ch10-fills), from main at 38304a9c9. The owner map it is built from is `docs/superpowers/plans/2026-11-21-ch10-fills-owner-map.md`, committed beside it and copied under "Owner map" below.

## What this does, in plain words

Today, with the "1.0 fills" box ticked, Hydra places generated fills with its own model of the old game. The old game's code has since been read, and it works differently. This plan replaces Hydra's 1.0 generator with a copy of the game's own steps.

The game walks its measure lines. It tries the second line first, then every fourth line, and after a line with no chord close enough it tries the very next line. A chord is close enough when it is within 0.25 seconds of real time of the line. The fill starts half way, in real time, between the previous line and the chosen line. The fill's lead time is measured to one 64th note past the chord.

Charts with written fills are not touched by the generator. The 1.1 rule (box unticked) does not change at all.

Every stored result goes stale once, 1.1 results too, because Hydra has one stamp for all stored results. The user's library re-analyses once after the update.

## Findings (not tasks, not questions)

**1.1 has the same exception and Hydra's grid lacks it.** In a meter with 1 on top, the game makes only the first beat after the meter change a measure line. `MeasureIndex` makes every beat a measure line. The 1.1 build has the same exception (`docs/clone-hero/code/6142/grid_restart_20DACA0.md` line 16, as owner map stop 6 reports). No user words ask for a 1.1 change, and no chart in `testdata/input` has such a meter. This plan changes only the 1.0 generator's lines.

**The Preview's drawn span is not changed by this plan.** The Preview draws a 1.0 generated fill from its engine start to its chord (`drawn_fill_start_tick`, row O11). The game's fill runs one 64th note past the chord. The plan leaves the drawing rule alone, so there is no question about it. The span will still move on screen, because the engine start it reads moves. The captures below show that.

**The "chord 0" claim rests on a helper nobody has read.** The earlier planner, and `fill_generator.md` lines 96 to 98, say a line after the last chord makes the game pick chord 0. That is true only if the game's backward search starts at the index it is given and runs down. The search helper (`EnumerateRangeReversedIndexed`) is not in the listing. If it runs from the end of the list down to that index instead, the game picks the last chord. A second thing decides it too. The tie test at `fill_generator.cs` line 162 subtracts two chord ticks, and if the chord tick field is unsigned (the code at lines 67 and 70 adds it to a `uint`, so it looks so), `chord 0's tick - target` wraps to a huge number when chord 0 sits before the target. Then the test returns the last chord, not chord 0, and a line after the last chord can take the last chord if it is within 0.25 s. Task T0 reads the helper and the field's type (premises P20 and P38), and the port copies whichever the game does. The plan holds no step that assumes chord 0.

**`fill_max_distance_beats` stops applying to 1.0.** The 1.0 reach becomes the game's 0.25 s. A user who edited that key in `hydra_rules.ini` will see it apply to 1.1 only. `fill_cooldown_measures` keeps applying to both, because row O1 names it as the owner of the step after a fill; its default, 4, is the game's number. The game's step is a fixed 4 (`fill_generator.cs` lines 40 and 47). So a user who edits that key in `hydra_rules.ini` gets a 1.0 result that differs from the game, by their own choice. With the default, nothing differs. The plan leaves the key in force and adds no rule of its own. Whether 1.0 should ignore the key and use the game's 4 is out-of-scope item 7, for the user.

**The start gap is reported, not judged.** The game keeps a fill's start as a raw second; Hydra keeps a whole tick. The gap is at most one tick's length. No ruling says how big a gap matters, so task T3 logs the figure beside `kHitWindowMs` (85) and passes or fails nothing on it.

## How the port maps to the game's code

Each line here is a step of `docs/clone-hero/code/4045/fill_generator.cs`, with the task that copies it.

The game builds its line list by walking beats to the chart's "last tick" (lines 199 to 253). Task T2 builds the same list from `MeasureIndex::walk`, and drops the lines the game stores as beats in a meter with 1 on top (lines 221 to 231).

The generator starts at index 1 and steps by 4, and a miss makes it try the next line (lines 40, 47 and 55). Task T3 copies that loop. The step after a fill comes from `Rules::fill_cooldown_measures`.

The game turns the line's second back into a tick and asks for the nearest chord, searching on from the last chord it used (line 44, and lines 144 to 193). Task T3 calls the one merged owner from T1 for that.

The game rejects the chord when it is more than 0.25 s from the line, comparing 32-bit floats (lines 51 to 57). Task T3 adds that test with the same number types T0 reads.

The fill starts at the midpoint second between line i-1 and line i, turned into a tick (lines 42 and 63). Task T3 stores the chord tick minus that tick in `SongTimestamp::activation_length`, which `fill_start_tick` reads.

The fill's length for the deadline runs from the start tick to the activation note's tick plus a 64th note of `RoundToInt(12 * resolution / 192)` ticks (lines 39 and 67). Task T4 moves Hydra's 64th note from before the fill's start to after the chord.
