This plan builds the two things the direct-start plan (`docs/superpowers/plans/2026-10-31-ch-mcp-direct-start.md`) needs before its kit steps and its end-of-song step can run. The user answered that plan's questions 7 and 8 on 2026-10-31 with "Take all five": the kit stays on the System Player and gets the drum map loaded onto it, and the game's network is blocked before any step that finishes a song. ## The plain version

**The map.** The game's command-line loader hands the song's player Rewired's System Player, and the drums input reads that player at every button read. So the kit has to sit on System. LS-D1 run 1 put it there, and the game gave it no bindings, because the kit's setup asks Rewired for the player's *default* maps for custom controllers, and System's default list is empty. The fix is one call swapped for another in the kit agent: instead of `LoadDefaultMaps(Custom)`, setup calls `LoadMap(Custom, <kit id>, <category>, <layout>, true)`, which loads one named map from the ones the game defines, onto whatever player holds the kit. The category and layout numbers (1 "Gameplay", 2 "Drums") live in `tools/ch_mcp/kit_tools.py` with the kit's other numbers and ride in the setup message, because the agent holds none of the kit's numbers. The existing bindings check then proves the map arrived: it already refuses unless every one of the ten kit elements maps to exactly the action `KIT_BINDINGS` names, and this plan adds a second check that the map it reads back is the one at that category and layout and is enabled. That is task M1, and LS-D1a is the run that first tries it.

**The block.** Nobody knows whether a finished song posts a score online with nobody logged in (page 07, IN-73, Unknown). The game does hold an online gateway, and its own log shows "Unauthorized" four times, so it talks to something at some point. The block is built inside the game process, with the same kind of Frida hook the launch agent already places: a second small agent, `netblock.ts`, attaches to the paused game right after the launch agent and before the game is let go, and hooks the Winsock calls that open a connection or send a packet (`connect`, `WSAConnect`, `sendto`, `WSASendTo`, the `WSAIoctl` request that hands out `ConnectEx`) and the three name lookups (`getaddrinfo`, `GetAddrInfoW`, `GetAddrInfoExW`). When the game calls one of them with an address that is not the machine itself, the hook swaps the socket argument for an invalid socket, so Winsock itself fails the call; the hook forges no return value and calls nothing. It counts every call it blocked, with the address and port the game asked for. That count is one half of the proof. The other half is outside the process and independent of the hook: a watch in Python polls Windows' own TCP table (`netstat -ano`) for the game's process id from the launch to `ch_stop` and lists any connection to an outside address. A new tool, `ch_net`, prints both, and `ch_status` and `ch_stop` print the one-line summary. The hook is a new kind of change to the game, so it is question 1 for the user; no task starts before the answer. Windows Firewall, system settings and security settings are never touched by any task, whatever the answer; the firewall route is described as the user's by-hand alternative in question 1 and the tools would only check it.

Why not a firewall rule, a hosts-file line or a packet capture: each is a system setting or needs an administrator, and the brief forbids every agent from touching those. Why not block at `socket()`: the game opens sockets at start-up that may be local (Unity's own services), and refusing every socket could break the game for no gain. Why the TCP table and not a packet capture: `pktmon` needs an administrator; `netstat` does not.

## What the code settles for the map (task M1)

Where the numbers live. `kit.ts` says in its header that it "holds none of the kit's numbers" and that `kit_tools.py` owns them and checks the map read back (rows P2, P3). So `KIT_MAP_CATEGORY_ID = 1` and `KIT_MAP_LAYOUT_ID = 2` go into `kit_tools.py` beside `KIT_DEFINITION_ID`, with a comment naming IN-76 as the fact's home, and `setup_message` carries them as `category_id` and `layout_id`. The agent reads both with its `needInteger`, which refuses a number below 1 (row P10); 1 and 2 pass, and a layout 0 would not, which is fine because nothing here loads layout 0.

Which overload. The dump has four `LoadMap` overloads with a `ControllerType` (row P6). The one to call is the five-argument form with `startEnabled` at `dump.cs` line 303889, RVA 0x1F508C0, invoked with `(ControllerType.Custom, kitId, categoryId, layoutId, true)`, through `.method("LoadMap", 5).overload("Rewired.ControllerType", "System.Int32", "System.Int32", "System.Int32", "System.Boolean")`, because the string-named five-argument form (line 303892) has the same count. `true` matters: `binding_problems` counts only enabled maps (row P3), so a map that loaded disabled would be refused as "no map".

Replace, not follow. The new call replaces `LoadDefaultMaps`; setup no longer calls it on any player. The reason is in the check: `binding_problems` wants exactly one action per element across every enabled map, so the cleanest proof is one map. On System, `LoadDefaultMaps` loads nothing anyway (row P5). On Player1 it would load the Gameplay category's layouts 0 and 2 (row P5), and whether layout 0 binds the kit's elements to other actions is not known; with `LoadMap` alone that never matters. The dump shows `LoadDefaultMaps` and `LoadMap` as separate methods, and Rewired's own documentation says `LoadMap` loads "from the maps defined in the Rewired Editor", replacing a map with the same category and layout; that it finds the drum map on System, whose default list is empty, is the one fact only the run settles (row P7).

How the check proves it. Today `binding_problems` proves the ten bindings. M1 adds `map_problems(maps)` in `kit_tools.py`, run before `binding_problems`: it refuses unless the reply's maps hold exactly one enabled map whose `category_id` and `layout_id` are the two constants, and names what it found instead (LS-D1 run 1's reply, `"maps": []`, is the first test case). So a pass of `ch_kit_setup(player="System")` means: the map at category 1, layout 2 is on System, enabled, with the ten bindings.

The allowed-calls test. `ALLOWED_CALLS` in `kit.ts` must equal the names in `kit_methods.json`, and `CALL_SITES` pins `kit.ts` at 44 `.invoke(` sites (row P4). `LoadDefaultMaps` leaves both lists and `LoadMap` joins them with dump line 303889, so the count stays 44: one `.invoke(` removed, one added. If the executor's count differs, it changes `CALL_SITES` and says so in its report.

## What the code settles for the block (tasks N1 and N2)

When it can be placed. The launch already runs in this order: start paused, attach `launch.ts` by process id, arm, resume, poll (row P11). At the arm, with the game still paused, 39 modules are loaded and `WS2_32.dll` is one of them (row P13), so its exports can be hooked before the game has run one instruction of its own. The block therefore goes between the launch agent's arm reply and the resume: attach `netblock.ts` by the same `Env.attach_agent` seam (row P12), send it `arm` with the contents of `tools/ch_mcp/net_block.json`, and resume only after it replies `armed`. The two caps are the launch's own, `LAUNCH_ATTACH_CAP_S` and `LAUNCH_ARM_CAP_S`, because the waits are the same kind; no new number is needed.

What the hook does. For each call named in the data file, `Interceptor.attach` on the export's address, found with `Process.getModuleByName(module).getExportByName(name)` (row P19). In `onEnter` the agent reads the socket address the game passed (family, port, and the IPv4 or IPv6 bytes) where the call has one, asks `decide` in `netblock_core.ts` whether that address is outside, and when it is, sets the socket argument to an invalid socket (`-1`), so Winsock fails the call with its own error (`WSAENOTSOCK`) (row P18). For the three name lookups, it sets the name and service arguments to null, so the lookup fails on its own too. For `WSAIoctl` it blocks only the request code the data file names, `SIO_GET_EXTENSION_FUNCTION_POINTER`, which is how a program gets `ConnectEx`; every other `WSAIoctl` passes. Loopback addresses (`127.0.0.0/8`, `::1`) pass, and `decide` blocks any family it cannot read (question 2). No `NativeFunction`, no forged return value, no address literal in the agent: the module name, every export name, every argument position and the one request code come in the arm message from `net_block.json`, the way `launch_patch.json` feeds `launch.ts`.

What it records. `status` replies `{state, blocked, allowed, by_call: {name: count}, first: [{call, dest, ms}]}`, with `first` capped at the data file's `list_max`. An export that cannot be found makes the arm reply `refused` with the name, and `launch_human` then kills the game, as it does for a refused patch: a block with a hole is no block.

The outside leg. `tools/ch_mcp/net_watch.py` holds `NetWatch`, shaped like `foreground.ForegroundWatch` (row P23): a thread that runs `netstat -ano` every `NET_POLL_S` (2 s) through a `run` seam, keeps every `TCP` row whose process id is the game's and whose remote address is not loopback and not the unbound `0.0.0.0:0` or `[::]:0`, counts its polls, and lists the first `NET_LIST_MAX` (20) distinct remote endpoints with the poll time. Its `line()` reads "network watch: N polls, no outside connection seen" or "network watch: N polls, M outside connections seen (first: 1.2.3.4:443 at 3.1 s)". It starts after every `ch_start` launch, bot or human, because it only reads, and stops in `ch_stop`.

Why both legs. The hook's count shows the game *tried* and was stopped, with the address; the TCP table shows nothing *got through*, by a source the hook does not touch. A run where the hook counts 0 and the table is empty means the game never tried in that run; that is also an answer, and page 07 records it as a live-run block. A run where the table shows an outside connection with the block on is a fail, and names the hole (the address, and which hooked call did not see it).

Human launches only. The bot launch is a plain `Popen` that is never paused, so a hook could land only seconds after the game has started talking. Extending the block to bot launches means making the bot launch a paused one, which is question 3.

## Questions for the user

1. **Is the in-process network hook allowed?** The hook is a new kind of change: it makes the game's own Winsock calls fail, in memory, in the game process only, for the run, through `Interceptor.attach` with every hooked name read from `tools/ch_mcp/net_block.json`. What is allowed today is method calls and field writes (ruling 2), record-only trace hooks, and the one-byte patch (ruling 3); none names a hook that changes a Windows call. Recommended: yes. At this end, a human launch places the eight hooks before the game runs, a call such as `connect` to `gateway-service.clonehero.net:443` fails inside the game with `WSAENOTSOCK` and is counted with its address, and a call to `127.0.0.1` passes; nothing outside the game process changes. The other side: no hook, and then the only sound block is a Windows Firewall outbound rule that the user makes by hand before a run and removes after, which no agent may touch: in an administrator PowerShell, `New-NetFirewallRule -DisplayName "Hydra: Clone Hero offline" -Direction Outbound -Program "C:\Clone Hero\1.1 june\Clone Hero\Clone Hero.exe" -Action Block -Profile Any`, and afterwards `Remove-NetFirewallRule -DisplayName "Hydra: Clone Hero offline"`. The tools would then only check it: `ch_start(human=True)` refuses unless `Get-NetFirewallRule -DisplayName "Hydra: Clone Hero offline"` reports the rule `Enabled` with `Action Block` and its application filter names that exe, and `ch_net` keeps the TCP-table watch as the proof. At that end a run with the rule in place blocks every outbound packet of the game, loopback included, and a run with the rule forgotten is refused before the game starts. If the answer is the firewall, tasks N1 and the hook half of N2 are not built and N2 builds the check instead.
2. **Does loopback pass?** The rule `decide` sets is which addresses count as outside. Recommended: `127.0.0.0/8` and `::1` pass, everything else is blocked, and an address whose family the hook cannot read is blocked. At this end a connect to `127.0.0.1:9999` passes and is counted as allowed, a connect to `192.168.1.10:80` on the user's own network is blocked, and a connect with a family of 0 (which fritm reports Windows sometimes shows) is blocked and listed. The other side: block loopback too, so the game can reach nothing at all. At that end a local service the game or Frida itself may use over a loopback socket fails as well; whether Frida's own channel into the game uses one is not known, so a run could cut its own link, which is why the recommendation leaves loopback open.
3. **Human launches only, or every launch?** Recommended: human launches now. At this end `ch_start(song, human=True)` blocks, and `ch_start(song)` (the bot) runs as it has for weeks, with the TCP-table watch reporting what it sees. The other side: every launch blocks, which makes the bot launch a paused launch with an agent attached before the resume; at that end a bot run that finishes a song is covered too, but a route that has run many times changes, and that is a separate build after LS-N1 shows the block works.

## Prior art

Rewired's API reference for `Player.ControllerHelper.MapHelper.LoadMap` (guavaman.com, the Rewired documentation) says the call "Loads a controller map from the maps defined in the Rewired Editor", replaces a map with the same category and layout, and that `startEnabled` sets whether the map starts enabled unless a map rule overrides it; that is why M1 loads by id rather than asking for the player's defaults. For keeping one process off the network from inside it, fritm (pypi.org, a Frida-based tool) hooks `connect` to redirect a program's TCP traffic, and notes that on Windows `sa_family` sometimes reads 0, which is why `decide` blocks an unreadable family; HookMe (Telefónica's blog) hooks the `WS2_32.dll` send and receive calls and suggests the same pattern as a per-application firewall. Neither covers `WSAConnect`, `ConnectEx` or the name lookups, which is why this plan hooks eight exports and keeps an outside watch. For Frida 17, community guides (skills.cat and the frida-17-skill repository) record that the static `Module.findExportByName` and `Module.getExportByName` were removed in 17.0.0 and that `Process.getModuleByName(...).getExportByName(...)` is the replacement; task N1 confirms that against the installed type definitions rather than trusting the guides. The Windows alternative that needs no code, an outbound rule with `New-NetFirewallRule -Program`, is a system setting and stays the user's by-hand route in question 1.
