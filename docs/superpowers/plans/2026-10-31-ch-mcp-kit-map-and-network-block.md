## The plain version

**The map.** The game's command-line loader hands the song's player Rewired's System Player, and the drums input reads that player at every button read. So the kit has to sit on System. LS-D1 run 1 put it there, and the game gave it no bindings, because the kit's setup asks Rewired for the player's *default* maps for custom controllers, and System's default list is empty. The fix is one call swapped for another in the kit agent: instead of `LoadDefaultMaps(Custom)`, setup calls `LoadMap(Custom, <kit id>, <category>, <layout>, true)`, which loads one named map from the ones the game defines, onto whatever player holds the kit. The category and layout numbers (1 "Gameplay", 2 "Drums") live in `tools/ch_mcp/kit_tools.py` with the kit's other numbers and ride in the setup message, because the agent holds none of the kit's numbers. The existing bindings check then proves the map arrived: it already refuses unless every one of the ten kit elements maps to exactly the action `KIT_BINDINGS` names, and this plan adds a second check that the map it reads back is the one at that category and layout and is enabled. That is task M1, and LS-D1a is the run that first tries it.

**The block.** Nobody knows whether a finished song posts a score online with nobody logged in (page 07, IN-73, Unknown). The game does hold an online gateway, and its own log shows "Unauthorized" four times, right after the song loads (row P16), so it talks to something at some point. "Unauthorized" is a server's answer, so at least those calls reached a server. The block is built inside the game process, with the same kind of Frida hook the launch agent already places: a second small agent, `netblock.ts`, attaches to the paused game right after the launch agent and before the game is let go, and hooks the Winsock calls that open a connection or send a packet (`connect`, `WSAConnect`, `sendto`, `WSASendTo`, the `WSAIoctl` request that hands out `ConnectEx`) and the three name lookups (`getaddrinfo`, `GetAddrInfoW`, `GetAddrInfoExW`). When the game calls one of them with an address that is not the machine itself, the hook swaps the socket argument for an invalid socket, so Winsock itself fails the call; the hook forges no return value and calls nothing. It counts every call it blocked, with the address and port the game asked for. That count is one half of the proof. The other half is outside the process and independent of the hook: a watch in Python polls Windows' own TCP table (`netstat -ano`) for the game's process id from the launch to `ch_stop` and lists any connection to an outside address that was open at a poll. It is a sample, not a recording: a connection that opens and closes between two polls leaves no row with the game's process id (row P34), and it sees TCP only, not UDP. A new tool, `ch_net`, prints both, and `ch_status` and `ch_stop` print the one-line summary. The third, cheapest sign is the game's own log: the "Unauthorized" lines it wrote after the song loaded (row P16) say a server answered; a run with the block on should not show a server's answer to those calls, and the report quotes the log lines either way.

What the eight hooks do not cover, said plainly. The game loads `WINHTTP.dll` and `DNSAPI.dll` at start-up (row P13), so its web calls may go through Windows' own HTTP stack rather than through plain sockets; that stack opens its connections through `WS2_32.dll` too, which is the assumption row P21 carries and LS-N0 and LS-N1 test. Four other `WS2_32.dll` exports can start a connection or send a packet and are not hooked: `WSAConnectByNameW`, `WSAConnectByNameA`, `WSAConnectByList` and `WSASendMsg`. If LS-N1 shows an outside connection with the block on, that is how a hole shows, and the fix is a data-file line, not a new agent. The hook is a new kind of change to the game, so it is question 1 for the user; no task starts before the answer. Windows Firewall, system settings and security settings are never touched by any task, whatever the answer; the firewall route is described as the user's by-hand alternative in question 1 and the tools would only check it.

Why not a firewall rule, a hosts-file line or a packet capture: each is a system setting or needs an administrator, and the brief forbids every agent from touching those. Why not block at `socket()`: the game may open local sockets at start-up (Unity's own services; not checked), and refusing every socket could break the game for no gain. Why the TCP table and not a packet capture: `pktmon` needs an administrator; `netstat` does not.

Which overload. The dump has four `LoadMap` overloads with a `ControllerType` (row P6). The one to call is the five-argument form with `startEnabled` at `dump.cs` line 303889, RVA 0x1F508C0, invoked with `(ControllerType.Custom, kitId, categoryId, layoutId, true)`, through `.method("LoadMap", 5).overload("Rewired.ControllerType", "System.Int32", "System.Int32", "System.Int32", "System.Boolean")`, because the string-named five-argument form (line 303892) has the same count. `true` matters: `binding_problems` counts only enabled maps (row P3), so a map that loaded disabled would be refused as "no map".

The dump shows `LoadDefaultMaps` and `LoadMap` as separate methods, and Rewired's own documentation says `LoadMap` loads "from the maps defined in the Rewired Editor", replacing a map with the same category and layout; that it finds the drum map on System, whose default list is empty, is the one fact only the run settles (row P7).

## What the code settles for the block (tasks N1 to N4)

When it can be placed. The launch already runs in this order: start paused, attach `launch.ts` by process id, arm, resume, poll (row P11). At the arm, with the game still paused, 39 modules are loaded and `WS2_32.dll` is one of them (row P13), so its exports can be hooked before the game has run one instruction of its own. The block therefore goes between the launch agent's arm reply and the resume: attach `netblock.ts` by the same `Env.attach_agent` seam (row P12), send it `arm` with the contents of `tools/ch_mcp/net_block.json`, and resume only after it replies `armed`. The two caps are the launch's own, `LAUNCH_ATTACH_CAP_S` and `LAUNCH_ARM_CAP_S`, because the waits are the same kind; no new number is needed.

What the hook does. For each call named in the data file, `Interceptor.attach` on the export's address, found with `Process.getModuleByName(module).getExportByName(name)` (row P19). In `onEnter` the agent reads the socket address the game passed (family, port, and the IPv4 or IPv6 bytes) where the call has one, asks `decide` in `netblock_core.ts` whether that address is outside, and when it is, sets the socket argument to an invalid socket (`-1`), so Winsock fails the call with its own error (`WSAENOTSOCK`) (row P18). For the three name lookups, it sets the name and service arguments to null, so the lookup fails on its own too. For `WSAIoctl` it blocks only the request code the data file names, `SIO_GET_EXTENSION_FUNCTION_POINTER` (row P33), which is how a program gets `ConnectEx`; every other `WSAIoctl` passes. That request carries no address, so the block is whole: it also stops loopback users of `ConnectEx` and of the other extension functions (`AcceptEx` among them), which is part of question 2. Loopback addresses (`127.0.0.0/8`, `::1`) pass, and `decide` blocks any family it cannot read (question 2). No `NativeFunction`, no forged return value, no address literal in the agent: the module name, every export name, every argument position and the one request code come in the arm message from `net_block.json`, the way `launch_patch.json` feeds `launch.ts`.

What it records. `status` replies `{state, blocked, allowed, by_call: {name: count}, first: [{call, dest, ms}]}`, with `first` capped at the data file's `list_max`. An export that cannot be found makes the arm reply `refused` with the name, and `launch_human` then kills the game, as it does for a refused patch: a block with a hole is no block.

The outside leg. `tools/ch_mcp/net_watch.py` holds `NetWatch`, shaped like `foreground.ForegroundWatch` (row P23): a thread that runs `netstat -ano` every `NET_POLL_S` through a `run` seam (the value is question 4's), keeps every `TCP` row whose process id is the game's and whose remote address is not loopback and not the unbound `0.0.0.0:0` or `[::]:0`, counts its polls, and lists the first `NET_LIST_MAX` distinct remote endpoints with the poll time (also question 4's). Its `line()` reads "network watch: N polls, no outside connection seen" or "network watch: N polls, M outside connections seen (first: 1.2.3.4:443 at 3.1 s)". It starts after every `ch_start` launch, bot or human, because it only reads, and stops in `ch_stop`.

Why both legs. The hook's count shows the game *tried* and was stopped, with the address; the TCP table shows whether an outside TCP connection was *open at a poll*, by a source the hook does not touch. It cannot show that nothing got through: a short connection between two polls is missed (row P34), and UDP is not read. So a clean table is weaker than a count of 1 or more, and the reports say "no outside connection seen at N polls", never "nothing got through". A run where the hook counts 0 and the table is empty means the game was not seen to try in that run, which is also an answer, and page 07 records it as a live-run block with the poll count beside it. A run where the table shows an outside connection with the block on is a fail, and names the hole (the address, and which hooked call did not see it).

Human launches only. The bot launch is a plain `Popen` that is never paused, so a hook could land only seconds after the game has started talking. Extending the block to bot launches means making the bot launch a paused one, which is question 3.

## Questions for the user

1. **Is the in-process network hook allowed?** The hook is a new kind of change: it makes the game's own Winsock calls fail, in memory, in the game process only, for the run, through `Interceptor.attach` with every hooked name read from `tools/ch_mcp/net_block.json`. What is allowed today is method calls and field writes (ruling 2), record-only trace hooks, and the one-byte patch (ruling 3); none names a hook that changes a Windows call. Recommended: yes. At this end, a human launch places the eight hooks before the game runs, a call such as `connect` to `gateway-service.clonehero.net:443` fails inside the game with `WSAENOTSOCK` and is counted with its address, and a call to `127.0.0.1` passes; nothing outside the game process changes. The other side: no hook, and then the only sound block is a Windows Firewall outbound rule that the user makes by hand before a run and removes after, which no agent may touch: in an administrator PowerShell, `New-NetFirewallRule -DisplayName "Hydra: Clone Hero offline" -Direction Outbound -Program "C:\Clone Hero\1.1 june\Clone Hero\Clone Hero.exe" -Action Block -Profile Any`, and afterwards `Remove-NetFirewallRule -DisplayName "Hydra: Clone Hero offline"`. The tools would then only check it: `ch_start(human=True)` refuses unless `Get-NetFirewallRule -DisplayName "Hydra: Clone Hero offline"` reports the rule `Enabled` with `Action Block` and its application filter names that exe, and `ch_net` keeps the TCP-table watch as the proof. At that end a run with the rule in place blocks every outbound packet of the game, loopback included, and a run with the rule forgotten is refused before the game starts. If the answer is the firewall, tasks N1 and N2 are not built, and this plan is amended and reviewed again before the firewall check is built: that check reads the firewall (`Get-NetFirewallRule`), whether that read needs an administrator is not known, and the scan in task N4 would have to allow that one read-only name.
2. **Does loopback pass?** The rule `decide` sets is which addresses count as outside. Recommended: `127.0.0.0/8` and `::1` pass, everything else is blocked, and an address whose family the hook cannot read is blocked. At this end a connect to `127.0.0.1:9999` passes and is counted as allowed, a connect to `192.168.1.10:80` on the user's own network is blocked, and a connect with a family of 0 (which fritm reports Windows sometimes shows) is blocked and listed. Two parts of the block are not by address, and this answer does not change them: a name lookup is blocked whatever it names, so `getaddrinfo("localhost")` fails while a connect to the literal `127.0.0.1` passes; and every request for an extension function pointer (the way `ConnectEx` and `AcceptEx` are obtained) is blocked on any socket, so a game that listens on loopback through `AcceptEx` would lose that listener. Neither is known to be in use; LS-N1's moving clock and `ch_net` are what would show it. The other side: block loopback too, so the game can reach nothing at all. At that end a local service the game or Frida itself may use over a loopback socket fails as well; whether Frida's own channel into the game uses one is not known, so a run could cut its own link, which is why the recommendation leaves loopback open.
3. **Human launches only, or every launch?** Recommended: human launches now. At this end `ch_start(song, human=True)` blocks, and `ch_start(song)` (the bot) runs as it has for weeks, with the TCP-table watch reporting what it sees. The other side: every launch blocks, which makes the bot launch a paused launch with an agent attached before the resume; at that end a bot run that finishes a song is covered too, but a route that has run many times changes, and that is a separate build after LS-N1 shows the block works.
4. **How often the outside watch looks, and how long its list is.** No ruling and no measurement sets these. Recommended: poll `netstat -ano` every `NET_POLL_S = 0.5` seconds and list the first `NET_LIST_MAX = 20` distinct endpoints. At this end a connection open for one second is seen at least once; the cost is one `netstat` process every half second for the run, and how long one `netstat` takes here is not measured (LS-N0 is the first run that shows it, as its poll count over its minutes). The game's calls after the song load are probably short, so a slow poll is the way the table leg misses them. The other side: poll every 2 seconds, which costs a quarter of the processes and misses any connection shorter than that. The list length only caps what the report prints; 20 is a size for a readable line.

### N2: the launch step (earlyStart: yes, after question 1 is answered yes)

Owns `tools/ch_mcp/bot_run.py` and `tools/ch_mcp/tests/test_bot_run.py`.

`launch_human` reads `net_block.json` (`Env.net_block_path`, and `Env.net_agent_path` for `netblock.js`, beside the launch agent's two fields); when `enabled` is true, after the launch agent's arm reply and before the resume, it attaches the net agent on its own thread with `LAUNCH_ATTACH_CAP_S`, the way the launch agent's attach runs (Frida's attach to a paused process has no cap of its own), through `env.attach_agent(game.pid, env.net_agent_path, <log>, said.append)`. It then sends `arm` with the file's contents under `LAUNCH_ARM_CAP_S`. On `refused`, an error or a cap it kills the game, detaches both agents and raises `LaunchFailed` naming the export or the cap. `HumanLaunch` keeps the net agent so `ch_stop` detaches it. `request_net_status(launch, cap)` returns a list of lines: "network block: N calls blocked, M allowed (connect 2, getaddrinfo 1; first: 1.2.3.4:443 via connect at 3.1 s)", or "network block: off (net_block.json enabled false)", or "network block: the net agent did not answer (<reason>)". ## Prior art

Rewired's API reference for `Player.ControllerHelper.MapHelper.LoadMap` (guavaman.com, the Rewired documentation) says the call "Loads a controller map from the maps defined in the Rewired Editor", replaces a map with the same category and layout, and that `startEnabled` sets whether the map starts enabled unless a map rule overrides it; that is why M1 loads by id rather than asking for the player's defaults. For keeping one process off the network from inside it, fritm (pypi.org, a Frida-based tool) hooks `connect` to redirect a program's TCP traffic, and notes that on Windows `sa_family` sometimes reads 0, which is why `decide` blocks an unreadable family; HookMe (Telefónica's blog) hooks the `WS2_32.dll` send and receive calls and suggests the same pattern as a per-application firewall. Neither covers `WSAConnect`, `ConnectEx` or the name lookups, which is why this plan hooks eight exports and keeps an outside watch. For Frida 17, community guides (skills.cat and the frida-17-skill repository) record that the static `Module.findExportByName` and `Module.getExportByName` were removed in 17.0.0 and that `Process.getModuleByName(...).getExportByName(...)` is the replacement; the installed type definitions agree (row P19), and only a run settles the runtime (row P35). The Windows alternative that needs no code, an outbound rule with `New-NetFirewallRule -Program`, is a system setting and stays the user's by-hand route in question 1.
