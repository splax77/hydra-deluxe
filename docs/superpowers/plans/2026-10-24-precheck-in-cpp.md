# The derive-once precheck moves to C++

Plan written 2026-10-24 (task PRECHECK-SCAN, session 1666228b). Nothing here is built yet; every task waits for the user's yes (CLAUDE.md rule 3).

## The one-paragraph version

`tools/derive_once_precheck.ps1` is a 1,441-line PowerShell script that does five checks on a git range before a derive-once review. Its self-test takes 5 min 57 s on CI (run 40136906822, the "Tool tests" job), and 206 of the 236 s of its whole-tree run is PowerShell re-doing, line by line, what the C++ single-owner scan does in 3.4 s. The user's ruling for this change, in their words: "just move everything to c++". So the whole precheck becomes a small exe, `hydra_precheck`, built from the same CMake tree as the tests. Its row matching is the scan's own code, pulled out of `tests/single_owner/scan.cpp` into an engine file both the scan and the precheck link. Checks 1 to 5, the kind letters with their notes, the range-size lines and the `-Range`, `-WholeTree`, `-RulesAt` and `-Disable` options are ported as they are. The PowerShell script and its self-test are deleted once the exe prints the same items on the same four inputs. The self-test's proofs move into one doctest file that runs inside `hydra_tests`.

## The design, decided

### Where the C++ precheck lives

A new exe, `hydra_precheck`, from new sources under `tools/precheck/` (`main.cpp`, `git_text.cpp/.h`, `range.cpp/.h`, `checks.h`, one `check_N.cpp` per check, `items.cpp/.h`). `tools/replay.cpp` and `tools/bench.cpp` already live there, so a developer exe under `tools/` is the house style. It is a plain exe with its own `main`, not a `hydra_tests` mode: doctest's default `main` (tests/test_main.cpp uses `DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN`) cannot take a range argument, and a test runner that also acts as a tool would make every reviewer start the whole test binary. `hydra_tests` gets `add_dependencies(hydra_tests hydra_precheck)` and an `HYDRA_PRECHECK_EXE` define, the way it already depends on `hydra_batch` and `hydra_fillcompare` for tests/test_cli.cpp, so building `hydra_tests` builds the precheck and the self-test can run it.

### One owner for the row matching

`tests/single_owner/scan.cpp` today holds both the engine (the loader, `compile_rule`, `flags_line`, `in_scope`, `walk_language`, `scan_file`, `listed_lines`) and the doctest cases that use it. Task 0 splits it: the engine goes to `tests/single_owner/engine.h` and `engine.cpp` with no doctest in them; `scan.cpp` keeps the cases. `listed.h` loses its doctest include; `check_scan`, which uses `INFO` and `CHECK`, moves to the test side. `hydra_tests` compiles `engine.cpp` beside `scan.cpp`; `hydra_precheck` compiles `engine.cpp` alone. After that, no file but `engine.cpp` decides whether a line answers a row's question. The precheck keeps its own kind letters (A/B/C/E from the file and the row's owner) and its own "is this a test file" rule, because those are the precheck's questions, not the scan's.

Three engine functions change shape so the precheck can feed them git content instead of disk files:

- `scan_file` already reads an `std::istream` and a repo-relative path, so a file's text from `git cat-file` goes straight in. It gains a hit sink: for every flagged line it reports the line number, the trimmed text, the rule, and the `Take` result (`taken`, `used_up`, `unlisted`) plus which listed entry it took. The scan's test case turns those into today's problem strings, pinned by "the row scan's messages, pinned on a made-up file", so the messages cannot drift.
- The rules loader gets a text entry point: `parse_rules_file(name, json_text)` and `parse_baseline(json_text)`, which the disk loader calls after reading each file. Which files are rules files becomes a pure function over relative paths, `select_rule_files(paths) -> sorted names`, used by both the disk lister and the precheck's `git ls-tree` list. That keeps `rule_files`'s rule (a `.json` in the folder or one folder down, name order) in one place.
- Nothing else in the engine reads `sourcetree::root()`; the two scan cases pass it in.

### How the precheck reads git

The exe runs `git` itself, from `tools/precheck/git_text.cpp`: `rev-parse`, `merge-base`, `diff -U0` for the added lines, `ls-tree -r --name-only` for the file lists, `diff --numstat` for the size, and one long-lived `git cat-file --batch` process that it feeds `<rev>:<path>` lines and reads the objects back. One process for every file instead of one `git show` per file is the brief's item 6 and is the main startup win. The launcher (create a process with piped stdin and stdout, wait, read) is new code; tests/test_cli.cpp's `run_exe` only captures output and kills on a cap, and src/app/report_files.cpp only launches. The precheck's launcher is a tool's, so it lives with the tool; the reviewer sees all three and the clone scan keeps them from sharing text.

The precheck never checks out, archives or writes anything. A fixture repo in a temp folder works the same way as the real one, because everything comes through `git -C <repo>`.

### The hits and their notes

The precheck scans every C++ and Python file the range touches (only the touched files, since listed entries are taken per file and question, so other files cannot change a file's result), at the tip, with the rules and baseline from `-RulesAt` or the tip. For `-WholeTree` it scans every file `walk_language` reads. From each hit it keeps only the added lines, then adds the note the script adds today: "this range lists it as an owner line: ..." when the owner line entry is new in this range, "known copy: <fix>" (plus "; this range added that entry") for a taken baseline entry, and "a second copy of a listed line; each entry covers one line" for `used_up`. An owner line the range did not write passes, as today.

"Did this range add that JSON element" is answered without the script's brace-matching span finder: the precheck parses the rules file at the base and at the tip and calls a row, owner line or known copy added when its key (question; question + file + line_text; question + file + line_text) is absent at the base. With `-RulesAt` naming another commit nothing counts as added, as today. That removes `Get-JsonObjects`, `Get-JsonItems`, `Test-ElementAdded` and the brace matcher's only use outside check 1 and 5.

The `.NET regex versus std::regex` warning lines go. There is one regex engine now, and the scan's own case "single-owner rules match their own examples" already checks every row's examples.

### What is hard about the port, said up front

The script uses .NET regex features std::regex (ECMAScript grammar) does not have: lookbehind `(?<!...)` in the number patterns and the check 3 "named value" test, named groups `(?<name>...)`, inline `(?m)` and `(?i)`, a `RightToLeft` match and a backreference for raw-string delimiters. The repo has no other regex library (third_party holds doctest, imgui, json, mimalloc, miniaudio, miniz, ogg, opus, rapidcheck, sqlite, stb). The port therefore rewrites those as small hand-written scanners: the raw-string and comment handling is already codelex's (tests/code_lexer.h, which splits C++, Python, PowerShell and YAML into Code, Comment and String pieces); a lookbehind becomes "match the wider pattern, then test the character before the match"; `(?i)` becomes `std::regex::icase`. std::regex is also slow, so the structural passes (the brace matcher, the function-definition finder, the tokenizer, the record-field reader) are written as loops over the lexed text, not as multiline regexes over whole files. The parity proof in task 8 is what tells us the rewrite matches.

### Running it, now that it needs a build

Build with `.\build_cpp.ps1 -Target hydra_precheck` (a cold build configures CMake and builds `hydra_core` plus the exe; I estimate one to three minutes, against three to six for `hydra_tests`). Run with `build-cpp\Release\hydra_precheck.exe --repo <path> --range main...<key>`, plus `--whole-tree`, `--rules-at <commit>` and `--disable 1,3` as today's switches. The exe reads revisions through git, so the main checkout's exe works on any worktree through `--repo`; a reviewer rebuilds only when the range itself changes `tests/single_owner/` or `tools/precheck/`. The docs say exactly that (task 8). If the exe is missing the shell fails to start it, which is loud; the precheck never falls back to a weaker scan.

### CI

The precheck self-test leaves the "Tool tests" job (which builds no C++) and runs where `hydra_tests` runs, as the doctest file tests/test_precheck.cpp inside the "Build and test" job. That job's checkout gets `fetch-depth: 0` so the two real ranges are in the clone (checkout with full history took 11 s in the tool-tests job against 10 s shallow, so the cost is seconds). "Tool tests" drops from 6 min 42 s to about 45 s. "Build and test" gains the `hydra_precheck` build (small, it shares every library `hydra_tests` already builds) and the self-test's run time, which I estimate at 30 to 60 s. The run's wall time is set by "Build and test", so the net change to the wall clock is roughly plus one minute; the total machine time falls by about five minutes. These are estimates until the first run.

### Expected times after the change (estimates, with how I got them)

The C++ row scan over the whole tree is measured at 3.4 s. Checks 1 and 5 read every test file and every src/ file at the tip through one `cat-file --batch` stream (about 1,000 files, roughly 30 MB; git serves that in a second or two) and lex them with codelex, which the scan already does for 125,000 lines inside its 3.4 s. So a whole-tree run should land between 5 and 15 s, against 236 s today. A range run does the same plus a diff and a dozen git calls: 2 to 5 s, against 41 s. The fixture self-test is ten exe runs on a tiny repo plus `git init` and four commits: 15 to 30 s, against 57 s. Each real range: 2 to 5 s. Whole self-test: under a minute, against 5 min 57 s on CI. The parity run in task 8 measures the real numbers and writes them into the task 8 commit message; if the whole-tree run is over 30 s, task 8 reports which check is slow instead of merging.

## Questions for the user (answered above)

1. **Regex differences at the edges.** std::regex has no lookbehind, so the number finder `(?<![\w.'])\d...` becomes "find the digits, then look at the character before". On the four parity inputs this should give the same items, but a line nobody has written yet could read differently (for example `a.5` or `x'5`, which today's lookbehind on `.` and `'` excludes). Is "same items on the fixture, both real ranges and the whole tree, every difference named in the commit" the bar you want, or do you want a wider corpus run (every merge commit on main since 2026-10-04, about 150 ranges, which I estimate at ten minutes once) before the delete?

2. **The mutation probe's lexer.** Today `tools/mutation_probe.ps1` has no comment stripper of its own; it loads the precheck's. Two options: (a) the four PowerShell definitions move into mutation_probe.ps1 and it becomes their owner (the plan's default; one PowerShell lexer and one C++ lexer stay, as today), or (b) `hydra_precheck` grows a `--code-mask <file>` mode that prints the file with comments and strings blanked, and mutation_probe calls it, leaving codelex as the only lexer in the repo.
