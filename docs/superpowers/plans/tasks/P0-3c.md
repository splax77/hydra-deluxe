# P0-3c: the watchdog's empty-fleet warning and the status monitor's interval

## The task in plain English

Two fleet tools need a small change each.

**The watchdog.** `agent_watchdog.ps1` runs in the background for one session, reads every subagent transcript, lists the stalled ones to `state\stalls_<session>.json`, and kills hung commands. It says nothing when the fleet is simply empty: a Workflow was launched, work is still open, and no agent has written anything for five minutes. That silence is how a dead launch goes unnoticed. Add a warning for that case, and make it reach the orchestrator the same way stalls do.

**The status monitor.** `status_batch_monitor.ps1` watches `state\status\*.md` and, every interval, prints one line per agent that wrote something new. The plan asks for a 10-minute interval that sends only changed lines. The script's default is already 600 seconds and it already says it prints nothing when nothing changed. Your job is to prove that, with a test, and to make sure every place that launches it or checks its command line (`workflow_monitor_reminder.ps1`, `monitor_batch_gate.ps1`) agrees on 600. If any of that is not true today, fix it.

Hooks fail loudly: a warning is a visible line, never an "ask", never a block on the user's prompt.

## What "open tasks" means

No hook file uses the word "ledger". The nearest records are `state\wf_launch_<session>.txt` (written when a Workflow launches in that session) and the per-agent `state\agent_<id>.json` files (first call, last status, call count). Define "open" as: the session's `wf_launch` file exists, the watchdog's stop file does not, and the session transcript's last line is not the orchestrator finishing its turn (read how the watchdog already decides a session is over, and reuse that). Say in the script's header which definition you chose and why. The warning fires once per quiet spell, not every pass: use the same seen-file idea `stall_inject.ps1` uses.
