## Part 2: `tests/test_docs_match_code.cpp`

Add the file and its line in the test list in `CMakeLists.txt` (beside `tests/test_single_owner.cpp`). Copy the walker and the `HYDRA_SOURCE_DIR` approach from `tests/test_single_owner.cpp`; don't invent a second way to find the repo root. One doctest case per rule, names starting "docs match code".

Docs it reads: every `docs/adr/*.md`, `CONTEXT.md`, `docs/UserGuide.md`, `docs/development.md`, `docs/cap-clamped-squeeze-frontend-anchor.md`.

1. **Code names exist.** Every backticked token that looks like code must occur in some file under `src/`, `tools/` or `tests/`. "Looks like code" means: `name(` or `name()`, `Type::name`, `kName` (k then a capital), or a snake_case name with an underscore. Strip a trailing `()` and argument list before searching; for `A::b` search for `b` and accept it if `A` also occurs. Skip file paths, ini keys shown with `=`, and anything inside a section whose heading contains "Superseded" or "Kept as history" (to the next heading of the same or higher level). Keep a short allow-list with one comment per entry saying why the name is gone on purpose (for example ADR 0011's `deact_tick_from_rows()` sentence). Settings keys in `hydra_rules.ini` such as `backend_leeway_ms` exist in `src/` as fields, so they pass naturally.
2. **The guide's rules sample equals the defaults.** The fenced `hydra_rules.ini` sample in `docs/UserGuide.md` (section "Scoring rules", around line 236) parses with the app's own rules-file reader (`src/app/rules_file.h`) and every value equals `core::Rules{}`'s default. Call the reader; don't parse ini text yourself.
3. **Marked defaults match the code.** A default in prose is marked with an HTML comment right after it: `10 ms<!-- default: Settings::mslimit_value -->`. The test takes the last number before the marker on the same line and compares it to the value from code. For a flag the marker follows the word "on" or "off": `starts on<!-- default: Settings::mslimit_enabled -->`. The table of known markers lives in the test and reads the real values. Use exactly these six marker names, because task p4-k6g writes the same names into the User Guide in parallel: `Settings::mslimit_value` (`Settings{}.mslimit_value`), `Settings::mslimit_enabled`, `Settings::backendlimit_value`, `Settings::backendlimit_enabled`, `Rules::backend_leeway_ms` (`core::Rules{}.backend_leeway_ms`) and `kSqueezeWindowMs` (`core::kSqueezeWindowMs`). A number may be written `3ms` or `3 ms`. An unknown marker name fails. Every table entry must appear at least once across the docs (your CONTEXT.md markers satisfy this on your branch).

A failure message names the doc path, the line number and the missing name or the mismatched number, so the fixer knows which sentence to edit.
