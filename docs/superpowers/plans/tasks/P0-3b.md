# P0-3b: the two hooks that answered "ask"

## The task in plain English

In step 2 the main session lost 13.5 minutes to two permission prompts that a hook raised. At 02:58 a `cat >>` heredoc append to the decisions file got "ask" from a Bash hook and waited 8 minutes. At 03:23 a plain `Read` of the plan got "ask" from a Read hook and waited 5.5 minutes. The rule since then is that hooks fail loudly: they deny with a reason or they allow (with a visible warning if they want attention). They never ask, because inside a subagent an ask can never be answered, and in the main session it silently stalls the whole fleet.

Your job: find which two hooks answered "ask" for those two inputs, prove it by feeding them the same inputs, change them so those inputs get allow or deny, and ship the proof as a test.

## The fix

For each culprit, the answer to those inputs becomes one of: allow, with the hook's message carried as `additionalContext` so the orchestrator still sees it (the delegation nag is advice, not a danger); or deny with a reason, if the command is one the fleet must never run. A plain file read and an append to a docs file are never dangerous, so expect "allow with the warning". Leave every other "ask" path alone (a `git reset --hard` from the main session may still ask; that is not this task). If your change forces a wider rule, stop and report instead of widening.
