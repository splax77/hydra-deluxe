## What changes

Owner: `Activation::needs_timing()` and `Path::needs_timing()` in `src/core/model.h`/`.cpp`, beside `hardest()` and `difficulty()`.

A squeeze needs timing when it is not free (`SPSqueeze::is_free`, D13). A required or optional early fill needs timing when its difficulty is 0.0 or more (zero slack counts, like the squeeze-out on the SP end; see open question 1). `Activation::hardest` picks only among timings that need hitting, so a free squeeze never names a badge; its tie rules and the optional-fill rule (D48 Q10) are untouched. `Activation::difficulty` keeps its meaning (hardest's ms when it is a squeeze or an E0 fill) and so becomes empty for an activation with nothing to time. `Activation::needs_timing` is "difficulty has a value"; `Path::needs_timing` walks the same activations `Path::difficulty` walks. Say in the comment that this is D51 call 4 and D13. The button, the badge, the stored `hardest_ms`, the report's dash and the library filter all follow from `difficulty()` without an edit of their own; `squeeze_sentences` keeps its free wording.

The all-0 pass asks the owner instead of a 0 ms limit. `EngineOptions` (`src/search/engine.h`) gains one switch meaning "keep only paths that need no timing"; `search_allzero` sets it in place of `ms_filter = 0.0` and `hard_ms_filter`. In the engine, `within_ms_limit` becomes the one place that says whether a timing is inside this run's limit, and it takes the timing's ms and whether it is needed. Under the user's Path limit the rule is unchanged: ms at or below the limit, free timings included (a negative limit demands slack), so no main-list result moves. Under the all-0 switch a timing is inside only when it is not needed; the switch acts everywhere the hard 0 ms limit acted (the group key's over count in `ready_class`, `passes_ms_filter`, the hard prune). A needed timing of exactly 0.0 ms is the only input whose answer changes. `search_allzero` also drops any returned path that fails `Path::is_allzero` (245), with the no-activations check kept. `attach_allzero`'s shortcut reads `best.is_allzero() && !best.needs_timing()`, and its comment says this is the same test the pass applies, so the search side and the display's identity dedupe agree by construction (243).

`build_path_list` keeps in `view.allzero` only the all-0 entries whose identity matches no listed path, and shows the section when any survive (call 4b). `allzero_label` is the score alone; the button's "N below optimal" line in `build_path_buttons` is the one delta (261). `within_label` takes a `DepthMode` and spells "scores"/"points" from the enum; the int the two UI callers pass is turned into the enum by asking `Settings::search_depth_mode()` (see open question 3). `build_record_status`'s comment says the blob's cap and limit equal the key's by ST1's `prepare_row` check (130). For a Ready record whose cap is 1, each path button's detail line reads exactly "A 1-bar cap can never activate Star Power." (call 16; see open question 2).
