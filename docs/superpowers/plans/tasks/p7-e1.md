## Goal

One question: how many tied paths does the search keep at one score, and which one leads? `Engine::reduce_group` in `src/search/engine.cpp` already owns it. Today it answers in two halves, one for paths inside the Path limit and one for paths over it, so "keep 4 tied paths" can keep 8. After this task it is one count per score, with the inside paths first, and the rest of `reduce_group` says each of its rules once. This task changes stored results (fewer tied paths on charts with ties on both sides of the limit). The results stamp stays "2.1.0".

## What the code does today

**95.** `reduce_group` folds ties with a key made of the score and a "filtered" bit (filtered means the path fails the Path limit). So an inside path and an over-limit path at the same score never meet, and the tie limit `max_tied_paths_` runs once per half. The guide (`docs/UserGuide.md` line 255) promises one count per score. The comment on `Rules::max_tied_paths` in `src/core/rules.h` says "one leader" and never mentions the split.

**330.** Below the fold, a filtered path is dropped only when a score in the "beating" set outscores it, and an optimal-score filtered path joins that set, so an over-limit path survives when it ties the best score. The comment block there states the intent. No test pins it.

**173.** Before the fold there is a shortcut: in Scores mode, a group of at most N+1 paths, none filtered, all scores distinct, is kept whole and the function returns. The general band at the end of the function decides the same thing by counting how many distinct beating scores outscore each path. Two spellings of one rule.

**179.** The engine keeps a running sum on each leader (`leader.tied_count += p.tied_count`) to enforce the limit. The finished tree is recounted by `Path::recount_tied_paths` in `src/core/model.cpp`, called from `rebuild` in engine.cpp, and that recount is what is stored and shown. Nothing checks the two agree. The engine's `OutPath` (defined in engine.cpp) does not carry the engine's count.

## What changes

Owner: `Engine::reduce_group`, `src/search/engine.cpp`.

The tie key drops the filtered bit, so every path at one score folds under one leader. Within a group the inside paths are offered first and the over-limit paths after, so the leader is an inside path whenever one exists, and when the limit is reached the dropped paths are over-limit ones. Say in the comment that this is D51 call 1.

The two bands after the fold keep working with mixed leaders. A leader is unfiltered when it is an inside path; its over-limit variants ride with it. An optimal-score path that is over the limit still stays kept (D51 call 2), whether it leads its group or rides as a variant. Hard mode (`hard_ms_filter_`) is untouched: it still removes over-limit paths before `reduce_group` sees them.

The shortcut and the general band become one predicate: one small function that says whether a score is outscored by more than the depth setting's number of distinct scores, which both the early return and the final loop call. If the early return cannot be expressed through that predicate, delete it; the general rule gives the same answer. Say which you did in your report.

`Path::recount_tied_paths` in `src/core/model.cpp` stays the owner of the stored count; E1 owns that one function in model.cpp (E2 owns `MultSqueeze` in the same file and nothing else). The engine's running sum is bookkeeping for the limit. Hand it out on the root `OutPath` from `emit_path`, and in `rebuild`, right after `recount_tied_paths`, throw a `std::logic_error` naming both numbers when they differ, in the style of the two rebuild checks already there. No fresh record may hit this.

The `max_tied_paths` comment in `src/core/rules.h` says: one count per score, inside paths lead.
