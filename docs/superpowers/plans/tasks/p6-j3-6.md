## What changes

**194 and 195, owner.** `path_codec.h` exports the head layout beside the format comment near the top: the format's offset and width (0 and 4), the fingerprint's offset and width (4 and 8) and the head size (12), as named constants, plus a small `StructureHead` reader: given a byte span (the whole blob or just a selected head), it returns the format and fingerprint, or nothing when the span is shorter than the head. Its body reads through `BinaryReader::u32` and `u64`, so the layout is written once (in `flatten_record`) and read once (here); `rebuild_record` keeps reading the same two values through its own `BinaryReader`, which is the writer's mirror, not a copy of the layout. `record_store.cpp` then drops `kStructureHeadBytes`, `read_le` and `write_le`. `layout_is_current` and `structure_is_current` call the head reader (or fold into `rank_row`, below). The SQL text is built from the constants: `rules_fp_of` spells `substr(<blob>,<fingerprint offset + 1>,<width>)` from them (SQLite's `substr` is 1-based; say so in one comment), a sibling spells the format's `substr`, and the three `substr(structure,1,12)` selects spell the head's. The bound blobs come from a `BinaryWriter` (`u32` for a format, `u64` for a fingerprint). The bytes are identical: the round-trip cases and the Stale cases prove it.

The hand-poked test bytes stay as pins of the layout, but index the format through the exported offset constant rather than a bare `0`, so the test and the store name the layout the same way. The values they poke (1, 5, 6, `written + 1`) are literals and stay.

**196.** `rank_row` reads the head once and returns the verdict and the reasons together: extend `Candidate` with `build` and `rules` (or return a small struct holding a `Candidate` and the two reasons). `stale_reasons` and `StaleReasons` go; `get_summaries` and `get_record` read the reasons off the picker's winning candidate. The rule stays what it is today: `build` is "another results stamp or an older path layout"; `rules` is "this layout, another fingerprint". "a Stale lookup says why: another build, other rules, or both" is the test and does not change.

The `hyversion` compare stays as its own line. The four one-column compares go. "a rewritten row that lands on its own id is read fresh, not mixed up" is the test.
