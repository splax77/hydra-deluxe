# Plan: the single-owner scan as data, with rows that cannot go stale

Planner: task TP-1, session c39f32f3, 2026-10-10. Read-only; nothing here is built yet. Every number below says where it comes from. Counts of rows and lines are from greps over the checkout at commit 784e47cc; the per-day history is from `git log` on the scan file; the docs-test numbers are from a Python script in this session's scratchpad (`tp1/docs_strictness.py`) that replays the test's own name rule over the same docs.

## What is wrong and what changes

`tests/test_single_owner.cpp` is the test that enforces the user's rule that every question in the code is answered in one place. It works, and nothing in this plan weakens it. The problem is its shape. The file is 6,558 lines, and 5,600 of them are a table of 357 rules written as C++ initializers (my count of rows starting `{"` with a capital letter; the audit said 341 a day earlier). Every derive-once review that fixes a copy adds a row there, so 352 of the 1,335 commits since 3 October touch this one file, almost all of them "add one row". Each such edit recompiles the largest test file and is the main merge conflict between parallel agents. A separate tool, `tools/derive_once_precheck.ps1` (1,283 lines), reads the same table out of the C++ by brace position at a git revision, with its own self-test to notice when a struct member moves. That is a parser for C++ written in PowerShell, which exists only because the rules are not data.

Two smaller things are also wrong. First, 173 of the 357 rows have no guard against going silently vacuous: a row with `owner_lines` fails when its owner line stops matching, but a row without one keeps passing after the owner is renamed or deleted, because it only ever says "nothing else may say this". (The row scan has a function-scope guard, but my grep found no row that uses it.) Second, the two baselines that are meant to "only shrink" have not: four known copies (three right-align copies from RW-T5 and one `ends_with` test) and all sixteen clone entries from 5 October are still there, and nothing makes them leave.

The plan moves the rules into JSON files, one per area, read at run time by the existing JSON library (already linked into `hydra_tests`: `third_party/json`, used by `tests/corpus_util.h`). The C++ keeps only the engine, split into three small files. Every row gains an owner file and symbol that the test checks still exist, a date, and the decision behind it. The baselines are emptied by fixing their twenty entries, and any future entry needs a removal date. The precheck reads the JSON with `ConvertFrom-Json` and loses its C++ parser. The docs test gets a stricter word set, chosen by the user from measured options. Scan time stays at or under today's 4.2 s, measured.

## What the history says changes most

Since 3 October: 9 rows added on the 3rd; about 316 added and 112 removed on the 4th and 208 added, 77 removed on the 5th (the derivation audit built the table, and those two days include merges counted twice); then 21, 25, 21, 9 and 1 rows added on the 6th to the 10th, with 0, 11, 7, 3 and 0 removed. Of 242 non-merge commits, 94 only add lines (75 of them 50 lines or fewer), 136 add and remove, 12 only remove. The four kinds of edit I saw in sampled diffs are: add one row (the common case, 17 to 43 lines), widen a pattern to a new spelling (`fc71c8e6`), tighten a pattern and add examples (`ec507621`), and drop a row whose owner is gone (`e631420f`, `3b8b3415`). So rows are retired sometimes, but only by hand when someone notices. The design makes "add one row" an edit to one small JSON file with no recompile and no shared hot spot, and makes "owner is gone" a test failure instead of a chance find.

## Prior art, and whether a tool could replace the scanner

ArchUnit's user guide is the clearest statement of the practice. Since 0.23.1 a rule whose subject set is empty fails by default (`archRule.failOnEmptyShould`, overridable per rule with `allowEmptyShould`), so a renamed package cannot turn a rule into a no-op; `FreezingArchRule` records existing violations in a store that only shrinks, with `allowStoreCreation=false` by default and `allowStoreUpdate=false` recommended for CI; and every rule carries a `because(...)` reason. Sources: https://www.archunit.org/userguide/html/000_Index.html (sections 7.6, 8.6, 10.4) and the 0.23.1 notes at https://newreleases.io/project/github/TNG/ArchUnit/release/v0.23.1. ArchUnit reads compiled Java bytecode; it has no C++ form. NetArchTest (https://github.com/BenMorris/NetArchTest) and ArchUnitNET (https://skills.managed-code.com/skills/archunitnet/, a summary page only) are the .NET versions and read assemblies through Mono.Cecil; neither touches C++. The C++ tools I found (cpp-dependencies, CppDepend at https://www.cppdepend.com/faq) check include and module dependencies, not "this spelling has one owner"; CppDepend is commercial.

clang-tidy now has query-based custom checks: a rule is a clang-query matcher written in `.clang-tidy`, enabled with `--experimental-custom-checks`, marked experimental and "not for complex checks" (https://clang.llvm.org/extra/clang-tidy/QueryBasedCustomChecks.html). It would express a good share of Hydra's rows structurally (a `binaryOperator` comparing `size()` to `MAX_PATH`, a call to `utf8_to_wide` outside `winstr.cpp`), which is better than regex for those. But it needs an LLVM install, a compilation database the Visual Studio generator does not emit, a full parse of the tree on every run (minutes, not seconds), and it cannot see the rows that scan Python, Inno Setup, comments or string spellings. Semgrep's C/C++ support is "Generally available" (https://docs.semgrep.dev/supported-languages) and `pattern-not-inside` says "flag X unless it sits inside Y" directly (https://docs.semgrep.dev/kb/rules/using-pattern-not-inside), but the pages I fetched do not state native Windows support, and an older issue shows Windows as an unofficial Cygwin build (https://github.com/semgrep/semgrep/issues/2991); I could not confirm it runs in this CI.

Verdict: no tool replaces the scanner on Windows and MSVC today. The scanner's real weakness is the one the W1 report named (a regex that misses a spelling proves nothing), and no listed tool fixes that for every row either. The plan keeps the text scan and borrows ArchUnit's three habits: fail when the subject is gone, give every rule a reason, and lock the baseline.

## The design

**Where the rules live.** `tests/single_owner/rules/<area>.json`, one file per area, named by the owner's top folder under `src/` (`core.json`, `search.json`, `parse.json`, `store.json`, `app.json`, `ui.json`, `audio.json`, `render.json`, `cli.json`) plus `tests.json` for the rows scoped to tests and `probe.json` for the Python rows. The rule for which file a row goes in is mechanical: the owner's folder. The C++ reads every `.json` in the folder, so adding an area file needs no code change. JSON is chosen because both readers already exist (nlohmann in the tests, `ConvertFrom-Json` in the precheck). The cost is that regexes need their backslashes doubled; the existing self-test (every `must_match` line must be flagged, every `must_not_match` line not) catches any regex that the escaping broke, so a mistake fails the suite at once rather than passing quietly.

**What each row carries.** Today's fields stay, with the same meaning: `question`, `owner`, `pattern`, `calls_owner`, `owner_files`, `exempt`, `must_match`, `must_not_match`, `owner_lines`, `scope`, `scan_comments`. The free-text `decided_by` splits into `decision` (an ADR number, a D-number from `docs/audit/2026-10-03-fix-decisions.md`, or a review key), `date` (the day the row was added, from `git log` for the existing rows), and `added_by` (the task or review that added it). The comment above each row today, which says why the pattern is shaped as it is, becomes a `note` field so it survives the move (JSON has no comments). Two new fields guard the row: `owner_file` (a repo path) and `owner_symbol` (the function, constant or struct named in `owner`). A one-time converter fills them from the owner strings, which almost all read "name in path"; the rows it cannot parse are listed for the agent to fill by hand.

**The guard against a silent no-op.** The scan fails a row whose `owner_file` does not exist or whose `owner_symbol` does not appear as a word in it outside comments, with the message "owner gone: name the new owner or retire the row". This is the scanner's form of ArchUnit's empty-should rule. A plain "the pattern matched nothing anywhere" check is the wrong guard here, because many rows are meant to match nothing on a clean tree (the owner spells it another way and nothing else may spell it the forbidden way). Rows with `owner_lines` keep that stronger guard too. The unused function-scope fields go if the build task confirms no row sets them.

**Retiring stale rows.** A row is retired when its owner is gone (the guard forces it) or when the forbidden spelling can no longer compile (the helper became the only public entry); the second is a judgement, so the plan adds a small listing in `tools/` that prints rows by age with their decision, for a review the user schedules. Rows have no expiry date (question 4 below).

**Baselines that shrink.** `known_copies` and `known_clones` move to `tests/single_owner/baseline.json`. The plan fixes all twenty entries now (tasks 4 and 5), so both lists start empty. After that an entry may be added only with a `remove_by` date, and the test fails on the day after it. That is the "every step has a stop condition" rule applied to the baseline, and ArchUnit's `allowStoreUpdate=false` in spirit: a copy may be parked, never kept.

**Splitting the C++.** `tests/single_owner/scan.cpp` holds the loader, the row scan, the listed-line logic and the self-tests (about 500 lines today). `tests/single_owner/clones.cpp` holds the clone scan (about 300 lines). `tests/single_owner/listed.h` holds `ListedLine`, `take_listed_line` and `check_scan`, which both scans and the probe scan share. The probe scan's separate `ProbeRow` struct and loop are a second copy of the row mechanism inside the scan itself; its rows become ordinary rows with `scope: ["tools"]` and `language: "py"`, and its loop goes. The E3/D85 case, which pins the exact text of two production lines, becomes two rows with `owner_lines`, so it gains the "update the owner line" message and loses the brittle whole-line pin the audit flagged. The D23 stamp-rule case and the D94 User Guide quote stay as they are in `tests/single_owner/special.cpp`.

**Failure messages.** The text stays exactly as today (`file:line: answers "<question>", which belongs to <owner>: <line>`, and the stale-entry lines), with one addition at the end: `(rule: rules/ui.json)`, so the fixer opens the right file. A self-test pins the message on a made-up file so a reword is deliberate.

**Speed.** Today's 4.2 s is 357 `std::regex` searches over about 88,000 lines (38,236 under `src/`, 1,370 under `tools/`, 48,079 under `tests/`, from `Get-Content` counts). The plan adds an optional `anchor` per row: a plain substring every match must contain (usually the function or constant name). The scan does `line.find(anchor)` first and runs the regex only on a hit; the self-test checks every `must_match` line and owner line contains the anchor, so an anchor can never hide a match the regex would have found. The converter fills anchors where the pattern has an obvious literal and leaves the rest empty. The build task measures with `--duration=true` before and after; the stop condition is below. Running files across threads is held back as an option (question 6).

**The precheck.** `tools/derive_once_precheck.ps1` reads the rows with `git show <rev>:tests/single_owner/rules/<file>` for each file `git ls-tree` lists, then `ConvertFrom-Json`. Its C++ table parser (`Get-TableElements`, `Get-Col`, `$ScanStructFields`, about 150 lines) and the self-test case for a moved struct member go. Its `.NET regex versus std::regex` note stays, since that difference is unchanged.

**The docs test.** `tests/test_docs_match_code.cpp` check 1 accepts a name found anywhere in `src/`, `tools/` or `tests/`, comments and strings included, and checks `Foo::bar` as two separate words. I replayed its rule over the same 31 docs (324 names) with four word sets. With today's set, 0 names fail. With words outside comments and string literals only, 50 names in 15 docs fail. With the same but `src/` and `tools/` only (no tests), 58 in 17. With definition sites only (struct, function, constant, `def`), 79 in 18. Reading the 50: most are executable names (`hydra_batch`, `hydra_fillcompare`, `hydra_uitest`, `hydra_replay`, `hydra_tests`), which live only in `CMakeLists.txt` and in command lines, and a handful are string values the code holds as literals (`first_note` and `whole_chord` are INI values, `ENABLE_CHART_DYNAMICS` is a chart tag, `transfer_pre` and `chart_meta_version` are stored names). The rest look genuinely stale or external: `hydra_report` (a deleted tool; ADR 0027 records its removal), `auto_cap_ladder` and `auto_budget_s` in ADR 0014, `lone_pricing` in ADR 0022, `ma_data_converter_reset` (a miniaudio function under `third_party/`, which the walk does not read), `directory_entry`. The recommended level (question 7) is: words from code outside comments, plus string literals in `src/` and `tools/` (production strings name real keys, tags and columns; test strings and comments do not), plus target and option names from `CMakeLists.txt`. Under that level my estimate is 10 to 15 names in about 8 docs that need a reword or an allow-list entry with a reason. The script also shows that `docs/agents/*` and `README.md` (62 names), which the test does not read, would fail 3 names today (`FIRST_TIME_CONTRIBUTOR` and `node_id` are GitHub API fields; `run_in_background` is a tool parameter): prose in backticks, not code. The estimate is from my script's reading of the test's rule, not the test itself, so the build task runs the real test and reports the real count.

## Decisions for the user

1. **Format.** Options: JSON (both readers exist; regexes need doubled backslashes), C++ `.inc` files per area (no escaping, but the precheck keeps its C++ parser and every row edit recompiles), or a custom line format (no escaping, but two new hand-written parsers). Recommendation: JSON.

2. **One file or one per area.** Options: one `rules.json`, or one per owner folder as above. Recommendation: per area, because the point is that two agents adding rows in different areas never touch the same file.

3. **What a row must carry.** Recommendation: `date`, `decision`, `added_by` and `owner_file`/`owner_symbol` all required; `note` and `anchor` optional. The converter fills them for the existing rows; a row missing a required field fails the self-test.

4. **Retiring rows.** Options: no expiry (a row is retired when its owner goes, which the guard forces, or when a person judges the copy impossible, helped by the age listing), or a review date per row that fails the suite when it passes. Recommendation: no expiry. A rule about where a question is answered stays true until the owner changes; a date would make agents bump dates, not review rows.

5. **Baseline cap.** After tasks 4 and 5 both baselines are empty. Options for a new entry: it needs a `remove_by` date at most N days out (N is your number; I suggest 14), or no new entries at all (a parked copy blocks the merge until fixed). Recommendation: the dated entry, so an agent that cannot edit a file another task owns can still land, but the clock runs.

6. **Speed.** Options: anchors only (recommended first; no concurrency, same results), or also split the files across threads with the listed-line step kept serial (likely well under 1 s, more code to review). Recommendation: anchors, and threads only if the measurement in task 3 stays over 4.2 s.

7. **Docs strictness.** Options: (a) code words outside comments and strings everywhere (50 names fail today by my estimate); (b) option a plus production string literals and `CMakeLists.txt` names (10 to 15 fail, my estimate); (c) definition sites only (79 fail, and it would reject stored column names and INI values that are real names). Recommendation: (b).

8. **Widen the docs test** to `docs/agents/*.md` and `README.md`. Three names fail today, all prose in backticks. Recommendation: yes, in task 6, with the three reworded rather than allowed.

9. **A structural tool later.** Recommendation: none now. If you want to try one, clang-tidy's query-based checks on the twenty rows about call shapes is the experiment, as its own task after this plan, with Ninja and `compile_commands.json` as its first hurdle.

## Risks

The converter is the one step that can lose meaning, so it reuses the precheck's reader rather than a third parser, and the self-tests plus the unchanged row count are the proof; the agent also diffs the questions list against a grep of the old file. The precheck must change in the same merge as the table, or every derive-once review breaks; tasks 1 and 2 share a branch for that reason. Other sessions add rows to the C++ file while this runs; the branch is short-lived and the converter runs again at merge time against the merged tree, so rows added meanwhile are carried. JSON backslash mistakes fail loudly through the self-tests, never quietly. The `remove_by` dates make the suite fail on a calendar day, which is intended, but the failure message must say which entry and whose task, or a cold CI run will puzzle someone; task 3 pins that message. The documents in task 7 and the doc edits in task 6 go through the doc-review gate, which adds one reviewer each. Nothing here changes what the scan flags; a row that flagged a line yesterday flags it after the move, and the tree is green both sides of the change.

## Size

About 8 to 10 agent-hours and 450 to 600 tool calls across six or seven agents, plus one reviewer per merged change (four merges: task 4, task 5, task 6, and tasks 1+2+3+7 together). One cold build for task 1's agents, warm builds for the rest.

## What done looks like

`tests/test_single_owner.cpp` is gone. `tests/single_owner/` holds three C++ files under 1,000 lines together, a `rules/` folder of area JSON files, and an empty `baseline.json`. Adding a rule is a dozen lines in one JSON file with no recompile. Every rule names an owner file and symbol the test checks still exist; a renamed owner fails the suite with "owner gone". The scan case runs at or under 4.2 s, measured. The precheck reads the JSON and its self-test passes. Failure messages read as they do today plus the rule's file. The docs test uses the chosen word set, its allow-list carries a reason per entry, and the real failing count before fixes is in the task's report. An ADR records the change, and the agent guide tells reviewers where a row goes.

## Open questions I could not settle

Whether `std::regex` compile time is a visible share of the 4.2 s (357 compiles happen once per case, in three cases); task 3 measures it. Whether the sixteen clone fixes in tests make those tests harder to read (the W1 report's "DAMP, not DRY" point); task 5's agent may leave an entry with a `remove_by` date and say why. Whether the precheck's `.NET` regex reads every row the same way after the move; its "precheck:" note already reports the ones it cannot, and task 2 lists them.
