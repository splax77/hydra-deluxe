## The plain version

An MCP server is a helper program that gives an agent a set of tools to call. The project already has one for Hydra, `tools/hydra_ui_mcp.py`. This plan builds the same kind of helper for Clone Hero, so an agent can start the game, launch a chart with a bot, attach to the running game and read its clock and state, see each note the game processes, press drum lanes, read the end-of-song stats, and stop the game with the user's files put back.

Nothing in the server is new mechanism. Each tool wraps a module that already exists in `tools/ch_mcp/` or `tools/ch_probe/` and already ran against the game on 2026-10-28: the bot launcher (`bot_run.py`), the Frida attach runner and its agents (`frida_attach.py`, `agent/*.ts`), the hit tracer (`trace_hits.py`), the key presser (`ch_probe/experiments/play_chart.py` and `ch_probe/input_driver.py`), the chart installer and the stats comparison. The server owns only the transport: the tool list, one live session at a time, the caps on waits and replies, and the reports when something dies. Every rule about the game stays in the module that already owns it.

Four things the user has not approved stay out: reading a note's hit result and timing offset from the hook's arguments, input injected inside the process instead of `SendInput`, the switch for the empty `HitDetection-*.log` files, and finding scrambled classes again by shape after a game update. Where a tool would be better with one of them, the open questions say so.

The work is six executor tasks. Five of them change one existing module each so the server can call it step by step instead of run-to-completion, and they run in parallel. The sixth writes the server and its tests and starts after the five merge. Then three short live steps with the user at the game check the server end to end, each with a run cap.

## Open questions for the user

Each has my recommendation. Say "go with the recommendations" to approve them all. Questions 1 to 7 change what gets built; everything else in the plan is decided and recommended.

1. **A launch with no song.** `bot_run.launch_command` builds `"Clone Hero.exe" --song <folder> --player <Instrument>,<Difficulty>` and nothing else. That always adds a bot player, and the bot plays the chart. Test 3's key-press run needed a song the user started from the menu, with no bot. The server cannot do that today: it has no proven way to open the menu other than the user double-clicking the exe. Recommendation: `ch_start()` with no `song_folder` runs `"Clone Hero.exe"` with no flags, which is exactly how the user starts the game by hand, and takes the same backup first. With a `song_folder` it is the proven bot launch. Both ends: `ch_start("C:\Clone Hero\songs\Hydra Probe\Window Map")` plays the bot run from the command line; `ch_start()` opens the menu and the user picks the song.

2. **A game the server did not start.** `game_files.backup` copies five files (`settings.ini`, `scorestats.json`, `scoredata.bin`, `scoresext.bin`, `user.bin`) and `restore` puts them back byte for byte. The handoff warns: "A human run changes `scoredata.bin`, so restoring discards that run's saved score." If the user has the game open already and an agent calls `ch_attach` or `ch_press`, the server has taken no backup. Recommendation: the first tool that touches a game the server did not start takes the backup then, and `ch_stop` restores it like any other run; the reply names the backup folder so the user can keep it. The other end: skip the backup for adopted games, which leaves one kind of live run with no restore. I recommend backing up, because the study's rule is "every live run".

3. **The server exits while the game runs.** `hydra_ui_mcp.Helper.shutdown` kills Hydra at exit ("never leave a Hydra behind"). For Clone Hero the game may rewrite the five files when it closes (`bot_run` prints "the game is still running and may write these files again when it closes"). Recommendation: at exit, if the server started the game and it still runs, terminate it (the existing `_Process.stop`, 30 s wait) and then restore. If the server only adopted a running game (question 2), restore and leave the game open. The other end: never kill, always restore; then a restore can be undone by the game's own write on close.

4. **An unknown game build.** `ch_probe.process` refuses a build whose constants do not match, and `trace_hits` checks the engine class's shape (sealed, generic base, a double at 0x2E0, the constructor's RVA) before hooking. The study recommends finding classes by signature after an update. Recommendation: the first version only stops. It reads `Clone Hero_Data\version.json` (today `v1.1.0.6142-final`), looks for `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\<build>\facts.json` with a matching `game_version`, and refuses every Frida and trace tool with "unknown build <version>: no facts for it; run dump_build.py and dump_facts.py" when it is missing. Re-deriving scrambled classes by shape is a follow-up with its own plan, because test 4 showed the engine's name does not survive an update and nothing has yet matched a class by shape alone. The other end: build the re-derive now, which needs a shape language nobody has written.

5. **Three new caps.** Every wait needs a number and these three are new. (a) Attach delay: the handoff says "Attach about 5 s after launch", because a command-line launch writes only its `Loading Song` log line at first and the first probe note is at 3 s; the passing run attached at 8 s. Recommended `ATTACH_DELAY_S = 5`: `ch_attach` waits until 5 s have passed since `ch_start` launched the process, then attaches. (b) Attach cap: `ATTACH_CAP_S = 30` for Frida to attach, load the agent and answer its first read. (c) Read cap: `READ_CAP_S = 5` for one state read to come back. Every other wait reuses a cap that already exists and was approved on 2026-10-28: the stats wait is the song length plus 60 s (`bot_run.POLL_CAP_EXTRA_S`), the exit check 30 s (`EXIT_CHECK_S`), the trace's song cap the length plus 30 s and its wall cap 120 s more (`trace_hits`), the play run 240 s (`play_chart.RUN_CAP_S`) and the engine search 120 s (`ch_probe.constants.ENGINE_SEARCH_CAP_S`). Replies are cut at 12,000 characters, the number the user chose for the Hydra helper on 2026-10-14 (`hydra_ui_mcp.REPLY_CAP_CHARS`).

6. **Which hook is "the note event".** Test 3 found three methods that each ran exactly once per note in the bot runs: engine `0x20DEEC0` (adds a hit's points; arguments a note and the base points, 50), engine `0x20DE770` (handles the accent and ghost flags) and base `0x100E6E0`. Hooking all three gives three events per note. Recommendation: `ch_trace_start` hooks `0x20DEEC0` by default, so one call is one note, and takes an optional list of the other two by name for anyone who wants them. One thing is unproven and the live step L2 checks it: every traced run so far hit every note, so nobody knows whether a missed note fires these methods at all. Until L2 says, a `ch_notes` line means "the game processed this note", not "hit".

7. **The score in the snapshot.** `GameManager` keeps `songTime`, `isPaused`, `isSongOver`, `isSongPlaying` and `songLoaded` readable, and Frida reads them by name. The score, combo, multiplier and Star Power live in scrambled fields of `ScoreManager` and the drum engine, so no name reaches them. `ch_probe` reads the score at engine offset 0x94 from outside the process, proven on 2026-09-25 and again in test 3 (25,550 read after the last note). Recommendation: `ch_snapshot` shows the score only while `ch_play_chart` runs, because that session has already found the engine the way `play_chart` does; otherwise the line reads "score: not read (no play session has found the engine)". The other end: a separate engine search for every snapshot, which blocks up to 120 s waiting for a moving clock. Combo, multiplier and Star Power stay out until their fields are found; that is a follow-up.

## Safety rules for every live step

These bind the server code and every live step below. The code paths named are the owners, so no step types them by hand.

A backup exists before any tool touches the game. `ch_start` takes it through `game_files.backup` before the launch. The first tool that touches a game the server did not start (`ch_attach`, `ch_press`, `ch_play_chart`, `ch_trace_start`) takes it then, if question 2 is approved. `ch_stop` and the exit handler restore through `game_files.restore` and print its line per file. A failed restore stops with the file name and the error, the backup folder is named, and no later step runs in that tool call.

Play is offline as the 2026-10-28 plan's question 7 defined it: no step opens the Online menu, the server passes only what `launch_command` builds (`--song`, `--player`, and `--profile` only when given), and nothing in `tools/ch_mcp` names a server, a lobby or a leaderboard setting. There is no setting to flip; the network adapter off is the only hard guarantee and stays the user's choice.

The Frida agents read and trace only. The grep in `tests/test_frida_attach.py` (`NO_WRITE_PATTERNS`) covers every `agent/*.ts`, the new `state.ts` included, so no agent writes game memory, sets a field, calls or replaces a game method, or reads by offset. Hooks are `Interceptor.attach` with an `onEnter` that reads; the EULA ruling stands as the user gave it ("Proceed, my call", 2026-10-28), and the study's note that an attached hook patches the start of a traced method in memory while attached applies to `ch_trace_start` too.

Every wait has a cap and prints one line when the cap is hit. The existing caps are listed under question 5 with their owners; the three new ones need the user's yes there. No tool retries on its own.

Frida runs under `py`, never `py -I`. The `.mcp.json` entry is `py tools/ch_mcp/server.py`, and every command line the server prints for the user (the restore hint) comes from `bot_run._restore_hint`, which already says `py`.

`node_modules` never sits in the main checkout. Executors run `npm install` and `npm run build:<agent>` inside their own worktree's `tools/ch_mcp/agent/` only. After T3 merges, the main session builds `state.js` and `trace.js` in the main checkout and moves `node_modules` out again (or confirms the gitignore fix of the single-owner scan has landed first). The server never builds; when a compiled agent is missing, its reply names the `npm run build:<name>` command, as `trace_hits` does today.

Nothing runs over the user's song library. The tools take one song folder or one chart folder at a time, and `install_chart` copies one named folder.

## The things that bit last time, and what the server does about them

Attaching to a command-line launch too early, or waiting on the session log, failed in test 2: the log holds only `Loading Song` until later. The server never reads the session log. `ch_attach` waits out `ATTACH_DELAY_S` from the launch and then attaches (question 5a).

The tracer needs a live `GameManager`, and the menu has none. `ch_trace_start` first does one state read through the live agent and refuses with "no live GameManager: start the song (pause it if you like), then call ch_trace_start" when there is none. The trace's song cap counts song time played since 6bdbc494, so a pause before play does not use it up.

A cap end used to print an error and exit 1. Since 6bdbc494 `run_agent` returns `END_CAP` with no error, and `ch_trace_stop` and `ch_notes` print the same `ended:` line `trace_hits.ended_line` prints.

The key-press run of test 3 counted 139 of 142 because the wall cap ran during a pause. That is fixed in `trace.ts` (song cap in song time). The server also exposes `ch_trace_stop` so a run can end on the agent's say, and `ch_notes(since)` so a long trace is read in pieces instead of one reply.

`SendInput` needs the game window in front. `ch_press` and the play session call `focus_window(find_game_window())` before every press, as `play_chart._live_press` does, and the reply says "no game window found" when `find_game_window` returns 0. Whether `SetForegroundWindow` works from a helper that Claude Code started is checked in live step L3; test 3's key-press run worked from a shell the main session started, which is the same kind of process.

A song launched with a bot cannot be played by keys (the bot plays it). The play tools need a song the user started from the menu (question 1), and `ch_play_chart`'s reply says so.

### T1: the bot run as three steps (one executor; offline; no dependencies)

Owns `tools/ch_mcp/bot_run.py` and `tools/ch_mcp/tests/test_bot_run.py`.

Today `run_bot` does backup, launch, wait, exit check and restore in one call, which the server cannot pause between. T1 pulls the steps apart without changing the command line or any existing test. `start_run(song_dir, *, player, profile, backup_root, env) -> Run` reads the song length and its source (the existing `song_length_ms`; a missing length still raises `SongLengthMissing` before anything starts), takes the backup, records the stats file's state, launches, and returns a `Run` dataclass holding the backup folder, the command line, the `Game`, the launch time (`env.now()`), the cap in seconds, the length and its source, and `before`. With `song_dir=None` (question 1) it skips the length, launches `[exe]` alone, and sets the cap to None, so `wait_stats` on such a run says "no song was launched from the command line; nothing to wait for". `wait_stats(run, out_dir, env) -> Optional[str]` is the existing `_poll_stats` on the run's cap and `before`. `exit_check(run, env)` is the existing `_exit_check`. `finish_run(run, *, stop, env) -> bool` stops the game when asked (the existing `game.stop`, 30 s), restores through `_restore`, prints the existing "still running" hint when the game stays, and returns False when the restore failed. `run_bot` is rewritten as the sequence of those four, so its behaviour and every existing test stay the same.

Tests, added to `test_bot_run.py` on the existing `Rig` and fakes: `start_run` returns before any sleep (the fake clock is still at 0) with the backup folder on disk and the stats `before` state; `start_run(None)` launches `[exe]` with no flags and takes the backup; `wait_stats` on a no-song run prints the line above and returns None without sleeping; `wait_stats` copies a changed file and names the seconds; `finish_run` with `stop=True` stops the game and restores all five files; a failed restore in `finish_run` prints the file name and returns False; `run_bot` through the four steps still passes every existing test unchanged (no existing assertion is edited). Run: `py -m pytest tools/ch_mcp/tests/test_bot_run.py -q`.

## The live steps (main session, user present)

Each step names its pass and fail lines before it runs, has a run cap, and ends with `ch_stop`'s restore lines. The user watches the game; agents never wait on a person.

### L1: a bot run end to end

Pass means: `ch_start("C:\Clone Hero\songs\Hydra Probe\Window Map")` returns the backup folder and pid; `ch_attach` (called at once; the server waits out the 5 s) answers with a state read; `ch_state` moves through "loaded, not started" or "playing" to "song over" (polled at most 40 times, 2 s apart); `ch_wait_stats` copies the file within its cap; `ch_stats` shows `is_bot: true` and `total_notes: 142`; `ch_compare` against `hydra_replay score` on the same `notes.chart` passes both lines; `ch_stop` prints five restore lines. Fail means any of those does not happen; the step records the reply that broke it. Also record what `ch_state` says after the user returns to the menu by hand: that settles whether a `GameManager` survives leaving the results screen, which nobody has checked. Two runs at most; if the first fails at `ch_attach`, check Task Manager for `Clone Hero.exe` before the second.

### L2: a key-press song with the trace, and what a miss does

Needs question 1 approved. `ch_start()` opens the menu; `ch_state` should say "menu (no live GameManager)". The user starts Window Map and pauses it at once; `ch_trace_start("...\Window Map")` hooks `RVA_NOTE_SCORE_ADD`'s method; `ch_play_chart(<scratch>\window-map.json)` starts the presser, which waits for a moving clock; the user unpauses. Pass means: `ch_play_status` shows hits climbing, `ch_notes` shows 142 calls by the end with every difference inside 85 ms, and `ch_trace_stop` prints `ended: done (agent: song over)`. Then a second run where the user deliberately lets about ten notes pass unplayed (the presser is not started): if `ch_notes` shows 142 calls, the hook fires on misses too and a line means "processed"; if it shows about 132, the hook fires only on hits, and the README's wording for `ch_notes` is changed to say "hit" before this plan's follow-up on hit results starts. Either answer is a pass; the point is to know. Dead means the trace refuses with the no-`GameManager` line while the song is paused on screen, which would mean a paused song has no live `GameManager` and the refusal is wrong; stop and report. Three runs at most.

### L3: focus and presses from the helper

`ch_start()`, the user opens any probe song, `ch_press("kick")` three times about a second apart while the user watches the kick lane. Pass means the game shows the presses (the overhit flash or a hit). Fail means nothing shows, which would mean `SetForegroundWindow` is refused from a Claude Code child; then `ch_press`'s reply must say so and the fix (for example `AllowSetForegroundWindow` or the user clicking the window once) is a follow-up question. Two runs at most.

## Prior art

I searched for other Clone Hero automation and for Frida-based MCP servers before settling the shape. No public tool auto-plays Clone Hero from outside; the search found only the game's own bot flags on the manual page and generic `SendInput` wrappers, so `play_chart.py` stays the only known presser and this plan reuses it ([the command-line manual page](https://wiki.clonehero.net/books/clone-hero-manual/page/chart-previews-via-the-command-line), which documents `-s/--song`, `-p/--player` up to four times, `--profile` as a template for the bots, `-i/--instrumentNames` and `-v/--verses`, and says nothing about exiting after the song). Several community Frida MCP servers exist and all expose Frida itself: attach, spawn, kill, run arbitrary JavaScript, read memory ([dnakov/frida-mcp](https://cdn.jsdelivr.net/gh/dnakov/frida-mcp@main/README.md), a Python stdio server on the official MCP SDK; [axhlzy/il2cpp-frida-mcp](https://glama.ai/mcp/servers/j65u2u4mh3), which uses `frida-il2cpp-bridge` through a compiled TypeScript agent and offers class and method listing, `gc_choose` and an `exec_js` tool). This plan deliberately does not copy that shape: a general "run any JavaScript" tool would let an agent write game memory or call game methods, which the no-writes rule forbids, and it would move the game rules into the agent's prompt instead of the owning module. What it does borrow is the pattern both servers use of one compiled agent and a request/response message loop over Frida's `script.post` and `send`, which is `LiveAgent` and `state.ts`.
