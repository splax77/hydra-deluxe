# Plan: the overlay spike, Phase 0 (2026-10-28)

Task id `overlay-spike-plan`, session `f756d547-af2c-46f3-b891-96dea4efb402`. Plan only; no code changed.

## The plain version

Hydra may one day draw a live overlay over Clone Hero: the next activation with a countdown, the player's SP bar beside the path's, a running "points vs optimal" figure, squeeze reminders, and "you activated one note late" feedback. Before anyone builds that, four things have to be true at the real game, and nobody has checked them live. This plan is the short spike that checks them. It adds a few small Python scripts to `tools/ch_probe`, runs them at the game in one sitting of about 25 minutes with the user, and writes the answers up under `docs/research/`. No Hydra C++ changes. No overlay UI.

The four questions, in order of importance. Question 1: do the Star Power fields the disassembly named (amount, maximum, active flag, multiplier, end time) read correctly while a song plays. Question 2: where the game keeps the playing chart's checksum, and whether a reader can reach it each song by following pointers instead of searching all memory. Question 3: whether the game's song clock agrees with Hydra's chart times, and whether the game's score climbs chord for chord the way `hydra_replay` says it should. Question 4: a handful of cheap checks: the per-hit field candidate, pausing, whether the session log is written live, what engine finding and polling cost, and whether a plain topmost window shows over the game in fullscreen.

One limit up front. On drums the game starts Star Power when a press lands on the last note of a fill, so the auto-player cannot choose to pass over a fill. The spike therefore plays a path that never passes over a fill, not Hydra's optimal path, which does (see "How Star Power starts on drums"). What the game does with a passed-over fill is left for Phase 1.

The work splits into a small first wave (a prerequisite and an offline dump), a second wave of five script tasks that run in parallel, one sitting where the main session runs the scripts with the user at the game, and one write-up task after. Every live step has a cap and says what to report when the cap is hit.

## What the code does today (checked in the source)

`tools/ch_probe/process.py` opens the game by name with `OpenProcess` asking for `PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_VM_OPERATION | PROCESS_QUERY_INFORMATION`, finds where `GameAssembly.dll` loaded, and checks two hit-window constants in `.rdata` before any other read (`verify_targets`, raising `BuildMismatchError`). Every read goes through `ReadProcessMemory`. There is no read-only open today; the write right is there for the debugger path, which this spike does not use.

`engine_finder.py` scans every committed read-write region for the 16 bytes an engine object holds at `+0x30` and `+0x38` (the back and front window constants), drops hits inside the module, drops candidates whose total window at `+0x20` is empty, reads each candidate's song clock at `+0x100` twice 0.12 s apart, and returns the first one whose clock moved. `find_live_engine` loops forever until a song plays, printing a dot every 0.4 s. It has no cap, and every runner would need one, so Task P adds the one shared capped wrapper.

`engine.py` names the fields: `+0x20` total window, `+0x30`/`+0x38` window constants, `+0x94` score (u32), `+0x100` clock (double seconds), `+0x198` flags, `+0x8C` note count, `+0x2E0` the hit-time candidate ("not yet confirmed live"). `snapshot()` reads the first `0x2E8` bytes of the object in one call. None of the Star Power fields is in `constants.py` yet.

`experiments/play_chart.py` loads a `hydra_replay score` JSON, finds the live engine, and for each chord waits on the clock (`live.wait_until`, 2 ms lead) and presses the chord's own pad keys with `SendInput`. Nothing in it presses a separate Star Power key, and `input_driver.DEFAULT_BINDINGS` has none. It reads the score 5 ms after each press and calls a rise a hit. It prints a table but writes no file; `diff_ms` in its table is the clock at the press minus the chord's ms, not the engine's own hit time. It handles a restart (clock jumped back) by re-syncing and a frozen clock (over 5 s, `live.STALL_S`) by stopping. `input_driver.press_chord` skips a lane with no binding, and `test_input_driver.py` pins that; this spike leaves it alone.

`tools/replay.cpp`'s `score` command writes, per chord, `index` (the chord's place in the chart's sequence, not a running count), `tick`, `ms`, `notes` (color, cymbal, sp_points, multiplier, dynamic), `is_fill`, `is_sp_phrase_end`, `combo_before`, `multiplier`, `multiplier_after`, `in_sp`, `points` (notes, combo, sp, accent, ghost, solo) and `cum` (the same six, with `total`). At the top level it writes `activations` with `act_tick` and `deact_tick` only, and `final`. With `--path <dump.json> --index N` it scores path N of the dump. `dump` writes the paths with `pathstring`, `total` and, per activation, `act_tick`, `deact_tick`, `skips` and `skipped_fill_ticks`. In the Trippin run I made, every `deact_tick` is the tick of a chord, so a deactivation's ms is that chord's `ms`. The chart has 194 tempo changes, so ms cannot be worked out from ticks without a chord to read it from. `--rules <file>` picks the rules; the default is `hydra_rules.ini` next to the exe.

`docs/audit/ch-evidence.md` answer 37 names, from the disassembly only: SP amount at `engine+0x68` as a whole number of chart ticks, the maximum at `+0x1B0`, the active flag at `+0x42` and the multiplier at `+0x48` (set by activation at `0x20F5640`), the end time at `+0x120`, and the overflow flag at `+0x130`. Answer 222 says score is added at `+0x94` as `points * [engine+0x48]`, with the asm `imul eax,[rsi+0x48]`, a 32-bit read. None of these was read live. The evidence does not give the width of the amount or the maximum, nor of the flag at `+0x42`, so the watcher records several widths and the write-up picks one.

## How Star Power starts on drums, and what the auto-player does

From the disassembly (`docs/audit/drum-lanes/FINDINGS-play-time.md`, "What the flag 0x800 is" and the grant paragraph above it): the last note of each fill carries flag `0x800`. A correct press on it while Star Power can be activated (not active, meter at least the activation level) calls ActivateStarPower, then hits the note. A wrong-pad press while such a note is in the window hits the note without activating. A fill-end note that is missed is hit automatically while Star Power can be activated; whether that automatic hit also activates was not read. This is disassembly only; nothing here was seen live.

No separate drums key for Star Power is known: the key table in `input_driver.py`, read off the game's Controller Remap screen on 2026-09-25, lists the pads, cymbals and kick and nothing else. Whether the screen offers one is checked at the sitting (step 1) and recorded, but the spike does not depend on it.

So the auto-player does exactly one thing: it presses every chord with the chord's own pads, the fill-end chord included. No code in the spike presses a separate activation key. Whenever the game offers a fill's last note while Star Power can be activated, the game activates. The auto-player therefore plays "activate at the first chance, pass over nothing", which is why Choice 2 picks a path that passes over nothing.

Two things can still make the game activate somewhere other than the chosen path says. First, path 3 carries two `E0` marks. `E0` means Star Power came ready with less than 60 ms to spare before the fill's spawn deadline (`is_e0` in `src/core/model.h`); the dump does not say whether either needs an early hit on the phrase note, and the auto-player hits only 2 ms early. If the game does not offer such a fill, it activates at the next one. Second, the game's fill rule may differ from Hydra's 1.1 rule in some other way. Both are real findings about fills, not faults in the Star Power fields, so the comparison is built to keep them apart. The Star Power field checks are anchored on the activations the game actually made (the watcher sees the active flag go 0 to 1), not on the path's tick. A separate line reports, for each game activation, whether it landed on the chord the path names, and if not, which chord it landed on and the two ticks.

Trippin also has 34 ghost notes and 9 accents (counted from the score JSON for path 3). A keyboard press carries no strike velocity, and nobody has seen what the game pays for a ghost or accent hit that way. The score comparison therefore tracks the running difference between the game's score and Hydra's total, and allows that difference to change only on a chord that carries a ghost or an accent; a change on any other chord is a failure. The write-up reports what the game paid on those 43 notes.

## If the game's bot plays a run

The bot is the fallback for run 1 and the player in run 3. What it does at a fill-end note is unknown: it may activate like the auto-player, or at its own chosen fills, or not at all. It sends no keys, so there are no presses and no press log.

These comparisons stay valid on a bot run, because they read only the game's own fields against the chord times in Hydra's JSON: each phrase end's rise in `sp_amount`, `sp_max` staying constant, the flag, multiplier and end-time behaviour at every activation the bot made, and the pause behaviour. The per-chord multiplier check and the score check stay valid only up to the first activation that differs from the reference path; the report prints that chord and marks everything after it "not compared". The final score is compared with Hydra's only when the bot's activations all matched the path.

These do not carry over, and the write-up says so for a bot run: the hit rate (the bot hits everything), the clock-against-press statistics, the calibration answer (nobody presses, so nothing shows whether the notes or the clock moved), and the `+0x2E0` hit-time check (the bot's hit may land exactly on the note's time, which would match whatever the field holds).

## Tasks

Each task is sized for one executor in 100 tool calls and 20 minutes. Every task adds its unit tests in `tools/ch_probe/tests` as `unittest` files and runs only its own files. No task builds Hydra. No task launches, attaches to or sends input to Clone Hero: every live-only function is marked LIVE-ONLY in its docstring and sits behind a callable the tests fake, as `process.py` and `engine_finder.py` do today. No task runs anything over the user's library.

The tasks run in two waves so that no task depends on a merge that may not have happened. Wave 1 is Task P (the shared pieces) and Task I (the offline dump); each merges after its one reviewer. Wave 2 is Tasks A, B, C, D and S; their worktrees are cut from `main` after Task P has merged, so they can import what Task P adds. Task I touches none of their files and may merge before, with or after wave 2.

The live scripts of Tasks A, B, C and D share two rules, both delivered by Task P:

- They open the game with `open_process(read_only=True)`.
- They find the engine with `engine_finder.find_live_engine_capped`, catch `EngineSearchTimeout`, print its message (`no playing song found in 120 s; start the song and run again`) and exit 2. Each task's test fakes the finder to check that exit.

### Task P: the shared pieces (wave 1)

Owns `tools/ch_probe/process.py`, `tools/ch_probe/engine_finder.py`, new `tools/ch_probe/experiments/overlay_logs.py`, new `tools/ch_probe/tests/test_process_readonly.py`, new `tools/ch_probe/tests/test_overlay_logs.py`, and `tools/ch_probe/tests/test_engine_finder.py` (new cases only; the existing cases stay as they are).

Step 1. `process.open_process(process_name, *, read_only=False)`. A pure function `access_mask(read_only)` returns the `OpenProcess` mask: `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION` (0x0410) when read-only, the existing four rights when not. With `read_only=True` the `Process` gets a writer that raises `PermissionError("process opened read-only")`. The default stays as it is so the debugger runners keep working. Test: `access_mask` returns the literals 0x0410 and 0x0438 (the existing four rights); a `Process` built with the read-only writer raises on `write` and reads normally.

Step 2. `engine_finder.find_live_engine_capped(proc, patterns, cap_s=ENGINE_SEARCH_CAP_S, *, scan, sleep, now, out)`, with `ENGINE_SEARCH_CAP_S = 120.0`. It calls `find_live_engine` with a `sleep` that raises `EngineSearchTimeout(f"no playing song found in {cap_s:g} s; start the song and run again")` once `now()` is `cap_s` past the start. The cap is checked each time the finder sleeps, so a run can overshoot by one scan; the docstring says so. Tests in `test_engine_finder.py`: a fake scan that never finds a moving clock raises after the cap with the exact message (fake `now` and `sleep`); a fake that finds one inside the cap returns the address.

Step 3. `overlay_logs.py` is the one home of the two CSV column lists, as tuples, so the writers and the readers cannot drift:

- `WATCH_COLUMNS = ("wall_s", "clock_s", "score", "sp_amount_u32", "sp_amount_u64", "sp_max_u32", "sp_max_u64", "sp_active_byte", "sp_active_u32", "sp_mult_byte", "sp_mult_u32", "sp_end_s", "sp_overflow_u32", "hit_time_s")`, written by Task A's `sp_watch.py`.

### Task S: the Star Power comparison against Hydra (wave 2)

Owns new `tools/ch_probe/experiments/sp_compare.py` and new `tools/ch_probe/tests/test_sp_compare.py`. Pure logic, no process, no press log; it reads the watcher CSV (columns from `overlay_logs.WATCH_COLUMNS`) and the `hydra_replay score --path` JSON of the reference path. It uses each chord's `ms` as the time of the chord in the clock, so it works the same for an auto-player run and a bot run.

Options: `--resolution N` (read off the chart's `[Song]` section: `Resolution = 192` for Trippin), optional `--sp-bar-ticks N` (from `scorestats.json`), `--width 32|64` (which `sp_amount` and `sp_max` columns to read, default 32; the main session looks at the first rows of the CSV and passes the width that gives sensible numbers, and the write-up says which). It reads the flag from `sp_active_byte` and the multiplier from `sp_mult_u32`.

It prints each check as `PASS`/`FAIL` with the numbers:

- Phrase rises. Every chord with `is_sp_phrase_end` true is followed, within 100 ms of its `ms`, by a positive step of `sp_amount` between two consecutive rows. Each is printed with its size and classed `full`, `clamped` (the amount after the step equals `sp_max`; answer 37's clamp) or `missing`. A `missing` rise is a FAIL; `clamped` is not. The report says whether every `full` rise is the same number of ticks, what that is, and `sp_max / 4` beside it (the expected size if four phrases fill the meter).
- `sp_max` is constant over the run. It is printed beside Hydra's full meter for the chart, which is resolution x 4 quarters x `kMeasuresPerSpBar` (2) x `kCloneHeroSpCap` (4) = resolution x 32 (6,144 for Trippin), and beside `--sp-bar-ticks` when given. The meter is counted in measures, so the tick figure is exact only on 4/4 stretches (Trippin has one 2/4 measure at tick 768).
- Activations. Each time `sp_active_byte` goes 0 to 1, within 100 ms of that row: `sp_mult_u32` is twice the previous row's value (4 to 8, or whatever it was) and `sp_end_s` is a clock time ahead of the clock. At `sp_end_s`, within 100 ms, the flag returns to 0 and the multiplier halves. For each game activation the report also names the chord it landed on (the latest chord at or before the flip, within 150 ms) and whether that is the chord at an `act_tick` of the path. When it is, the report prints Hydra's deactivation ms (the `ms` of the chord at that activation's `deact_tick`) beside the game's `sp_end_s` and their difference. When it is not, the report prints both ticks as a separate FAIL line "activation not on the path's chord" and goes on; the field checks above are not affected.
- Multiplier at each chord. Around each chord's `ms`, the game's `sp_mult_u32` equals the chord's `multiplier` doubled when `in_sp` is true (`kStarPowerMultiplier` in `src/core/timing.h`), or the same for `multiplier_after`; one chord of lag is allowed because a 4 ms poll can land just before or after the chord is credited. The printed expected value is the doubled one: answer 222 says the score uses `[engine+0x48]` as the multiplier, so in Star Power the field should read 8 where the JSON's `multiplier` says 4. After the first activation that is not on the path, this check is not run for later chords and the report says so.

Tests in `test_sp_compare.py` on a small hand-written CSV and JSON: everything passes when phrase rises, activation, deactivation and multiplier line up; each of these fails: a missing rise, a flag that never sets, an end time that never clears, a multiplier that stays 4 (and one that reads 4 where the chord is `in_sp` with multiplier 4); an activation one fill early is reported as "not on the path's chord" while the field checks still pass; a `clamped` rise passes. Run `py -m unittest tools.ch_probe.tests.test_sp_compare`; report the pass count.

### Task B: the auto-player logs its presses; the score comparison (wave 2)

Step 1. `play_chart.py` opens the process read-only and finds the engine with the capped finder (exit 2 with the message on a timeout). The run ends on the frozen clock as today (5 s) or at 240 s of wall time, and prints the hit count, miss count and best streak as today.

### Task C: the checksum finder (wave 2)

Owns new `tools/ch_probe/experiments/find_checksum.py`, new `tools/ch_probe/il2cpp_strings.py`, new `tools/ch_probe/tests/test_find_checksum.py`. It does not touch `engine_finder.py`, `process.py` or `constants.py`; candidate offsets it finds go into its printed report and the write-up, not into `constants.py`.

Step 1. `il2cpp_strings.py`: pure helpers. `encode_forms(hash_hex)` returns the byte patterns to search for: the 16 raw bytes, the upper-case hex as UTF-16LE, the lower-case hex as UTF-16LE, and both as ASCII. `decode_il2cpp_string(raw)` reads an Il2Cpp `System.String` object (length as i32 at `+0x10`, UTF-16LE chars from `+0x14`) and returns the text or `None` when the length is absurd (over 1,024). Tests pin each form as a literal for the known hash `234C917654CC7257E2BAFCF7D761304B`.

Step 2. `find_checksum.py`: open read-only, `verify_targets`, find the live engine with the capped finder, then:

- Scan all committed read-write regions for every form of the chart's hash, given on the command line as `--hash`. The region walk is a copy of the 30-line walk in `engine_finder.scan_for_engine` (it calls `VirtualQueryEx` the same way), with a comment naming the original; nobody refactors `engine_finder.py` in Phase 0, and the duplication is listed under Out of scope. Print every hit: address, form, and the 32 bytes before it. Cap: one pass, which is the same cost as the engine scan.
- For each UTF-16 hit, work out the candidate `System.String` object address (hit minus `0x14`) and then look for a pointer to it: first in the engine object's first `0x400` bytes, then in every object the engine's pointer fields point to (one hop, each read as `0x400` bytes), then two hops. Cap: 2 hops and 4,096 objects read; when hit, print "pointer path not found within 2 hops" and still exit 0 with the direct hits listed. Each found path prints as `engine+0xAA -> +0xBB -> +0xCC = <string>`.
- Print how long the text scan took and how long the pointer walk took, and whether each ran while the clock was moving, frozen or stopped.
- Repeat the direct scan once more 10 s later and say whether the same addresses still hold the hash (a stable location is a weaker but still useful reader).

Step 3. Tests in `test_find_checksum.py`: the pointer walk over fake memory (a fake engine with a pointer to a fake object that points to a fake string) finds the two-hop path and reports the exact offsets; a fake with no path hits the cap and reports not found; hits at the region edge are not double-counted; a fake memory that moves the hash between passes reports "moved"; the process is opened read-only; a fake finder that never finds exits 2 with the message.
