## The plain version

Two things are wrong, and they are one bug seen from two sides. In the engine, a squeeze-in whose note sits exactly on the Star Power end is treated as needing no timing, while a squeeze-out on that same note is treated as needing 0.0 ms. That is D13, from 2026-10-03, a reviewer's call. The user was asked about it once, a day later, inside D51 question 4 (`docs/audit/2026-10-04-phase-7-questions.md` line 28: "A free squeeze is a squeeze-in at exactly the SP end; it needs no timing") and answered "all recommended" to the whole list (D51). The user now says: "0ms is not the same thing as no timing" and "i never asked for suqeeze ins to be treated differently for no reasons". This plan reverses that, so the new decision record names D51 question 4 as well as D13. Every screen that reads that answer then says something odd: the Paths tab tells you to hit the note "no more than 0.0 ms late" where the squeeze-out says "more than 0.0 ms late" (the user: "why does the squeeze in text say "no more than 0.0ms late" instead of "more than 0.0ms early" ??? who approved this text?? this makes no sense"), and the Path Builder's ending button read "no timing needed" for The Reaper's m91 ending.

Part A fixes the one answer at its one owner: a squeeze-in at offset 0 needs 0.0 ms, the same as the squeeze-out beside it. A squeeze-in already inside Star Power (a negative offset) still needs none. Nothing about where Star Power ends moves, and no score moves. Then every reader is checked: the badges, the hardest figure, the sentences, the report columns, the search, the all-0 list and the builder. The stored summaries hold the old answer. The user ruled that this is a display change and must not make the library read Stale ("nothing in the analysis is changing. only display text"; "the purpose of stale is when the underlying analysis changes"; to "Should the library save the engine's figure, so display changes never need Stale?": "yes that is what i have been asking for this whole time", 2026-10-31). So the saved row keeps the engine's own figure from now on, the "needs timing" rule is applied when the number is shown, and rows saved before this change get their figure back by replaying the saved path, not by re-analysis. The results stamp does not move.

Part B rebuilds the builder's steps panel the way the fourth page shows it. A step's row carries its span, its phrases and its squeezes in the Paths tab's badge words (`activation_badges`). The opened step shows only its endings, one line each, the kept one marked, and Remove. What a player sees change, all of it, so nothing is a surprise: the Paths tab's squeeze-in sentence at exactly 0.0 ms; the path button's "0.0 ms" for a path whose only timing is that squeeze-in; the report's Hardest ms and tier and its "No timing needed" filter, and the `squeeze` search, for the same paths; the Path Builder's violet limit note, only under a negative limit, and, for any limit, shown the moment a step opens and under the ending lines (it used to wait for the step's cost and sit under the sentence); the builder's step rows, opened step, ending lines, empty panel and the missing leftover line; the squeeze words in the builder's "Where to activate next" rows, in the fill card's "Hydra would end it at" line and in the step sentence (until B5 removes it), which now read the Paths tab's badge words ("squeeze out 130.4 ms", not "squeeze-out 130.4 ms" or "ending with a squeeze-out that needs 130.4 ms"), a squeeze inside Star Power with its figure ("squeeze in -130.4 ms", not "no timing") and an early fill when the badges list one; and, on the first open after the update, a progress step on the startup screen while saved paths are replayed, if the fill runs long enough for that screen to show (Q2 asks when, and its time on your library is not yet measured). ## Part A. Reverse D13: what the code does today, and what moves

### The owner

`SPSqueeze::needs_no_timing` (`src/core/model.h` line 383) answers "is this squeeze already done with no frontend timing". It reads `core::paid_by_sp_walk(offset_ms)` (`src/core/backend_value.h` line 30, `offset_ms <= 0.0`): a squeeze-in needs none when its note is at or before the end, a squeeze-out when its note is after it. That is D13 (`docs/audit/2026-10-03-fix-decisions.md` line 31). The squeeze's figure is `difficulty()` (line 369, through `squeeze_difficulty`, line 275: the offset for a squeeze-in, minus the offset for a squeeze-out), so at offset 0 both figures are 0.0 and only the yes/no differs.

The fill rule beside it already says what the user wants. `early_fill_needs_timing` (line 324) is "the fill's difficulty is 0.0 or more": zero slack counts as a timing. The new squeeze rule is the same sentence: a squeeze needs timing when its difficulty is 0.0 or more. One helper in `model.h`, `timing_needs_hitting(double difficulty_ms)` (`>= 0.0`), becomes the one home of "a timing of zero must still be hit", and both `early_fill_needs_timing` and `SPSqueeze::needs_no_timing` (which returns its negation) call it. `paid_by_sp_walk` is not touched and nothing else reads it differently: Star Power still ends at one point (the user on 2026-10-29: "there should never be two different answers for where star power ends. ever.", in `docs/agents/rulings/code-and-engine.md` on `main`). The search, the SP walk, the backend pricing and the scores do not read `needs_no_timing`, so no score moves. `tests/test_perf_digest.cpp` does not prove that on its own: its four engine digests fold the prepared record's summary, `hardest_ms` included (`tests/song_digest.h` line 180, `row_hash`), so they move whenever that column moves. A1's reviewer checked it the other way round: with `hardest_ms` left out of the digest, the four digests were identical under the old and the new logic, so the engine's own output (every path, every score, every all-0 path, through `record_hash`) did not move. A3 repins the four engine digests from one run and says so in their comment; the two parse digests and the two parse-count digests stay.

### Every reader, and what moves

Each reader was found by grepping `needs_no_timing`, `needs_timing`, `difficulty()`, `hardest`, `badge_timings` and `hardest_ms` over `src/`, `tests/` and `docs/`. Session cards and the audit ledgers were left out; they record history.

`Activation::badge_timings` (`src/core/model.cpp` line 497) lists every squeeze with `required = !needs_no_timing()`. A squeeze-in at 0 becomes required. Its badge text, "squeeze in 0.0 ms", is the same words as today (the badge always carried the figure, D80), so the Paths tab's row badge does not change; its colour does not either (`is_difficult` is false at 0.0).

`Activation::hardest` (line 503) weighs required squeezes only. A squeeze-in at 0 now takes part with 0.0 ms. ### Stored results

The stamp does not move. The user's ruling (2026-10-31, quoted in "The plain version") is that Stale is for a change in the analysis, and this is a change in display text that should read what the engine already knows. `src/store/stored_versions.h` (lines 42 to 51) today says the opposite for this case, in two places: the bump list ends "or what a summary row holds" (line 46), and the last sentence says "the summary columns (bestpath, score, stars, hardest_ms and the rest) are the analysis's own output, so a change that alters any of them is covered by this rule too" (lines 48 to 51). ADR 0018 (`docs/adr/0018-stored-data-has-one-set-of-version-stamps.md`) says the same twice, "or what a record holds" in its decision and in its consequences. A3 rewrites both comment places to the ruled rule: the stamp covers what a fresh analysis would compute differently (the engine, the scoring, the chart readers); a stored figure that this build can fill back in from the saved path is not a bump, and `hardest_ms` is the example. DOC-8 adds a dated note to ADR 0018 in the shape of its 2026-10-15 note ("stored failures did not move the stamp"), so the ADR and the header say one thing. The same header says nothing about layout: a new column is not a stamp matter. A file's layout is `classify_library_file`'s question (`src/store/library_file.h` line 20, `LibraryFileKind`), and the open adds what an older layout lacks in place (`add_album_column`, `add_failure_columns`, `record_store.cpp` lines 832 to 860) with no stamp and no Stale. This plan adds no column: `hardest_ms` keeps its name and its REAL type and changes meaning, and one `meta` row (the `meta` table, line 812) records that the one-time fill below has run, so an open never repeats it. A library file an older Hydra opens afterwards would write old-meaning rows and not know the row; that is the same exposure every in-place column add has today and is out of scope.

**Old rows, and whether replay can fill them.** A `record_paths` row holds `path` (the pathstring, "1 0+ 0 0"), `score`, `actcount`, `maxskip`, `hardest_ms`, `hardest_efill`, `avgmult`, `sqin_count`, `sqout_count` and `optimal` (`record_tables_sql`, line 262); the profile row it is filed under holds the chart mode, the SP cap, the lens (ms limit, depth, fill rule), the stamp and the rules fingerprint. No ticks are saved, so `hydra_replay score --path`'s way (a dump JSON with each window's `act_tick` and `deact_tick`, `core/replay.h` line 45) does not apply to a saved row as it is. What does apply is `paths_from_pathstring` (`src/search/pathstring_read.h` line 34): given the chart, the profile's search settings and the pathstring, it places each window in turn by trying the song's fills in chart order with the earlier windows pinned in full, through `search_target`, and returns the path with every activation's squeezes and `e_offset` stamped, so `SPSqueeze::difficulty()` and `e_difficulty()` read off it. It is a pinned search, not a walk with no search.

**Which old rows need it, and why no row needs a re-analysis.** A row saved before this change holds the largest timing that needed hitting under D13. That is the engine's raw figure whenever the row has one, because a figure of 0.0 or more exists only when something needed hitting, and the one timing D13 left out with a figure of 0.0 or more was a squeeze-in at exactly 0.0 (0.0 never beats a figure already saved). So a row with a saved figure shows the same before and after. A row with `hardest_ms` empty differs on screen only when it hides a squeeze-in at exactly 0.0, and that needs `sqin_count > 0`. SQL cannot see "exactly 0.0", so the query takes every row with `hardest_ms IS NULL AND sqin_count > 0`, and the replay settles it. Rows with an empty figure and no squeeze-in need nothing: if the engine's figure for them is negative (an E0 fill with slack), `shown_timing` shows none for it, as an empty column does today. On the corpus the rows that change on screen are few (13 of 97 charts carry a squeeze-in at exactly 0.0 on some path, 6 on their best path; "Measured on the corpus"). The rows the query takes are more, because a row whose only squeeze-ins are inside Star Power also has an empty figure and `sqin_count > 0`; its replayed figure is negative and shows as none, as before. How many rows that is on the corpus was not counted; A5 counts it.

**Whether replay is exact.** On the corpus, yes: `pathstring read: every corpus best path round-trips` (`tests/test_pathstring_read.cpp` line 62) reads back every kept path of every corpus chart, main search and all-0 pass, and checks the activation ticks, the text, the ends and the score are the saved path's (`path_identity`). The corpus is not the user's library. Two kept paths of one chart could print the same text and place differently, and the corpus has none. So the fill checks each replayed path against the row it fills: the replayed path's text, score, squeeze-in count and squeeze-out count must equal the row's, and a row that fails the check keeps its empty figure (it reads as it does today). That is a guard on an input the corpus does not show; it adds no rule the user must rule on.

**What it costs, as far as measured.** The same test, run on 2026-10-31 from the `pbr3-sc4b` worktree's build (`hydra_tests.exe "-tc=*every corpus best path round-trips*"`, 1,805 assertions, so about 450 paths over the 97 corpus charts), took 1.6 s in the planner's run and 1.4 s in the reviewer's re-run, process start included. That time also covers parsing and fully analysing all 97 charts, which the test does first (`corpus::analyzed`), so the replay alone is less than 3.5 ms a path. It was not timed on the user's library, which is far bigger: ADR 0026 counted 38,255 result rows in 2026-10. The fill therefore needs a progress bar and a stop, and RA-7 reads its real time on a copy of the user's database. Besides the replay, each candidate chart costs one parse, because the fill reads the chart from disk through the charts table's `path`.

**The design.** On the first open under this build, for each Ready row of the running settings' profile with `hardest_ms` NULL and `sqin_count > 0` whose chart file still gives its saved signature, replay the saved path with `paths_from_pathstring` under the running settings, check it as above, and write the engine's figure (`engine_hardest_ms`); a chart that is gone or changed, a text that is refused, or a row that fails the check keeps NULL (it reads "no timing" as it does today and the next analysis writes it); then write one `meta` row for that profile saying the fill has run. Only the running profile is filled, because the app can build the search settings for it (`Settings::to_analysis_settings`) and has no reverse from a stored cap and lens to settings (`Settings::with_chartmode` reverses the chart mode alone). A profile the user switches to later is filled at the next open, since the `meta` row is per profile. The store cannot do this alone: `hydra_store` links `hydra_core` and `hydra_search` and not `hydra_parse`, and `tests/test_layering.cpp` fails a file that includes a library its own library does not link (`CMakeLists.txt` lines 299 to 301 and 360 to 371). So the store answers two questions, which rows are candidates and writing the figures (A4), and the app does the reading and the replaying (A4b), on the open job's own thread, between the store opening and the library being read. The only cost the user has to weigh is the time at first open, and Q2 asks it.

### How an earlier step gets its endings: computed when opened

The user's design requirement, word for word: "the real app should only calculate paths as needed in real time. calculating and storing every possible path combination would be insanely inefficient for long tracks".

Two ways fit it. Keep the endings the step had when it was last (one small list per step, no new searches), or compute them when the step is opened (the same searches the last step costs today). This plan computes when opened. Why: the figures are the same either way. An ending's cost is its best finish with the windows before it pinned and nothing after, and the player builds left to right, so the windows before an earlier step cannot change without removing it; the list computed later is the list it had. Keeping would need a store that survives undo, redo, paste and "Finish the rest for me", where the endings were never computed, so those steps would have none to show; and `DecisionList::select` already does the computing for any row. The cost of one open is one `search_target` and one `best_finish` per ending, the same as opening the last step today, started only when the player opens the step, and nothing is stored past the current path (a new key clears it, as today). While the job runs the opened step shows its Remove button and no ending lines, as today's last step does; no new "pending" text is added.
