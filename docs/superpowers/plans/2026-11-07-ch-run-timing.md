# Why LS-O2 stalled: a quiet check, a recorder and two controlled runs (2026-11-07)

## The plain version

LS-O2 of `docs/superpowers/plans/2026-11-06-optimal-score-run.md` ran on Window Map on 2026-11-07 and hit 128 of 142. The first press reached chord 0 on time, so the chained start worked. What failed was the middle of the song: for about forty seconds the Python side stalled hundreds of times, the game's frames stretched from 3 ms to as much as 37 ms, and the song clock ran up to 127 ms ahead of wall time. Then everything settled and chords 104 to 141 all hit. Builds from other sessions were running during that stretch, and the file times they left show it: one build (`fx-10`) was compiling while the song played and a second (`fx-9`) was configuring, and the stalls stop within a second of the last object file of `fx-10` (row P17). But a test with many busy Python processes and no game gave far fewer stalls, and a file time shows when a file was written, not who held the CPU. So nobody has proved what did it.

The user said: "we need to understand why", "we need to understand every factor and account for every factor before our next run", and "why are you asking for a repeat? we already know it will fail". So this plan contains no bare repeat. Every run here changes one thing on purpose and records enough to say what happened.

Three things were approved ("Yes, plan them"), and this plan holds only those three:

1. A quiet-machine check before every launch. It lives in the `ch` server's worker, in `ch_start`, because that is the one place a game starts. It refuses the launch when a compiler is running, when the CPU is busy, or when a worktree build folder was written to in the last little while. Its numbers are questions 1 and 2.
2. A recorder for the run. An ETW trace (Windows' own event log of who held the CPU and the disk) runs beside the game, and the run's own files grow: the press rows go to a file as they happen, the Star Power watch learns the audio clock and the raw clock, and its status reports its own stalls. Each part's own cost is measured, because a recorder that slows the thing it watches spoils the result. WPR, the trace recorder, is on this machine but needs an elevated window, which only the user can open; that is question 3.
3. Two controlled runs on Window Map. Run A on a machine the check calls quiet. Run B with real builds started on purpose a few seconds after the song starts, as many as LS-O2 had if the user agrees (question 9). The recorder runs in both and starts before the game does. The outcomes section says what each pair of results means, including the one where A stalls too.

What this plan can and cannot show. The recorder sees the machine from outside: who held the CPU and the disk, and which threads sat ready but not running. It does not see inside the game. If the trace shows the game's own threads busy or waiting with no other process to blame, the plan can say "the slowdown is inside the game" and nothing finer. Unity's memory cleanup (its garbage collector, which frees unused memory in slices) is one thing that could be, and so is audio work or the game's own frame work. Telling them apart needs a hook inside the game, which this plan does not take and the user has not approved. If A shows that, the next step is a separate plan with its own approval, and question 10 asks the user to confirm that limit.

## Prior art, read on 2026-11-07

WPR and ETW. Microsoft's own walkthroughs run `wpr.exe -start <profile> -filemode` from an administrator prompt (`https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-av-performance-issues-with-wprui` and `https://learn.microsoft.com/en-us/windows/win32/tracelogging/tracelogging-record-and-display-tracelogging-events`), and the built-in profiles page (`https://learn.microsoft.com/windows-hardware/test/wpt/built-in-recording-profiles`) lists `GPU` as "GPU-specific events, such as GPU utilization". A Microsoft Q&A thread (`https://learn.microsoft.com/en-us/answers/questions/2280822/i-am-unable-to-start-windows-performance-recorder`) shows `wpr -start CPU` failing with "The requested resource is in use" when another trace session holds the loggers, and that stopping those needed elevation. None of the pages states the exact error an unelevated `wpr -start` gives, so whether it refuses here is row P13, settled by LS-T1. Converting a trace to text needs no elevation: `xperf -i <etl> -o <csv> -a dumper` and `tracerpt` both read a finished file. The `CPU` profile's own description is the one source for whether it records context-switch and ready-thread events (the events that say how long a thread sat ready but not running, and who ran instead); this plan did not read it and treats it as row P29 until LS-T1 reads a dump.

PresentMon. Intel's console app (`https://github.com/GameTechDev/PresentMon`, console README `README-ConsoleApplication.md`) records DXGI present events per process, selects a process with `--process_id`, writes a CSV with `--output_file`, and gives the frame interval as `MsBetweenPresents`. Its README names a `--restart_as_admin` flag and the Kaldaien fork says an unprivileged user needs the "Performance Log Users" group or gets "failed to start trace session (access denied)"; Intel's 2.3.1 notes (`https://www.kitguru.net/gaming/joao-silva/intel-presentmon-2-3-1-brings-new-gpu-telemetry-features`) say the service was reworked to run without administrator rights. It is not installed here, so it is question 4, not a task.

Unity's incremental collector. Unity's manual (`https://docs.unity3d.com/Manual/performance-incremental-garbage-collection.html`) says the time slice is a guideline of 3 ms by default, that a full collection can still run under memory pressure, and that GC work shows as spikes in the frame-time graph. The `gc-max-time-slice` key in `boot.config` is documented only by community pages (a gist, `https://gist.github.com/spongeyperson/869ed83f72d51b029bc41e62d906688a`, and a forum anecdote), so what the key does in this build is row P27, unchecked, and this plan does not change it.

## The design, point by point

### 1. The quiet check lives in the worker, at `ch_start`

A new module, `tools/ch_mcp/quiet.py`, owns one function, say `quiet_report(env)`, that returns the facts and one verdict. The facts: every running process whose name is in `COMPILER_NAMES` (`cl`, `link`, `MSBuild`, `cmake`, `ninja`, `clang-cl`, `lld-link`, `rc`, `mt`, `tsc`, `esbuild`), each with its pid and the worktree or folder its command line names; the CPU share averaged over `QUIET_SAMPLE_S` seconds read from the processor performance counter; every folder under `C:\Users\Patrick\Downloads\Hydra\hydra-test\.claude\worktrees\*\build-cpp\` and `C:\Users\Patrick\.claude\worktrees\*\` whose newest file is younger than `BUILD_RECENT_S`; free physical memory; the active power scheme; and whether `Spotify.exe` and `MsMpEng.exe` are running (reported, never a refusal). The verdict is quiet when no compiler runs, the CPU share is at or below `QUIET_CPU_PCT`, and no build folder is recent. The thresholds are constants at the top of the module, each with a comment naming this plan's question, and the numbers are the user's (questions 1 and 2).
`ch_start` calls it first, before `_new_scratch`, and refuses with the report when the verdict is not quiet: "refused: the machine is not quiet: <the lines>; hold the other sessions' builds and call ch_start again". A refused launch has taken no backup and made no folder. When quiet, the report's lines go into the reply anyway, so every run's `replies.txt` records what the machine looked like. The check runs once, in `ch_start`, and nowhere else. `ch_run_chart` gets no check: it promises no wait of its own before the first press (`game_tools.py` line 765), a sample there would add seconds before that press, and the running game would itself make the machine read busy. A build that starts after `ch_start` is caught by the trace, which records every process over the whole song. There is no argument to skip the check (question 6). Holding the other sessions is the user's job: the refusal names the processes and the worktree folders so the user knows which session to hold.

The sampling wait is a cap: `QUIET_SAMPLE_S` seconds, and the reply says how long it sampled. The check makes no change to the machine. In a recorded run the trace is already on when `ch_start` runs (design point 3), so the sample includes the recorder's own load; the trace reports that load as its cost line, and the number of question 1 is unchanged.

### 2. The recorder has four parts, each with its own cost line

**The ETW trace** is a script, `tools/ch_mcp/etw/record.ps1`, that runs `wpr -start CPU -start DiskIO -start FileIO -start GPU -start Audio -filemode` and, on `-Stop`, `wpr -stop <etl>`; then `xperf -i <etl> -o <csv> -a dumper` to text. Whether it must run elevated is row P13; question 3 asks the user to open one elevated PowerShell for a run and run the script there, because the worker cannot elevate itself and a scheduled task or a service is a machine change this plan does not take. A reader, `tools/ch_mcp/etw_check.py`, takes the text dump and a process id and prints: the trace's start and end wall times; CPU share per process name over the whole trace and over any window given as two wall times; disk and file bytes per process in the window; the present intervals (DXGI `Present` events) for the given pid as count, median, 99th percentile and the ten longest with their wall times; the audio glitch events with their times; and the trace's own cost: the CPU share of `wpr.exe` and the logger threads, which the trace records about itself. Share per process cannot say why a thread waited, so the reader also prints wait data for the worker's threads and the game's threads over the same window: how long each sat ready but not running (the context-switch and ready-thread events), how many times, the longest waits with their wall times, and for each long wait which process ran on that CPU instead. The reader also prints "the trace holds N events from process <pid>" as its first line, and refuses to go on when N is 0, because that is the "did we record the right process" check the ruling asks for. It prints "no wait data in this trace" and stops when the dump holds no context-switch or ready-thread events. Which text columns the dumper gives for presents, glitches and context switches, and whether the chosen profiles record the switch and ready-thread events at all, is row P29, settled by LS-T1 on this machine before the reader's tests are pinned to it. If they are not recorded, LS-T1 reports it, the profile list changes only with the user's yes, and the factors that rest on wait data stay unconfirmed in the report.

**The press log** always reaches a file. `ch_run_chart` gives its `_PlaySession` a `log_path` under the session folder (`press-<n>.csv`), the same way `ch_play_chart` does for a named `log`. `play_chords` already hands each row to an `on_press` (`play_chart.py` line 386); the session's own `on_press` (`game_tools.py` lines 1117 to 1119) also appends the row to that file as it is made, so a worker that dies mid-run keeps the rows so far. The write at the end of the play thread (`game_tools.py` lines 1129 to 1134) would then write the file a second time; it must not overwrite or double the rows, and T2's test pins that. Each row gains `wall_s_at_read` (the wall time just after `wait_until` returns, a few microseconds after the clock read that released the wait) and `wall_s_at_reply` (the wall time after the press returned).
