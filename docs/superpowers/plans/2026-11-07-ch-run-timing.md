# Why LS-O2 stalled: a quiet check, a machine recorder and two controlled runs (2026-11-07)

## The plain version

LS-O2 of `docs/superpowers/plans/2026-11-06-optimal-score-run.md` ran on Window Map on 2026-11-07 and hit 128 of 142. The first press reached chord 0 on time, so the chained start worked. What failed was the middle of the song: for about forty seconds the Python side stalled hundreds of times (370 gaps over 50 ms between the watch's samples), the song clock's step between two samples reached 272 ms, and the song clock ran up to 127 ms ahead of wall time (rows P36 and P52). Then everything settled and chords 104 to 141 all hit. Builds from other sessions were running during that stretch, and the file times they left show it: one build (`fx-10`) was compiling while the song played and a second (`fx-9`) was configuring, and the stalls stop within a second of the last object file of `fx-10` (row P17). But a test with many busy Python processes and no game gave far fewer stalls, and a file time shows when a file was written, not who held the CPU. So nobody has proved what did it.

The user said: "we need to understand why", "we need to understand every factor and account for every factor before our next run", and "why are you asking for a repeat? we already know it will fail". So this plan contains no bare repeat. Every run here changes one thing on purpose and records enough to say what happened.

Three things were approved ("Yes, plan them"), and this plan holds only those three:

1. A quiet-machine check before every launch. It lives in the `ch` server's worker, in `ch_start`, because that is the one place a game starts. It refuses the launch when a compiler is running, when the CPU is busy, or when a worktree build folder was written to in the last little while. Its numbers are questions 1 and 2. Merged (T1).
2. A recorder for the run. A small separate process, the machine recorder, runs beside the game. `ch_start` starts it by itself, so nobody opens anything, and it needs no administrator rights: it reads the process table the way Task Manager does and reads the game's clock from memory the way the Star Power watch already does. It writes CSV files into the run's session folder, and a reader prints a report from them. The run's own files grow too: the press rows go to a file as they happen (T2, merged), the Star Power watch reads the audio clock and the raw clock (T4, merged), and its status reports its own stalls (T5, merged). Each part's own cost is measured, because a recorder that slows the thing it watches spoils the result. The first design used a Windows trace (WPR) instead, which turned out to need an elevated window; the user refused that on 2026-11-07 ("i dont accept that you need an elevated run. figure out another solutio."), and refused PresentMon too ("proceed without it for now"). So: no elevated window, no trace, no PresentMon, no install and no change to the machine.
3. Two controlled runs on Window Map. Run A on a machine the check calls quiet. Run B with real builds started on purpose a few seconds after the song starts, as many as LS-O2 had if the user agrees (question 9). The recorder runs in both. The outcomes section says what each pair of results means, including the one where A stalls too. Run A ran on 2026-11-07 and hit 142 of 142, but it was not quiet and the recorder's cost line failed; "What Run A showed" below holds the result, and the user said "plan run b" (row P73). Run B is reworked below so it loads the stretch where LS-O2 failed, song seconds 3 to 39, and questions 20 to 25 settled its open points.

Why a second process is the point. The worker (the `ch` server's Python process) is one of the suspects, so it cannot be the only witness. The recorder keeps its own pace. If the worker's watch shows a gap while the recorder's samples kept coming and the game's clock kept stepping, the stall was in the worker's Python. If the recorder's samples stop too, the machine or the game stalled everything. If the recorder stayed steady but the game's clock stopped stepping for a while, the game slowed. The three records line up on one wall clock (`time.time`).

What this plan can and cannot show. The recorder sees the machine from outside, in slices: at each sample it reads how much CPU every process has used so far, and for the game's and the worker's threads whether each was running, ready but not running, or waiting. A stall shorter than one sample can be missed. "Who ran instead" becomes "who used CPU in that slice", not which process took that exact CPU at that exact moment. The game's side comes from one number per pair of samples, the excess: how much the song clock gained minus how much wall time passed between the two samples (design point 2, "The clock's excess"). A late sample alone leaves the excess near zero, because the clock and the wall both advanced by the late gap; a clock that stood still or jumped shows as a negative or positive excess. So the recorder cannot show single frames, and a stall shorter than a sample can be missed. There are no audio glitch events, so the audio row of the factors table rests on the watch's clock columns. Disk use is read per process, not per file, and whether a thread was waiting on the disk cannot be read. It does not see inside the game. If the game's own threads were busy or waiting with no other process using the CPU, the plan can say "the slowdown is inside the game" and nothing finer. Unity's memory cleanup (its garbage collector, which frees unused memory in slices) is one thing that could be, and so is audio work or the game's own frame work. Telling them apart needs a hook inside the game, which this plan does not take and the user has not approved. If A shows that, the next step is a separate plan with its own approval, and question 10 asks the user to confirm that limit.

The recorder is also one more thing running. It is a Python process that reads the whole process table 50 times a second and the game's clock once each time, in a study of stalls, and nothing in this plan proves that costs the game or the worker nothing (row P54, unchecked). Its budget (question 15) limits its own CPU, not its effect on others: one call walks every process and thread, and whether that holds a kernel lock a game thread needs is not known. The plan has no unrecorded control run: LS-O2 had no recorder and stalled under builds, and every run from here has one (question 13). So Run A passing says the game passes with the recorder on, and Run A stalling cannot be put down to the machine until the recorder's own part is read first (the outcomes of design point 3). The recorder also reads the game's clock only from the moment the worker sends the engine's address, which is after the attach, kit setup and watch steps. In LS-O2 the watch's first row read song clock 1.336 s (row P53), so the clock column starts at about song second 1.3, about 1.7 s before the first press at 3.0 s; the process rows run from the recorder's start.

## Prior art, read on 2026-11-07

The process table. Geoff Chappell's reference pages for `SYSTEM_PROCESS_INFORMATION` (`https://geoffchappell.com/studies/windows/km/ntoskrnl/api/ex/sysinfo/process.htm`) and `SYSTEM_THREAD_INFORMATION` (`https://geoffchappell.com/studies/windows/km/ntoskrnl/api/ex/sysinfo/thread.htm`) give the 64-bit layout `NtQuerySystemInformation` returns for information class 5: a 0x100-byte process entry with `NextEntryOffset` at 0x00, `NumberOfThreads` at 0x04, `UserTime` at 0x28, `KernelTime` at 0x30, `ImageName` at 0x38, `UniqueProcessId` at 0x50, `InheritedFromUniqueProcessId` at 0x58, `PageFaultCount` at 0x80, `ReadTransferCount` at 0xE8 and `WriteTransferCount` at 0xF0, followed by one 0x50-byte thread entry per thread with `ClientId` at 0x28 (its second member, `UniqueThread`, at 0x30), `ContextSwitches` at 0x40, `ThreadState` at 0x44 and `WaitReason` at 0x48. Those are the offsets the main session's probe used (process entry 256 bytes, times at +40 and +48, pid at +80; thread entry 80 bytes, tid at +48, context switches at +64, state at +68, wait reason at +72), so the probe and the reference agree. The thread page lists `ClientId` as one member, so the thread id's 0x30 is the standard `CLIENT_ID` layout (process id, then thread id), not a line of the page; the probe's +48 agrees with it. The parent process id at 0x58 was not read by the probe, so it rests on the page alone until LS-T1. The page gives `HardFaultCount` only for 32-bit (0x10) and says it exists from Windows 7 on; the 64-bit position is row P44, unchecked. The page does not say which `ThreadState` number is which; the probe read 1 as ready, 2 as running and 5 as waiting, which is the kernel's `KTHREAD_STATE` order, and LS-T1 checks it the simple way: the recorder's own sampling thread must read as 2 when it samples. A gist on the same API (`https://gist.github.com/TheWover/71079af504ba8e056c9ebbe017d288a0`) notes that only the "full" variant of the class needs administrator rights; the plain class 5 answered unelevated here (row P39). The API is undocumented and Microsoft says it may change; this plan pins the offsets in one place with a test that reads a fixture built from them.

Keeping a child alive only as long as its parent. Raymond Chen's "Destroying all child processes (and grandchildren) when the parent exits" (`https://devblogs.microsoft.com/oldnewthing/?p=2433`) describes the Windows job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which the kernel enforces when the parent dies, and .NET's `KillOnParentExit` uses it. Its known pitfall, noted in Rust's bootstrap (`job.rs`) and in the Aspire CLI's `WindowsConsoleProcessJob.cs`, is that a process already inside a job may not be able to put its child in a new one; Claude Code starts the front, which starts the worker, and nobody has read whether that tree sits in a job. So this plan does not use a job object. It uses the other common pattern: the child opens a handle to its parent's pid and waits on it, and exits when the parent is gone. That needs no rights beyond `SYNCHRONIZE` on a process of the same user, which `_PidProcess` in `tools/ch_mcp/bot_run.py` (line 307) already asks for on the game. The two together, a stdin that the parent closes to say stop and a parent handle to notice a crash, are the same two the front already uses on the worker (`front.py` lines 244 to 259) and the recorder copies them.

Unity's incremental collector. Unity's manual (`https://docs.unity3d.com/Manual/performance-incremental-garbage-collection.html`) says the time slice is a guideline of 3 ms by default, that a full collection can still run under memory pressure, and that GC work shows as spikes in the frame-time graph. The `gc-max-time-slice` key in `boot.config` is documented only by community pages (a gist, `https://gist.github.com/spongeyperson/869ed83f72d51b029bc41e62d906688a`, and a forum anecdote), so what the key does in this build is row P27, unchecked, and this plan does not change it.

## The design, point by point

### 1. The quiet check lives in the worker, at `ch_start` (T1, merged)

A module, `tools/ch_mcp/quiet.py`, owns one function, `quiet_report(env)`, that returns the facts and one verdict. The facts: every running process whose name is in `COMPILER_NAMES`, each with its pid and the worktree or folder its command line names; the CPU share averaged over `QUIET_SAMPLE_S` seconds read from the processor performance counter; every build folder whose newest file is younger than `BUILD_RECENT_S`; free physical memory; the active power scheme; and whether `Spotify.exe` and `MsMpEng.exe` are running (reported, never a refusal). The verdict is quiet when no compiler runs, the CPU share is at or below `QUIET_CPU_PCT`, and no build folder is recent. The thresholds are constants at the top of the module, and the numbers are the user's (questions 1 and 2; the changes of the "Changed during the build" paragraph in the Questions section apply).
`ch_start` calls it first, before `_new_scratch`, and refuses with the report when the verdict is not quiet. A refused launch has taken no backup and made no folder. When quiet, the report's lines go into the reply anyway, so every run's `replies.txt` records what the machine looked like. The check runs once, in `ch_start`, and nowhere else. `ch_run_chart` gets no check: it promises no wait of its own before the first press, a sample there would add seconds before that press, and the running game would itself make the machine read busy. A build that starts after `ch_start` is caught by the recorder, which records every process over the whole song. There is no argument to skip the check (question 6). Holding the other sessions is the user's job: the refusal names the processes and the worktree folders so the user knows which session to hold.

The sampling wait is a cap: `QUIET_SAMPLE_S` seconds, and the reply says how long it sampled. The check makes no change to the machine. The recorder starts after the check has returned (design point 2), so the sample never includes the recorder's own load, and the number of question 1 is unchanged.

### 2. The recorder has four parts, each with its own cost line

**The machine recorder** is a new script, `tools/ch_mcp/machine_recorder.py`, that runs as its own process beside the game, started by the worker and never by hand in a game run. It needs no rights an ordinary process of the same user lacks: no elevated window, no trace session, no install. It writes three CSV files into a folder `machine-<n>\` under the run's session folder, sharing one sample number.

What it does at each sample, `RATE_PER_S` times a second (question 12): one `NtQuerySystemInformation` call for the whole process table, through `ctypes` as `quiet.py` already calls PDH; for every process, its name, pid, parent pid (`InheritedFromUniqueProcessId`), and the CPU time (user plus kernel), read bytes, write bytes and hard-fault count it has gained since the previous sample; for the game's, the worker's and its own threads, each thread's state, wait reason, context switches gained and CPU gained; and one 8-byte read of the game's song clock at `engine + OFF_SONG_CLOCK`, through `access_mask(read_only=True)` and `make_reader` from `tools/ch_probe/process.py`, the exact rights the watch uses. It stamps each sample with `time.time`, the clock the watch's `wall_s` and the press log's two wall columns use, so the three records line up. To keep the files small it writes a process row only when that process gained CPU, bytes or faults in the slice, and a thread row only when the thread was not waiting or its context switches moved; the game, the worker and the recorder itself always get their process rows, so their shares are complete. `samples.csv` has one row per sample: the sample number, `wall_s`, the time the sample itself took, how many processes and threads the table held, how many threads of the whole table read as ready (the machine's run queue), and `clock_s` or empty before the engine is known. `processes.csv` and `threads.csv` carry the rows above with the sample number first. The offsets of the process table live in one place at the top of the module, each with the reference page named, and a test reads a fixture buffer built from them (row P38).

Each sample's rows are written to the three files and flushed together, so a terminated recorder loses at most one sample and `samples_line()` never reads a half line. A clock read that fails (the engine is gone after the song, or the game ended) leaves `clock_s` empty for that sample and the recorder goes on. Its first stdout line names its own pid and folder, so a hand run knows which row is its own, and the last row of `samples.csv` also holds its own `time.process_time()`, the one independent figure LS-T1 checks the table's CPU offsets against.

**The clock's excess.** The recorder does not read frame times. For two consecutive samples that each have a clock reading it computes the clock's gain, the wall gain (the difference of the two `wall_s`) and the excess, gain minus wall gain. A sample the recorder took late moves both gains by the same amount and leaves the excess near zero, so the reader judges the game by the excess and not by the step; row P52 shows the step alone cannot tell the two apart. A game whose clock stops advancing for a while gives a negative excess in the pair that covers it, and a clock that catches up gives a positive one.

How it learns what to record. It is started with the session folder, the worker's pid (`os.getpid()` in the worker), the rate and its caps as arguments. It learns the game's pid and the engine's address on its stdin, as one line each: `pid <n>` when `ch_start` has the `Run` (a few hundred milliseconds after the launch), and `engine <hex>` when `ch_run_chart`'s watch step has the address. Until the `pid` line it records every process and no threads; until the `engine` line it leaves `clock_s` empty. Nothing else crosses from the worker. So the worker never writes the recorder's files, the recorder never reads the worker's, and a worker that stalls after the two lines changes nothing the recorder does. In a run with no `ch_run_chart` (a bot run, a menu run) the clock column stays empty and the report says "no clock in this recording". For a run by hand with no worker, `--target <pid>` stands in for the `pid` line and `--seconds <n>` for the stop; LS-T1 uses both.

How it ends, so nothing is left running. Three ways, any one of which ends it. First, the worker closes its stdin: the recorder sees the end of its input, writes its last rows and exits; `ch_stop` and the worker's own `shutdown` do this through `_stop_all`, waiting up to `RECORDER_EXIT_CAP_S` and then terminating it (question 18), the same shape the front uses on the worker. Second, the worker is gone: the recorder holds a `SYNCHRONIZE` handle on the worker's pid from its first second and a thread waits on it; when the worker dies, by a crash or by the front's terminate after a hung reload (which reaches the Python behind the `py` launcher, `test_front.py` line 828), the recorder exits within a second even though no worker code ran. Third, its own cap: the run cap plus `RECORDER_CAP_EXTRA_S` (question 18), after which it exits on its own and says so in its last row, so a recorder can never outlive a run by more than that. `ch_reload` cannot orphan it: the game side lists it in `open_lines` ("machine recorder: running, pid N"), and `reload_refusal` already refuses while that list is not empty, so the user calls `ch_stop` first and the stop ends the recorder. The pid it records as the game's is also checked at the end of the recording against `ch_stop`'s `game process id`; the reader refuses a recording with no thread rows for the pid it is asked about, which is the "did we record the right process" check the ruling on captures asks for. A recorder never harms a run: `send` writes one line and never waits, and a write error (the recorder is gone) is one line in the reply, not an exception; `stop` closes stdin on its own thread, as `front.py`'s `_end` does because "a close waits behind a write a hung worker never reads", waits `RECORDER_EXIT_CAP_S`, then terminates, and is safe to call twice; a launch that fails after the recorder started (`SongLengthMissing`, `LaunchFailed`, `OSError`) stops it before `ch_start` returns, and a second `start` stops one still running from before; a recorder that exits by itself drops out of `open_lines`, so a dead recorder never blocks a reload, and its exit is a line in the next reply.

What it costs, and where that shows. Its own process row is in every sample, so the report prints its CPU share over the run from the same table it reads for everyone else, and its write bytes beside the size of its own files. The sample's own duration is in `samples.csv`, and gaps between its samples over `GAP_MS` (the watch's threshold, question 7, reused so the two are comparable) are counted by the reader as the recorder's own stalls. The budget is question 15; LS-T1 fails when the recorder's share passes it. It is Python because Python is what every other tool here is, the measured walk is well under one core, `psutil` is not installed and a native helper would need a build step for one loop; if LS-T1 shows the budget missed, the fallback is a lower rate first (question 12's other side in reverse) and a native helper only as a new question.
