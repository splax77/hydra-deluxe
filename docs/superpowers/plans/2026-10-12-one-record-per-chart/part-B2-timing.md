## The short version

Hydra counts measures one way today, from the last measure line before each time signature change, and Clone Hero counts them two ways. Its beat-line grid starts again where a change takes effect, and its Star Power drain counts measures continuously, cutting at each change's own tick. So Hydra gets two measure owners, both built from the chart's time signature list: a grid (where the measure lines are, used by the measure lines, the position text and generated fills) and a continuous count (how many measures lie between two ticks, used by Star Power's end). Generated fills then start on the measure line as Clone Hero's do, with Clone Hero's one-tick-wider distance limit and its first candidate. Section names come from Clone Hero's own list. `hydra_replay`'s dump prints positions as the screen does. Scores move only where Star Power crosses a mid-measure change or a generated fill's deadline moves, so the results stamp is bumped and the user sees the list of changed charts before merge.

## What Clone Hero does, from the disassembly

Each rule below names the function it was read from. The `.ann` files in the evidence folder are the disassembly with data-slot labels; there are no prose notes in the folder, so I read the instructions myself. The main session had already checked the six addresses in the handoff's table.

**The beat-line grid (0x20DACA0, `f20daca0.ann`).** It walks from tick 0 to the chart's end in steps. At every step tick it looks up the time signature entry with the latest tick at or before the step tick, by binary search over the chart's list (lines 65 to 101 of the file; at tick 0 it takes the first entry). A step is a measure line when it is the first step, or when the entry's numerator or denominator differs from the entry used at the previous step (lines 107 to 119: it compares the values, so a second entry with the same values changes nothing), or when the beats counted since the last measure line reach the numerator (lines 129 to 135). Otherwise it is a beat line (kind 1), or a weak beat (kind 2) when the denominator is above 4 and the beat index is not a multiple of denominator/4 (lines 138 to 147). The step after each line is `trunc(resolution * K / denominator)` ticks, where K is the double at data slot 0x3065BC0 (lines 185 to 192); the spec and the main session read K as 4.0, and I could not re-read the DLL's bytes (the `rdd.py` helper points at a scratchpad folder from session 28fad19c, which still exists, but running it is outside my brief). So in 6/8 the grid steps every eighth note and a measure line falls every 6 steps. A change that lands between two steps is first seen at the next step, which becomes the measure line; the grid does not add a line at the change's own tick.

**The fill generator (0x20D2B30, `f20d2b30.ann`).** It reads the grid's measure-line list (the list at +0x20 of the object 0x20DACA0 filled, handed in as the third argument). The distance limit is `trunc(resolution * 0.5) + 1` ticks (lines 66 to 72: the multiply by the double at slot 0x3063FB0, read as 0.5 by the scout, then `inc rax` at 0x20D2C91). It starts at measure-line index 1, the second line (line 71, `mov ebx, 1`). For each line it asks 0x5DDB50 for the chord nearest the line's tick, searching onward from the last chord it looked at (line 103); -1 means no chord. If the chord is farther than the limit, the next candidate is the next line (lines 184 to 188, net `ebx += 1`). Otherwise the fill's start tick is the line's tick (line 168, `[rdi+0x28] = rbp`, where rbp is the line tick), its length is chord tick minus line tick (lines 169 to 173), the chord gets the fill flag (line 135), and the next candidate is the line four further on (line 182, `add ebx, 4`). I could not read 0x5DDB50, so whether "nearest" looks at chords before the line as well as after is not proven; the scout's Python copy (`sim.py`) used the absolute distance either way with ties to the later chord, which is what `Song::check_activations` does today, and it found no fill moving to another chord on `testdata/input`.

**The deadline (0x20DDB70, `drums.ann` lines 887 to 955).** When the Star Power meter crosses half (lines 895 to 900) and SP is not active (line 901), every fill whose start tick is at or below the current tick plus `[+0x300]` loses its flag (the compare at 0x20DDC20, the clear at 0x20DDC33). `[+0x300]` is `resolution << 2` (`ctor.ann` line 68), 4 quarter notes in every meter. Only the fill's start tick counts, so a generated fill's deadline is 4 quarter notes before its measure line.

**The Star Power drain (0x20D3FC0 and 0x20D2930).** Neither function is in the evidence folder or in the older scratchpad folder, and no file there mentions those addresses, so I could not re-check the CH-sp-grid scout's reading. The plan copies the rule as the spec states it (section 9, item 3, which the main session checked against the post-pass constants): Star Power drains continuously, 3.75 × resolution units per measure at the local measure's length, over a list of tempo and time signature entries placed at each change's own tick, and one phrase is worth round(resolution × 7.5) units, so one phrase lasts exactly 2 measures (`kMeasuresPerSpBar`). The thing that moves Hydra's numbers is only this: a partial measure before a mid-measure change counts as its share of the old measure's length, where Hydra's `plusmeasure` re-measures it at the new length.

**The section-name list (0x2095040, `section_table.tsv`).** 2,718 rows of `key<TAB>shown name`, keys lower case with underscores (for example `aco_gtr_intro` → `Acoustic Guitar Intro`). The spec's rule, checked by the main session: strip `section ` or `prc_`, look the rest up, and a miss only turns underscores into spaces.

What it builds, in order.

`SongTiming` takes a fourth argument, the chart's time signatures `std::map<int64_t, std::pair<int,int>>` (`Song::timesig_changes`), and `Song::build_timing` passes it. The three-argument constructor goes, because a ticks-per-measure map alone cannot give the grid its beat step (1680 ticks at resolution 480 is 7/8, not 3.5 quarter notes). Every `SongTiming st(480, tpm, bpm)` in `tests/test_timing.cpp` gets its signature map (1920 → 4/4, 1680 → 7/8, 840 → 7/16, 960 → 2/4, 1440 → 3/4 unless the test says 6/8). The constructor checks the two maps have the same keys and throws `std::out_of_range` otherwise, as it does for a missing tick-0 entry today.

`MeasureIndex` becomes the grid. From the signature map and the resolution it builds spans. Each span has a restart tick, a numerator, a beat step of `trunc(resolution × 4 / denominator)` ticks (Clone Hero's step; K read as 4.0 above), a measure length of numerator × step, and the number of measure lines before it. The first span restarts at tick 0. A later signature entry whose numerator and denominator both equal the previous span's is skipped (Clone Hero compares values). Otherwise its span restarts at the first beat of the previous span at or after the entry's tick: `prev.restart + ceil((entry.tick - prev.restart) / prev.step) × prev.step`. The measure lines in the previous span are `ceil((restart - prev.restart) / prev.length)`, so a cut-short measure still counts as one. `span_at(tick)` is the last span whose restart is at or before the tick (a tick exactly on a restart belongs to the new span, which is what makes the label and the position agree there). The accessors are renamed to spans: `span_at`, `restart_at`, `step_at`, `numerator_at`, `length_at`, `lines_before_at`, `count`. A tick's measure, beat and tick come from one function on the grid, `at(tick)` returning the three numbers: measure = lines_before + rel / length, beat = (rel mod length) / step, tick = rel mod step, where rel = tick - restart. One grid walker, `MeasureIndex::walk(last_tick, fn)`, calls fn(tick, kind) for every grid line from 0 to last_tick with kind measure line, beat, or weak beat exactly as 0x20DACA0 decides it; B2-2's `build_beat_events` and `Timecode` both read the grid through this class, so the "mid-measure change restarts the measure" wording becomes true of the code and the old comment goes with the old loop. The grid's measure length may differ from `apply_timesig`'s ticks per measure only when `resolution × 4 / denominator` is not whole (resolution 25 in 7/8, say), which no real chart has; the header comment says so.

`MeasureCount` is new: the continuous count. One span per signature entry at the entry's own tick, with `apply_timesig`'s ticks per measure (`tpm_changes`, the same keys), and the measures elapsed at each span's start as the running sum of `(next_tick - tick) / tpm` in doubles. `measures_at(double tick)` and `tick_at(double measures)` are today's `measures_at_tick_f` and `tick_at_measures_f` moved onto these spans; `sp_end_ms` composes them as before; `ms_per_measure_at` reads this class's span at the tick (a tick on a change reads the new span, as the test at `test_timing.cpp` line 111 already expects).

`Timecode` keeps both: `measure_beats_ticks()` from the grid and `measures_decimal()` from the continuous count. `plusmeasure` walks the continuous spans in whole numbers: from the start tick, if `add × tpm` fits before the next change the end is `tick + add × tpm`; otherwise the remainder of measures is carried as a fraction (numerator and denominator reduced by gcd each span) and the end in the last span is `change_tick + remainder × tpm` truncated to a whole tick, as today's `plusmeasure` truncates its partial. So a Star Power stretch that crosses no change ends exactly where it does today up to today's double rounding (see question 1), and one that crosses a mid-measure change ends where Clone Hero's drain empties. `extend_deacts` and `add_act_edge` in `src/search/graph.cpp` (lines 296 to 318 and 376 to 395) call `plusmeasure` and need no edit.

The lookups: `SongTiming::tempo_at(tick)` returns the BPM in force (the `MsIndex` span, a tick on a change reads the new tempo, the rule `tps_at` already has) and `SongTiming::time_signature_at(tick)` returns the grid span's numerator and denominator. Both are the one place these questions are answered; B2-2 makes the info box call them. Sections are not in `SongTiming` (the `.mid` reader fills `practice_sections` after `build_timing`, `song.cpp` lines 1202 to 1215), so the section lookup is a free helper in `timing.h`, `last_at_or_before(first, last, tick, tick_of)`, the one `upper_bound` that `tempo_at`, `MsIndex`, the grid and the section search all use. This is the one departure from the spec's letter ("on SongTiming" for all three); the reason is the parse order.

## Questions for the user

1. `plusmeasure` arithmetic. The recommended walk uses whole numbers and reduced fractions, so a Star Power stretch inside one time signature ends at exactly `start + measures × ticks_per_measure`. Today's code gets there through doubles (`measures_decimal`, `timing.cpp` lines 169 to 194) and can land one tick early in rare cases. The score check lists any chart where that one tick changes a score. Accept the exact walk (recommended), or require bit-identical ends outside mid-measure crossings by keeping today's double path for stretches that cross no change?

2. A chord that sits before its measure line, inside the limit. Clone Hero's generator gives such a fill a start on the line and a negative length. Recommended: Hydra stores `activation_length = chord tick - line tick`, which may be 0 or negative for a generated fill, the deadline math reads the line as today, the Preview draws the fill from the earlier of the two ticks to the chord, and `test_song_parse.cpp`'s invariant becomes "an authored fill's length is never negative, a generated fill's may be". The alternative is to refuse chords before the line, which is a rule Clone Hero's code does not have as far as the evidence shows (0x5DDB50 unread).

3. The release version for the stamp (B2-6): "2.8.0" if this ships as the next release after v2.7.0 (memory `concept-audit-2026-10`), or whatever the release is called.

4. Clone Hero draws a weak beat (kind 2) on the off-beats of 6/8 and similar meters. Draw them with the same texture as a beat line (recommended, no new asset), or add a third, fainter kind?

5. `video-tools\replay.py` line 213 reads the dump's old `measure`/`beat`/`tick` numbers. Who edits that one line in the video-tools repo (you, or a follow-up session), and should the dump keep the three old numbers beside `label` for a release so old video-tools runs keep working?

6. The grid's beat step copies Clone Hero's `trunc(resolution × 4 / denominator)` exactly, so a chart with a resolution that is not a multiple of denominator/4 (resolution 25 in 7/8, say) gets a grid measure a few ticks shorter than `apply_timesig`'s ticks per measure. No corpus chart does this. Copy Clone Hero (recommended) or round?
