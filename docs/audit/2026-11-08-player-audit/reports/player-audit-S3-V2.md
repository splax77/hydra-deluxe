### F3-3: squeeze activation lead, two formulas
Verdict: CONFIRMED (by reading).
Python `_solve_lead` (play_chart.py 379-428): lead = need/ratio + ACT_LEAD_MARGIN_MS, where need = end + 15 - chord.ms - side (squeeze-out) or chord.ms + 15 - end - side (squeeze-in), refuses when lead > side_act - 6, raises when `end.anchor_index != act.index` (399-404). C++ `equal_room_lead_ms` (replay_schedule.cpp 238-247): out: (side_a - side_s + gap + 15)/(1+r) + 6; in: (side_a - side_s + gap + 15 - 6 - 3r)/(1+r); `anchor_lead_ms` (277-327) refuses below 2 ms; anchors on the squeeze's own anchor chord.
Input where they differ: a squeeze-out with side_a = side_s = 85.72, chord-to-end gap 130 ms, r = 1: Python need = 130 + 15 - 85.72 = 59.28, lead 65.28; C++ lead = (0 + 130 + 15)/2 + 6 = 78.5. Anchor not equal to the activation chord: Python raises, C++ plans it.
Plan stance: freak-fixes/replay plan says the C++ is the intended rule; user quote "Yes, start it" (handoff ruling list) covers the freak-fixes answers, "yes revise the plan" the replay plan.
Handoff open questions that I verified in code: `anchor_lead_ms` refuses a lead < kPressLeadMs (lines 303-308) and `sqin_fallback_before_ms` is chord - side + 15 + kJudgeEarlyMs (line 339-341), i.e. +18, as the handoff says.
