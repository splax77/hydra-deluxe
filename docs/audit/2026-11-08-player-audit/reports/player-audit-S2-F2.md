## Part A. How a run is judged: the chain of numbers

Plain version. Four different pieces say "pass" or "fail", and none of them looks at the others or at the same file.
1. play_chart / game_tools say "sent N, hit H, misses N-H" (game_tools.py:1534-1535). N counts non-declined, non-dropped chord messages. H counts messages after which the score rose 5 ms later.
2. score_compare.py (press log vs Hydra score JSON) says PASS/FAIL on the running score difference and on a 98 percent hit rate.
3. compare_scorestats.py (the game's scorestats.json vs Hydra score JSON) says pass/fail per line; this is the only judge that reads the game's own final stats.
4. sp_compare.py (sp_watch CSV vs score JSON) says PASS/FAIL on Star Power events.
Nothing ties these four to one run: each is handed two paths by hand, and no script checks that the files belong to the same song, path, or run (J1).

### J1. No file in the judging chain checks it is judging the same song/run (kinds 1, 6)
Homes: compare_scorestats.py:81-134, game_tools.py:860-871 (ch_compare), score_compare.py:313-322, sp_tools.py:286-312 (ch_sp_compare).
What each does: ch_compare takes any stats path and any score JSON. The stats file carries `checksum`, `song_name`, `playback_speed`, `no_fail`, `modifiers`, `instrument`, `difficulty`, `game_mode` (proven by ls-m2-run1/scorestats-...json: `"checksum": "AF44D5C8...", "playback_speed": 100, "no_fail": true, "modifiers": ["DoubleKick"]`). The score JSON carries `chart` (path of notes.mid), `chartmode`, `path_source`, `warnings`. I searched tools/**/*.py for `checksum`, `song_name`, `chartmode`, `["warnings"]`, `playback_speed`, `no_fail`, `modifiers`: no judging script reads any of them (only unrelated find_checksum.py and test_compare_db.py hit). 
Table: stats of song A vs score of song B -> total_notes, score lines FAIL by count mismatch (loud, but only by coincidence of counts); stats from a 75 percent speed run -> the score differs, FAIL, no word about speed; stats from an earlier attempt -> bot_run._poll_stats (bot_run.py:446-471) takes any change of scorestats.json after launch, names the copy by the launch folder slug (not the song in the file).

### J2. ch_compare "pass" lines are chart facts, not play results (kind 6)
Home: compare_scorestats.py:94-120.
`total_notes` is compared with Hydra's gem or chord count (chart size, not notes hit); `sp_phrases_total` with Hydra's phrase-end chords (chart size, not phrases earned); `sp_activations` is a count only (not times); `accent_notes_hit`/`ghost_notes_hit` are real play results. `notes_hit`, `sp_phrases_earned`, `excess_hits`, `end_streak`, `max_streak` are never compared.
Proven by ls-m2-run1: stats say `notes_hit 3753` of `total_notes 3767` (14 notes not hit), `sp_phrases_earned 30` of 31; the tool's lines "total_notes: pass", "sp_phrases_total: pass", "sp_activations: pass" all print pass; only `score` FAILs (replies.txt line 2). The facts "notes_hit 3753 of 3767; sp_phrases_earned 30 of 31" appear only in the session's own replies.txt, not in any tool output.
Table: all notes hit but SP end 3.5 s early -> activations "9=9 pass", score FAIL. Declined chords (by design not pressed) -> notes_hit < total_notes, no line says so; score FAIL is the only trace, and cannot tell "declined on purpose" from "missed".
`activation 2: game end 163483 ms vs Hydra deact 167027 ms` is in replies.txt (human-written); ch_compare's sp_activations line has no times.

### J3. score_compare.py cannot pass a run that has order-split chords or declined chords (kind 6, 5)
Home: score_compare.py:167-197 (compare_scores), 216-231 (credited_hits), 234-251 (hit_rate_line); play_chart.py:1163-1204 (rows).
Proven by running score_compare.py over ls-m2-run1/press-2.csv with kick-prep/who score JSON: "Score at 2150 presses: 1834 equal, 0 lagged, 39 changed at a ghost or accent chord, 277 failed. FAIL score at chord index 3: game 495, Hydra 695 (difference -200 ...) ... Final: game 1051655, Hydra 1143035 ... PASS hit rate 99.6% (2141 of 2150)", exit 1. The same script over ls-m0-run1/press-1.csv with the Ahab score JSON: 1478 equal, 0 failed, PASS hit rate 100.0 percent, exit 0.
Causes by reading plus rows:
- A chord split in order groups gets one score read after the whole message (play_chart.py:1145-1146), and every row of the chord holds that same `score_before`, `score_after` and `hit` (docstring 1029-1030). Chord 3 in press-2.csv is two rows, both `445 -> 495 hit=1`, the second with blank down_frame; the +200 for the second group is not in the next row's score_before either (chord 4 starts at 495). So the comparison sees -200 at chord 3. The "lagged" rule (score_compare.py:186) only recognises a whole-chord lag, not a one-group lag.
- All 13 split-chord rows after the first row in that log are copies: `hit=1` on a row whose press the game may not have scored. A missed second group would still print hit=1 (copied from the first group's rise). Proven by press-2.csv: 13 duplicated indexes, 12 of the second rows have blank down_frame/up_frame/down_ms/scored_between (the reply had no `groups` entry for them; see J5), and index 1893 is the only split chord whose second row has its own score (933845->934045).
- Rows with `hit` = `declined` or `dropped` are counted as presses and as misses (score_compare.py:120 `row["hit"] == "1"`; 247 `n_hit * 100 >= 98 * n`). A run that declines 2 percent of chords fails the hit rate by design; the 9 declined chords in ls-m2-run1 are 0.4 percent so it passed.
- n counts rows, not chords: 2150 rows for 2137 chords.
- The end-of-solo bonus (12,100 in this run) is never in the last row's score_after: final difference -91,380 = -79,280 (stats gap 1,143,035 - 1,063,755) - 12,100. Final line prints "game 1051655" next to scorestats band_score 1063755 without saying why.
Split: score_compare's "game score at the last press" (1,051,655) vs compare_scorestats's `score` (1,063,755) vs Hydra final.total (1,143,035): three numbers for "the score", two of them for the same game run. Open for a live run: why chord 3's second group shows no points (a real miss, or a read before the credit).

### J4. The score check absorbs a miss on any ghost or accent chord (kind 6)
Home: score_compare.py:186-194.
`elif chord.ghost_or_accent or change_may_show: status = "ghost_accent"; running = difference`. Any change of the difference at a chord that has a ghost or accent gem, or on the chord after a lagged one, is not a FAIL, whatever its size; the module docstring gives the reason (keyboard presses carry no strike velocity). The kit route presses with axis values, so the reason may no longer hold; the rule is unchanged for kit runs. Table: a chord with an accent gem missed entirely (-500) -> status ghost_accent, no FAIL; hit column 0 for that row would count against the 98 percent only. The hit rate allows 2 percent misses (MIN_HIT_PERCENT 98, score_compare.py:64): a 100-chord run with 2 misses prints PASS.
Edge: n_hit*100 >= 98*n: 49 of 50 passes (98.0 percent exact), 48 of 50 fails.

### J5. The press log's reply columns are blank for later order groups and nothing flags it (kinds 2, 7)
Home: play_chart.py:1165-1190 (previous agent's C8/C17 cover the code); evidence here is new.
Proven by press-2.csv: 12 of 13 second-group rows have empty `down_frame`, `up_frame`, `down_ms`, `up_ms`, `scored_between`. kit.ts:651-656 does write a `groups` array when a press has more than one group, so the blanks come from the Python side, not the agent: `replies = pressed["groups"]` is used only `if replies and later and isinstance(pressed.get("groups"), list)` (play_chart.py:1166). Which of these is true cannot be told from the code alone: (a) the real reply had `groups` and the rows lost it, or (b) the reply was a dict whose `groups` had fewer entries. By reading, kit.ts:652 always sends one entry per group, so (a) or an off-by-one at `k < len(replies)`. Open: read kit-1.jsonl / a fresh reply from a live split chord. Row 1893 (the only split row with a second down_frame, 131764) shows the second group did get a reply entry there.

### J6. sp_compare passes on the game's own consistency, not on the path's times (kind 6)
Home: sp_compare.py:439-546 (_check_activation, _check_activations), 554-601, 404-421.
- "activation N on the path's chord" is a `report.check(True, ...)` whenever the flip lands within 150 ms of the path's chord; the end difference `difference {end_ms - deact['ms']:+.1f} ms` is printed in the text but is never a check (sp_compare.py:525-534). In ls-m2-run1, activation 2 ended 3,544 ms before Hydra's deactivation (replies.txt); a PASS line carries that number inside it.
- "flag clears at the end" compares the game's flag drop against the game's own `sp_end_s` (sp_compare.py:470-478), within 100 ms: it checks the game against itself.
- Phrase-rise check (sp_compare.py:360-390): any rise in the window counts, any size; "Full rises: not all the same" is only a note (396-401).
- sp_max constant: a check only that the column does not change.
- Multiplier check (554-601): accepts the expected value of chords i-1, i, i+1 (three chords of slack), stops at the first activation that parts from the path, and skips chords with no watcher row; with every chord skipped it prints "PASS ... 0 of 0 chords match" (sp_compare.py:594-596: `fails == 0` -> PASS, no minimum compared).
- Logs without the clock columns load with `clock_s` NaN (sp_compare.py:166): `t < lo` and `t > hi` are both False for NaN, so the phrase-rise search takes the first unused rise whatever its time and passes it. By reading; no run has such a log.
Table: path activations 0, game made 0 -> no activation line at all, no check; the report can end "Summary: N PASS, 0 FAIL" with nothing about activations.
