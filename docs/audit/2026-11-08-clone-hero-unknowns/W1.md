# W1, chart files: results (task CH-UNK-W1)

How callers were found. The `rea` MCP tools were not offered to this agent: a ToolSearch for them returned no tools. The Ghidra decompile holds only 987 functions and none of the callers below, so its text search found nothing. Instead a short script scanned every E8 (direct call) instruction in the DLL's `il2cpp` and `.text` sections for the target RVAs, using `tools/ch_mcp/chdis.py`'s `Image` for the sections and method names. Every caller named below is "direct callers only (byte scan of call instructions)": a call made through a pointer or a virtual slot is missed. The script was a scratch file and is not committed.

Listings were made with `tools/ch_mcp/chdis.py` run by `C:\Python314\python.exe` without `-I`, because `py` has no capstone and `-I` hides the user site-packages that hold it. The new listings' facts were not rowed into `facts-6142.tsv`, because this round's brief forbids editing that file.

## CR-03

- Unknown was: whether the game's .srb reader reads the layout the bytes show (16-byte header, four DEFLATE streams, encrypted audio).
- Looked at: the direct-call scan for `0x214EFD0` (one caller, at 0x2B868A in the method at 0x2B84A0); new listings `docs/clone-hero/code/6142/srb_reader_2B84A0.asm`, `srb_inflate_2E0A10.asm` and `srb_stem_ctor_1F2550.asm`.
- Found: the reader maps the file and skips a 16-byte header (srb_reader_2B84A0.md, lines 88 to 113). It inflates the song info from offset 16 with a raw DeflateStream (lines 130 to 172; srb_inflate_2E0A10.md), then the chart stream right after it (lines 350 to 404). It then passes over a run of bytes whose sizes it read from the song info (lines 405 to 417); the images sit there. It does not inflate those bytes in this method. After them, it cuts the audio section into one stem per counted item, each starting with a 32-byte entry header (lines 418 to 478; srb_stem_ctor_1F2550.md). So the header, the two DEFLATE streams before the images, and the audio section are proven in the game's code. That the two image blobs are DEFLATE streams is not shown here: the constructor only passes over them.
- Proposed label: Proven in the game's code for the 16-byte header, song info and chart as DEFLATE, the image run, then the stems. The image streams' encoding stays as the bytes show it. The page executor may split the sentence or keep the block Unknown for that part.
- Hydra: agrees on the order. Hydra skips the 16 bytes (`kSrbHeaderSize` in src/parse/srb.h line 43) and inflates from there (src/parse/srb.cpp line 192). One small difference: the game takes the song-info stream's stored length from the header, while Hydra inflates from offset 16 until the stream ends. On a valid file both read the same bytes, so this is no visible difference.

## CR-05

- Unknown was: which header bytes the game passes into the two header functions.
- Looked at: `docs/clone-hero/code/6142/srb_reader_2B84A0.asm` lines 88 to 116.
- Found: the game reads bytes 0 to 7 as a little-endian u64, then byte-swaps each 32-bit half and swaps the halves (lines 91 to 95 and 107 to 110). The result is bytes 0 to 7 read big-endian. It reads bytes 8 to 15 as a little-endian u64 (lines 99 to 102). It calls the decoder `0x214EFD0` with bytes 8 to 15 first and the big-endian bytes 0 to 7 second (line 113). The result is the number of bytes of the song-info stream that follow the header (lines 114 to 116 and 156 to 160). A count larger than the file makes the reader leave. The encoder `0x214F0A0` has no direct caller in the DLL.
- Proposed label: Proven in the game's code. The session's reading holds: bytes 0 to 7 are the key, read big-endian, and bytes 8 to 15 are the scrambled size, read little-endian. Add one word to the block: the size is the song-info stream's stored length.
- Hydra: no owner. Hydra skips the 16 bytes (src/parse/srb.h line 43) and never decodes them.

So Hydra does not test the version. DIFFERS (possible): a .srb whose version is not 20210228 is refused by the game's reader at this step, while Hydra reads it. For example, a bundle with version 20210228 is read by both, and a bundle with version 20200101 is read by Hydra and dropped by the game's reader. None of the 30 shipped bundles is known to have another version. What the game shows for a refused bundle is not read, because the exit at 0x2B8D8B was not followed.

## CR-24 (second pass)

- Unknown was: what the coda and _ENDOFSONG branches of the .mid events reader store.
- Looked at: docs/audit/note-shuffle/step0/open1/midi_events_track_21544E0.asm lines 98 to 388 (the whole text loop); dump.cs lines 540570 to 540582 (class #8500) and lines 543380 to 543490 (the song class, its fields at +0x100 and +0x108 and the methods `0x212C350` and `0x212E310`).
- Found: each events-track text is trimmed and tested in this order. If it starts with `[section` (lines 99 to 128) and the untrimmed text does not contain `_ENDOFSONG` (lines 129 to 136), it becomes a section name (lines 137 to 189). Otherwise, if it starts with `[prc` (lines 190 to 216), it becomes a section the same way (lines 329 to 384). Otherwise, if it equals `[end]` (lines 217 to 243), the reader calls the song's method `0x212E310` with the event's tick (lines 319 to 324). Otherwise, if it equals `[coda]` (lines 244 to 270) or `coda` (lines 271 to 297), both lead to the same code (lines 298 to 314). That code makes an object of class #8500, whose constructor takes a name and a tick, with the name `coda` and the event's tick, and stores it in the song's field at +0x100, but only when that field is still empty (line 300 and 301). So only the first coda event counts. Any other text is skipped (line 297 jumps to the loop's next step). So `_ENDOFSONG` has no branch of its own: it only stops a `[section ...]` text that contains it from being a section, and that text then falls through to the `[prc`, `[end]` and coda tests. The block's "any text containing _ENDOFSONG" is wider than the code: the test runs only on texts that start with `[section`. Who reads the coda object at +0x100 later was not searched; its getters are short shared stubs (RVAs 0x71920 and 0x718A0 in dump.cs line 543450 to 543458) that a byte scan cannot tie to this field.
- Proposed label: Proven in the game's code for what each branch stores: the first `coda` or `[coda]` text stores a "coda" marker with its tick on the song, `[end]` calls the song's end method with its tick, and `_ENDOFSONG` only vetoes a `[section` text. What the game does with the coda marker afterwards stays Unknown (searched: the events listing only).
- Hydra: no owner. A grep of src/ for `coda` and `ENDOFSONG` finds nothing (re-run 2026-11-08). Whether Hydra reads `[end]` was not checked in this pass.
