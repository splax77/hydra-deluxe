# W1, chart files: results (task CH-UNK-W1)

How callers were found. The `rea` MCP tools were not offered to this agent: a ToolSearch for them returned no tools. The Ghidra decompile holds only 987 functions and none of the callers below, so its text search found nothing. Instead a short script scanned every E8 (direct call) instruction in the DLL's `il2cpp` and `.text` sections for the target RVAs, using `tools/ch_mcp/chdis.py`'s `Image` for the sections and method names. Every caller named below is "direct callers only (byte scan of call instructions)": a call made through a pointer or a virtual slot is missed. The script was a scratch file and is not committed.

Listings were made with `tools/ch_mcp/chdis.py` run by `C:\Python314\python.exe` without `-I`, because `py` has no capstone and `-I` hides the user site-packages that hold it. The new listings' facts were not rowed into `facts-6142.tsv`, because this round's brief forbids editing that file.

## CR-03

- Unknown was: whether the game's .srb reader reads the layout the bytes show (16-byte header, four DEFLATE streams, encrypted audio).
- Looked at: the direct-call scan for `0x214EFD0` (one caller, at 0x2B868A in the method at 0x2B84A0); new listings `docs/clone-hero/code/6142/srb_reader_2B84A0.asm`, `srb_inflate_2E0A10.asm` and `srb_stem_ctor_1F2550.asm`.
- Found: the reader maps the file and skips a 16-byte header (srb_reader_2B84A0.md, lines 88 to 113). It inflates the song info from offset 16 with a raw DeflateStream (lines 130 to 172; srb_inflate_2E0A10.md), then the chart stream right after it (lines 350 to 404). It then passes over a run of bytes whose sizes it read from the song info (lines 405 to 417); the images sit there. It does not inflate those bytes in this method. After them, it cuts the audio section into one stem per counted item, each starting with a 32-byte entry header (lines 418 to 478; srb_stem_ctor_1F2550.md). So the header, the two DEFLATE streams before the images, and the audio section are proven in the game's code. That the two image blobs are DEFLATE streams is not shown here: the constructor only passes over them.
- Proposed label: Proven in the game's code for the 16-byte header, song info and chart as DEFLATE, the image run, then the stems. The image streams' encoding stays as the bytes show it. The page executor may split the sentence or keep the block Unknown for that part.
- Hydra: agrees on the order. Hydra skips the 16 bytes (`kSrbHeaderSize` in src/parse/srb.h line 43) and inflates from there (src/parse/srb.cpp line 192). One small difference: the game takes the song-info stream's stored length from the header, while Hydra inflates from offset 16 until the stream ends. On a valid file both read the same bytes, so this is no visible difference.

## CR-05

- Unknown was: which header bytes the game passes into the two header functions.
- Looked at: `docs/clone-hero/code/6142/srb_reader_2B84A0.asm` lines 88 to 116.
- Found: the game reads bytes 0 to 7 as a little-endian u64, then byte-swaps each 32-bit half and swaps the halves (lines 91 to 95 and 107 to 110). The result is bytes 0 to 7 read big-endian. It reads bytes 8 to 15 as a little-endian u64 (lines 99 to 102). It calls the decoder `0x214EFD0` with bytes 8 to 15 first and the big-endian bytes 0 to 7 second (line 113). The result is the number of bytes of the song-info stream that follow the header (lines 114 to 116 and 156 to 160). A count larger than the file makes the reader leave. The encoder `0x214F0A0` has no direct caller in the DLL.
- Proposed label: Proven in the game's code. The session's reading holds: bytes 0 to 7 are the key, read big-endian, and bytes 8 to 15 are the scrambled size, read little-endian. Add one word to the block: the size is the song-info stream's stored length.
- Hydra: no owner. Hydra skips the 16 bytes (src/parse/srb.h line 43) and never decodes them.

## CR-07

- Unknown was: whether the audio is AES-128-CFB with the swapped-halves IV.
- Looked at: the direct-call scan for `0x215AFE0`, which found four callers, all in class #1448: 0x333790, 0x333AB0, 0x333E80 and 0x334750. New listings `docs/clone-hero/code/6142/aes_key_user_333790.asm`, `srb_stem_ctor_1F2550.asm`, `srb_stem_read_1F2260.asm` and `srb_stem_iv_1F2060.asm`. Class #811's and #248's method lists in `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\6142\dump.cs` lines 44130 to 44179 and 15750 to 15794.
- Found: the stem entry header holds the two 64-bit IV fields at bytes 8 and 16 (srb_stem_ctor_1F2550.md, lines 58 to 61). Class #1448 builds an expanded key from the AES key builder with an S-box lookup and a round constant: the shape of an AES key expansion (aes_key_user_333790.md). The stem's read method xors each stored byte with a byte of a 16-byte block (srb_stem_read_1F2260.md, lines 66 to 89). It refills the block through a method of class #1448 (srb_stem_iv_1F2060.md). That refill is fed either stored bytes from earlier in the stem or, at the start, a buffer built from the field at +0x60 first and then +0x58. The block cipher's output xored with the ciphertext, with the earlier ciphertext as the next input, is the shape of CFB, and +0x60 before +0x58 fits "halves swapped". But several immediates and displacements in these three methods decode to odd values: both IV stores show `[rdi]` with no offset, the position is doubled, and the loop bound reads 0x50. So the block size, where each IV half lands, and the round count cannot be read off these listings. The block cipher at 0x334620 was not listed.
- Proposed label: Unknown. The CFB shape and the IV fields are found. The mode and the swap are not proven, because the listings' odd encodings stop a byte-exact reading. Next step: list 0x334620 and 0x1F1D50, and read the obfuscated encodings (the brief gave no time for that).
- Hydra: the decryptor beside `kSrbAesKey` in src/app/preview_source.cpp (AES-128-CFB, comment at line 45). Nothing found contradicts it.

## CR-51

- Unknown was: the rest of the song-info layout and the audio table, and the version constant 20210228.
- Looked at: `docs/clone-hero/code/6142/srb_reader_2B84A0.asm` lines 176 to 478 and `srb_stem_ctor_1F2550.asm` lines 54 to 94. The call at line 189 (0x1CF270), which reads the text fields, difficulties, preview, length and checksum, was not listed.
- Found: the first u32 of the inflated song info is compared with 0x1346234 (20210228), and any other value makes the reader leave (lines 176 to 182). So the game refuses another version at this step. What the shared exit at 0x2B8D8B does next was not followed. After the fields that 0x1CF270 reads, the reader reads, in order:
  - a u64 chart size (lines 190 to 198);
  - a u32 stem count, capped by the length of a BassAudioManager array (lines 201 to 207);
  - a flag byte (lines 208 to 214);
  - a u32 image count of at most 0x10000 (lines 217 to 223);
  - a u32 when the flag has bit 2, and another when it has bit 1 (lines 224 to 241);
  - one u64 image size per image (lines 242 to 270);
  - two arrays of one u64 per stem (lines 279 to 349).

  The second array is each stem's size, used to cut the audio section in order (lines 418 to 478). The first array's use was not read; the block calls it the offsets. Each audio entry is a u32 stem type at byte 0, four unread bytes, a u64 at byte 8 and one at byte 16 (the IV halves), and a u64 size at byte 24 with its top bit cleared. The entry is 32 bytes, and an entry whose size plus 32 overruns the stem throws "size too small" (srb_stem_ctor_1F2550.md). The block's field list matches this. Two details it lacks are the bit-2 and bit-1 extra words and the cap of 0x10000. The block's "image count and indices" fits the count plus the two flag-gated words. The text fields, difficulty order, preview, icon, playlist and album track, length and checksum come from 0x1CF270 and were not read. The stem-type names (0 guitar to 13 crowd) and the alphabetical order were not read in code.
- Proposed label: Proven in the game's code for the version check and everything from the chart size to the audio entry. Unknown for the part 0x1CF270 reads and for the stem-type names. The page executor may split the block.
- Hydra: `srb_parse_metadata` in src/parse/srb.cpp line 136 reads up to the checksum. src/parse/srb.h line 18 names the version only in a comment, and a grep of src/ for `20210228` and `0x1346234` finds nothing else. So Hydra does not test the version. DIFFERS (possible): a .srb whose version is not 20210228 is refused by the game's reader at this step, while Hydra reads it. For example, a bundle with version 20210228 is read by both, and a bundle with version 20200101 is read by Hydra and dropped by the game's reader. None of the 30 shipped bundles is known to have another version. What the game shows for a refused bundle is not read, because the exit at 0x2B8D8B was not followed.
