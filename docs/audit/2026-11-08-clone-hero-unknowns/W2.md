## CR-35

Done in the second round (task CH-UNK-W2b). - Unknown was: whether a note on the `soloend` tick is inside the solo, and whether the plus-1 length is the whole reason, from how the score code reads a solo record.
- Looked at: new listings `docs/clone-hero/code/6142/solo_records_20D1ED0.asm`, `engine_solo_reader_20F62C0.asm` and `engine_solo_count_20F7610.asm`; the committed `solo_flags_20D18F0.asm`; the two note tests at RVAs 0x214B630 and 0x214B7D0 (three instructions each, printed by chdis and quoted below); dump.cs lines 528225 to 528248 (the note-list struct), 529509 to 529529 (the chart solo record, class #8284), 529952 to 530001 (the engine base class #8288), 530367 to 530376 (the built solo record, class #8291) and 551859 (the track's solo list at +0x78). The scan looked for every reference to the 23 metadata slots that name the chart solo type and the 7 that name the built solo type.
- Found: the score code never reads the chart's solo list. Its only readers outside the chart loaders are the flag step 0x20D18F0 (CR-37) and 0x20D1ED0. The rest of the hits are the loaders that fill or copy the list (0x20CF1B0, 0x213CAF0, 0x213DD40, 0x2155050, 0x2156990, 0x20E39A0, 0x20E3CF0, 0x215FFC0), the track's own constructor, copy and Dispose methods, and a writer to a Stream at 0x20E25F0. Two hits fall inside runtime code (0x2EFBB4C and 0x3038B29) and look like chance byte matches; they were not read. 0x20D1ED0 builds a second list, of class #8291, that goes into the note-list struct at +0x20. It walks the track's solo list (listing lines 99 to 124), but then decides membership from the note flags, not from the ticks. The test at 0x214B630 is `test dword ptr [rcx + 0x7c], 0x200` (SoloBegin) and the test at 0x214B7D0 is `test dword ptr [rcx + 0x7c], 0x400` (SoloEnd). Lines 167 to 174 start the count at the first note with SoloBegin. Lines 177 to 184 add the current note to the count unless 0x214BCC0 is true for it. Lines 195 to 200 then stop at the first note with SoloEnd, after that note was counted. Lines 201 to 227 store the count at +0x10, the first note's time and tick, and the span to the last note's end. The engine (class #8288) reads only this built list. 0x20F62C0 copies the record's note count to engine +0x16C when a solo starts (listing lines 17 to 23). 0x20F7610 ends it: when engine +0x164 is at least 50 (line 25), it computes ((hit / total) - 0.5) x 2 x hit x 10, rounds it with 0x182C49A60 (a function the dump does not name), multiplies by 10 and adds it to engine +0xA0 (lines 28 to 50). Here hit is +0x168 and total is +0x16C. So the score code reads the note count, and the note count comes from the flags that CR-37's rule sets. With the .chart length of end minus start plus 1 (CR-34), a note on the `soloend` tick is at a tick below start plus length, so it gets the flag and is counted. The plus-1 length is the whole reason: the score side adds no tick test of its own. Not traced: what +0x164 and +0x168 hold (the 50 test reads like a hit percentage), which code adds to them, what 0x214BCC0 tests, and how nested .chart solos (Q-11) come out of the flag step.
- Proposed label: Proven in the game's code. The two readers of the built solo list were found by the reference scan and read whole, and the only path from the chart's solo list to them goes through the note flags.
- Hydra: agrees. Hydra ends a .chart solo after the tick's notes, so a note on the `soloend` tick is in the solo (src/parse/song.cpp lines 1642 to 1645, pinned by the test the comment names). Nested solos stay the open split Q-11; this round adds no new DIFFERS.
