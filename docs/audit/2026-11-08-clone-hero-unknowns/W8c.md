- Looked at: the two file names in `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\6142\stringliteral.json` (lines 83291 and 83327, slots 0x3CFF2E0 and 0x3CFF3A0). New listings: `docs/clone-hero/code/6142/fast_logger_setup_213040.asm`, `log_file_sink_ctor_2158F60.asm`, `log_file_sink_write_2158DF0.asm` and `log_writer_2128F10.asm`, each with its `.md`. In `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\6142\dump.cs` I read class 897 (lines 48597 to 48609), the Unity logger class 981 (lines 52193 onward), the log entry class 8248 (lines 527038 to 527050), the tagged logger struct 8422 (lines 536787 onward), the logger class 8495 (lines 539670 to 540330), the file sink class 8639 (lines 551015 to 551068), the level enum 8680 (lines 553271 to 553280) and GameInit.PreUnityInit (line 38597). I also checked `script.json` for `ScriptMetadataMethod` entries and `stringliteral.json` for the writer's name.
- Found: the game makes both files itself, at start-up, and then writes to them only log lines carrying one tag. GameInit.PreUnityInit calls 0x213040 with no test in front of it (`call` at 0x1646f0). That method's only check is whether it already ran (`fast_logger_setup_213040.asm` lines 55 to 63). It makes the `Logs` folder (lines 196 to 218) and adds three log targets at level 4, which is Trace, the most detailed level (lines 239, 259 and 279). Two of those targets are file sinks. One goes to `HitDetection-Standard.log` with the tag `GuitarEngine` (line 248), the other to `HitDetection-Validation.log` with the tag `GuitarEngineValidator` (line 268). The sink's write method writes an entry only when the entry's tag string (entry +0x40) is exactly the sink's tag, compared ordinally (`log_file_sink_write_2158DF0.asm` lines 27 to 42). That tag is the fifth argument of the logger's writer (`log_writer_2128F10.asm` lines 93 and 94).

  Unity's own `Debug.Log` does not reach these files. Line 165 of the setup sets Unity's logger to class 981, and class 981's Log methods hand the line to Unity's `Internal_Log` through a stored delegate (0x22e2ca in the method at 0x22E1D0). They never call the game's writer.

  Nothing in the shipped build seems to make a tagged entry. Every public log method of the logger (class 8495) and of its tagged struct (class 8422) carries `[Conditional("ENABLE_LOGGING")]` in `dump.cs`, for example line 539686. The C# compiler drops every call to such a method unless the calling code was built with that symbol. Direct callers only (byte scan): no call or jump reaches the writers 0x2128F10 and 0x2128B70, the dispatch method 0x2128770, or any method of class 8495 with a real address, except 0x2129740 (adding a target, called only by 0x213040) and two methods with no log arguments, 0x2129CE0 and 0x212A610, reached from GlobalVariables.Awake and GlobalVariables.OnApplicationQuit. The struct's methods and the writer copy at 0x2111950 are called only from inside the logger and from unnamed code after the last named method (0x2C7E1ED to 0x2F00DD2). What that unnamed code is, and whether anything reaches it, was not read. The struct's factory, 0x18D8C10, shares its code with five other methods in `dump.cs` (for example `ParticleSystem.get_emission`), so its 60-odd callers do not show the logger in use. The only pointer to each writer is its entry in the `.data` method pointer table, which every method has. `ScriptMetadataMethod` holds no entry for them, and `stringliteral.json` does not hold the writer's name.
- Proposed label: Proven in the game's code, for a reworded rule: "The game makes both files at start-up (GameInit.PreUnityInit, 0x213040) and writes to each only log entries tagged `GuitarEngine` or `GuitarEngineValidator`. No setting is read on the way." The listings above show every step of that. The block's open question was whether a setting fills the files. The answer that the shipped build never makes a tagged entry rests on the `Conditional` attribute and a byte scan, so it should stay worded as "no caller found (byte scan)". It should not be stated as proven until the unnamed code at 0x2C7E1ED to 0x2F00DD2 is read. The live check in `live-checks.md` (IN-44) is still the way to show the files stay empty in a real run.
- Hydra: no owner. Hydra never reads these files.

## IN-55

The caller scans are `docs/audit/2026-11-08-clone-hero-unknowns/W8c/xref.py`, a byte scan for `call`/`jmp` rel32 and RIP-relative references, so every caller list is direct callers only (byte scan); its IN-55 output is `W8c/xref_IN-55.out.txt`.

- Looked at: the literal `scoredata.bin` in `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\6142\stringliteral.json` (lines 16787 and 16788, slot 0x3CA8678), and its neighbours `scoredata_backup.bin`, `scoredata_corrupted_{0}.bin`, `scores.bin` and `scoresext.bin` (lines 16819 to 16979). New listings under `docs/clone-hero/code/6142/`: `score_store_paths_2F4300.asm`, `score_store_write_2F57C0.asm`, `score_chart_write_2167B0.asm`, `score_chart_write_216FA0.asm`, `score_entry_write_2BAB60.asm`, `score_chart_add_2161E0.asm`, `score_entry_merge_2BA4F0.asm` and `song_entry_add_score_358560.asm`. I also surveyed, without committing listings, the other score store methods 0x2F4EC0, 0x2F4510, 0x2F5EF0, 0x2F6170, 0x2F7250, 0x2F7830, 0x2F5A40, 0x2F5640, 0x2F5250, 0x2F6A60, 0x2F4790, 0x2F3A50, 0x2F74D0 and 0x2F7B40 for `File`, `BinaryWriter` and `BinaryReader` calls. For route (c) I looked for `scoredata.bin` copies under `C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-mcp-runs\` (none found by a recursive search for `scoredata*.bin`, nor any `backup-*` folder there) and in the tools' backup folders `%TEMP%\ch_live_*\backup-*` (19 copies, every one 80 bytes and dated 2026-10-28 20:45). No after-run copy of the file is kept anywhere I searched (a search of the `ch_live_*` folders for any other file with `score` in its name found only `scorestats` JSON files). `W8c/read_scoredata.py` reads a file in the writer's layout; its output for the live file and one backup is `W8c/read_scoredata.out.txt`.
- Found: the game's writer settles the layout. `scoredata.bin`'s path is set by 0x2F4300 (`score_store_paths_2F4300.asm` lines 22 to 41). The writer 0x2F57C0 opens that path (`score_store_write_2F57C0.asm` lines 30 to 46), writes the 32-bit version 20211009 (lines 55 to 57), the number of chart records (lines 63 to 66), then each record through 0x2167B0 (lines 67 to 90). A record is a 16-byte chart hash (`score_chart_write_2167B0.asm` lines 36 to 54), a byte holding the entry count (lines 55 to 59), a ushort play count (lines 60 to 64), one more byte of unread meaning (lines 65 to 69) and one entry per instrument (lines 70 to 104). A record with no entries writes nothing (lines 29 to 35). An entry is 16 bytes: instrument as 2 bytes, difficulty, a byte, a flag, a short, a byte, the modifier flags as 4 bytes and a 32-bit int (`score_entry_write_2BAB60.asm` lines 8 to 50). No title or artist is written anywhere in the record or the entry. The real file matches: the live `scoredata.bin` and the backup parse to their last byte in this layout, version 20211009, two records with one Pro Drums Expert entry each (`W8c/read_scoredata.out.txt`).

  One entry per chart and instrument: the record's entries sit in a dictionary keyed by instrument (`dump.cs` line 49307). Adding a run looks up the instrument's entry and merges the old one with the run (`score_chart_add_2161E0.asm` lines 20 to 51). The merge does not keep one whole best run. It keeps the larger int at +0x4, the larger bytes at +0xC and +0x14, and a set flag from either run; the difficulty, modifiers and the short at +0xA come from the run with the larger +0x4, and from the new run on a tie (`score_entry_merge_2BA4F0.asm` lines 13 to 92). That the int at +0x4 is the score was not read from a name; it is the value the merge decides by, and the getter 0x2BA7A0 returns the larger of it and +0x18.

  Play count spans instruments: the add method adds one to the record's ushort at +0x28, capped at 0xFFFF, on every run it adds, before it stores the entry under the run's instrument (`score_chart_add_2161E0.asm` lines 55 to 60). That ushort is on the chart record, not on an entry, and the writer writes it once per record (`score_chart_write_2167B0.asm` lines 60 to 64). So a chart's play count counts runs on every instrument together. The add is reached from `SongEntry` 0x358560 (`song_entry_add_score_358560.asm` line 34), which then saves through 0x2F5A40 (line 40); 0x2F5A40 calls the writer 0x2F57C0 (byte scan). Callers of 0x358560 (byte scan): `EndOfSong.Start` and one more `EndOfSong` method, 0x161C70.

  Route (c) answers nothing new: every backup equals the live file byte for byte, and no after-run copy exists, so no kept file shows a run changing the file. That a human run changes `scoredata.bin` and `scoresext.bin` stays on session 6a549de0's record alone. The code shows the end of a song adding and saving (`song_entry_add_score_358560.asm` lines 28 to 40), but whether a bot run reaches that path was not read.
- Proposed label: Proven in the game's code, for a reworded rule: "`scoredata.bin` starts with the version 20211009 and a record count. Each record is a 16-byte chart hash, an entry count, a 2-byte play count, one more byte, then one 16-byte entry per instrument (instrument, difficulty, a byte, a flag, a short, a byte, modifiers, an int). No title or artist is stored. Each finished run adds one to the chart's play count whatever its instrument, and is merged into that instrument's entry field by field." The listings above show all of it. The claim that a human run changes both files, and the meaning of the unnamed entry fields, stay as Evidence notes, unchecked. This block's Hydra line says "no owner", so the label move needs no user list.
