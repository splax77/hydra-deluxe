Class 8623 derives from class 8537, whose only field is that string at +0x20, and whose read method at RVA 0x2121340 is `sealed override`, so class 8623 uses it unchanged. That method reads the event's bytes, calls `Encoding.GetString` on them and stores the result straight into +0x20 (listing lines 95 and 96); its other branch stores the empty string (lines 99 to 102). No trim, case change or other edit runs between the byte read and the store. What was not read: any other writer of the public +0x20 field between the track read and the drum reader. The event list the reader walks is built from these event objects (NL-13), and no such writer was seen on the path, but no search over every writer of the field was made.
- Proposed label: Proven in the game's code. The text is built by one method with no trim, and the reader compares it with no trim, so a tag with a trailing space does not count.
- Hydra: agrees. `is_dynamics_marker` in src/parse/song.cpp lines 300 to 302 compares `msg.str` (line 971) exactly. One small gap: the game decodes the bytes with an Encoding object whose kind was not read, while Hydra compares bytes; both tag spellings are plain ASCII, so they agree for every tag the reader accepts.

- Second pass (CH-UNK-W3b). The MIDI reader's first argument holds the track list at +0xF8 (midi_reader lines 6 and 90); it passes element i's +0x18 list to the drum reader (lines 518 to 526), and the drum reader walks that argument with the list's enumerator (drum reader lines 102 to 123). The track reader 0x214F6D0 is a method of the same track class (its TypeInfo 0x3C9FCC8 is the element type of the MIDI reader's track list, metadata 0x3CD8AA0). Its loop reads one event at a time (lines 168 to 201) and appends each one to the track's +0x18 list with `List.Add` (lines 405 to 411). A note-on pushes the index it is about to get onto a stack kept per channel and pitch (lines 238 to 260); a note-off pops that index and stores itself in the note-on's +0x30 (lines 300 to 327). That is the pairing W3 looked for: it is done in place, with no second list. A note-on with velocity 0 is copied into a note-off object first (lines 279 to 299). When the track ends, 0x213ACB0 sets to null every note-on still on a stack and then removes the null slots with `RemoveAt`, walking from the end (new listing lines 19 to 150). So the drum reader meets the events in file order. The tag sets the dynamics flag when the walk reaches it (drum reader line 432), and each note-on reads the flag when the walk reaches it (lines 325 to 333). The scan found the MIDI reader as the drum reader's only direct caller, and no direct call to 0x214F6D0 at all, so how the track reader is reached (likely a virtual call) was not read. Two limits: the scans are direct references only (byte scan of call instructions and RIP-relative loads), and a write into the list's backing array through a span would show as a plain memory store, which no scan finds; the three `AsSpan` users run on other tracks (guitar-type readers), not the drum track. A side fact found here: the game drops a note-on that has no matching note-off before any reader sees it.
- Proposed label: Proven in the game's code. The list is built in file order by `Add` alone, nothing in the game sorts or inserts into it, the only removal keeps order, and the reader marks notes in that order.
- Hydra: agrees. src/parse/song.cpp line 975 runs the tag in the `Notes` phase with the notes, in file order (comment lines 972 to 974). Hydra's handling of a note-on with no note-off was not checked; the game drops it (above), so that is a question for whoever owns Hydra's note pairing, not part of this block.
