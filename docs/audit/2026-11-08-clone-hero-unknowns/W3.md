## NL-12

- Unknown was: whether the drum track's event text is trimmed where the event is built, before the drum reader compares it.
- Looked at: the new listing `docs/clone-hero/code/6142/mid_text_event_read_2121340.asm` (with its `.md`); `docs/clone-hero/code/6142/mid_drum_reader_2155050.asm` lines 356 to 363 and 419 to 433; C:\Users\Patrick\Downloads\Hydra\hydra-data\ch-dumps\6142\dump.cs lines 543325 to 543337 (the text base class, TypeDefIndex 8537) and 550220 to 550235 (the text event class the drum reader tests, TypeDefIndex 8623); script.json, where TypeInfo address 0x3CA0268 (the class test at drum reader line 356) names class 8623.
- Found: the drum reader takes its text from field +0x20 of a class-8623 event (drum reader lines 356 to 363) and compares it as is (lines 420 to 433). Class 8623 derives from class 8537, whose only field is that string at +0x20, and whose read method at RVA 0x2121340 is `sealed override`, so class 8623 uses it unchanged. That method reads the event's bytes, calls `Encoding.GetString` on them and stores the result straight into +0x20 (listing lines 95 and 96); its other branch stores the empty string (lines 99 to 102). No trim, case change or other edit runs between the byte read and the store. What was not read: any other writer of the public +0x20 field between the track read and the drum reader. The event list the reader walks is built from these event objects (NL-13), and no such writer was seen on the path, but no search over every writer of the field was made.
- Proposed label: Proven in the game's code. The text is built by one method with no trim, and the reader compares it with no trim, so a tag with a trailing space does not count.
- Hydra: agrees. `is_dynamics_marker` in src/parse/song.cpp lines 300 to 302 compares `msg.str` (line 971) exactly. One small gap: the game decodes the bytes with an Encoding object whose kind was not read, while Hydra compares bytes; both tag spellings are plain ASCII, so they agree for every tag the reader accepts.

## NL-13

- Unknown was: how the drum track's event list is built and sorted, so whether a note written before the dynamics tag at the same tick stays plain.
- Looked at: `docs/clone-hero/code/6142/mid_drum_reader_2155050.asm` lines 95 to 123 (the walk) and 325 to 333 (the note reads the dynamics byte as it goes); `docs/audit/note-shuffle/step0/open1/midi_reader_2155C00.asm` lines 144 to 153 and 196 to 264 and its call to the drum reader at line 526; `docs/audit/note-shuffle/step0/open1/mtrk_read_214F6D0.asm` (calls and list methods, lines 17 to 25 and 170 to 466); `docs/audit/note-shuffle/step0/open1/mtrk_read_event_2150010.asm`.
- Found: the drum reader walks a `List` with its enumerator, in list order (drum reader lines 102 to 123), and sets the dynamics byte the moment it meets the tag (line 432); each note reads that byte when the walk reaches it (lines 325 to 333). The later sort in the track finalizer 0x215C320 (NL-33) runs after the notes already carry their marks, so it cannot change which notes are marked. So the answer rests only on the order of the list the reader is given. The MIDI reader passes each track object's +0x18 list (midi_reader lines 256 to 264 for another instrument's reader; the argument set up before the drum reader's call at line 526 was not read). The chunk reader 0x214F6D0 adds events to a list with `List.Add` (line 409), but it also uses `RemoveAt` and `set_Item` (lines 19 and 25 load those methods), and the drum reader's note events carry a paired note-off at +0x30 (drum reader line 125 onward), which the raw chunk reader's events may not. So the list the drum reader sees may be built by a second pass that pairs note-ons with note-offs, and that pass was not found.
- Proposed label: Unknown. Searched: the four listings above. Not found: the code that turns the chunk reader's raw events into the per-track list at track +0x18, and whether `RemoveAt` and `set_Item` in 0x214F6D0 reorder events at one tick. Next step: list the callers of the methods of the track class whose +0x18 list the MIDI reader reads (the element type of the List at metadata 0x3CD8AA0), or run live check NL-13 as the plan's fallback says.
- Hydra: `kick_mark_before_tag_` and the note pass in src/parse/song.cpp; the tag is handled in file order at line 975, whose comment states the game rule this block has not proven.
