# Concept inventory from the types (scout C2)

Task concept-audit-C2, phase 3. I started from `types.md` (62 enums, 232 structs and classes), sorted each type into a concept, and read the definitions and converters for every concept that had two homes. Everything below was checked against `src/` at the checkout on 2026-10-11. Where a claim rests on reading only, the note says so.

How to read the table. "Owner" is the type or function that should answer the question. "Other homes" are the types in other modules that hold the same idea. "Candidate" is yes only when I found two homes with no named converter joining them, or two vocabularies for one idea. Rows marked "read" had their definitions read. Rows marked "by name" were sorted from `types.md` alone (name and field list); those are listed again under "Not reached" if I could not say they are single-home with confidence.

### C2-1. What does Hydra know about one scanned chart, and where is it copied from one shape to another?
Looks like: K1 (the same 8 fields in two types, hand-copied in three places).
Homes: `store::ChartLibraryEntry`, `src/store/record_store.h` 262-274 (md5, title, artist, charter, notespath, rootfolder, sig, timing);
       `app::ScanItem`, `src/app/analysis.h` 36-48 (the same 8 fields in the same order);
       `store::ChartCacheEntry`, record_store.h 278-285 (sig, md5, title, artist, charter, timing, keyed by notespath in `ChartLibraryCache`).
The three copies: `to_library_entry` (analysis.cpp 421-432, ScanItem to entry, all 8 fields); `scan_item_of` (`src/ui/library_jobs.cpp` 280-290, entry to ScanItem, 7 fields, no `sig`); the inline copy in `discover_charts` (analysis.cpp 674-683, cache entry to ScanItem, notespath, rootfolder and sig taken from `PendingChart`). The comment at analysis.cpp 672-673 says it copies "Field by field, like to_library_entry: seven strings in a positional list could swap unseen."
Table, home 1 (entry or ScanItem to the other): md5 -> md5; title -> title; artist -> artist; charter -> charter; notespath -> notespath; rootfolder -> rootfolder; timing -> timing; sig -> sig in `to_library_entry`, sig dropped in `scan_item_of`; a ScanItem made from a row an older scan wrote has `timing` empty and `chart_timing_meta` fills it (analysis.h 44-47).
Table, home 2 (cache entry to ScanItem): sig -> compared with `sig_unchanged`, then replaced by the freshly listed `PendingChart::sig`; md5/title/artist/charter/timing -> copied; notespath/rootfolder -> not in the cache entry, from the listing.
Differ on: `sig`. A ScanItem made by `scan_item_of` has an empty `sig`; one from a scan has the file's fingerprint. They agree today because only `save_scan_as_library` (which writes `sig` through `to_library_entry`) takes scan-made items; batch items are never saved back as library rows. The change that would split them: passing a batch's ScanItems to `save_scan_as_library`, which would blank every `sig` and make every chart look changed on the next rescan (`sig_can_show_unchanged`, record_store.h 288-). By reading only; the verifier should grep the callers of `save_scan_as_library`.
Note: the cleaner reading is that `ScanItem` is `ChartLibraryEntry` and nothing else; `ChartMeta` (analysis.cpp 138-143: title, artist, charter, timing) is the fresh-read half of the same data. `LibraryChart` (library_model.h 46-50) is a documented subset, so I cleared it.

### C2-7. How is a row with no value sorted?
Looks like: K1 (the rule), spelled in two sort engines.
Homes: `LibraryModel::resort`, `src/ui/library_model.cpp` 225-277 (the Best path sort: scored rows first in both directions, unscored rows ordered by `unscored_rank(status)`; text columns sorted by folded string with a fixed tie-break of title, folder, path);
       `compare_keys` and `SortKey` (`src/app/report_view.cpp` 36-50, `report_view.h` 24-26): a `std::monostate` key is "empty" and "sinks to the bottom whichever way the column sorts"; `ms_key` (path_report_view.cpp 21-23) and `optional_key` (dm_report_view.cpp 46-49) make an empty optional into that key.
Table, home 1 (library, Best path column): scored vs unscored, ascending -> scored first; scored vs unscored, descending -> scored first; two scored, equal score -> tie-break by title, then folder, then path; two unscored -> by status rank (Stale before Not analyzed or the reverse per `unscored_rank`), then tie-break. Text column, empty charter, ascending -> sorts as the empty string, so first; descending -> last.
Table, home 2 (report table): empty optional (monostate), either direction -> bottom; empty text such as `posted` -> monostate, bottom; any other empty text -> a plain empty string, so first when ascending, last when descending.

## Parallel on purpose

Each pair below holds one idea in two types and a named converter joins them. For each I list what each side knows and why every entry is a per-module fact.

- `ReportBuild` and `ReportOutOfDate` (report_state.h) against `ReportSlot`'s use of them (app_state.h 195-219): the slot holds the result, built_at, window_open, message and error; the enums hold the states. One enum per idea; no mapping between copies.

The row knows only a copy and the chip knows only a filter choice.
- `SummaryLookup` and the store's `Candidate` (record_store.cpp 359-371): `Candidate` is the store's private working form for `ready()`; `SummaryLookup` is what it hands out. The "is a row Stale" rule is in the store (`ready()`), not in either struct.
