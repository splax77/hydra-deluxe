# Phase 6: the fix wave, split into executor tasks

This is the plan for building D114 (`docs/audit/2026-10-03-fix-decisions.md`, items 1 to 22). Every finding with a fix is placed in one task below. Each task is one Opus executor in its own worktree, sized to fit one build, its own tests and 100 tool calls. The findings are in `docs/audit/2026-10-11-concept-audit/findings.md`; the decisions quoted here are D114's items; the questions behind them are in `questions.md` in this folder.

The tasks run in three waves, not two. Two waves was the target, but three files are hubs that nearly every area touches (`src/ui/library_dialogs.cpp`, `src/ui/app_state.cpp` and the rules file `tests/single_owner/rules/app.json`), and the rule below forbids two tasks in one wave owning one file. The split that keeps every wave clash-free is eight tasks, then six, then three. The user can stop after any wave. The one cost of this shape: the comparison page's new words (D114 items 1 and 2, task H3) land in wave 3, because that task and task F6 both have to rewrite an owner line in `rules/app.json`, and F6 carries the bug fix for the comparison gate (item 6), which should land first.

## Which rules file a row goes in

The single-owner scan reads every `.json` under `tests/single_owner/rules/` and one folder down (ADR 0029, `rule_files` in `tests/single_owner/scan.cpp`), so a new row never has to touch an area file. Every task puts its new rows in its own file, `tests/single_owner/rules/<area>/concept-<task>.json`, in the same `{"rules": [...]}` form, where `<area>` is the owner's folder (`app`, `ui`, `core`, `store`, `search`, `parse`). That keeps the area files out of every task but four. Those four edit an area file in place because the scan checks each row's `owner_lines` against the code (`scan.cpp` line 611, "owner line no longer matches") and the owner symbol against its file (line 354, "owner gone"), so a change to a quoted line forces an edit: F6 (`app.json`, the `describe_settings` row's two owner lines), G1 (`app.json` and `ui.json`, if any owner line it moves is quoted; probably none), G5 (`search.json`, the `settings_key` row, whose owner leaves `src/`), and H3 (`app.json` and `ui.json`, the status-word rows that quote `"not analyzed"` and the tile line). Each is the only task in its wave that owns that file.

The scan itself runs with `hydra_tests.exe -tc="single-owner*"`; every task that adds a row runs that filter.

## The tasks

Test filters are for `build-cpp\Release\hydra_tests.exe`. `-sf=` takes a comma-separated list of source-file patterns. The uitest names are for `build-cpp\Release\hydra_uitest.exe --test <name>` (one name per `--test`, see `docs/agents/ui-testing.md`). Nobody runs the whole suite, `hydra_uitest --all`, or anything over the song library.
