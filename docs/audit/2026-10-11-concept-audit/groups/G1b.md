# G1b report: the report windows and the library table

Scout: concept-audit-G1b (status file used: `G1b.md`, because the progress hook never named an agent id). Read in full: all twelve files in the group, plus (for the other home of an idea) `app/report_view.h/.cpp`, `app/path_report_view.h/.cpp`, `app/dm_report_view.h/.cpp`, the `ReportSlot` and close/collect code in `ui/app_state.*`, `app/dm_report.cpp` lines 60-155, `app/report.cpp` lines 120-260, `store/record_store.cpp` (get_summaries and list_records), and `app/html_page.cpp` lines 290-440 (the page script).

Short answer to the group question. The two report windows do not own table rules of their own: sorting, searching, the count line, the "#" column, column widths and the table frame all sit in `report_frame` and `app/report_view`. The library table owns a second, separate set of rules for the same jobs. Most of those differences are written down as on purpose (D56 item 1, D103 items 1, 16, 18). Four of them are worth a phase 4 look: what text a name column sorts on, what "Not analyzed" means, how a count line is worded, and the plain-JavaScript report page that re-implements the report table a third time.

### G1b-1. What text does a name column sort by (title, artist, charter)?
Looks like: K2 (the library sorts on folded raw text, the report windows sort on folded display text; the user sees both orders).
Homes: `LibraryModel::resort` (key lambda lines 262-271) with `make_searchable` (`app/library_query.cpp` 362-370), `ui/library_model.cpp` 225-276 (inputs: the scan's raw title, artist, charter, folder);
       `TableView::resort` + `folded_key` (`app/report_view.h` 178-205, `app/report_view.cpp` 29-34) fed by the report columns' `sort_key` (`path_report_view.cpp` 26-36, `dm_report_view.cpp` 37-44), which read `ReportRow::song/artist/charter` (inputs: the display strings set by `display_title/artist/charter`, `report.cpp` 52-54, `dm_report.cpp` 100-103).
Table, home 1 (library sort key = fold_for_search(strip_rich_tags(raw))): title made only of tags or blank -> "" (sorts first ascending), although the cell shows "(unknown)"; artist blank or the scan's placeholder `<unknown artist>` -> "" or "<unknown artist>" (sorts under `<`), although the cell shows "(unknown)"; title with leading spaces -> keeps one leading space (fold collapses runs, it does not trim), so sorts before the same title without; charter that is only tags -> "" and shown "" (agree); ordinary title -> folded text (agree).
Table, home 2 (report key = fold_for_search(display string)): the same four inputs -> "(unknown)" folded, "(unknown)", trimmed text, "" (empty charter is an empty *string*, not an empty value, so it sorts first ascending, last descending, same as the library); ordinary title -> folded text.

Note: I read `display_title/artist/charter` only from `parse/song.h` comments (lines 111-125), not their bodies. Whether the scan ever stores a title with surrounding spaces was not checked. The comment in `folded_key` ("the library table orders its text columns by their folded form too") is true of the fold but not of the input text. The fix-decisions entry for D103 item 16 was not read; only the code comment names it.

### G1b-2. How do ties and missing values order in a sorted table?
Looks like: K2 (same sort header, two rule sets; some parts agree on purpose).
Homes: `LibraryModel::resort` + `unscored_rank` + `tie_break`, `ui/library_model.cpp` 23-32 and 225-276 (inputs: sort column, direction, score presence, status, folded title/folder, notespath);
       `TableView::resort`, `app/report_view.h` 178-205 (inputs: up to two `SortSpec`s, `SortKey` variant, row order).
Table, home 1 (library): two rows equal on the sort column -> title, then folder, then file path, always ascending, whichever direction is on; Best path with a score vs without -> scored rows first in both directions; two unscored rows -> Ready-with-no-path, then Stale, then Not analyzed, in both directions; two scored rows with equal score -> the tie-break; sort keys per click: one key only (`Specs[0]`, `library_table.cpp` 310-318).
Table, home 2 (report): two rows equal on every sort key -> original row order (`stable_sort`), not reversed when the direction is Descending; a missing value (monostate) vs a value -> missing sinks in both directions; two missing -> next key, else row order; numeric vs text mixed in one column -> by kind (never happens); keys per click: up to `kMaxSortKeys` = 2 (Shift+click).
Differ on: ties (library has a fixed three-step tie-break; the report keeps row order), and the extra Stale/Not-analyzed ranking, which has no report twin because report rows are all scored or have a dash. "Missing sinks in both directions" is the same idea in two code shapes (library: the `xs != ys` line plus `unscored_rank`; report: the `xe`/`ye` lines).
Note: agree today on "equal keys never flip with the direction" and "missing never leads". A change like "unscored rows sort by title" would need both. The first-click direction is a third small copy of one idea: `report_view::first_direction(numeric)` (numbers high to low) against the library's hand-set `ImGuiTableColumnFlags_PreferSortDescending` on Best path only (`library_table.cpp` 286-289). They agree because the library has exactly one numeric column.

### G1b-3. What does the search box match, and what does the user have to type?
Looks like: K2, written down as deliberate (D56 item 1, comment in `report_view.h` 69-72).
Homes: `parse_library_query` + `query_matches` + `term_matches`, `app/library_query.cpp` 312-396 (inputs: the typed text; the row's four folded fields; stars and hardest ms facts);
       `search_words` + `search_matches`, `app/report_view.cpp` 8-27 (inputs: the typed text; one joined search string per row built by `search_field`, `library_query.cpp` 372-382).
Table, home 1 (library): `dream theater` -> two terms, each must be in some field; `"dream theater"` -> one phrase, must sit inside ONE field; `artist:foo` -> term limited to artist; `stars:7` -> filter on stored stars, rows with no scored best path never match; `squeeze<=20` -> filter, a path needing no timing passes; bad value -> an error sentence under the box, the filter is dropped; empty/whitespace -> empty query, all rows; unknown prefix `foo:bar` -> plain word.
Table, home 2 (report): `dream theater` -> two words, each must be in the joined string; `"dream theater"` -> the quotes are part of the words (`"dream` and `theater"`), so it matches nothing unless the data has quotes; `artist:foo` -> literal word `artist:foo`, matches nothing; `stars:7`, `squeeze<=20` -> literal words, match nothing; empty -> all rows.
Differ on: any quote, `field:` prefix or filter. Plain unquoted words agree (words hold no spaces, so joining fields cannot create a false match). The two search-box hints differ in what they promise (`library_table.cpp` 93 and 113-117 against `path_report_window.cpp` 116 and `dm_report_window.cpp` 80).
Note: shared on purpose and verified: both fold with `fold_for_search`, and both build their searchable text through `make_searchable` (`search_field` calls it). The fold itself is one home. Typing `artist:foo` into a report is a silent empty table (it shows "Nothing matches those filters."), not an error line; the library shows an error sentence for bad filters.

### G1b-7. What a report window forgets, and when (close, reopen, refresh)
Looks like: K3-with-a-rule-inside (two mechanisms for one product rule).
Homes: path report: `PathWindow::rebuild(keep)` (`path_report_window.cpp` 66-104), the `drop_rows` on close (172-178), `PathReportInput::keep_filters`, `ReportSlot::built_on_open` and `close_path_report` (`app_state.cpp` 730-739, 781-782);
       DM report: `DmWindow::rebuild` (`dm_report_window.cpp` 50-69) with no keep flag, no close handler (`dm_report_input` sets none), and nothing on close.
Table, path report: Close -> slot reset, window drops its copy of the rows, search/timing/Best-path-only/sort remembered; Reopen -> a new build runs, `built_on_open` is set, the filters come back, selection and "Show files" do not (`Memory::reset`); Refresh -> new result, `built_on_open` false, everything starts over; the user's cap or hit window changes -> timing choice resets if the labels differ, a kept sort naming a missing column falls back to the first.
Table, DM report: Close -> `*open` false only, result stays in the slot and the window's `TableView` (a full copy of the rows) stays; Reopen -> same result, no rebuild, so search, status, sort and selection all come back; Refresh or a new player -> a new result, `rebuild` starts over including the search.
Differ on: what is freed on close (path frees, DM does not) and what survives reopen (selection survives in DM only). Agree today on the user-visible parts: filters survive a reopen, a refresh resets them.
Note: if the DM report is meant to free memory on close too, it needs its own copy of path's three-part mechanism. Whether D103 item 28 meant to cover the comparison was not checked; the header comment (`app_state.h` 213-217) says "The path report only".

## Parallel on purpose

### PathWindow / DmWindow (`ui/path_report_window.cpp`, `ui/dm_report_window.cpp`): K3, with the answer to the K3 test
Verdict: parallel on purpose for the fields and for `apply_filters`; `rebuild` and `draw_body` repeat a shared skeleton but hold no second copy of a rule, except the items filed above as G1b-7 and G1b-8. Every sort, search, count, width and chip rule is called from `report_frame` or `app/report_view` and never decided in either window file.

The eight shared field names are `built_from`, `view`, `widths`, `choices`, `labels`, `tiles`, `tiles_dirty`, `memory`. Each has the same job in both windows (which result the view was built from, the table's rows, their measured widths, the dropdown's choices, the choices' labels, the tile row and whether it needs redoing, the frame's per-frame memory). What each window adds: Path has `timing` (index), `best_only`, and `sort` (kept while the window has no rows); DM has `status` (index). The only types that differ are the row type, the choice type and the tile function.

`apply_filters` (3 lines each). Path knows: take the search text from `memory.search`; feed `path_keep(tier of choices[timing], best_only)`; mark the tiles dirty. DM knows: the same search line; `dm_keep(status of choices[status])`; the same tiles line. Entry by entry: which controls feed the keep-rule is a per-module fact; the keep-rule itself lives in `path_report_view.cpp` 167-175 and `dm_report_view.cpp` 196-200; the search line and tiles line are the same step with no rule in them.

`rebuild`. Path knows: drop the old rows and keep their sort; keep or reset the search, timing, Best path only and sort depending on `keep` (G1b-7); stop early with no paths; build one search text per row with `path_search_text`; make the view with `path_columns(hit_window_ms)`; measure widths; check a kept sort still names a column and else use `path_first_sort()`; make the timing choices from the hit window and reset `timing` if their labels changed; apply filters. DM knows: reset memory/view/widths/status; stop early with no rows; one search text per row with `dm_search_text`; `dm_columns()`; measure; `dm_first_sort()`; `status_choices()`; apply filters. Entry by entry, which function names the columns, the first sort, the search text and the choices is a per-module fact. The shared steps (stop early, loop that builds the search texts, make the view, measure, copy the choice labels) are steps with no rule in them. The two rules that live only in Path (a kept sort must name a real column; a kept index is reset when the labels change) are both consequences of Path keeping state across rebuilds, which DM does not do.

`draw_body`. Path knows: tiles from `path_tiles(rows, visible, hit_window_ms)`; search hint "Search song, artist, charter, or path notation"; the Timing dropdown, the Best path only checkbox; what Clear filters resets (search and timing, not the checkbox); `RowLook` with the gold best bar and the tier chip token; table id and no click restriction. DM knows: tiles from `dm_tiles`; search hint "Search song, artist, or charter"; the Status dropdown; Clear filters resets search and status; `RowLook` with the status chip token, a "clickable unless not in library" test and the hint "Not in your library"; its table id. Entry by entry, the tile function, the hints, the control set, the reset set and the row look are per-module. Two things written in both and not per-module: the table height expression `ImGui::GetContentRegionAvail().y - report_frame::footer_height(frame)` (two copies) and the order tiles -> search -> dropdown -> count line -> nothing-matches branch -> table. These are a pipeline repeated by hand, with no differing rule, so phase 4 can call them K3 or "line-level".

Small things also seen and cleared: `"Compare another player..."` is a literal three times in `report_window.cpp` (header width list line 66, header button line 74, failed state line 212). The width list and the button must agree for the right-edge alignment to be right, but all three are in one file and one function family. Line-level, same-file. `"Not in your library"` is a literal in `dm_report_window.cpp` 99 (the hover hint) and in the status dropdown label (`dm_report_view.cpp` 191); the chip text itself comes from `kStatusNotInLibrary` ("not in library"). Three spellings of one status: the chip lower-case, the dropdown "Not in your library", the hint "Not in your library". Reading shows these are drawn by different code for different purposes; not one rule. Worth a one-line mention to phase 4 as a words-in-three-places item.

### Library table and report table frame (`ui/library_table.cpp` 265-318 against `report_frame::table`, `ui/report_window.h` 294-421): K3
Verdict: parallel on purpose. Both run the order set out in the `column_widths.h` header (table_room -> place_columns -> BeginTable with `table_flags()` -> `setup_column` per column -> `keep_table_column_order()` -> `apply_column_widths` -> sort -> rows), and both wait for `table_settled()` before pushing state into ImGui. What the library knows: five fixed columns, all of them may cut; its columns are measured with incremental updates when a summary changes (`update_cells`, `rows_version`); its sort comes from the user's saved ImGui state and is read back into the model (`sort_synced`); a single sort key; Charter and Folder hidden while the song panel is open; a two-line row while a word search is on and a column is hidden; title cut by hand with a highlight overlay. What the report frame knows: a "#" column, columns from the view's column table, a chip's padding, up to two sort keys with the view's sort pushed *into* ImGui once the table settles (whatever the ini held is overwritten), best-path bar, unclickable rows, arrow-key selection, minimum window size. Every entry is a fact about one table. The measuring, placing, header-width and flag rules are called, not repeated. Note for phase 4: the one rule the two tables answer opposite ways is "who owns the sort across runs" (library: ImGui's ini; reports: the view). Documented in comments at `library_table.cpp` 294-300 and `report_window.h` 353-356.
