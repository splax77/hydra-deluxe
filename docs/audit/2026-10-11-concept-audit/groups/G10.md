# G10 report: the store and what its callers repeat

Scout: G10 (the agent id was never named by the progress hook, so the status lines went to `G10.md`). Files read in full: `src/store/record_store.cpp` (1,636 lines), `upgrade_files.cpp`, `upgrade_files.h`, `stored_versions.h`. I also read `record_store.h` lines 95-340 for the types the methods return. Call sites were read only around each call.

## The short answers

The store decides three things and the callers mostly just use the answer: which row wins, whether that row is Ready or Stale, and whether the rescan cache is valid. No caller re-derives Stale. `LibraryRow` and `Candidate` both carry the two "why Stale" flags, but they are copies of the store's answer, not a second rule.

`list_records` and `get_summaries` share one winner rule. Both feed their candidate rows to `WinnerPicker` (record_store.cpp 440-461), which compares two rows only through `outranks` (427-431): this build's results version first, then this process's rules, then the newest write. Neither method picks a winner any other way. They differ only afterwards. `get_summaries` reports a Stale winner as Stale (1370-1374). `list_records` drops a chart whose winner is not Ready (1498), and it does not fall back to the next candidate. `CONTEXT.md` line 42-43 and derivation audit store-28 (line 6919) record that split as the design, so G1a-1 is a documented difference and not drift on the store side.

The real repeats are on the caller side and inside the store's SQL. They are in the candidates below.

## Candidates

### G10-1. Scan the folders against the last scan's cache, then save the result as the library
Looks like: K1, small (the same eight lines twice, with different surroundings).
Homes: `main` in `src/cli/batch.cpp` 203-215 (inputs: the store, the folder list, `folder_args.empty()`);
       `ScanJob::run` in `src/ui/library_jobs.cpp` 183-227 (inputs: the store, the root folders, a cancel flag, progress callbacks).
Both do the same steps in the same order: ask `store.chart_library_cache()` inside a try that swallows any failure ("no cache is only a slower scan"), call `discover_charts(folders, callbacks, cache.empty() ? nullptr : &cache)`, then call `save_scan_as_library`.
Table, home 1 (batch): cache read throws -> empty cache, scan reads every chart; cache empty -> pass null; scan ran over the app's folders (no folder arguments) -> save; scan ran over folder arguments -> do not save; save fails -> print the problem line.
Table, home 2 (ScanJob): cache read throws -> empty cache; cache empty -> pass null; cancelled -> do not save, leave the library; otherwise save; save fails -> add the problem to the progress errors.
Differ on: the save gate (batch skips saving for folder arguments; the app has no such mode) and the cancel check. These are per-caller facts. The shared part, "load the cache without failing, scan, save", has no owner.
Note: `discover_charts` already handles an empty cache the same as a null one (analysis.cpp 669-671 does `cache->find`, which misses on an empty map), so `cache.empty() ? nullptr : &cache` is not a rule, only a habit repeated twice. Verifier: confirm `discover_charts` has no other reader of the pointer.

### G10-2. Which rows of the `charts` table does a scan row become, and who reads them back into a struct? (also seen in G10: G2-1)

Homes: `RecordStore::chart_library_cache`, record_store.cpp 1553-1573 (reads `path, sig, md5, name, artist, charter, stated_length_ms, delay_ms`; skips `folder`);

The two list methods repeat the same four lines apart from the WHERE and ORDER BY.
Table, chart_library_cache: stamp missing or old -> empty cache; sig empty -> row dropped; otherwise the row, with timing always read.

The offset and limit parameters and the SQL order look unused; verifier to confirm nothing depends on the SQL order.

## Parallel on purpose

`StampRule` in `stored_versions.h` is used by two stamps, `kResultsStamp` and `kChartMetaStamp`. Each stamp's entry knows only its own facts: the value written, the values accepted, and nothing else. `is_current` is the only place a stored stamp is compared. The SQL twin `row_readable_sql` (record_store.cpp 410-414) and `bind_readable_params` are built from the same `accepted` list, so they cannot drift. `rank_row` (378) asks `is_current` for the row's version. `chart_meta_current` (1575-1578) parses the stored text with `atoi` and asks `is_current` for the chart stamp. The parse is per-stamp (the results stamp is text, the chart stamp an int), so it is a per-stamp fact.

`upgrade_files.cpp` and `upgrade_files.h` against `RecordStore::copy_upgrade`: the files own names and renames and the recovery rule for a stopped swap; `copy_upgrade` owns the row copy. Neither holds the other's rule. The one shared fact, "a database has a log and a shared-memory side file", lives once in `with_side_files`. `side_files_present` and `remove_with_side_files` both read it.

`summary_columns` / `kSummaryColumnList` / `bind_summary` / `read_summary` (record_store.cpp 150-188 and 265-301): the list is one string. The two walkers are slot-by-slot copies, and the `static_assert` on `kSummaryColumnCount` (282) stops the build if the list grows without them. Parallel on purpose, because binding to and reading from SQLite must be written by hand for each type. They hold no rules.

## Per-method answer: do the callers each work out the same thing around the call?

`chart_library_cache`. Yes, the "load, swallow failure, pass null if empty" frame is written twice (G10-1). The sig filter is not repeated: `sig_can_show_unchanged` is the one owner and it is called from the store, `sig_unchanged` and the click's save.

`engine_mode`. Partly. Three readers read the stamp their own way (G10-7), and the policy differs per tool on purpose.

`get_summaries`. Callers build the key three ways: from settings one by one (library_jobs.cpp 67), from a `RecordKey` unpacked by hand (app_state.cpp 430), and via the `get_summary` wrapper (app_state.cpp 127). None of them decides Stale. They all hand the answer to `LibraryModel` or compare `status == Ready` (G10-5, G10-6).

`list_records`. Both callers (report.cpp 160 and 233) pass `SortColumn::Score`, descending, and no limit, then each applies its own library filter and its own per-chart rule. `records_by_hash` normalises the hash, drops charts the library does not list, and keeps the first listing per normalised hash (`emplace`), which relies on the store's `ORDER BY r.score DESC`. `collect_rows` normalises, drops the same charts, and keeps every listing (it `push_back`s a slot per row). The two agree unless two listings in one chart mode have hashes that differ only in case. Then `records_by_hash` keeps the higher score and `collect_rows` lists both. This is an add-on to G1a-7 for the verifier. The sort, `limit` and the other `SortColumn` values have no production caller.

`list_chart_library`. Callers use it only as "every row" (G10-2). `select` (app_state.cpp 243-249) fetches every copy of an md5 and then scans for the one whose `notespath` matches. `library_matches` (145-148) reads the whole library and picks rows by `notespath`. The store has no "entry by path" method, so the UI's `row_key` (library_model.h 56-57, `notespath`) and the store's `WHERE path = ?` (reidentify, 1259) and the cache key (1568) are three homes of "a library row is identified by its notes path". The `charts` table has no UNIQUE on `path`. Verifier: check whether `discover_charts` can return the same path twice when two chosen roots overlap.

`save_analysis`. Both callers build the row with `prepare_row` first. The click path (app_state.cpp 428-436) checks whether the stored row already says the same and skips the write; the batch path (analysis.cpp 814-819) never does, since its skip is decided earlier by `analyzed_hashes`. They answer different questions (is this already stored, versus is this chart already done), so I count it K0 apart from the `get_summary` spelling in G10-5.
