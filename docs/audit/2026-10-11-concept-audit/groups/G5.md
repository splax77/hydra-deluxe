## Short answers to the brief's three questions

Is `Path` defined twice? Yes by name, but it is not an idea with two homes. `hydra::Path` (core/model.h 733) is the finished result record. The `Path` in search/engine.cpp 269 is a live search node, in an anonymous namespace (a file-private scope), and the same file calls the record `MPath` (engine.cpp 26). See "Dropped leads".

Do the model and the view both format activation and squeeze text? Yes, in a split way. The model writes the path notation, the whole-ms figures in the verbose string, the backend rating word and the multiplier-squeeze "how to" sentence. The view writes the badge words, the squeeze sentences, the early-fill line and the "squeezed out" tags. The two never write the same sentence. The one cell they both touch is the backend table's Rating cell, which has three authors (candidate G5-1). `"squeeze in -316 ms"` is only a comment in model.h 626 and path_view.h 131; no code string holds it.

Do the details panel and the Paths tab each lay out an activation row? No. `details_panel.cpp` draws no activation row at all (it draws the header, the headline and the record states, then hands the Paths tab to `paths_tab.cpp`). The one row layout is `activation_row_layout()` in ui/activation_row_layout.h, called once from `render_activation_row` in paths_tab.cpp. The Preview tab has a different widget (the next-activation box), which is G6a's.

## Parallel on purpose

- View-model structs against the records they show (`ActivationRowView`, `BackendRowView`, `PathButtonView`, `ActivationsView` in app/path_view.h against `Activation`, `BackendSqueeze`, `Path`). The view side knows: the 1-based row number, the display strings, the warn colour flags, the song fraction, which backend rows survive the user's Backend limit, and which unfold state each row has. Every entry is a per-screen fact. The rules (hardest part, difficult floor, counted, squeezed-out row, transfer scale) are read from `Activation`, `core::` and `rate_activation`, not recomputed, with the exceptions already listed as G5-1 and G5-7.
- `PreviewActivation::SpEndChange` (app/preview_view.h 122-130) against `SpEndStep` (core/model.h 468). The preview copy keeps the refill tick and the end tick and drops the kind. It takes the tick from `Activation::refill_tick`, the owner. It knows only what the gauge draws. G6a owns the file; noted so they do not report it as new.
- Engine flat arrays (`Act`, `SqNode`, `EndNode`, `OutAct`, `OutSq`, `OutPath` in search/engine.cpp 191-340) against `Activation`, `SPSqueeze`, `SpEndStep`, `Path`. They hold the same facts in index-linked form for speed, and `rebuild` inflates them. G4b's. One rule sits inside the parallel part: `Engine::act_within_limit` (engine.cpp 1137-1146) repeats the walk of `Activation::within_ms_limit` (model.cpp 543-547), each calling the same leaf helpers. Known as finding 152 in the derivation audit (then called `act_difficulty`); it is line-level and agrees today.
- `render_timeline` and the Preview's `draw_scrub_marks` both draw one gold mark per activation at a song fraction. Both get the fraction from `song_fraction` (app/preview_view.cpp 640), and the end-measure label from `display_tick_at_ms`. Each side knows only its own pixel geometry.
