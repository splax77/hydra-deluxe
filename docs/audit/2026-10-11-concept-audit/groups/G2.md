## The short answer to the group question

A chart and its library row has one stored shape (the `charts` table) and five in-memory shapes in this group: ScanItem, ChartLibraryEntry, ChartCacheEntry, ChartMeta, and (outside the group) LibraryChart/LibraryRow in ui/library_model.h. The pairs the struct probe flagged split into three kinds.

Built from each other through a named converter: ScanItem to ChartLibraryEntry (`to_library_entry`, analysis.cpp 421-432) and ChartLibraryEntry to ScanItem (`scan_item_of`, library_jobs.cpp 280-290). ChartLibraryEntry to LibraryChart/LibraryRow is `LibraryModel::set_charts` (library_model.cpp 131-151), also a named function.

Each filled on its own from the source, with no converter: ChartCacheEntry (record_store.cpp 1553-1573) and ChartLibraryEntry (record_store.cpp 1591-1612) are both read straight from the `charts` table with two separate column lists. ChartMeta is filled from three container readers, and then copied into ScanItem by an inline block, not by a converter (analysis.cpp 689-701). ScanItem is also filled a second time inline from ChartCacheEntry (analysis.cpp 672-683).

BatchProgress and `BatchJob::Snapshot` are the clearest case of a copy: Snapshot takes five of BatchProgress's six fields in one lambda (library_jobs.cpp 422-429). The sixth, `current_title`, is not copied, and the two same-named fields mean different things.

Counting sites that copy the same eight chart-row fields by hand (md5, title, artist, charter, notespath, rootfolder, sig, timing), there are eight:
1. discover_charts, cache-hit block, ChartCacheEntry to ScanItem, analysis.cpp 672-683 (inline).
2. discover_charts, fresh-read block, SongIdRead + ChartMeta + PendingChart to ScanItem, analysis.cpp 689-701 (inline).
3. `to_library_entry`, analysis.cpp 421-432 (named).
4. `scan_item_of`, library_jobs.cpp 280-290 (named, drops sig).
5. `rebuild_chart_library`, ChartLibraryEntry to SQL binds, record_store.cpp 1527-1538.
6. `chart_library_cache`, SQL to ChartCacheEntry, record_store.cpp 1553-1573.
7. `read_library_entries`, SQL to ChartLibraryEntry, record_store.cpp 1597-1612.
8. `LibraryModel::set_charts`, ChartLibraryEntry to LibraryRow, library_model.cpp 131-151.
Sites 3, 4 and 8 are named converters. Sites 1, 2, 6 and 7 are not.

## Candidates

### G2-1. What does one row of the `charts` table say about a chart file, and who reads it into a struct?
Looks like: K1 (the column list and the field order), with a deliberate filter inside the cache (a rule that has one owner, `sig_can_show_unchanged`).
Homes: `RecordStore::chart_library_cache`, record_store.cpp 1553-1573 (inputs: the `charts` table, the stamp `chart_meta_current()`, `sig_can_show_unchanged`); `read_library_entries` with `kLibraryEntrySelect`, record_store.cpp 1591-1612 (inputs: the same table, the same stamp, passed in as `timing_read`).
Table, home 1 (cache, ChartCacheEntry): stamp not current -> empty cache. Stamp current, row with empty sig -> row left out. Stamp current, row with sig -> entry keyed by path holding sig, md5, title, artist, charter, and timing as `{stated_length_ms, delay_ms}` (each may be NULL, which reads as no value). No rows -> empty cache.
Table, home 2 (list, ChartLibraryEntry): stamp not current -> every row listed, timing unset. Stamp current, row with empty sig -> row listed, sig "". Stamp current, row with sig -> row listed with all eight fields and timing set (members may be empty). No rows -> empty list.
Differ on: the empty-sig row, and the stamp-not-current case. Both differences are deliberate and the filter itself is owned once (`sig_can_show_unchanged`, record_store.h 294). The part that is copied is the SELECT's column list and the column numbers (cache uses numbers 0-7 in its own order: path, sig, md5, name, artist, charter, length, delay; the list uses 0-8 in a different order). A change to the `charts` table, such as a new stored field, has to be made in the table setup, `rebuild_chart_library`, `kLibraryEntrySelect`, `read_library_entries` and `chart_library_cache`.
Note: the cache's `timing` is not optional (the cache is empty unless the stamp is current), while the list's `timing` is optional. Both mean the same thing once the stamp is current. The derivation audit item 6254 is about the stamp check only and is already done (the `chart_meta_current` gate).

### G2-2. How does a scan row become a library row, and back?
Looks like: K3 (parallel on purpose with named converters), with one real difference: the types hold identical fields.
Homes: `ScanItem`, analysis.h 36-48 (md5, title, artist, charter, notespath, rootfolder, sig, timing); `ChartLibraryEntry`, record_store.h 262-274 (the same eight fields in the same order). Converters: `to_library_entry`, analysis.cpp 421-432 (all eight fields); `scan_item_of`, library_jobs.cpp 280-290 (seven fields; `sig` is left empty because "nothing the batch runs reads it", library_jobs.h 227-230).
Table, ScanItem to Entry: each field copied by name; sig kept; timing kept (set or unset).
Table, Entry to ScanItem: each field copied by name; sig dropped; timing kept (set or unset).
Differ on: `sig`, one way only. Today nothing reads a ScanItem's sig after the scan (run_batch reads md5, notespath, title; batch.cpp and BatchJob read title and artist; plan_batch reads md5), so the loss is invisible. A reader that later wants sig on a ScanItem built from the library would get "" and `chart_changed_since` would treat it as changed.
Note: this is derivation-audit finding 256, which was fixed line by line by `to_library_entry`. The audit's other fix, "ScanItem as an alias of ChartLibraryEntry", was not taken, and the two types are still the same eight fields. What ScanItem knows that Entry does not: nothing. The batch pipeline uses four of its eight fields. `scan_item_of` sits in ui/ only because analysis.h could not include it (library_jobs.h comment 229).

### G2-3. Where is a ScanItem filled from its source, and how many ways?
Looks like: K1 (two inline fill blocks in one function plus the metadata step before them).
Homes: discover_charts cache-hit block, analysis.cpp 669-686 (inputs: a ChartCacheEntry, a PendingChart); discover_charts fresh-read block, analysis.cpp 687-703 (inputs: `song_id_read` result, a ChartMeta, a PendingChart); then one shared fallback loop, 719-731 (`title_or_unknown`, `artist_or_unknown`, `charter_or_unknown`).
Table, cache hit (sig unchanged, `sig_unchanged`): md5, title, artist, charter, timing come from the cached entry; notespath, rootfolder, sig come from the PendingChart (fresh walk values).
Table, fresh read: md5 from `song_id_read`; title, artist, charter, timing from `read_metadata_ini` for a folder chart and from `SongIdRead::meta` for a .sng or .srb; notespath, rootfolder, sig from the PendingChart.
Table, both then: title/artist/charter pass through the one fallback each, so an old cached "<unknown title>" and a blank both land on the same stored word.
Differ on: agree today. The inline comment (analysis.cpp 672) says "Field by field, like to_library_entry", which is a copy of the idea, not a call to it. A ninth field would need to be added in both blocks, in `to_library_entry`, in `scan_item_of`, in the SQL readers and in `LibraryModel::set_charts`.
Note: ScanItem could hold a ChartMeta (title, artist, charter, timing) as one member, which would turn the 695-698 block and the 677-679 block into one copy each. I did not check whether anything outside analysis.cpp needs ChartMeta public.

### G2-4. Which metadata key means which field, for .ini, .sng and .srb?
Looks like: K1 (key-to-field mapping, written once per container) with a K2 edge on empty values for .srb.
Homes: `read_metadata_ini`, analysis.cpp 151-164; `parse_sng_metadata`, analysis.cpp 173-185; `srb_chart_meta`, analysis.cpp 194-204. The delay key is read by `ini_delay_ms` and `sng_metadata_delay_ms` in app/preview_source.cpp 181-187 and 300-304 (outside the group), which share `parse_delay_ms`.
Table, .ini and .sng: "name" -> title; "artist" -> artist; "charter" -> charter (the `frets` alias is deliberately not read, per the comment at 157); "song_length" -> timing.length_ms through `stated_length_ms_of_text`; "delay" -> timing.delay_ms through `parse_delay_ms`. A key seen twice keeps the last value in both (ini: map assignment; sng: later pair overwrites). Key case: ini reader lowercases, sng lowercases per pair.
Table, .srb: name -> title only when non-empty; artist and charter assigned even when empty; length from a number via `stated_length_ms`; no delay.
Differ on: the .srb sets title only when non-empty but artist and charter unconditionally. This makes no visible difference today because all three names pass through the same fallback loop (analysis.cpp 719-731), which is the repair for the old derivation-audit item at line 1274 of the audit file (known, line-level, fixed).
Note: if a .sng or .ini key is renamed or added (for example a `year` field), the change has to be made in two places in this file plus the delay reader in preview_source.cpp.

### G2-5. What counts does a batch report, and who words them?
Looks like: K2 on wording, K1 on the counts (counts come from one owner).
Homes: `BatchProgress`, analysis.h 217-224, written only by `run_batch` (analysis.cpp 880-913); `BatchJob::Snapshot`, library_jobs.h 271-298, copied from BatchProgress in one lambda at library_jobs.cpp 422-429 (total, completed, analyzed, skipped, failed; five of six fields). Wording homes: `batch_counts` in ui/library_dialogs.cpp 54-58 and the CLI summary printf in cli/batch.cpp 260-263.
Table, GUI wording: analyzed -> "N analyzed", failed -> "N failed", skipped -> "N skipped (already had a result)", joined with a middle dot; the strip's progress is `completed of total`.
Table, CLI wording: "Analyzed N, skipped M already stored, F failed in Xs."; each line prints `[completed/total]` taken from the last progress. The CLI copies the whole BatchProgress (`last = p`, batch.cpp 234); the GUI copies five fields into Snapshot.
Differ on: the words for skipped ("already had a result" in the GUI, "already stored" in the CLI) and the order of the three counts (analyzed, failed, skipped against analyzed, skipped, failed). Counts themselves cannot disagree (one writer, `run_batch`).
Note: `current_title` is a name collision. `BatchProgress::current_title` is the title of the last chart whose row was counted, raw (analysis.cpp 912). `Snapshot::current_title` is the title of the chart a worker started most recently, cleaned with `display_title` (library_jobs.cpp 378, set from `note_started`), and `current_artist` goes with it. Nothing reads `BatchProgress::current_title`: I grepped src/ and found only the write at analysis.cpp 912 and the declaration. The Snapshot comment says the counts are "copied from app::BatchProgress" and does not say the title is not. This is a dead field with a live same-named field next to it (verify on the tests folder too; I searched src/ only).

### G2-7. What does a CLI tool do to start, and how does the app do the same?
Looks like: K1 between the two tools; K2 against the app (the failure policy differs on purpose).
Homes: cli/batch.cpp 95-116 and 137-143; cli/fillcompare.cpp 50-77 and 82-89; ui/app_state.cpp 23-31 and 40-46 (outside the group).
Table, bad `hydra_rules.ini` or bad `--rules` file: batch -> prints the error, exit 2. fillcompare -> prints the error, exit 2. App -> keeps `rules_error`, keeps default rules in settings, opens the store with `RulesStamp::none()` so every row reads Stale and analysis is off.
Table, `--rules <path>` given: batch and fillcompare load that path; the app has no such option.
Table, unknown option: batch -> any argument starting with `--` that it does not know prints "Unknown option: %s" and exits 2; an argument without `--` is a folder. fillcompare -> every argument it does not know prints the same text and exits 2 (no positional arguments).
Table, store open failure: both go through `app::open_store` and `app::tool_error(e, 2)`.
Differ on: the app tolerates a bad rules file; the tools do not. The seven-line `load_rules_file` try/catch with `rulespath ? u8path(*rulespath) : default_rules_path()` is spelled the same in both tools (batch.cpp 110-116, fillcompare.cpp 71-77), the same arg-loop shape and "Unknown option" text are in both, and the `RulesStamp::of(settings.rules)` open is in both. There is no shared "start a tool" step; each tool does its own. `run_tool` and `tool_error` already own the exit path (user_messages.cpp 120-131).
Note: batch uses `Settings::load_for_command_line(legacy_fills)`; fillcompare uses `Settings::load()`. `fillcompare` sets the two lens fill values inside `generate_fill_report` (fill_report.cpp 177-178), so its settings.legacy_fills does not matter. I checked this at fill_report.cpp only by grep.

## Parallel on purpose

ScanItem and ChartLibraryEntry (G2-2): both sides know the same eight fields. ScanItem is the in-memory row a scan or batch carries. ChartLibraryEntry is the row the store reads and writes. Every entry is a per-chart fact (hash, names, path, folder, fingerprint, stated length and delay); neither type holds a rule. I could not find a per-side fact that differs, so I list it under Candidates, not here.

BatchProgress and Snapshot, counts only (G2-5): BatchProgress knows the five counts and the last counted title. Snapshot knows the same five counts plus the GUI's own facts: `preparing`, `paused`, `elapsed_s`, `eta_s`, the failure lists, `run_error`, `finished`, and the started-chart title and artist. Each extra entry is a GUI-run fact (clock, pause, display text). The ETA rule `batch_eta_s` lives once in library_jobs.cpp 275-278.

ScanProgress (library_jobs.h 166-180) against the scan's callbacks: ScanProgress knows the phase and the counts; `ScanCallbacks` fires them. ScanProgress is built from the callbacks in one place (library_jobs.cpp 190-201), so it is parallel on purpose.
