Short answers to the group question.

- Does each background job run on `job_base.h`? Yes, all five. Store open, library scan, batch, Preview load and the DM fetch all start their thread through `JobBase::spawn` (job_base.h 46). The only other threads in src are the batch and report worker pool (app/work_pool.h 83), the scan's folder-walk helpers (app/analysis.cpp 583-596) and two `std::async` calls inside the Preview load. Those are inside a job, not jobs. So no job hand-rolls its own thread or cancel flag.
- What the jobs do hand-roll is the progress hand-off and the "I am finished" answer. Scan and batch keep their own `finished` inside a mutex-guarded snapshot and never set the base class's `finished_`. See G11a-2.
- Are "which window is open" and "is a job running" each held once? Mostly yes for windows (one bool per window on `AppState`). The exceptions are in G11a-8. "Is a job running" is held once per job but spelled five different ways, and the scan and batch spellings differ from the rest. See G11a-2.
- Do the shell and `main.cpp` hold a copy of window or job state? No job state. Window placement lives once in `g_placement` and `g_report_placements` (app_shell.cpp 38-42) and is written only through `remember_*`. `main.cpp` holds Direct3D handles and one pending-DPI value, nothing `AppState` also holds. Two monitor-list readers exist on purpose (parallel section).

### G11a-1. How does a finished job become "Ready", "Cancelled" or "Failed"?
Looks like: K1, with one input where the order of the checks differs.
Homes: `land_report`, src/ui/app_state.cpp 752-771 (inputs: the job's `ok()`, `is_cancelled()`, `message()`, `error()`; used for the path report and the DM report);
       `AppState::update_view_job`, src/ui/app_state.cpp 348-424, the test is at 361-367 (the same four inputs, for the click's analysis).
       Two more readers of the same job surface: `collect_store_open`, app_state.cpp 78-91 (reads `ok()` only; failure comes from `failure()`), and `render_dm_picker_modal`, src/ui/library_dialogs.cpp 609-629 (reads `ok()`, `message()`, `error()`; outside my group). The base class they all read is `ResultJobBase`, job_base.h 65-104.
Table, home 1 (`land_report`), inputs (ok, cancelled):
  (true, false) -> Ready, result kept
  (true, true)  -> Ready, result kept (ok is tested first)
  (false, true) -> Cancelled, old result and message kept
  (false, false) -> Failed, message and error copied
Table, home 2 (`update_view_job`), same inputs:
  (true, false) -> goes on to read the outcome (Ready, RulesBroken or Failed)
  (true, true)  -> Cancelled, result thrown away (cancelled is tested first)
  (false, true) -> Cancelled
  (false, false) -> Failed, message and error copied
Differ on: ok and cancelled both true. The base class lets that happen: `run_guarded` sets `ok_` from the body's return, and a cancel can still land after the body's last check. `ViewJob::run` returns true after its last `throw_if_cancelled` (library_jobs.cpp 533-544), so for the click that input is reachable and the click throws the result away on purpose (app_state.h 259-264). The report jobs check `is_cancelled()` right before returning true, so today the path report cannot land (true, true). If a cancel lands in the short gap, `land_report` would keep the result as Ready.
Note: the verifier should check that gap in `ReportJob::run` (library_jobs.cpp 583-620 read only to line 613). The base class has no single "outcome" word; every consumer re-derives it from `ok()` and `is_cancelled()`. The job's `message()` is withheld when cancelled (job_base.h 94-99), which is a third small rule living in the base.

### G11a-5. StoreOpenJob and PreviewLoadJob: the progress and time-left machinery written twice
Looks like: K3-with-a-rule-inside. The parallel parts hold per-module facts; the rule inside is "seconds since the job started" and "how the byte-rate clock is fed".
Homes: `StoreOpenJob` / `StoreOpenProgress`, library_jobs.h 48-73 and 100-155, library_jobs.cpp 27-46 and 71-122;
       `PreviewLoadJob` / `PreviewLoadJob::Progress`, preview_load_job.h 109-209, preview_load_job.cpp 127-130 and 246-309.
What the two share by shape (my count of the four fields the lead names): `started_` (a `steady_clock::time_point` set in `start()`), `clock_mutex_`, `clock_` (a `ByteRateClock`, one by pointer and one by value), and a done/total pair of atomics (`rows_done_`/`rows_total_` against `bytes_done_`/`bytes_total_`). Both also have a `Progress` struct holding `step`, `elapsed_s` and `time_left_s`, and `label()` / `time_left_text()` methods.
What is already one home: the words and the 3-second gate for time left (`gated_time_left_text`, preview_load_job.cpp 299-302, called from both `time_left_text` methods), and the byte-rate maths (`ByteRateClock::update`, preview_load_job.cpp 94-113).
What is still written twice:
  seconds since start: `StoreOpenJob::elapsed_s` (library_jobs.cpp 90-92), the inline expression in `PreviewLoadJob::progress` (preview_load_job.cpp 258-259) and a third in `AppState::view_progress_shown` (app_state.cpp 341-346). `steady_seconds()` (library_jobs.cpp 239-242) is a fourth, for `BatchClock`.
  the clock feed under the mutex: library_jobs.cpp 104-108 and preview_load_job.cpp 260-263.
Table, home 1 (StoreOpenJob::progress): feeds `clock_->update(elapsed, rows_done, rows_total)` on every step; the "time left" text then shows only in step Copying (library_jobs.cpp 43-46).
Table, home 2 (PreviewLoadJob::progress): feeds `clock_.update(elapsed, bytes_done, bytes_total)` only while the step is Opening audio; the text shows only in that step (preview_load_job.cpp 306-309).
Differ on: which steps feed the clock. The startup open feeds it from the first frame, with rows at 0 of 0; the Preview feeds it only inside its byte-rate step. `ByteRateClock` restarts its window every second, so the first Copying estimate can include up to a second of idle time before the copy began. That is an estimate that may read one tick high, not a wrong total.
Note: `Step` is K0 as a type. `StoreOpenProgress::Step` is {Opening, UpdatingResultsKey, Copying, Finishing, LoadingLibrary} (library_jobs.h 49) and `PreviewLoadJob::Step` is {Reading, Opening, Building, Highway} (preview_load_job.h 156). The step-reading rule differs too: the Preview derives its step from four bools (preview_load_job.cpp 248-255); the startup open stores the step. The claim on the first-estimate effect is by reading `ByteRateClock::update` only.

## Parallel on purpose

- Monitor work areas: `monitor_work_areas` (main.cpp 71-76, asks Windows) and `imgui_work_areas` (app_shell.cpp 502-511, asks ImGui). Each knows only how to read a monitor list in its own environment: main.cpp runs before the ImGui backend exists, the runner has no real monitors. Both feed `placement_on_screen`, which is one rule in one place (app_shell.cpp 176-184). A per-environment fact on each side, no rule.
- `store::OpenStep` against `StoreOpenProgress::Step`, translated by `screen_step` (library_jobs.cpp 127-136). The screen's enum adds `LoadingLibrary`, which the store cannot know. The translator holds only a name-for-name map.
- The five job types on `JobBase` / `ResultJobBase`. Each knows its own inputs, its own result type and how its progress is read (one atomic float for the click, an atomic pair for the path report, per-field atomics for the startup open and the Preview load, a mutex-guarded struct for scan and batch). Each of those is a per-job fact. The rules in the machinery are G11a-1, G11a-2 and G11a-5.
- Where a report window reopens: three sources in `saved_rect` (app_shell.cpp 520-530): the `[Hydra][Window:<key>]` entry, the live ImGui window, then ImGui's own `[Window]` entry from an older ini. The order is one rule in one function. One note for the verifier: the report windows call `ImGui::Begin` without `NoSavedSettings` (report_window.cpp 244-245), so ImGui keeps writing its own entry for them, and that entry is only a fallback behind Hydra's section. Not checked: whether anything ever reads the ImGui entry once Hydra's section is valid.
- `Layout` (library share and hidden) and `WindowPlacement` in one ini handler (app_shell.cpp 119-153): both are saved facts; the handler routes by section name.
- `DetailsViewState`, `LibraryViewState`, `HeldRow` (app_state.h 54-154): view-only copies kept on `AppState` on purpose (the header says why, so a static does not outlive the app). Each field is a per-view fact. The two "was open last frame" flags are covered in G11a-8.
