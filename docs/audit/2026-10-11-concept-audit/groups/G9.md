# G9 report: strings, errors, file access, network client

Scout: concept-audit-G9 (agent id not named by the hook; I used `G9`). Read-only. All 19 files in the group were read in full. I grepped outside the group to find the other homes.

Short answer to the group question. The string helpers, the sizing of files, the thread pool, the allocator calls and the network client each have one home. The weak spots are the words a user reads when something fails, and a few small file rules that are written twice. The user_messages header says "Every job and view that shows an error takes the wording from here, so it lives in one place." That is not true today (G9-1, G9-4).

## Candidates

### G9-1. What does the user read when hydra_rules.ini is bad?
Looks like: K2 (one state, three wordings, all on screen; the sentence in user_messages is not reached in production as far as I found).
Homes:
- `kRulesFile`, src/app/user_messages.cpp 48-50, picked by `kind_sentence` line 96 (input: a `RulesFileError`, whose kind is `RulesFile`, src/app/rules_file.h 20-22).
- `AppState::kAnalysisOffSentence`, src/ui/app_state.h 279-281, plus the raw text `rules_error` (set at src/ui/app_state.cpp 27-28 from `e.what()`). Shown by src/ui/library_toolbar.cpp 148-152 and src/ui/path_report_window.cpp 160-161.
- Four tool entry points catch `RulesFileError` and print `e.what()` raw to stderr: src/cli/batch.cpp 113-115, src/cli/fillcompare.cpp 74-77, tools/replay.cpp 778-781, tools/bench.cpp 518-521. They return 2.
Table, home 1 (kRulesFile): any bad line -> "hydra_rules.ini has a line Hydra can't read. Fix or delete that line, then restart Hydra." Only a test reaches it (tests/test_user_messages.cpp 94). I found no production path that hands a `RulesFileError` to `plain_error`: `load_rules_file` is called only inside `catch (const RulesFileError&)` blocks (the five above plus tests).
Table, home 2 (the app): any bad line -> "hydra_rules.ini has an error, so analysis is off until the file is fixed and Hydra is restarted." and, under it, the raw text such as `<path>: <key> = "<value>" is not a number`.
Table, home 3 (the tools): any bad line -> the raw text alone, exit 2. A database that will not open in the same two CLI tools goes through `tool_error`, so it gets the plain sentence plus the raw text (batch.cpp 142, fillcompare.cpp 88).
Differ on: all inputs. Three wordings for one state, and the one in the owner file is the one nobody shows.
Note for the verifier: check that no catch of `std::exception` upstream of these sites turns a `RulesFileError` into `plain_error`. I grepped every `plain_error` call site and every `load_rules_file` call; I did not trace the tests.

### G9-2. What text counts as a number in a hand-edited ini file?
Looks like: K2 (three readers, three grammars; the stored value and the run's rules can differ). Partly written down as deliberate for the settings file ("as atoi always made it", src/app/config.cpp 178).
Homes:
- `parse_finite_number`, src/core/strutil.cpp 80-92 (input: text; decimal keys of hydra_settings.ini read it, config.cpp 180-183; also the .chart Offset and song.ini delay).
- `std::atoi` for whole-number keys of hydra_settings.ini, src/app/config.cpp 177-179.
- `to_double` and `to_int` (`std::stod`, `std::stoi`, then "all text used"), src/app/rules_file.cpp 28-42, for every numeric key of hydra_rules.ini.
Table (my reading of the standard-library rules, not run): value text -> result.
- "4": atoi 4; stoi 4; parse_finite_number 4.
- "4.0": atoi 4 (stops at the dot); stoi throws "a whole number" (used 1 of 3); parse_finite_number 4.
- "5abc": atoi 5; stod/stoi throw; parse_finite_number nothing (reads as 0 in settings).
- "abc": atoi 0; stod throws; parse_finite_number nothing (0 in settings).
- "+5": atoi 5; stoi 5; parse_finite_number 5.
- "nan": atoi 0; `stod` accepts it, and `check_min` lets a NaN through (`d < min` and `d == min` are both false), so the rule becomes NaN; parse_finite_number nothing.
- "inf": stod accepts it and it passes a minimum; parse_finite_number nothing.
- "0x10": atoi 0; stod reads hex 16; parse_finite_number nothing.
- "1e400": stod throws out_of_range (rules file errors); parse_finite_number nothing.
Differ on: nan, inf, hex, "4.0" in a whole-number key. The strutil header says parse_finite_number is "read one way for every such number (.chart Offset, song.ini and .sng delay)", which does not cover the rules file.
Note: the rules file errors on junk by design ("a typo can never silently run the defaults", rules_file.h 3-5), so the junk policy differs on purpose. The grammar (what counts as a number) is the part that may be split by accident. Needs a user decision before any change.

### G9-3. How is a song file opened for reading, and what does the user see when it cannot be?
Looks like: K1 on the message and kind (line-level, known as G2-8), K2 on the sharing rule and on the click path.
Homes:
- `file_byte_source`, src/core/winstr.cpp 238-274 (input: path; `CreateFileW` with `FILE_SHARE_READ | FILE_SHARE_WRITE`).
- `stream_md5`, src/app/analysis.cpp 121-133 (`fopen_utf8` "rb"). Already in G2-8.
- `MappedFile::open`, src/audio/mapped_file.cpp 20-51 (`CreateFileW` with `FILE_SHARE_READ` only; four throws of the same text and kind at lines 25, 30, 43, 46).
- The click path: `hash_chart_file`, analysis.cpp 389-396, swallows any exception and returns an empty hash; src/ui/library_jobs.cpp 506-507 then throws a plain `std::runtime_error("could not read " + path)` with no kind.
Table, file missing: winstr, stream_md5, mapped_file all throw `KindedError(SongFileMissing, "cannot open file: <path>")` and the user reads "Hydra couldn't open the song file. It may have been moved or deleted; run Scan library to update the library." The click path reads "Something went wrong. Try again, and if it keeps happening, report it with the details below." (no kind, so `kSomethingWentWrong`).
Table, file held open for writing by another program: winstr opens it (its comment says this is deliberate, winstr.cpp 239-240). stream_md5 uses `_wfopen` "rb", which the same comment says shares the same way. `MappedFile::open` asks `FILE_SHARE_READ` only, so Windows refuses it with a sharing violation (my reading of the Win32 rule, not run), and the user reads "may have been moved or deleted".
Table, zero-byte file: winstr gives an empty source; mapped_file returns an empty map with no error (lines 34-38).
Table, mapping or view fails (not a missing file): mapped_file throws the same "cannot open file" and `SongFileMissing` (lines 43, 46), so the "moved or deleted" advice is wrong for that cause.
Table, size unreadable: winstr says "cannot read file size: <path>" (lines 229, 248) with the same kind; mapped_file says "cannot open file".
Differ on: sharing mode, and the click path's missing kind.
Note: mapped_file.cpp 21-23 builds its handle without the byte-source helper, so a change to the sharing rule has to be made in two files.

### G9-6. How is a file written so a reader never sees half of it?
Looks like: K2 (three rules for writing a file; the reasons are written down for one).
Homes:
- `write_report_file`, src/app/report_files.cpp 89-117: write to `<path>.tmp`, then `std::filesystem::rename` over the target; remove the temp on failure.
- `Settings::save_file`, src/app/config.cpp 217-239: opens the ini with `std::ios::trunc` and writes in place. Returns `f.good()`.
- The library file swap, src/store/upgrade_files.cpp 40-49 and 67-100: two plain renames with `MoveFileExW` and `MOVEFILE_WRITE_THROUGH`, and no replace flag, because "on FAT and exFAT a replacing rename is a delete and then a rename" (comment 41-44).
Table, the process stops mid-write: report page, the old page stays (the new one never appears). Settings ini, a truncated file (a short or empty file loads as defaults, config.cpp 197). Library file, `recover_upgrade_files` finishes or undoes the swap.
Table, target on FAT or exFAT: the report's `std::filesystem::rename` replaces the target; whether that is one step is not stated there. The upgrade code says a replacing rename is not safe there.
Differ on: the stop-mid-write case, and the replace rule.
Note: the report is regenerable and the settings file is small, so the weaker rules may be deliberate. No comment in config.cpp or report_files.cpp says so. Verifier: decide K2 versus K0.

### G9-8. Hand-trimming in the song.ini reader

## Parallel on purpose

- `starts_with` in strutil.cpp 55 (byte strings) and `starts_with` in winstr.cpp 59-61 (wide strings, in an unnamed namespace). Different types; the wide one serves only the Win32 path prefixes. strutil.h has no wide overload. Each knows only its own string type.
- JSON readers: `jstr`, `jint`, `joptint` in src/net/dmbot_client.cpp 241-257 (an absent or null field becomes a default, because the API sends nulls) versus `need`, `get_f`, `get_i` in src/render/preview_config.cpp 58-70 (an absent key is an error naming its dotted path, because the file is the app's own). Each knows only its own failure policy, which is a per-file fact.
- song.ini reader versus `split_ini_line` (see G9-8): song.ini has `[song]` sections, `;` and `#` as whole-line comments, last value wins, and a BOM. Settings and rules files have flat keys and `#` anywhere. The formats differ.
- Network client: only src/net/dmbot_client.cpp uses WinHTTP. One transport, one test seam (`set_fetcher`), one `ErrorKind` mapping in `fail`. Nothing duplicates it.
- Thread pools: `run_work_pool` (src/app/work_pool.h) is used by src/app/analysis.cpp 657 and 946 and src/app/report.cpp 269. The folder walk at analysis.cpp 583-596 runs its own helper threads, because the work list grows as folders are found (my reading of `walk`; not read in depth, so G2 may want to confirm). The allocator calls (src/app/allocator.cpp) are the only users of mimalloc by name.
