# G8 report: the audio readers (src/audio/, 20 files)

Scout: concept-audit-G8 (agent id used for status lines: G8, because the progress hook never named another). Read in full: all 20 files in src/audio/. Outside reads: core/winstr.cpp 205-300, ui/app_shell.cpp 70-115, ui/preview_controller.cpp 300-345, ui/preview_tab.cpp 385-393, plus greps for users of the audio API.

## The direct answer to the dispatch question

`StemReader` (stem_reader.h 39-61) is an interface only. It holds no data and no loop. Four readers sit on it: `MaReader` (WAV/FLAC), `Mp3Reader`, `VorbisReader`, `OpusReader`. Two small helpers in stem_reader.h's `detail` namespace carry the parts the readers share:

- `seek_clamp_or_end` (stem_reader.h 119-132): the first step of every reader's `seek`. All four call it.
- `CountedLength` (stem_reader.h 145-196): counting a stem whose header says 0 frames, and seeking that stem by decoding. Only `MaReader` and `VorbisReader` use it.

Everything else is written once per reader. The shared member names the leads found are real, but they are state each class repeats, not state on a base. I checked the lead's counts against the code:

- `VorbisReader` and `MaReader` both hold `at_end_`, `channels_`, `counted_`, `length_`, `pos_`, `rate_`, `scratch_`. Seven, as the lead says.
- `VorbisReader` and `Mp3Reader` share six of those (all but `counted_`). Correct.
- `OpusReader` and `MaReader` share `at_end_`, `channels_`, `length_`, `failed_`, `dec_`. `dec_` is a name collision: an `ma_decoder` in one and an `OpusDecoder*` in the other. That is K0. `OpusReader` has no `rate_` (it returns the constant `kRate`), no `pos_` (it counts in `gpos_`, link samples), and no `scratch_` (it has `pcm_`).

What each reader writes for itself:

| | MaReader | Mp3Reader | VorbisReader | OpusReader |
|---|---|---|---|---|
| read loop | loops `ma_decoder_read_pcm_frames` until `frames` or 0 (ma_reader.cpp 202-219) | one call to `ma_dr_mp3_read_pcm_frames_f32`; a short answer ends the stem (415-422) | loops `stb_vorbis_get_samples_short_interleaved` in 4096-frame chunks, int16 to float (vorbis_reader.cpp 64-81) | drains `pcm_`, then `decode_next` per packet (opus_reader.cpp 257-277) |
| end flag | `at_end_`, set on `MA_AT_END` or 0 frames | `at_end_`, set on a short read | `at_end_`, set on 0 or less frames | `at_end_`, set when the last link runs out |
| length | header; if 0, counted by `CountedLength` | `ma_dr_mp3_get_pcm_frame_count` (the library counts) | header; if 0, counted by `CountedLength` | sum of link lengths from its own page index; throws if 0 |
| restart / "back to frame 0" | `restart()` = seek to 0 | `restart_and_skip()` = seek to 0, then decode forward | `restart()` = `stb_vorbis_seek_start` | `start_link()` resets the decoder |
| position counter `pos_` | yes | yes | yes | no |
| `failed()` | yes | no (default false) | no (default false) | yes |

So: read loop, end-of-stream rule and `restart` are per reader. The length rule is per reader too, with `CountedLength` shared by two of the four. The shared member names are real repetition, the loops are per-decoder. The differences that matter are in G8-2 to G8-4.

## Candidates

### G8-1. Do the readers repeat the same cursor bookkeeping (end flag, position, the three accessor lines, the clamp)?
Looks like: K3-with-a-rule-inside. The framework is `StemReader` plus `seek_clamp_or_end` and `CountedLength`. The rule inside is "when is a stem at its end, and where is its cursor".
Homes: `MaReader`, ma_reader.cpp 170-258; `VorbisReader`, vorbis_reader.cpp 30-117; `Mp3Reader`, ma_reader.cpp 382-540; `OpusReader`, opus_reader.cpp 208-415. Inputs: the decoder's answer to a read or a seek, plus `length_`.
Table, end of stem (the rule each reader applies):
- decoder returns fewer frames than asked: MaReader keeps looping until 0 frames or `MA_AT_END`; VorbisReader keeps looping until 0; Mp3Reader sets `at_end_` at once; OpusReader keeps decoding until the link list is empty.
- seek to `frame >= length_`: all four end the stem there (`seek_clamp_or_end`, one rule, one home).
- seek to `frame < length_` but the decoder refuses: MaReader and VorbisReader set `at_end_ = true` and still set `pos_ = frame`; Mp3Reader sets `at_end_` and sets `pos_ = frame`; OpusReader has no refusal path (`start_link` clears `at_end_`).
- reads past the end: all four return 0 and stay at the end until a seek.
- cursor `pos_`: kept by three readers, not by Opus (which keeps `gpos_` in link samples).
Table, the one-line accessors `channels()`, `sample_rate()`, `length_frames()`: written four times, each returning the class's own member.
Differ on: none today that a user hears. The part that could split is the "short read means end" rule (Mp3Reader treats a short read as the end; the other three need a read of 0). With a decoder that returns a short read mid-stream, Mp3Reader would end the stem early and the other three would not.
Note: the verifier should decide whether the repeated members are worth lifting onto a base class or are fine as they are. I read all four classes in full.

### G8-2. How many frames does a stem have, and who decides?
Looks like: K2 (same word "length", rules differ at the edge). Not a word the user sees; it changes how much audio plays at a stem's tail.
Homes: each reader's `length_frames()` (the table above); `read_all`, decode.cpp 18-45 (inputs: a reader; it reserves `length_frames()`, then keeps reading until the reader returns 0, and keeps any extra frames); `StreamMix` constructor and `read`, stream_mix.cpp 183-221 and 225-253 (inputs: `length_frames()`; converts it with `ma_data_converter_get_expected_output_frame_count` and stops reading the stem at that count).
Table, home 1 (`read_all`, test path): decoder yields D frames, header or count says L.
- D == L: L frames.
- D > L: D frames (the extra is kept, comment decode.cpp 13-17).
- D < L: D frames; throws only if `failed()` is true.
Table, home 2 (`StreamMix`, the Preview's path): same inputs.
- D == L: L frames.
- D > L: L frames (`want = min(m, converted_length - out_pos)` stops at L; the extra is never played).
- D < L: D frames, then the stem is marked `ended` and plays silence; the mix's own `length_` still includes the silent tail.
Differ on: D > L. `OpusReader` cannot hit this (its `read` stops at `end_g`). `MaReader`, `Mp3Reader` and `VorbisReader` could, if the header or the library's count is short of what the decoder yields.
Note: I did not check whether `ma_dr_mp3_get_pcm_frame_count` always equals what `ma_dr_mp3_read_pcm_frames_f32` produces after the encoder delay; the code in ma_reader.cpp 8-25 says the two once disagreed and the reader works around that. A stem length of 0 also differs by reader: an empty Opus throws at open ("no Opus audio decoded"), an empty WAV/Vorbis opens with length 0, and `read_all` returns an empty result without throwing. In the Preview the outcome is the same (silence), because `open_song_stems` skips a stem that throws and `StreamMix` gives a length-0 stem nothing to play.

### G8-3. What does a decode error do, and who finds out?
Looks like: K2 (same idea, different rules by reader and by caller). In the Preview the user sees nothing; the effect is a stem going silent.
Homes: `failed_` in `MaReader` (ma_reader.cpp 210-215, and the counted-seek path 225-227) and `OpusReader` (opus_reader.cpp 375-379); no `failed()` in `Mp3Reader` and `VorbisReader`; `read_all`, decode.cpp 42 (throws `KindedError(AudioDecode)` if `failed()`); `StreamMix::read`, stream_mix.cpp 246 (any short stem goes silent, never asks `failed()`); `open_song_stems`, song_audio.cpp 57-62 (any exception at open skips the stem).
Table by reader, error mid-stream:
- MaReader: `failed_` set, stem ends.
- OpusReader: `failed_` set (when `opus_decode_float` returns below 0), stem ends. A page with a bad checksum is skipped silently (opus_reader.cpp 341), and the index pass resyncs silently over damage (112-124).
- Mp3Reader: stem ends at the short read, `failed()` stays false. No comment says this is on purpose.
- VorbisReader: stem ends, `failed()` stays false. Comment says why: stb_vorbis cannot tell an error from the end (vorbis_reader.cpp 86-87).
Table by caller, same error:
- `decode_audio`/`decode_stem` (only tests call them; I counted callers in src/, tests/ and tools/): throws for MaReader and OpusReader, does not throw for Mp3Reader and VorbisReader.
- Preview (`StreamMix`): the stem goes silent for all four.
Differ on: the same damaged stem throws in `decode_audio` if it is a FLAC or Opus and returns short audio if it is an MP3 or Ogg Vorbis. `failed()` has no reader in the Preview path (no caller of `failed()` outside decode.cpp).
Note: the header (stem_reader.h 56-60) says `failed()` exists so `decode_audio` keeps failing loudly "as the old decoders did". The two readers without `failed()` therefore may or may not match the old decoders; I did not check history.

### G8-4. How does a reader get to a frame by decoding forward and throwing the audio away?
Looks like: K1 on the loop shape, K2 on the error and the distance rule.
Homes: `CountedLength::seek`, stem_reader.h 172-192 (inputs: target frame, current `pos`, a `decode(n)` that returns `DecodeStep`); `Mp3Reader::skip` and `restart_and_skip` and the short-hop branch in `Mp3Reader::seek`, ma_reader.cpp 424-443 and 509-523 (inputs: target frame, `pos_`, `rate_`).
Table, home 1 (`CountedLength::seek`, used by MaReader and VorbisReader on a counted stem):
- target ahead of `pos`: decodes forward from here, any distance.
- target behind `pos`, or stem at its end: restarts at frame 0 and decodes forward.
- decode error during the skip: the call returns true; MaReader sets `failed_`, VorbisReader ignores it.
- decode ends before the target: `at_end` set.
Table, home 2 (`Mp3Reader::seek`):
- target equal to `pos_` and not at the end: nothing.
- target ahead by at most one second (`rate_` frames): decodes forward from here (`skip`).
- target farther: seeks by the table, checks where it landed, and falls back to `restart_and_skip` (frame 0, decode forward).
- decode ends before the target: `at_end_` set; no error is ever reported.
Differ on: how far ahead "decode forward from here" is allowed (any distance in `CountedLength`, one second in Mp3) and whether a decode error is reported (MaReader yes, VorbisReader and Mp3Reader no). Both differences have reasons (Mp3 has a table seek to fall back on; `CountedLength` has none), so this may read as K3.
Note: `restart` is one of the leads (ma_reader.cpp, vorbis_reader.cpp). In both it is a one-line wrapper over a different decoder call (`ma_decoder_seek_to_pcm_frame(&dec_, 0)` against `stb_vorbis_seek_start`), handed to `CountedLength` as a lambda. That is per-decoder, not a copy. The shape around it is `CountedLength`. I count `restart` as K0 and this block as the live part.

### G8-5. Is this stem usable audio (channels, rate)?
Looks like: K1, line-level (agree on every input I could reach; one input I could not reach may differ).
Homes: `MaReader` constructor, ma_reader.cpp 176-181 (channels only); `Mp3Reader` constructor, 389-391 (channels and rate; failure leaves `ok_` false and the bytes go to MaReader); `VorbisReader` constructor, vorbis_reader.cpp 43-48 (channels and rate); `OpusReader` constructor, opus_reader.cpp 215-217 (channels must be 1 or 2); `read_all`, decode.cpp 22 (channels); `StreamMix` constructor, stream_mix.cpp 192 (null reader, channels or rate not above 0: dropped).
Table (channels, rate): (0, any): all six refuse (throw, or drop in StreamMix). (above 0, 0): MaReader and `read_all` accept; Vorbis, Mp3 and `StreamMix` refuse. (3 or more, any): Opus refuses; the others accept.
Differ on: (above 0, 0) for `MaReader` only. Probably unreachable, since `ma_decoder` fills the rate from the file; I did not check miniaudio.
Note: the same "drop a stem that cannot play" happens a third time in `open_song_stems`, which skips any stem whose open throws (song_audio.cpp 60-62), and in `map_song_stems`, which drops a loose file that will not map (13-32).

### G8-6. The mixing rule written twice: `mix_stems` and `StreamMix`
Looks like: K3-with-a-rule-inside, parallel on purpose. `mix_stems` is a test oracle kept in src/ (mixer.h 12-15). Callers of `mix_stems` in src/: none outside src/audio (my grep of src/ for `mix_stems`, `decode_audio`, `decode_stem` found only src/audio hits; users are tests/test_audio_mixer.cpp, test_audio_decode.cpp, test_stream_mix.cpp, test_stem_reader.cpp and tests/fuzz/harness.h).
The shared owner: `stem_converter_config`, mixer.cpp 10-19, called by both (the settings and the passthrough rule have one home).
What each side writes for itself: the length of a converted stem; the sum; the error type.
Homes: `convert_stem` and `add_into`, mixer.cpp 28-65; `StreamMix` constructor and `read`, stream_mix.cpp 183-253.
Table, converted length of one stem: `mix_stems` uses `out_produced` (what the converter really gave); `StreamMix` uses `ma_data_converter_get_expected_output_frame_count` (the estimate) as `converted_length`. They agree today because tests/test_stream_mix.cpp pins the equality (comment stream_mix.h 58-63).
Table, sum: both start from 0.0f and add stem by stem, in order.
Table, error on converter failure: `mix_stems` throws `std::runtime_error("mix_stems: data converter init failed")`; `StreamMix` throws `KindedError(AudioDecode, "StreamMix: data converter init failed")`.
Differ on: converter length (estimate against produced) if a rate pair ever makes them differ by one frame; the exception type on a converter failure (a plain `runtime_error` against a kinded error).
Note: mixer.cpp and device.cpp throw a plain `std::runtime_error`; every other throw in src/audio is a `KindedError`. Only `StreamMix`'s kind can reach the user's message (user_messages.cpp 53-55, 97); the device failure shows a fixed sentence plus the raw text on hover (preview_tab.cpp 389-393). So the plain type causes no wrong wording today.

### G8-8. How many frames go in a decode block (4096)?
Looks like: K1 on the number, K0 on the meaning.
Homes: `kSkipChunk` ma_reader.cpp 166 (MaReader, Mp3Reader); `kChunkFrames` vorbis_reader.cpp 28; `StreamMix::kBlockFrames` stream_mix.h 89; the literal `4096` twice in decode.cpp 34-35.

## Parallel on purpose

- `StemReader` against `MixSource` (stem_reader.h 39-61, stream_mix.h 29-40). Both are an interface of `channels`, `sample_rate`, `length_frames`, `read`, `seek`, with the same contract sentences ("returns frames read, 0 at the end", "never throws", "seek clamped to [0, length]"). `StemReader` knows: one codec's native rate and channels, `failed()`, and the rule that a decode error ends the stem. `MixSource` knows: the one output format the mix plays at. Each entry is a per-module fact. The contract text is copied between the two headers, which is a comment and not a rule, so I did not make it a candidate.
- `Playhead` against its source (player.cpp 14-18, player.h 68-77): it copies `channels_`, `sample_rate_` and `length_` out of the source once. It knows: the playing flag, the position, the gain and where the source's own cursor is. Per-module facts.
- `PreviewAudioDevice` (device.h/.cpp): it knows only the pull callback, the headless switch and the start-fail test switch. Nothing it holds overlaps another audio module. Its errors are plain `runtime_error` (G8-6 note).
- The four readers against each other (G8-1): the per-codec parts (frame header scan and seek points in Mp3; page index, links, pre-skip and gain in Opus; stb_vorbis calls in Vorbis; ma_decoder calls in Ma) are codec facts and sit only in their own reader.

## Dropped leads

- `dec_` shared by `MaReader` and `OpusReader`: K0, two different decoder types under one member name.
- `restart` in ma_reader.cpp and vorbis_reader.cpp: K0 for the function itself (each is one call into a different decoder); the shape around it is G8-4.
- `read_all` in audio/decode.cpp and core/winstr.cpp: K0. decode.cpp's reads frames out of a `StemReader` (and throws on `failed()`); winstr.cpp's (line 293) reads all bytes out of a `ByteSource`. Same word, different questions. Group G9 owns winstr's.
- `rate_` and `kRate` (Opus) against `kOutRate` (song_audio.h 28): K0. Opus always decodes at 48 kHz (a codec fact); `kOutRate` is the mix and device format. They are equal on purpose, so an Opus stem passes through without resampling, but nothing needs them to be.
- `Mp3Reader` six shared members with `VorbisReader`: covered by G8-1; no further finding.
