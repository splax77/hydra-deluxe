# G11b report: the library's dialogs, toolbar and widgets

Scout: G11b (agent id G11b; the progress hook never named another id). Read-only. All 16 files in the group read in full. Paths below are under `src/` unless a full path is shown.

Short answer to the group's question. The dialogs and toolbar mostly ask the model or app state: `can_scan`, `batch_running`, `analysis_blocked`, `path_report_build`, `with_analysis_defaults`, `fill_rule_name`, `counted`, `group_thousands`, `why_not_comparable` all have one owner and are called, not copied. The leftovers are word-level and a few small rules the dialogs spell for themselves. The most useful new finding is that `describe_settings` in `app/config.cpp` says it is "the one place" a setting's value is spelled, and the dialogs spell the same three values again with different words.

### Also seen in G11b: G2-5 (the batch's counts worded twice)
What is new from `ui/library_dialogs.cpp`:
- GUI order and gloss: "N analyzed · N failed · N skipped (already had a result)" (`batch_counts`, 54-58). CLI (`cli/batch.cpp` 260-263): "Analyzed N, skipped N already stored, N failed". So the order differs (failed and skipped swap) and the gloss for the same count differs ("already had a result" against "already stored").
- `batch_counts` writes the first two words through `counted(n, "analyzed", "analyzed")`, using `counted` only for its thousands grouping. `counted` in `core/model.h` 873-875 is documented as "Every screen writes counts here"; the CLI does not use it (it calls `group_thousands`).
- The word "finished" means two counts on the GUI side. The Stop tooltip (dialogs 481-482) says "Keeps the N charts already finished" and passes `s.analyzed`. The progress line "N of M" (dialogs 443) passes `s.completed`, which is analyzed plus failed (`app/analysis.h` 218). The stopped line says "Every result finished before Stop is kept." (536). So "finished" counts stored charts in two places and counts stored plus failed in the progress line.
- The same skipped count is worded three ways inside the confirm and strips: "skipped (already had a result)" (strip), "that already has/have a result" (confirm question, 351 and 354) and "(N charts)" beside "Also re-analyze charts that already have a result" (379-382). All come from `batch_scope_with_result()` = `batch_plan.skipped` (`ui/app_state.h` 579), so the number has one owner.

### G11b-1. Can an analysis start, and how many charts does the Analyze button cover?
Looks like: K1 (with a difference on purpose between two counts).
Homes: `render_actions_row`, `ui/library_toolbar.cpp` 78-98 (inputs: `library.searching()`, `library.counts().all` through `library_match_count`, `library.rows().size()`, `analysis_blocked()`, `batch_running()`);
       `render_batch_confirm`, `ui/library_dialogs.cpp` 344-345 and 391 (inputs: `batch_plan.skipped`, `batch_plan_for(redo).todo_rows()`, `analysis_blocked()`);
       `AppState::start_batch`, `ui/app_state.cpp` 556-558 (inputs: `analysis_blocked()`, `batch_running()`);
       `AppState::open_batch_confirm`, `ui/app_state.cpp` 526-548 (input: `library_matches()` = `library.matches()`, `ui/library_model.cpp` 217-223).
Table, home 1 (the toolbar button, enabled or not):
  - Library empty (0 rows): off (`analyzable == 0`).
  - Library of 5 rows, no search: on, label "Analyze library...".
  - Search typed that does not parse: `searching()` false, so on, whole library.
  - Search matching 0 rows: off, label "Analyze search (0)...".
  - Rules file bad (`analysis_blocked`): off.
  - Batch running: off, tooltip "Busy: a batch is running.".
  - All 5 rows already have a result: on (the button counts matched rows, not to-do rows).
Table, home 2 (the confirm's Start button) and home 3 (`start_batch`):
  - All 5 rows already have a result, Also re-analyze unticked: confirm opens, says "Every chart here already has a result.", Start off (`to_run == 0`).
  - Same, ticked: Start on, `to_run` = 5.
  - Rules file bad: Start off; `start_batch` returns.
  - Batch running: the confirm has no check (it cannot be opened then, because the toolbar button is off); `start_batch` returns.
Differ on: the zero test. The toolbar disables on zero matched rows. The confirm disables on zero to-do rows. They count different things on purpose (matched rows against rows without a result), so this is the intended split. Also the count itself: the toolbar's N is `searching ? counts().all : rows().size()`, while `open_batch_confirm` uses `matches().size()`. They agree today because `counts_.all` is built from the same query match (`library_model.cpp` 285). The comment at `app_state.cpp` 529-530 already says a stale row list could make the confirm count fewer than the button's N.
Note: there is a `can_scan()` owner for the scan button (`app_state.cpp` 458-460) but no `can_analyze()`. The scan side is one predicate in one place; the analyze side is spelled in three. The same is true of "start a scan and open its modal": the toolbar does `start_scan(); OpenPopup("Scanning charts")` (library_toolbar.cpp 70-73) and the main window does the same behind `request_scan` and `if (app.scan_job)` (library_view.cpp 182-186). The toolbar form opens the popup whether or not `start_scan` made a job; it is safe only because the button is greyed by the same `can_scan`.

## Parallel on purpose

- Time-left text. `time_left_text` (`ui/library_parts.h` 63-65) is the one wording ("about 1:30 left"), used by the batch strip (`library_dialogs.cpp` 456) and by `gated_time_left_text` (`ui/preview_load_job.cpp` 299-302), which the Preview loader and the startup box share. What each side knows: the batch side knows the "3 charts finished" gate (`batch_eta_s`, `library_jobs.cpp` 275-278) and its average-per-chart estimate; the loader side knows the "seconds elapsed" gate and a byte rate. Both are per-job facts about when an estimate is believable. I did not read the byte-rate clock's code, only the gate line; the verifier should confirm there is no second copy of the estimate.
- Disabled looks. `begin_disabled_button`, `begin_disabled_input`, `begin_disabled_checkbox` (`ui/theme.cpp` 80-129) each push their own list of colours. Each list is a per-control fact (which ImGui slots a button, an input and a checkbox have). The three share `kDimTextColor` and `kDisabledInputBgColor` through the theme constants, so no colour is written twice.
- Progress bars. `progress_fraction` (`ui/widgets.h` 68-71) is the one clamp; `progress_bar_counted`, `progress_bar_percent` and the strip's direct `ProgressBar` call (`library_dialogs.cpp` 452) all take their fill from it or from a fraction already built from it. The overlays differ because the screens differ ("done / total" and "42%").
- Strip backgrounds. `kDoneStripBg` and `kProblemStripBg` are the theme's (shared with the report windows); `kStripBg`, `kStripText2`, `kStripTrack`, `kDoneText2`, `kProblemText2` are local to `library_dialogs.cpp` 41-45. The local ones are used only by the batch strips, so they are per-module facts.
- Fixed-width slots (`widest_digits`, `button_slot_width`, `text_in_slot`, `button_in_slot` in `widgets.h`). The one rule ("a changing number takes the width of its widest value") is stated once and each caller supplies its own sample. The toolbar's `analyze_w` and `manage_widest` are per-button samples.
- `ui/icons.cpp`/`icons.h`, `ui/fonts.h`, `ui/label_layout.h`, `ui/win32_dialogs.*`, `ui/imgui_files.cpp`, `ui/resource.h`. Each holds one thing (icon file list, font handles and `px`, label spacing arithmetic, the folder picker, ImGui's file hooks, one resource id). I looked for a second home of each and found none inside `src/ui`. `spaced_labels` is used by the Paths tab timeline only (stated in its header).
