# G3 report: who knows which settings an analysis, a page or a view depends on

Scout: concept-audit-G3 (read-only, phase 2). All paths are under `C:\Users\Patrick\Downloads\Hydra\hydra-test\src` unless a test path is given. Line numbers are from the files as read on 2026-10-11.

## The short picture

Ten fields of `app::Settings` decide which result Hydra shows: Difficulty, Pro Drums, 2x Bass, Note Shuffle, the SP cap, the ms limit (on/off and value), the score range (mode and value) and 1.0 fills. The rules file is an eleventh input, but it only changes on restart. The same ten fields are the Analysis settings panel, the Reset button, the record key, and `to_analysis_settings`. Nothing in the code says "these ten are one set". Each consumer spells the set again by hand. `Settings::record_key` is a good single owner for one chart, but the same three parts (chart mode, cap, lens) travel as loose arguments or are compared field by field in at least eight other places.

I found no place where two of those hand lists disagree about a result. I found two places where a consumer reads a setting that the matching list does not name (candidates G3-2 and G3-3). Both are unreachable today for a stated reason, which is the exact shape the audit looks for.

## Every place that lists which settings matter

Each line gives the list, then where it got it.

**The store key** (`store/record_store.cpp` 215-239, `lens_match` and `bind_lens` 318-330). Columns: hash, chart mode text, `sp_cap`, `ms_enabled`, `ms_value`, `depth_mode`, `depth_value`, `legacy_fills`, `rules_fp`. Hand-kept in four spots inside the store (the table definition, the UNIQUE clause, `lens_match`, `bind_lens`) and again in the INSERT list at line 1221. It got the list from `store::Lens` and `CapQuery` in `store/record_store.h` 100-146, which in turn were written by hand to match `Settings::lens()` and `cap_query()`. Rules arrive separately as the stamp. Stale (store lines 359-383) is two facts only: the row's version stamp is current, and the row's `rules_fp` equals the process's. Settings never make a row Stale; a different key just finds no row (NotAnalyzed).

**`Settings::chartmode_key`** (`app/config.cpp` 266-279). Difficulty, Pro Drums, 2x Bass, Note Shuffle. Hand-kept text. `with_chartmode` (297-313) walks the same four fields by brute force and compares through `chartmode_key`, so its answer is derived from the key. Its loops still name the four fields by hand.

**`Settings::cap_query`, `lens`, `record_key`, `batch_run`** (config.cpp 336-352). `cap_query` is the SP cap. `lens` is ms limit, depth mode, depth value, 1.0 fills. `record_key` and `batch_run` assemble the pieces from those two and `chartmode_key`, so the set is derived there.

**`Settings::to_analysis_settings`** (config.cpp 315-328). All ten fields plus rules, copied into `AnalysisSettings` (`app/analysis.h` 158-168) and its base `SearchSettings` (`search/pather.h` 31-44). Hand-kept. The comment on `SearchSettings` says it "mirrors the user's settings" but holds only what reaches the search.

**`hydra::settings_key(SearchSettings)`** (`search/pather.cpp` 65-75, declared at `search/pather.h` 46-49). Cap, depth mode, depth value, ms filter, fill rule, rules fingerprint. Hand-kept. The header says "A new SearchSettings field that changes the result must be added here." It leaves out the four parse choices on purpose; the test cache in `tests/corpus_util.h` 217-222 spells prodrums, bass2x and difficulty beside it and leaves out Note Shuffle (that helper does not apply Note Shuffle at all, so this is consistent today). A test pins the key text and has one hand-written line per field (`tests/test_engine_sweeps.cpp` 549-565), so a new field is caught only if someone adds a line there too.

**`AppState::apply_settings`** (`ui/app_state.cpp` 853-872). The "reload when a setting changed" check. Refresh library summaries and restart the open song's analysis when `chartmode_key`, `cap_query` or `lens` changed. Hand-kept triple. Then ask each report's own function.

**`report::settings_change_touches`** (`app/report.cpp` 431-437). `cap_query` and `lens`. Reason in its comment: the report lists every chart mode, so the mode does not reach a row.

**`dm_report::settings_change_touches`** (`app/dm_report.cpp` 237-241). `chartmode_key` and `lens`. Reason in its comment: results are always at Clone Hero's cap.

**`dm_report::why_not_comparable`** (`app/dm_report.cpp` 33-49). Difficulty, SP cap, 1.0 fills, Note Shuffle. Its callers: `ui/library_toolbar.cpp` 104-107 (from the Settings fields) and `collect_dm_rows` (dm_report.cpp 61-65).

**`PreviewSongKey` and `PreviewController::open`** (`ui/preview_controller.h` 56-68 and 94-97). md5, difficulty, Pro Drums, 2x Bass, Note Shuffle, plus the cap and path key. The comment says these are "the inputs `Settings::to_analysis_settings` reads to pick the notes". Hand-kept; `preview_tab.cpp` 356-358 passes them from the Settings fields.

**`PathsTabCache::details` and `buttons`** (`app/path_view.cpp` 562-599). Details are rebuilt when the record generation, the path, the hit window, the backend limit, the song length or Pro Drums changes. Buttons are rebuilt when the record generation, depth mode or depth value changes. Hand-kept. The comment in `path_view.h` 265-268 says the rules are left out because they only change on restart.

**`dynamics_for_settings`** (`app/dynamics_breakdown.cpp` 143-160). Pro Drums, 2x Bass, difficulty, Note Shuffle as separate arguments. `ui/dynamics_tab.cpp` 145-147 reads Pro Drums and 2x Bass from Settings again to decide which rows to draw.

**The panel** (`ui/settings_bar.cpp` 81-194). One widget per setting. It holds no list of "what changes results"; every control calls `commit_settings` (or `edit_settings` for number boxes) and `apply_settings` does the deciding. The header comment of `commit_settings` (`ui/app_state.h` 623-635) claims it is "the single place that knows which settings change a record's identity". That is true of the refresh. It is not true of the reports (their own functions) or the Preview and Paths tab (their own keys).

**`Settings::with_analysis_defaults`** (config.cpp 281-295) and **`settings_change_phrases`** (`ui/library_dialogs.cpp` 104-123). The Reset button's ten fields and the summary's eight phrases. Hand-kept. The second takes its defaults from the first, so they cannot disagree about values, only about which settings are in the set.

**`batch_settings_summary`** (library_dialogs.cpp 86-98) and **`describe_settings`** (config.cpp 354-361). The batch confirm's five rows and the CLI header's three words.

## Candidates

### G3-1. Which settings pick a stored result? (the chart mode, cap and lens, kept as three loose parts)
Looks like: K3-with-a-rule-inside. The shared framework is `RecordKey`. The per-module parts should be only facts. Several parts hold a rule: "which parts must match" and "which settings count".
Homes: `Settings::record_key`, `app/config.cpp` 346-348 (hash, chartmode_key, cap_query, lens);
       `AppState::apply_settings`, `ui/app_state.cpp` 858-859 (chartmode_key, cap_query, lens compared one by one);
       `report::settings_change_touches`, `app/report.cpp` 431-437 (cap_query, lens);
       `dm_report::settings_change_touches`, `app/dm_report.cpp` 237-241 (chartmode_key, lens);
       `run_batch` seed guard, `app/analysis.cpp` 877 (seed chartmode, cap, lens against the run);
       `collect_rows` guards, `app/report.cpp` 207 and 210-211 (cap, lens, max_paths against options and seed);
       the loose-argument calls `library_jobs.cpp` 67-68, `app_state.cpp` 683-684 and 702, `cli/fillcompare.cpp` 78-80, `RecordStore::get_summaries`, `list_records` and `analyzed_hashes` (chartmode, cap, lens as three arguments).
Table, home 1 (`apply_settings`: does the open song and the library summaries reload?): Difficulty, Pro Drums, 2x Bass, Note Shuffle -> yes. SP cap -> yes. ms limit on/off -> yes. ms value while the limit is on -> yes. ms value while the limit is off -> no (the lens is canonical, value stored as 0). Score range mode or value -> yes. 1.0 fills -> yes. hit window, backend limit, volume, auto-open, dm user -> no.
Table, home 2 (path report out of date?): chart mode fields -> no. SP cap -> yes. ms limit, score range, 1.0 fills -> yes (all in the lens). hit window -> no. auto-open -> no.
Table, home 3 (comparison out of date?): chart mode fields -> yes. SP cap -> no. ms limit, score range, 1.0 fills -> yes. hit window -> no. auto-open -> no.
Differ on: the three agree wherever the settings are in the key. They differ on purpose on the cap and the chart mode, and each reason sits in a comment, not in data. See G3-3 for the one setting they leave out.
Note: nothing derives the three lists from what each consumer actually passes to the store. `ReportOptions` holds `cap`, `lens` and `run` (which holds the same two again), and `collect_rows` fails loudly if they disagree (report.cpp 206-212), so the duplication is already a source of guards. The verifier should check whether a `ChartIdentity {chartmode, cap, lens}` value would remove the guards, or whether the guards are cheap enough to leave.

### G3-2. Can this chart mode be compared with the leaderboard? (two callers of one gate, different inputs)
Looks like: K2.
Homes: `why_not_comparable` called from the toolbar, `ui/library_toolbar.cpp` 104-107 (real `settings.difficulty()`, `settings.sp_cap`, `legacy_fills`, `view_noteshuffle`);
       `why_not_comparable` called from `collect_dm_rows`, `app/dm_report.cpp` 61-65 (difficulty is the literal `Difficulty::Expert`, cap is the literal `kCloneHeroSpCap`, legacy_fills from the lens, Note Shuffle read back from the chart mode text through `with_chartmode`).
Table, home 1 (toolbar button): a Hard mode -> refused, "Needs Expert". SP cap 8 -> refused. 1.0 fills on -> refused. Note Shuffle on -> refused. All four at their normal values -> allowed.
Table, home 2 (`collect_dm_rows`, what Refresh and Try again run through `launch_dm_report`, `app_state.cpp` 681-686, with the current `chartmode_key()`): a Hard mode -> not refused, the Hard results are compared with the Expert leaderboard. SP cap 8 -> not refused, but the rows come from the cap-4 results, so this one is correct. 1.0 fills on -> refused. Note Shuffle on -> refused.
Differ on: a non-Expert chart mode in the second caller. The comment at dm_report.cpp 55-60 says "the difficulty is folded into `chartmode`, so the caller's settings take that rule to the same owner", meaning the toolbar is the gate for difficulty. The window's Refresh (`ui/dm_report_window.cpp` 142-143, `AppState::request_dm_report`) is not gated by the toolbar, and it runs on the current settings.
Note: I read this from the code only; I did not run it. The verifier should check (a) that Refresh is reachable with Difficulty set to Hard after a comparison was built (the touches function marks the window out of date for a mode change, so the Refresh button is the expected next click), and (b) that no test calls `collect_dm_rows` with a non-Expert chart mode (I found none in `tests/test_dm_report.cpp`; its `why_not_comparable` tests at lines 701-745 only call the gate directly). `with_chartmode` returns the difficulty as part of `mode`, so the real value was available at that line.

### G3-3. Which settings does the path report read? (a setting it reads that its out-of-date rule does not name)
Looks like: K1, hand list shorter than what the consumer reads.
Homes: `AppState::launch_path_report`, `ui/app_state.cpp` 705-713 (hands `settings.hit_window_ms` to `ReportJob`, which uses it for the timing tier labels, `app/report.cpp` 299 and 359);
       `report::settings_change_touches`, `app/report.cpp` 431-437 (cap_query, lens; no hit window).
Table, home 1 (what the report reads): cap, lens, hit window (tier bands and the Beyond edge text), rules (restart only), run settings from `batch_run()`.
Table, home 2 (what the out-of-date rule names): cap, lens.
Differ on: hit window. The report reads it; the rule does not list it.
Note: unreachable today. `hit_window_ms` has no widget (the only writers are `Settings::load_file` and the INI), so it cannot change while a report sits in memory. The 2026-10-08 wave 2 handoff (`docs/handoffs/2026-10-08-report-windows-wave2-handoff.md`, line 68) already records "if a hit-window control is ever added, the path report's out-of-date rule needs the hit window too. It's one line". The test at `tests/test_report_rows.cpp` 839-868 uses `auto_open_report` as its "a setting no report reads", so it would not catch this. The Paths tab handles the same setting a third way: it re-reads `hit_window_ms` every frame and compares it with the last build (`PathsTabCache::details`, path_view.cpp 567). So one dependency (the hit window) is carried by a pull-style cache key in one place and a push-style out-of-date list in another, and the list is the one that is missing it. The lead is not in the derivation audit.

### G3-4. Which settings does the Analysis panel own, and what is their set? (the ten fields spelled by hand in six or more places)
Looks like: K3-with-a-rule-inside (the rule is "which settings are in the set").
Homes: `with_analysis_defaults`, config.cpp 281-295 (10 fields);
       `to_analysis_settings`, config.cpp 315-328 (the same 10 fields, plus rules);
       the key trio `chartmode_key` + `cap_query` + `lens`, config.cpp 266-279 and 336-344 (the same 10 fields);
       `with_chartmode`, config.cpp 297-313 (4 of them, by loop);

       `render_chart_group`, `render_rules_group`, `render_paths_group`, `ui/settings_bar.cpp` 81-194 (8 settings, 10 widgets).
Table, home 1: for each of the ten fields, is it in the Reset set, the key and the analysis settings? Yes in all three for every field. Rules is in `to_analysis_settings` only, correctly (restart only). Hit window, backend limit, volume, auto-open, dm user, folders are in none.

Differ on: nothing today. They agree on every field.

Which of these the compiler or a test would catch if one were forgotten: `settings_key` has the pinned test (test_engine_sweeps.cpp 549-565); `record_store.cpp` has a `static_assert` on the summary columns only, not on the key columns. ### G3-5. What does 0 and 1 mean for the score-range unit? (one switch kept as an enum and as two ints)

## Parallel on purpose

**`SearchSettings` against `AnalysisSettings` and `Settings`.** `SearchSettings` holds: depth mode, depth value, ms filter, SP cap, fill rule, rules. `AnalysisSettings` adds: Pro Drums, 2x Bass, Note Shuffle, difficulty. `Settings` adds the INI-only fields (folders, volume, hit window, backend limit, auto-open, dm user). Every entry is a per-layer fact: what reaches the search, what reaches the parser, what the user stores. `report::settings_for_mode` (report.cpp 69-77) relies on the split and takes the parse half from `with_chartmode`, so it is derived, not copied.

**`PreviewSongKey` against the chart mode.** The Preview's key holds md5, difficulty, Pro Drums, 2x Bass, Note Shuffle. That is a per-module fact (what makes the Preview load a different set of notes), but the four parse choices are the same four that `chartmode_key` names. It is a candidate only if phase 4 wants a single "parse choices" value. I cleared it because the Preview's comparison is by value on the real fields, not by the text key.

**The two `settings_change_touches` functions.** Each knows one thing only: which of cap and chart mode its report lists. That is a per-report fact. The rule they share, "the lens always counts", is repeated in both (`before.lens() != after.lens()`) and is part of G3-1.

**`BatchRun::cap_query` against `Settings::cap_query`.** Both are `CapQuery::at(sp_cap)` (analysis.h 242 and config.cpp 336-338). Both say "`CapQuery::at` is the owner". One line each; I treat this as known line-level duplication and fold it into G3-1.

**The config key table (`keys()`, config.cpp 122-149).** Used by `load_file`, `save_file` and `clamp`; each reads the one table, so there is no second home. Cleared.
