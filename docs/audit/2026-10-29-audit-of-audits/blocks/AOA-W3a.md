- **How it left:** Asked as a question, then fixed. Closure's words: "The fill page sorts text the way the windows do: each row carries a folded sort field from C++ and the script compares bytes. - **User's words:** Q3 "Should the fill page sort text the way the Library and the windows do, and should the Library sort on the text it shows?" with "Recommended: the fill page takes the folded field, and the Library sorts on the shown text." (docs/audit/2026-10-11-concept-audit/questions.md:39 and :49); the question names all three sort rules, "Étude" against "Etude", and the "+" against "-" Path case (:41-43), and says the windows have "up to two sort keys" and the fill page "one key" (:41). The user answered "go with recommended" (fix-decisions.md:553, D114). Older base ruling: "Text columns sort the way the Library table does ... The pages' browser order is not copied." (fix-decisions.md:470, D103 item 16).
- **Code today:** Fixed by commit 74f40bd3 (2026-10-11, "M03 fill half: the fill page sorts text on the windows' folded sort text"). `localeCompare` is gone from html_page.cpp (Grep over src/app finds none). Each text column (song, artist, charter, both paths, status) names a `sort:'..._s'` field (fill_report.cpp:105-115). Pinned by tests/test_fill_report.cpp:476-496 (checks "etude", "0 1 3 0+" and that `localeCompare` is absent). By reading.
- **Verdict:** GONE
- **Why:** The fill page now orders text from the windows' own folded key, compared as plain text, so "Étude"/"Etude" tie and "+" sorts before "-" there as in the windows. Q3 named the fill-page side and the windows' side in the user's words, so the choice has a ruling behind it.
- **Side picked without a ruling:** None for the sort order. Two small leftovers the question did show but the recommended option did not promise: (1) the fill page still has one sort key, the windows two (html_page.cpp:331 `sortKey, sortDir`; report_view.h:208-219); Q3 stated both numbers (questions.md:41), so the user saw it. Code-only fix: in the script, return 0 when both are null. Also JS `<` compares UTF-16 units while the windows compare UTF-8 bytes, which only differs between a character above U+FFFF and one in U+E000-U+FFFF; not visible in real chart names.
