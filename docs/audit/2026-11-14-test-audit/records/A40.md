# A40: the GUI test harness (tests/ui/uitest_engine.cpp, tests/ui/uitest_harness.cpp)

Auditor: T5-A40. Neither file holds a test case. Each record below is one function that a GUI test or `hydra_uitest.exe` calls. Common reading for every record: the function's own lines, its declaration and comment in `tests/ui/uitest_engine.h` or `tests/ui/uitest_harness.h`, and a grep of `tests/`, `src/` and `tools/` for its callers (full word match; the harness's own file excluded unless noted). Adding commits not opened beyond subjects: `dbae2ab1` split the engine out of the harness and names no failure for any function here. So question 7 below names the failure itself.

Short names for callers, all under `tests/ui/` with the `uitest_` prefix: library, details, paths, preview, batch_reports, report_windows, live, commands, script, main. The Path Builder runner under `tests/pb_ui/` shares the engine half only (`pbtest_harness.h` line 18: `struct Harness : uitest::Engine`), and has its own `reset_app` (`pbtest_harness.h` line 44); its callers are named `pbtest_*`.

The real thing for these helpers is the real ImGui test engine driving the real `AppState` on the `testdata/input` corpus. The main session's captures in `records-screen/` were produced by this harness (`records-screen/index.md`: "run by `hydra_uitest.exe --script`"), and they use only the `scan`, `click`, `wait-text`, `wait-idle`, `open`, `text` and `screenshot` paths. A function those captures do not reach is "claim not checked" for question 3. I ran nothing (agent rule 14). Every "can this fail" answer is reasoned, none confirmed.
