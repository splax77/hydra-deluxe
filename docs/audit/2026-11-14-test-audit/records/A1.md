## sample_path_rows (tests/report_samples.cpp:11-45)

Used by: `path_tiles: the six sample rows` (test_report_page.cpp:130), `path_tiles: the tiles count only the rows shown` (:141), `path_tiles: Charts shown adds each chart's copies once` (:168), and every GUI test listed above through `sample_path_result`.

1 Claim: Six rows from three charts ("Song A", "Song B", "Song C") stand for six stored paths of three charts as the path report lists them, with a spread of timing tiers (the helper's header says "labeled on the report's timing tiers"), one very long path text, and rows with and without an early-fill figure.

2 Owner: The real rows are made by `place_record` (`src/app/report.cpp:44-72`), which copies each field from a stored `store::PathRow`. Each field's own rule lives in the engine and the store: `p.path` is `Path::pathstring` (`src/core/model.cpp:586-595`), built from each activation's `notationstr` (`:543-548`) joined by single spaces. `tier` and `tok` come from `hydra::tier_for` (`src/core/squeeze_rating.cpp:260-272`); the helper calls `report::tier_for` (`report.cpp:76-81`), the same owner, so its tier labels are not typed. The other fields (acts, skip, sqin, sqout, efill, mult, optimal, notes) are typed by hand and no engine function is called for them. The helper's callers in `src/`: none.

3 Real chart: Engine, Pitch Dark, path "3+ 2+ 1" (screen index, 393,885): three activations, first one skips 3 fills (`pitch_dark_ratio.dump.json`, activation 0 `"skips": 3`, `sqinouts` one SqIn). A real row for it would read acts 3, skip 3, sqin 2, sqout 0. Claim: sample row 1 says path "1-E2+ 0-E1" with `acts = 3 + rank = 4`, `skip = rank - 1 = 0`. They differ: that notation has two activations, a largest skip of 2 (the "E2") and one squeeze-in plus one squeeze-out, so a real row would read acts 2, skip 2. The sample's acts and skip contradict its own path text on every row except where they happen to agree (see the list below). Screen side: claim not checked (no capture of the report windows exists).

Row by row, against what `place_record` and `Path::pathstring` would give:
- Row 0 "Song A" rank 1, path "1-E2+ 0-E1": acts typed 4 but the text has 2 activations; skip typed 0 but the text's largest skip is 2. Also "1-E2+" can never be written: `notationstr` is `[E]<skips><symbols>` and `pathstring` joins activations with a space, so an E sits at the start of an activation, after a space. A real text would be "1- E2+ 0- E1". The sample text is not a string Hydra can produce.
- Row 1 rank 2, "1-E2 0-E1-": same missing space; 2 activations vs acts 5; sqin typed 2 but the text has no "+"; sqout typed 2 matches its two "-". efill is `nullopt` although the text carries two E marks (a real path with an E has its early-fill figure; `Activation::notationstr` writes the E when `is_e_critical`, and `e_difficulty` then gives a figure, `model.cpp:477-480`).
- Row 2 rank 1 again for "Song A" with score 98,000 under row 0's 123,456, path "0 0 1": a second rank-1 path in one chart's record, scoring less than another rank-1 path. In the store, rank is "best score first" (`report.h:34`) so two rank-1 rows with different scores cannot both come from one record; real ranks run 1, 2, 3 within a chart. acts typed 4, text has 3 activations. This row is probably meant as "Song A's mode with no squeeze" (the test comment at `test_report_page.cpp:152`) and the rank is just a reused parameter.
- Row 3 "Song B" rank 1, a path of 80 copies of "1-E2+ " (480 characters with a trailing space; again the unproducible "1-E2+"): acts typed 4, text has 80. Eighty activations is far beyond the engine's real records (Pitch Dark's best path has 3; Believer's has 4 per `records-screen/index.md`). As a stress input for a column's text width it is a reasonable stand-in, but nothing in the file says so.
- Rows 4 and 5: "2 1-E3" (rank 2) and "1 1 1": acts 5 and 4 vs 2 and 3 activations in the text.
- optimal is never set on any row (stays `false`). A real record always has at least one optimal path, because `optimal` is "every path tied at the top score" (`report.h:36-39`). The GUI tests depend on that: `test_sort` says "Optimal paths only starts ticked, and no sample row is optimal" (`uitest_report_windows.cpp:253`) and asserts "0 of 6 paths" (`:255`).
- notes typed 1200 + rank, so Song A's rows carry 1201 and 1203 and 1201 again: `place_record` copies one `record.notecount` for every row of a chart (`report.cpp:66`), so rows of one chart always share one note count. The sample's rows of the same chart disagree.
- hyhash is the song title ("Song A"); a real one is the chart's md5-like song id (`pitch_dark_ratio.dump.json` `"hyhash": "1125c9a5..."`). The helper `sample_index` copies the same convention (`e.md5 = song`), so the two agree with each other.
- ms/tier: 12.5, 48.0, none, 171.0, 1.5, 90.0 with tier from the owner. 171.0 is chosen to be just past the Beyond edge; the edge is `beyond_edge_ms()` = the largest tier cutoff, which is `nominal_budget_ms()` (`squeeze_rating.cpp:248,274-279`). The tile test's label "Past 170 ms" and the comment at `uitest_report_windows.cpp:631` ("Song B's 'Beyond' tier among them (171 ms)") both rest on that edge being 170; the sample's 171 is a copy of a number, not read from `beyond_edge_ms()`.
- efill values -3.25, 4.5, 0.0: real `early_fill_difficulty` figures are the negative of `e_offset`; Beg's real early fill on screen is "0.0 ms" (`records-engine/index.md`, "An early fill"), so the sign and range are possible. The exact values are free inputs.

4 Direct: not a test; the helper types fields. Fields typed to agree with nothing: acts, skip, notes, sqin, the rank sequence, the notation text.

5 Reason: `acts = 3 + rank` and `skip = rank - 1` are patterns for making rows differ, not values from a chart. Nothing says why. No D-number is cited in the file.

6 Display: the tests that use it are display tests (tiles, window rows). The expected side comes from the typed fields themselves (see below), not from the engine; that is how a unit test of a tile works, and the tile test's fields (copies, ms, skip, tier) are read straight from the rows. The only fields the tile tests read are `hyhash`, `copies`, `ms`, `skip` and the tier. The inconsistent fields (acts, sqin, path text, notes, rank, optimal) are read by the GUI tests, which draw them as cell text.

7 Failure: added with the report pages 2026-10-08 (5cf3f186); the commit body not read. The sample stands in for "any six rows", so the failure is whatever the tests that use it catch.

8 Deleted: nothing to delete line by line; every field a test reads is typed here. The risk is not a line failing but a field a test trusts being impossible.

9 Stand-in: the sample is a stand-in for a real report. A sort, a filter or a width test run on rows that no search could produce (text with no space, two rank-1 rows with different scores, no optimal row, notes that differ inside one chart) may pass while a real report fails, for example a sort or filter that reads `rank`, `optimal` or `notes`, or a search over path text that the real "E2+" shape would break.

10 Same rule: every use above shares this one sample; one verdict covers all of them.

11 Real: partly. Row 2's "0 0 1", row 5's "1 1 1" and rows' tiers are things a real chart can produce. The rank sequence, the missing optimal row, the text without a space and the acts/skip/sqin disagreement are not.

Verdict: Rewrite. Build the rows from a real record's fields, so path text, acts, skip, sqin, sqout, notes and optimal agree with each other (for instance Pitch Dark "3+ 2+ 1": acts 3, skip 3, sqin 2, sqout 0, one optimal row), and give the long row a note saying it stands for a stress width. Read the Beyond edge from `beyond_edge_ms()`.

What it catches today: the tile counts and the window's six-row behaviour (sort, filter, hide, fit) on a table of six varied rows with one long text and one Beyond timing. The rewrite keeps all of that.

Finding (production code): none. `place_record` copies stored fields and `tier_for` is single-owner. The helper's problem is in the test data.

Split: the sample row's `acts`, `skip` and `sqin` disagree with the same row's `path` text. Two parts of the test data answer "how many activations has this path" differently. On a real row they cannot.

Side notes: `sample_path_rows` lambda parameter names `ms` and `efill` shadow nothing; `r.tier` is assigned from a structured binding (`report_samples.cpp:25`) which is fine.
