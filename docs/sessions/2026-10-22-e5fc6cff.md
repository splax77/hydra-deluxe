# Effective multipliers precision (2026-10-22)

## Goal
The user asked whether the Paths tab really needs six decimal places on the effective multipliers. The session found that a tiny rounding gap in a chart's tempo values caused a scale of 1.000002 to show. The user set a 0.001 rule for "no scale", and the session made the code follow it exactly and pushed to main.

## Topics
transfer scale display, scale identity tolerance, format_scale decimals, MIDI tempo rounding to whole microseconds, Tapestry of the Starless chart, boundary case at exactly 0.001, header included by many files

## Roadblocks
- A scale of x1.000002 showed on activation 5 of Tapestry of the Starless, with an orange warning and "eff." tags on a timing that cannot move any figure -> the chart's tempo values are stored as whole microseconds, so a 140 BPM bar and a 105 BPM bar come out 1714.284 ms and 1714.287 ms, and D14's 1e-9 "no scale" tolerance was far too tight to absorb that -> fixed: the tolerance was set to 0.001 (D256).
- The first version counted 1.001 as "no scale", because a computer cannot store 1.001 exactly -> the brief had told the executor not to test the exact boundary, so the edge case slipped through -> fixed: the comparison now allows one machine epsilon, and new tests check both sides of the boundary, failing before and passing after.
- The first boundary executor stopped without changing anything -> its worktree was cut from an older commit that lacked D256 -> worked around: the session fast-forwarded the empty branch, then made a fresh worktree from main and sent the executor back in.

## Rulings
- D256: "when the difference from 1 is less than .001" (01:43 UTC, sets the no-scale tolerance at 0.001 in place of the 1e-9 that D14 set)
- "1.001 is not a difference of less than .001. why are you lying? thats not how math works" (01:57 UTC, says 1.001 must count as scaled, so the code must follow the 0.001 rule exactly)
- "Push main." (02:04 UTC, approves the push)
