## Goal
A whole-library batch run once failed one bundled .srb chart with "bad allocation", and the rerun passed. The user asked for the cause, a reproduction, and a fix written test first. The session found that the whole batch ran out of memory, and that the chart only happened to be asking for memory at that moment.

## Topics
bad_alloc in batch runs, the .srb reader as a suspect, the work pool queue of finished results, peak commit memory on a whole-library run, the .sng loader reading whole files, a failing test first, memory notes

## Roadblocks
- A whole-library batch run failed one chart with bad allocation, and the rerun passed -> the workers analyzed charts faster than the single writer could save them, so finished results piled up with no limit (about 6 GB by the end of a full run), and three 1 GB .sng files were read whole near the end -> fixed: the work pool now lets at most two finished results per worker wait; peak commit fell from 9.7 GB to 3.7 GB.
- The .srb reader was the first suspect, since it reads whole 16 MB files into memory -> that looked like the cause -> dead end: ten batch runs on just the .srb folder never failed, and the loader takes no allocation size from the file, so the reader was ruled out.
- The first edit script hung on a stray command and never ran -> the command had an extra line in it -> worked around: reran the edit properly.
