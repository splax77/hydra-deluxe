## Goal
Find out why the weekly Fuzz workflow failed and how to fix it. Then stop the same kind of bug from slipping past the per-push tests.

## Topics
fuzz workflow failure, Clone Hero 1.1 fill generator hang, MIDI chunk-header overread, audio decoder hang, CI replay of the saved fuzz corpus, reviewer question about loops that grow with numbers from a file

## Roadblocks
- The weekly Fuzz run hung in all four chart parsers (.mid, .chart, .srb, .sng) -> the Clone Hero 1.1 fill generator listed every measure line from the song start to the last note, and a fuzzed note at a huge position made that list tens of millions long -> fixed: the generator now steps through measure lines by number and jumps to the next line that has a note; the four hanging inputs are saved as regression tests, and the fills come out the same (9417d973)
- The per-push tests never fed broken charts, so the bug showed up only on the weekly run -> the saved fuzz files sit in a GitHub cache that the per-push tests never read -> fixed: CI now replays the saved corpus on every push and pull request (f0f0de21), and a new reviewer question asks about loops that grow with numbers read from a file (c18749a4)
- A manual Fuzz run found a MIDI chunk-header overread -> the chunk reader checked the MTrk tag but not the 4-byte length after it, so a file that ended right after the tag read past its buffer -> fixed: added the same end-of-data check that the next branch already had (0090bcf4)

## Open threads
- The audio decoder hang is found but not fixed. A 14 KB .ogg file declares a lookup table (a codebook) with about 16.2 million entries. The bundled decoder, stb_vorbis, builds all of them before it notices the file is broken. Under the fuzz build each open takes about 6 seconds.
- The session recommended copying the reference libvorbis rule: a codebook may need at most 24 bits for its entry count and dimensions together. That is a two-line change in third_party/stb/stb_vorbis.c. The other options were a memory cap tied to file size, or a cap on entries per codebook. The user has not picked one.
- The recommended rule still lets a smaller slowdown through, about 3 seconds under the fuzz build, so a later fuzz run may find it.
