## Goal
Audit the chart scan and analysis code, search the web and experiment for ways to make it faster, and report a ranked list. The user said no real code may change during the experiments.

## Topics
library scan speed, folder walking, MD5 hashing, path search algorithms and dominance pruning, database writer and commits, score graph build, .chart and .mid parsing, kick dynamics count, compiler and allocator settings, worktree and scratchpad cleanup

## Roadblocks
- The first plan aimed at the path search -> the search turned out to be about 7 to 8% of analysis time; the single save thread to the database was the real choke point -> dead end: the search-speed work was dropped, and the writer, graph and parsing work was measured instead.
- Dominance pruning looked like the strongest search idea -> it drops paths that a true best path needs, because SP can't be spent in part -> dead end: it changed 58 of 18,811 stored results and lost the true best score on 3 charts; the August rejection was right.
- A web scout reported 200x for a faster folder-listing call -> the 200x was measured against a slower per-file call the app does not use -> dead end: the experiment showed no measurable gain.
- Skipping unchanged song folders on a rescan -> folders nest inside other song folders, and an edited song.ini does not change its folder's date -> dead end: it missed 117 nested charts and would miss the edit.
- More analysis workers (12 or 15) -> the extra workers take CPU from the one saving thread -> dead end: 8 workers was fastest (12.6 s), 15 took 18.1 s.
- Reading the drive's file table directly, as Everything and WizTree do -> it needs admin rights or a background service -> dead end: ruled out.

## Outcome
Ended with a full report and a handoff, no real code changed, and the scratchpad cleaned up.
The main finding: a full library run is held back by the one thread that saves results to the database. Inside each worker, parsing and graph building are most of the work.
Each change below kept every stored result identical across the library. They were measured one area at a time in throwaway copies, not together: the database writer (full run 16.3 s to 11.6 s), graph build (13.6 s to 2.7 s on one thread), parsing (15.0 s to 8.9 s on one thread), kick dynamics (3.8 s to 0.5 s), and the library scan (4.2 s to 2.1 s, rescan 0.8 s to 0.2 s).
Nothing was committed. Six patch files, the agents' notes and the timing logs are saved in docs/handoffs/2026-10-06-perf-exploration/ (untracked). The six worktrees were removed. The 13.4 GB scratchpad was deleted. Main is still at the 2.1.0 commit.
