## Roadblocks
- The premise was wrong: Python was thought to be the slow part -> per-chart analysis measured 0.12 s, and most of the time went to mido (the MIDI library Hydra used) -> worked around: profiled first, then wrote its own MIDI reader, hydra/hymidi.py, which is 5.5x faster at parsing.
- No C++ compiler could build the exes -> the machine had no MSVC, MinGW, CMake or Ninja, and winget needs admin rights to add one -> fixed: the user approved a portable MinGW toolchain, which built the first DLL (a compiled library file).
- The first build was blocked -> both running Hydra apps held the DLL files that PyInstaller must replace -> fixed: after the user chose to have them closed, Claude terminated both, and both records databases passed integrity_check afterwards.
- The first MIDI reader gave track names the wrong field -> mido keeps track names in .name and other text in .text, and the draft used .text for everything -> fixed: the reader now matches mido's split and decodes text as latin-1, and test_midi_parity guards it.
- Reading two fields on graph edges could fail -> ScoreGraphEdge declares them in __slots__ but never sets them -> fixed: hyflat.py reads them with a default value.
- The C++ scoring function ran slower -> each call from Python into the DLL, through ctypes (Python's built-in way to call DLL code), cost more than the work it saved -> dead end: a per-call C++ category_scores was abandoned as the default, measured 1.6% slower; it stays off unless HYDRA_NATIVE=1 is set.
- MSVC would not run from the build script -> vcvars64.bat calls vswhere.exe without its full path, and the VS 2026 install keeps that tool off PATH -> worked around: the session built in a scratch folder with the Installer folder added to PATH and left the repo alone; build_native.py still lacks the fix.
