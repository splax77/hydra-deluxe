# Hydra squeeze discrepancy (2026-10-29)
session: 07074f3d-ef75-407e-8a32-295a063ef219 | project: hydra-test | commits: none | D: none | tags: squeeze, sp-phrase, tick, measure, tempo | agents: 0

## Goal
The user asked why a public copy of Hydra shows a squeeze of -2.7 ms on the second activation of the Shop Theme chart, while our Hydra shows 0 ms, and which number is right.

## Topics
squeeze timing, SP end position (the tick where Star Power ends), measure and tick maths, floating point rounding, Python int() truncation, public Hydra 1.3.1 versus our engine, the More Paths squeeze-in display

## Roadblocks
- The two Hydras disagreed by 2.7 ms on the same squeeze -> public Hydra stores a position as a decimal number of measures, rounds it with floating point, then cuts it with int(), so each phrase collected can lose one tick -> worked around: our engine adds whole measures in ticks and never uses decimals, so it keeps the exact 0 ms; the one-word fix (round instead of int) belongs in public Hydra's source, which was not changed.

## Rulings
- none

## Outcome
Ended with a written answer after about seven minutes: our 0 ms is right, and public Hydra's -2.7 ms comes from a rounding and truncation bug in its measure maths.
The public Hydra 1.3.1 source was cloned into the session scratchpad and read, not changed. No repo file changed and no commit was made; the only file written was a scratch script, pub_ends.py, in the scratchpad.
