## Goal
The user asked to widen the calibration-fill window from ±70 ms to ±250 ms in both directions. Then the user asked for a sortable Cal fill column in the HTML report and for the GUI report to open by itself. At the end the user reverted the window to ±70 ms.

## Topics
calibration fill window, golden test data, record version bump, Cal fill report column, sign convention, GUI report auto-open, revert to 70 ms

## Roadblocks
- The golden generators existed only at the frozen python-oracle tag, and a 250 ms window would change the golden data -> the port plan forbids editing that oracle -> worked around: the user chose C++ as the oracle, and a new hydra_gen_golden tool regenerated the golden files.
- The first Cal fill column counted every E-critical activation, even skipped ones -> the column ignored the rule that only E0 fills matter -> fixed: only unskipped E0 fills count, and a path with none shows a dash.
- The first Cal fill column showed the opposite sign to Hardest ms -> it used the raw offset, not the difficulty sign -> fixed: it now uses the same negated offset as Hardest ms, with a +0.0 step so an exact zero never shows as -0.0.
- The GUI never wrote a report; only the hydra_report command did -> the report was CLI-only -> fixed: added a ReportJob to the GUI that builds the page on a worker thread and opens it when library analysis finishes.
- After the version bump, the existing database showed no records at all -> its rows were stamped with the old version and count as stale -> worked around: the library must be analyzed again.
- One golden regeneration failed a test during the revert -> the generator skipped its report step when the score-regression check fired, which a revert causes on purpose -> fixed: reports always regenerate, and the flag only sets the exit code.
