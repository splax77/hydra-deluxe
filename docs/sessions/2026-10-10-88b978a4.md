# Cap every uncapped wait in the test suites (2026-10-10)
session: 88b978a4-cfdf-4e5b-b148-3b7e9c1837dc | project: hydra-test | commits: f2e901e0 | D: D108 | tags: tests, ci | agents: 0

## Goal
Make every wait in the test suites stop on its own, so a hang becomes a named failure instead of a frozen run. The session surveyed the waits, asked the user for the limits, got a yes, and committed the change to its branch.

## Topics
test wait limits, shared wait helper (tests/wait_util.h), gates inside fake analyzers and fetchers, command-line test output read, hydra_uitest --jobs child limit, GPU wait in the GUI harness, timing evidence from CI

## Roadblocks
- About 30 test waits had no time limit at all -> a test that failed before opening its gate left a worker thread waiting forever, so the run hung instead of reporting the failure -> fixed: a shared wait_util.h helper that gives up and throws an error naming what it was waiting for.
- The command-line test could block in two places, the output read and the INFINITE wait -> capping only the wait would not have helped, because the read blocks first -> fixed: the output is read on its own thread, and a run past 30 s is killed.

## Rulings
- D108: "yes to all three, go ahead" (15:18 UTC, approves the three decisions asked: the 30 s limit for waits in a test process, the 5 minute limit per GUI test child, and one rule for the waits that already had their own limits)

## Outcome
The session ended with the change committed as f2e901e0 on claude/agitated-blackwell-5761dc. It is not merged; the derive-once review still has to run before it goes to main.
The seven touched test files passed: 134 of 134 unit cases in 6.9 s. Six GUI tests that use the changed gates passed with --jobs 2. Both kill paths were forced once by shrinking the limits to 20 ms and 1 s, then the real limits were restored and everything was rerun green.

## Open threads
- The branch still needs the derive-once review and a merge to main.
- Left alone on purpose: the GUI harness's frame-driving wait (about 150 call sites, each with its own limit) and one 60 s loop in uitest_batch_reports.cpp. They already stop, and they must keep the GUI running between checks.
- In a few tests the release flag is declared after the app, so a check that fails early can leave the job thread reading a flag that no longer exists. It can no longer hang the run, but it is a dangling reference to fix later.
- The site inventory and timing evidence are in wait-caps-inventory.md in the shared notes folder, not in the repo.
