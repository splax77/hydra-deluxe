# Timing limit performance diagnosis (2026-08-15)
session: af25b8cc-83cb-4aa6-8036-abbf915fed67 | project: hydra-test | commits: none | D: none | tags: performance, tests, chart | agents: 0

## Goal
Find out why the 10 ms "Limit timings" filter made the blink-182 Discography search about 60 times slower, and fix it so the filter costs no more than 2x. The user had supplied the timings and the chart's measured results.

## Topics
search engine pruning (reduce_group), the Limit timings filter, Python, ctypes and C++ engine copies kept in step, timing on the blink-182 chart, golden test matrix, search engine parity tests

## Roadblocks
- The 10 ms limit made the uncapped search 60 times slower -> the filter exempted timing-failed paths from the normal top-band pruning, so they piled up in every bucket and compounded -> fixed: an all-survivors depth band now removes timing-failed paths, mirrored in hydra/hypath.py, native/hydra_search.cpp and src/search/engine.cpp.
- The local corpus has no chart near the blink size (largest about 380 KB, against a 3.26 MB notes.mid) -> the test set was too small to show the slowdown -> worked around: the user gave the real blink folder and the session timed that file.
- The session hit its usage limit in the middle of the before-and-after timing -> the usage cap, not a fault in the code -> worked around: after the user's "Try again" at 14:01 UTC, the session rebuilt the old code, timed it, then restored and rebuilt the new code.
- The C++ golden tests never covered uncapped plus filter, the blink case -> the matrix in tests/test_search.cpp only had capped with filter and uncapped without filter -> worked around: the blink case was checked by hand with hydra_bench.exe and the Python parity chain. No rows were added.

## Rulings
- "you need to understand why limit timing is so much slower and figure out how to fix it" (13:27 UTC, asks for a real fix, not an accepted slowdown)
- "it shouldnt be more than 2x slowdown" (13:27 UTC, sets the target: the limit may slow the search by at most 2x)

## Outcome
The session ended with the fix in place in all three engine copies and verified, with no commit made.
Timed on the same machine, the old code took 202.4 s with the limit on and 7.8 s with it off. The new code takes 13.2 s with the limit on and 8.9 s with it off. The production engine (src/search/engine.cpp) took 9.17 s on the real chart with the GUI defaults. All runs gave the same optimal score, 71,786,175 at cap 128.
The rule is now: a timing-failed path is kept only while it sits in the top depth band of all survivors. The old rule only compared it with timing-passing paths.
Checks: Python output matched the old output byte for byte across 336 filtered configs. The native-versus-Python parity suite passed 12 tests. The C++ golden matrix passed all 4015 assertions.
The changes were left uncommitted in hydra/hypath.py, native/hydra_search.cpp and src/search/engine.cpp. A memory note recording the fix was written and it corrects an earlier one.
