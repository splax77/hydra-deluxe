## Goal
Find out why the "Limit timings" setting seemed to do nothing when Analyze paths was clicked on Karn Evil 9. The user reported it as a bug. The session first had to show what the live app was really doing.

## Topics
Limit timings setting, Analyze paths button, analyze modal state, stored records in hydra.db, Windows debugger (cdb) attach, crash dump, AnalyzeJob thread start

## Roadblocks
- The stored result never appeared after Analyze -> the analyze modal kept per-job flags keyed on the job's memory address, and the heap reused an old address for the new job -> fixed: a generation counter (analyze_generation in src/ui/app_state.h and app_state.cpp) now keys those flags, in src/ui/details_view.cpp.
- Guesses from the source and from exe timestamps did not reproduce the fault -> the session guessed before looking -> dead end: the stale-exe and wiring theories were dropped. The user said "stop guessing" twice. The cause was found only with a debugger on the live process.
- The cdb command line broke when the commands were passed inline -> PowerShell quoting mangled the -c string -> fixed: the commands went into a script file and cdb ran with -cf.
- Killing a cdb session left patched breakpoint bytes in the running process -> the session killed cdb instead of detaching it -> worked around: both debug instances were closed and the scratch copy relaunched clean.
- A crash dump showed an unguarded thread-start exception that ended the app -> AnalyzeJob::start had no catch around the thread constructor -> fixed: start() catches the error and sends it to the modal's error path (src/ui/jobs.cpp).
- Early clicks missed the Analyze button and left the Limit timings box off -> wrong click coordinates, the click landed in the row above -> worked around: the box was set back on (mslimit_enabled=1, 10 ms) and the button was clicked at its real position.

## Outcome
The session ended with the bug fixed and checked on an instrumented build. The changes are uncommitted in the working tree.
The Analyze click did run. The result was thrown away because the modal's flags pointed at a reused address, so no record was stored and the modal closed early.
The limit setting itself worked. The CLI run printed "Timing cap: 10 ms" and stored it. The optimal path ignores the filter by design; only the More Paths alternates are filtered.
Verified: three analyze cycles on the fixed build, with the limit changed each time, gave three stored records. Hydra and HydraUncapped both rebuilt clean in Release.
The user's Hydra was relaunched on the fixed Release build, with its database untouched. The Karn Evil 9 record still predates the filter, so one Analyze click is needed to refresh it.
