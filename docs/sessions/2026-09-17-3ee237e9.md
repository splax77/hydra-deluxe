# Clone Hero hit window investigation (2026-09-17)
session: 3ee237e9-48e7-4ca2-bea8-79f9222b6c01 | project: hydra-test | commits: none | D: none | tags: clone-hero, hit-window, squeeze, agents | agents: 9

## Goal
The user wanted to know exactly how the Clone Hero hit window works. The hit window is the time on either side of a note in which a hit still counts. Hydra's squeeze checks had been running on an 85 ms guess.

## Topics
hit window values, how the game is built (machine code, not readable C#), Ghidra decompiling (turning machine code back into readable pseudocode), dynamic window formula, accuracy display, input registration, whether a cap exists

## Roadblocks
- The first answer, plus or minus 70 ms, did not fit the user's screenshots -> it came from YARG (an open-source rhythm game) and community posts, not from Clone Hero's own code -> fixed: read the real constants from the drum engine's setup code in GameAssembly.dll, which gave 85 ms as the widest per-side window.
- Il2CppDumper (a tool that recovers names from the game's compiled code) would not run -> the safety sandbox blocked the downloaded program, and it needs .NET 7 while this machine had .NET 8 and 10 -> fixed: the user downloaded it, and it ran with .NET roll-forward (a setting that lets a newer runtime run an older program).
- Ghidra (a free reverse-engineering tool) took about 20 minutes, and the first decompile output was only 59 KB -> the first script, ghidra_with_struct.py, opens a file picker that a run with no window cannot show, Ghidra 12.1 needs PyGhidra for Python scripts, and the first Java script asked for only 21 functions -> fixed: wrote a Java script that decompiled 987 functions into 2.3 MB of pseudocode.
- The +85.9 ms hit on drums lies past the 85 ms in the code -> cause not found -> worked around: guessed it was rounding to one step of the game's internal clock (about 1.3 ms); the guess was never tested.
- The assistant first claimed the formula was capped between 37.5 and 85 ms, then said there was no cap when the user pushed back -> the claim was made before the formula's caller was checked -> fixed: retracted in the reply, and the cap question was marked open.
- The formula's caller could not be found -> it is called through a table of function pointers, and the cross-references only reached that table -> dead end: tracing it further did not show whether the result is capped.

## Rulings
- "the hit window is actually dynamic, 85ms is the default widest window. it shrinks in faster sections." (23:53 UTC, the user's correction: the window is not a fixed 85 ms)

## Outcome
The session ended after the user asked for a summary, which the assistant published as an artifact, with the cap question still open.
Nothing was committed and no repo files changed; the report page and Ghidra scripts sit in the session's scratchpad.
Read from the code: normal drum mode uses 85 ms as the widest per-side window and 37.5 ms as the narrowest, and precision mode uses 40 and 25 ms. A formula in the engine sets the window from the spacing between notes, and its raw output peaks near 89.5 ms per side.

## Open threads
Whether the formula's result is capped, and why a hit at +85.9 ms registered. The session suggested a test: hit notes at 86 to 90 ms in a sparse section. No test was run.
