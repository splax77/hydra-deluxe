## Outcome
Ended with a handoff for the path report speed work, and no code changed. The handoff is untracked and not committed.
The profile was a recording of about 5 minutes of real use of a scratch copy, with the user's library, database and settings. It captured 73,097 CPU samples over 306 seconds. The user's own files were not touched.
Building the path report took about two thirds of the CPU in the session (41.6 of 62 CPU-seconds). Only about 21 percent of that went to the path search. About 57 percent went to reading and parsing chart files again.
Clicking through songs cost almost nothing. An open report window used about 15 percent of a core just sitting there, mostly re-fitting cell text every frame.
The likely cause of the slow build is Windows Defender scanning every chart file as Hydra opens it. This is unproven, because the profiler cannot record time spent waiting.
The handoff is docs/handoffs/2026-10-11-path-report-speed-handoff.md. It covers three combined changes: keep the report rows (option 1), read each chart once for both modes (option 2), and cache fitted cell text in the open report (option 4).
The flame graph page, folded stacks and scripts are saved in build-cpp\prof\gui-2026-10-11\. The session also saved the method to memory.
No commit was made in this session.
