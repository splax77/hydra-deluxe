# Extreme multiplier causes (2026-09-29)
session: 96ae6b89-0cef-4bb4-804e-e995aa36f9eb | project: hydra-test | commits: 8d4d9e0, a84ea1a | D: none | tags: squeeze, frontend-squeeze, path, release, docs, tests | agents: 0

## Goal
Find out what makes some Star Power activations show a huge timing multiplier, and why the Paths tab did not show the numbers the user saw. Then fix the display, publish a report of the squeeze-outs it changes, and release Hydra 1.9.6.

## Topics
frontend timing multiplier, Star Power activation timing, Paths tab text, stored-results checks, eased squeeze-outs report, version 1.9.6 release

## Roadblocks
- The first multiplier scan counted every stored path, so the 19.2x on Dr. Breacher looked like a real activation -> the scan did not say which path each number came from, and that number sat on the all-0 path -> fixed: the scan was rerun on optimal paths only (the count over 2x fell from 614 to 353), and the 19.2x was then checked with the app's own Paths-tab code.
- The first copy of the database left out its -wal side file, so recent writes were missing -> the copy took only the main file -> fixed: the database was recopied with its -wal file, and the checks were rerun on that copy.
- The GUI never printed the 8.76x on Gore activation 4 -> the orange line was skipped when the multiplier changed no displayed number, and a note at exactly 0.0 ms stays at 0.0 ms -> fixed: the line now shows on every activation whose multiplier is not x1.00, early first, orange when it changes a squeeze or backend number and gray otherwise.
- The first eased squeeze-outs summary had wrong counts and a wrong claim about tiers -> the counts used a different rounding rule, and the claim that the effective number set the backend tier was never checked against the backend code -> fixed: the counts were redone with the app's rounding (309 eased, 276 harder), and the tier claim was corrected in chat.
- The published report still listed squeeze-outs over 170 ms, and some names had color tags -> the first build did not filter on effective ms or strip the tags -> fixed: rows at 170 ms or more were dropped (309 down to 177), and every name now goes through Hydra's own tag stripper.

## Rulings
- "the app should always display a multiplier when one exists." (22:41 UTC, the Paths tab must show every multiplier that exists, early first, then late)
- chose "Orange only when it matters (Recommended)" to "Should the line stay orange on every activation ..." (22:42 UTC: orange only when the multiplier changes a timing, gray otherwise)
- chose "Drop it, one format (Recommended)" to "Keep the '+10ms at the frontend moves the SP end +X ms' ..." (22:42 UTC: drops the example sentence, one format only)

- "yes make a new release" (23:06 UTC, approves the GitHub release and the installer)
