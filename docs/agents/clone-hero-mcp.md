# Driving Clone Hero with the `ch` MCP server

The `ch` server lets an agent drive Clone Hero as text. It can start the game, read its state through Frida (a tool that loads a small script into a running program), trace each note the player hits, press drum pads and menu buttons through a virtual drum kit inside the game, start a song from the menus, read Star Power while a song plays, read the end-of-song stats, and stop the game with the user's files put back. Claude Code starts it from the `ch` entry in `.mcp.json`. It was built from three plans: `docs/superpowers/plans/2026-10-28-ch-mcp-server.md` (removed; `git show 444631e6:docs/superpowers/plans/2026-10-28-ch-mcp-server.md`); `docs/superpowers/plans/2026-10-30-ch-mcp-star-power-and-song-start.md` for Star Power and the menus; and `docs/superpowers/plans/2026-10-30-ch-mcp-in-game-input.md` for the virtual kit.

## When to use it

Use it when a question needs the real game: how Clone Hero scores a chart, whether a note fires a hook, what the game's clock says while a song plays. Use Hydra's own tools for anything Hydra can answer alone. A live run needs nobody at the keyboard and never takes it: the game is launched minimized, never shown, and driven from inside through a virtual drum kit, so the user keeps using the machine while it runs. The user says in chat when a run may start, and the server's backup and restore undo the files and the registry key.

## The tools

The list of tools lives in one place: `build_server()` in `tools/ch_mcp/server.py`. Each tool there has a one-paragraph description, and Claude Code shows the same text. Read the list there rather than from a copy. `tools/ch_mcp/README.md` says how the server is registered and how its Frida agents are built.

## Safety rules

The server backs up the user's game files before it touches the game, and puts them back when it stops. `ch_start` backs up before it launches. The first tool that touches a game the server did not start takes the backup then. `ch_stop` restores the files and prints one line per file. If a restore fails, the reply names the file and the backup folder; nothing else runs in that call.

The backup also saves a registry key. Rewired, the game's input library, saves its bindings under `HKCU\Software\srylain Inc.\Clone Hero`, and the backup exports that key as `rewired.reg` beside the files. At the restore, the server exports the key again and compares it with the saved copy. When they match, the reply says "rewired registry: unchanged". When they differ, it deletes the key, imports the saved copy, checks it once more and says "rewired registry: restored". A key that still differs, or a `reg.exe` call that fails or passes its cap, is a failed restore named `rewired.reg`.

The run changes one line of the user's `settings.ini`. `ch_start` sets `pause_on_focus_lost = 0` after the backup and before the launch, so the game keeps running while it is not in front, and says so in its reply. The restore of `settings.ini` puts the user's own line back. A file with no such line launches with a warning, and `ch_kit_setup` then refuses, naming `ch_start`.

The game window is never brought to the front. `ch_start` asks Windows to open the game minimized and not active. From then until `ch_stop`, a watch counts every time the game's window becomes the front window, and `ch_status`, `ch_kit_status` and `ch_stop` print that count. The count is information, not a pass condition: the user ruled on 2026-10-31 that the game taking focus briefly does not matter ("why does it matter if the game is focused briefly?"). No tool on the kit route focuses or shows the window.

The user's own keyboard and mouse reach no player in the game while a run goes on. `ch_kit_setup` takes the keyboard and mouse away from every Rewired player. It also switches Rewired's keyboard device and its mouse device off for the run, so nothing the user types or clicks reaches the game at all. The user ruled both on 2026-10-30. If either device does not read back as off, setup refuses and tears the kit down again. Its reply has a line for the keyboard and a line for the mouse, and `ch_kit_status` prints both too. `ch_kit_setup` in `tools/ch_mcp/kit_tools.py` and `setup` in `tools/ch_mcp/agent/kit.ts` own how the switch is made and checked.

The kit is always taken away again. Besides the keyboard and mouse, `ch_kit_setup` lets the game listen while it is not in focus and hands the kit to one player with the game's own drum map. It checks the bindings it reads back against `KIT_BINDINGS` in `tools/ch_mcp/kit_tools.py`, and a setup that fails or reads other bindings is torn down at once. `ch_kit_teardown` clears the kit's pads and buttons and removes the kit. It gives every player back exactly the keyboard and mouse setup took, and puts each Rewired device back to what setup recorded. It also turns the game's "ignore input when not in focus" switch back to what it was. It prints one check per step, as "ok" or the mismatch. `ch_stop` runs the same teardown before it stops the game, and a failed check reads like a failed file restore: "kit teardown failed on" the step, then what it found.

The key route is locked. `ch_key`, `ch_press` and `ch_play_chart` with `route` set to "keys" press keys through Windows, so they take the game window and the user's keyboard. The `allow key run` hook in `C:\Users\Patrick\.claude\gates\percall.py` refuses each such call unless the user has typed exactly `allow key run` in chat in this session, and each such message lets one call through. The key route exists only for a day the kit route breaks; if you need it, ask the user in chat first. `ch_play_chart` with no route uses the kit once `ch_kit_setup` has built it, and refuses until then.

Play stays offline. The server launches the game only with the command line `bot_run.launch_command` builds. `ch_open_song` drives the profile screen, the main menu, the song list and the player screen by kit presses and reads whether the Online menu is on screen before every step, refusing to go on while it is. A ch_start_song tool, once it exists (task T8, below), calls the game's own start method and checks the same way. No tool opens the Online menu, Settings, Practice or the control mapper.

The Frida agents read, trace, call game methods and, where a feature needs it, set game fields. The user allowed method calls and field writes on 2026-10-30. Each agent that calls game methods holds its own list of the calls it may make: `tools/ch_mcp/agent/menu.ts` for the menu read, and `tools/ch_mcp/agent/kit.ts` for the kit, whose list must equal the names in `tools/ch_mcp/kit_methods.json` (each with the dump line it was read from). No agent starts a song yet, so no list of song-start calls exists; the method watch paragraph under "The shape of a live run" says where it will go. A test in `tools/ch_mcp/tests/test_frida_attach.py` checks that every call in every agent is on its own file's list and that the kit's list matches its data file. No agent sets a game field directly today: the kit changes the game only through the setter methods on its list in `tools/ch_mcp/kit_methods.json`. The same test file still checks that no agent reads game memory by raw offset. A trace hook patches the start of the traced method in memory while it is attached; the user approved that on 2026-10-28. The state agent places one hook of the same kind while it is attached: on a per-frame method of the player screen, `watchPlayerScreens` in `tools/ch_mcp/agent/menu.ts`. That hook only records the object the method runs on, because the garbage collector's search cannot find the player screen; it reads no field and calls no game method. The method watch skips, in a class it hooks whole, any method whose code other classes share, and names each one it skipped in its start reply; `shared_rvas` in `tools/ch_mcp/method_watch.py` decides which.

Two facts about the menu driver matter for safety, and its code holds the details. The Online check refuses on more than an Online menu that reads as open: an error in place of the flag, or a read with no menu block, stops the run too. `online_refusal` in `tools/ch_mcp/menu_tools.py` says which reads count as closed. The step file presses no keys at all. Every item in it is a `kit:` item, and `item_problem` in the same file refuses a key name, a lane or typed text; `load_steps` runs that check on every step. So no step can press Space, which the manual's Keyboard and Gamepads page says opens the control mapper from the main menu.

Every wait has a cap and says so in its reply when the cap ends it. No tool retries on its own.

Nothing runs over the user's song library. Each tool takes one song folder or one chart folder.

## The shape of a live run

Each live run names its pass and fail lines before it starts, has a cap on how many times it runs, and ends with `ch_stop`'s restore lines. A typical run on the kit route goes like this:

1. `ch_start` with no song folder. The game opens minimized at its menu, and the reply shows the `settings.ini` line it set for the run. (With a song folder, the bot plays the song from the command line and needs no kit.)
2. `ch_attach`, then `ch_state`, `ch_snapshot` or `ch_menu` to read the game.
3. `ch_kit_setup`. Its reply shows Rewired's keyboard and mouse switched off, every player's keyboard and mouse flags before and after, the kit, and the bindings it read back. `ch_kit_status` shows the frame rate, whether the game has focus and the foreground count. `ch_kit_watch` reads every player for a few seconds and says whether any key reached one.
4. For Star Power, `ch_sp_watch_start` before the song starts. The watcher waits for a moving engine clock and logs every change of the Star Power fields to a CSV. `ch_sp` prints its latest read, `ch_sp_watch_status` lists the activations and the rises of the meter, `ch_sp_between` answers a question about one stretch of the song, and `ch_sp_watch_stop` ends it. `ch_sp_compare` checks the CSV against a `hydra_replay` score JSON. A bot run cannot answer a Star Power question, because the game's bot never gains or spends Star Power (docs/clone-hero/live-checks.md). So a Star Power run needs a song started from the menus.
5. For the auto-player, `ch_play_chart` before the song starts, with `song_folder` so the run cap follows the song's length. With the kit set up and no route given, it presses each chord through the kit. `ch_kit_press` presses one chord by hand. A song launched with a bot is played by the bot, so the auto-player needs a song started from the menus.
6. To start the song, `ch_open_song` with its folder. It presses the kit items in `tools/ch_mcp/menu_steps.json` and reads the menus after every press. That file is written from the manual and marked unverified until a live run corrects it, so the first runs go one step at a time: `ch_kit_press` for each step's items, and `ch_menu` after each.
7. For a trace, `ch_trace_start` once the song is loaded, `ch_notes` to read the calls in pieces, and `ch_trace_stop`. The default hook fires once per note the player hits; a missed note and an overhit fire nothing, so a run with misses has fewer calls than notes.
8. `ch_stop`. It tears the kit down and prints each check, prints the foreground count, then closes the game and prints one restore line per file and one for the registry key. Check that every check is "ok" and that everything was restored.

The restore puts the user's own scorestats.json back, so copy a run's end-of-song stats before `ch_stop`. `ch_wait_stats` makes that copy only for a song launched from the command line (`wait_stats` in `tools/ch_mcp/bot_run.py`). For a song started from the menus, copy `Documents\Clone Hero\scorestats.json` yourself.

The server keeps the Python code it loaded when it started. A change to one of its Python files under `tools/ch_mcp/` reaches a running session only after the `ch` server is reconnected.

Steps 4 and 5 come before step 6 because the watcher and the auto-player each search for the engine, and that search waits for a moving clock up to its own cap (`engine_finder.ENGINE_SEARCH_CAP_S`). Started after the song, they miss its first notes.

The method watch is for finding which game method starts a song. `ch_method_watch_start` hooks the methods `tools/ch_mcp/start_candidates.json` names, and `ch_method_watch_stop` names the call just before each scene load, then lists every call in order. The call list comes last because the server cuts a long reply and a menu walk logs thousands of calls; the cut then keeps the scene loads. Live step LS-M of `docs/superpowers/plans/2026-10-30-ch-mcp-star-power-and-song-start.md` runs it around `ch_open_song`. The main session then writes the method it names into a new file, start_method.json in the `tools/ch_mcp/` folder, and a ch_start_song tool (task T8 of the same plan) calls it; until LS-M has run, neither that file nor that tool exists. The watch looks up the song clock once, when it starts (`songClock` in `tools/ch_mcp/agent/menuhooks.ts`). A watch started at the menu therefore has no song time, so its calls are ordered by `t_ms`, the wall time since the watch started.

The two things the live steps of 2026-10-29 found now live in docs/clone-hero/07-internals.md (IN-36 for the results screen after a bot run, IN-03 for the finished `GameManager`). For the tools, that means two things. End a bot run with `ch_stop`. The state agent skips a destroyed `GameManager`, so back at the main menu `ch_state` says "menu (no live GameManager)" and its `destroyed` line counts the skipped one.

The agents now skip any `GameManager` the game has destroyed. Every Unity object holds a pointer to its native half in `m_CachedPtr`, a field of `UnityEngine.Object`, and Unity clears that pointer when it destroys the object. The object itself can stay in memory until the garbage collector runs, which is how a destroyed one can still be found. The lookup in `tools/ch_mcp/agent/gamemanager.ts` reads that field by name, and the state, clock and trace agents all go through it. Each `ch_state` reply carries `destroyed`, the number of destroyed `GameManager`s the read skipped. When none is alive, the reply says `found: false` and the state word is "menu (no live GameManager)".

The one live run that checked this skip (2026-10-29) is recorded in docs/clone-hero/07-internals.md (IN-03). If a later read at the menu still says "song over" with `destroyed: 0`, the game kept a `GameManager` alive, and the skip would not tell them apart.

If the game is updated, every Frida tool refuses until a dump of the new build exists; the refusal names the scripts to run.
