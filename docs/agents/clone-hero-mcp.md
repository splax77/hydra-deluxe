# Driving Clone Hero with the `ch` MCP server

The `ch` server lets an agent drive Clone Hero as text. It can start the game, start a song for a human player straight from the command line, read the game's state through Frida (a tool that loads a small script into a running program), trace each note the player hits, press drum pads and menu buttons through a virtual drum kit inside the game, start a song from the menus, read Star Power while a song plays, read the end-of-song stats, and stop the game with the tools' own changes undone. Claude Code starts `tools/ch_mcp/front.py` from the `ch` entry in `.mcp.json`. That small front process runs the real server, `tools/ch_mcp/server.py`, as its child, called the worker, and forwards every call to it. So a fresh worker can replace the old one mid-session. It was built from five plans: `docs/superpowers/plans/2026-10-28-ch-mcp-server.md` (removed; `git show 444631e6:docs/superpowers/plans/2026-10-28-ch-mcp-server.md`); `docs/superpowers/plans/2026-10-30-ch-mcp-star-power-and-song-start.md` (removed; `git show 6804353f:docs/superpowers/plans/2026-10-30-ch-mcp-star-power-and-song-start.md`) for Star Power and the menus; `docs/superpowers/plans/2026-10-30-ch-mcp-in-game-input.md` (removed; `git show 6804353f:docs/superpowers/plans/2026-10-30-ch-mcp-in-game-input.md`) for the virtual kit; `docs/superpowers/plans/2026-10-31-ch-mcp-direct-start.md` (removed; `git show 6804353f:docs/superpowers/plans/2026-10-31-ch-mcp-direct-start.md`) for the human start from the command line; and `docs/superpowers/plans/2026-11-06-ch-server-reload.md` (removed; `git show 6804353f:docs/superpowers/plans/2026-11-06-ch-server-reload.md`) for the front.

## When to use it

Use it when a question needs the real game: how Clone Hero scores a chart, whether a note fires a hook, what the game's clock says while a song plays. Use Hydra's own tools for anything Hydra can answer alone. A live run needs nobody at the keyboard and never takes it: the game is launched minimized, never shown, and driven from inside through a virtual drum kit, so the user keeps using the machine while it runs. The user says in chat when a run may start, and the server's backup and restore undo the tools' own changes to the registry key. No file in the game's folders is backed up or restored: `settings.ini` keeps the run's `pause_on_focus_lost` line, and the files the game saves itself stay as the game left them. Some steps below use `hydra_replay` output, such as a score JSON or a dump. An agent never runs `hydra_replay` (agent rule 14), so the main session makes that file first and the brief names it.

## The tools

The list of tools lives in one place: `build_server()` in `tools/ch_mcp/server.py`. Each tool there has a one-paragraph description, and Claude Code shows the same text. Read the list there rather than from a copy. The front copies that list and adds two tools of its own, `ch_reload` and `ch_call`, from `FRONT_TOOLS` in `tools/ch_mcp/front.py`. `tools/ch_mcp/README.md` says how the server is registered and how its Frida agents are built.

## Safety rules

The server backs up one thing before it touches the game, the registry key below, and puts it back when it stops; `backup` in `tools/ch_mcp/game_files.py` owns it. No file in the game's folders is backed up, restored, moved or deleted. That covers `settings.ini` and the files the game saves itself (`C:\Users\Patrick\Documents\Clone Hero\scorestats.json`, `profiles.ini`, `profiles.bin`, and `scoredata.bin`, `scoresext.bin` and `user.bin` in the LocalLow folder). The user ruled on 2026-11-13: "stop messing with the game's save file. just let it stay.", and chose "Leave the line changed" for `settings.ini`. A backup an older worker took that still names files gets the line "<file>: left as the game saved it" for each, and the file is not touched. `ch_start` first checks that the machine is quiet, which adds about 6 s; `tools/ch_mcp/quiet.py` owns the check. A machine that is not quiet refuses the launch before any backup, and the reply says why. Then `ch_start` backs up before it launches. The first tool that touches a game the server did not start takes the backup then. `ch_stop` restores the key and prints one line for it. If the restore fails, the reply names `rewired.reg` and the backup folder; nothing else runs in that call.

Every run is recorded, and the recorder cannot outlive the run for long. `ch_start` starts `tools/ch_mcp/machine_recorder.py` as its own process, after the quiet check and before the launch, with no wait, and there is no argument to leave it out. It needs no rights an ordinary process lacks and only reads the game's memory. A recorder that fails to start, or that the worker can no longer write to, is one line in the reply and the run goes on. `ch_stop` and the worker's own exit close its stdin first, wait `RECORDER_EXIT_CAP_S`, then terminate it; `tools/ch_mcp/recorder_link.py` owns that. If the worker dies, or the recorder's own cap passes, it ends by itself. While it runs it is listed as open, so `ch_reload` refuses until `ch_stop`. One that has exited is not listed, and `ch_status` and the next `ch_stop` say so.

The backup also saves a registry key. Rewired, the game's input library, saves its bindings under `HKCU\Software\srylain Inc.\Clone Hero`, and the backup exports that key as `rewired.reg` into the backup folder. At the restore, the server exports the key again and compares it with the saved copy. When they match, the reply says "rewired registry: unchanged". When they differ, it deletes the key, imports the saved copy, checks it once more and says "rewired registry: restored". A key that still differs, or a `reg.exe` call that fails or passes its cap, is a failed restore named `rewired.reg`.

The run changes one line of the user's `settings.ini`. `ch_start` sets `pause_on_focus_lost = 0` after the backup and before the launch, so the game keeps running while it is not in front, and says so in its reply: "settings.ini: pause_on_focus_lost set to 0 for this run (not put back after the run)". Nothing puts the user's own line back, so the line stays at 0 after the run; the user chose "Leave the line changed" on 2026-11-13. A file with no such line launches with a warning, and `ch_kit_setup` then refuses, naming `ch_start`.

A run asked for a finer frame grid changes one more line. `ch_start` with `frame_multiplier` sets `simulated_frame_multiplier` in the same file, at the same moment, and says so in its reply with the old and new value and the same "(not put back after the run)". With vsync off the game runs `framerate` times the multiplier frames a second (TM-54 on `docs/clone-hero/03-timing.md`). The user answered "Yes, set it" for this line on 2026-11-21 (session 97245ab7), and it is left changed after the run, as the 2026-11-13 choice above leaves the pause line. Left out, the line is not touched, so a later run without it plays at whatever the line was left at. `_frame_multiplier_refusal` in `tools/ch_mcp/game_tools.py` owns when the argument is refused; a refusal comes before any backup or launch and changes no file. Every start writes a frame settings file into the session folder (its name is `FRAME_SETTINGS_FILE` in `tools/ch_mcp/game_tools.py`), with `framerate`, `vsync` and the multiplier before and after, and prints one line for it. The frame step the run really gets is measured on the game's frames, not read from that file. `tools/ch_mcp/game_files.py` is the one reader and writer of `settings.ini`.

The game window is never brought to the front. `ch_start` asks Windows to open the game minimized and not active, and a human launch keeps that ask when it starts the game paused. The one launch that cannot ask is the spawn form of the human launch (`launch` set to `spawn` in `tools/ch_mcp/launch_patch.json`), because Frida's spawn takes no show-window option (`_real_spawn` in `tools/ch_mcp/bot_run.py`). The file ships set to `suspended`, and the direct-start plan's question 2 says when a live run may switch it. From then until `ch_stop`, a watch counts every time the game's window becomes the front window, and `ch_status`, `ch_kit_status` and `ch_stop` print that count. The count is information, not a pass condition: the user ruled on 2026-10-31 that the game taking focus briefly does not matter ("why does it matter if the game is focused briefly?"). No tool on the kit route focuses or shows the window.

The user's own keyboard and mouse reach no player in the game while a run goes on. `ch_kit_setup` takes the keyboard and mouse away from every Rewired player. It also switches Rewired's keyboard device and its mouse device off for the run, so nothing the user types or clicks reaches the game at all. The user ruled both on 2026-10-30. If either device does not read back as off, setup refuses and tears the kit down again. Its reply has a line for the keyboard and a line for the mouse, and `ch_kit_status` prints both too. `ch_kit_setup` in `tools/ch_mcp/kit_tools.py` and `setup` in `tools/ch_mcp/agent/kit.ts` own how the switch is made and checked.

The kit is always taken away again. Besides the keyboard and mouse, `ch_kit_setup` lets the game listen while it is not in focus and hands the kit to one player with the game's own drum map. It loads that one map by its category and layout, `KIT_MAP_CATEGORY_ID` and `KIT_MAP_LAYOUT_ID` in `tools/ch_mcp/kit_tools.py`, not the player's default maps, because the System Player has no default map for the kit (IN-76 on page 07). It checks that the map it reads back is that one and is enabled (`map_problems`), then checks that map's bindings against `KIT_BINDINGS` in the same file. A setup that fails, reads another map or reads other bindings is torn down at once. The kit agent answers every message even when the game's own code faults inside a call: `settled` in `tools/ch_mcp/agent/kit.ts` catches the throw on the main thread, so the agent keeps listening and the teardown gets its reply, and `faultOf` in the same file puts the fault's details in the error reply as a `fault` object, which `fault_lines` in `tools/ch_mcp/kit_tools.py` prints under the failed request's line (a failed press inside `ch_play_chart` carries the same lines in its error message). `ch_kit_teardown` clears the kit's pads and buttons and removes the kit. It gives every player back exactly the keyboard and mouse setup took, and puts each Rewired device back to what setup recorded. It also turns the game's "ignore input when not in focus" switch back to what it was. It prints one check per step, as "ok" or the mismatch. `ch_stop` runs the same teardown before it stops the game, and a failed check reads like a failed restore: "kit teardown failed on" the step, then what it found.

The key route is locked. `ch_key`, `ch_press` and `ch_play_chart` with `route` set to "keys" press keys through Windows, so they take the game window and the user's keyboard. The `allow key run` hook in `C:\Users\Patrick\.claude\gates\percall.py` refuses each such call unless the user has typed exactly `allow key run` in chat in this session, and each such message lets one call through. The key route exists only for a day the kit route breaks; if you need it, ask the user in chat first. `ch_play_chart` with no route uses the kit once `ch_kit_setup` has built it, and refuses until then.

Play stays offline. The server launches the game only with the command line `bot_run.launch_command` builds. A human launch (`ch_start` with a song folder and `human=True`) opens no menu at all. It changes one byte of the game's command-line player loader, in memory only, with the bytes `tools/ch_mcp/launch_patch.json` names, so the loader makes a human player and not the bot. The game file on disk is never written. The user allowed this one-byte patch on 2026-10-31 (question 6 of the direct-start plan). The loader and its byte are IN-61 on `docs/clone-hero/07-internals.md`. A human run may play any chart, from its own folder. The user dropped the earlier rule that kept human runs on the test chart on 2026-11-21 ("Yes, drop it", session 97245ab7), on their 2026-10-31 ruling that network blockers are not wanted. An agent had copied that rule from the direct-start plan's LS-D2 stop line, and no question ever put it to the user. Whether a human score is posted anywhere when nobody is logged in is still open (IN-73 on `docs/clone-hero/07-internals.md`). `ch_open_song` drives the profile screen, the main menu, the song list and the player screen by kit presses and reads whether the Online menu is on screen before every step, refusing to go on while it is. No tool opens the Online menu, Settings, Practice or the control mapper.

The Frida agents read, trace, call game methods and, where a feature needs it, set game fields. The user allowed method calls and field writes on 2026-10-30. Each agent that calls game methods holds its own list of the calls it may make: `tools/ch_mcp/agent/menu.ts` for the menu read, and `tools/ch_mcp/agent/kit.ts` for the kit, whose list must equal the names in `tools/ch_mcp/kit_methods.json` (each with the dump line it was read from). No agent calls a game method that starts a song, so no list of song-start calls exists. A test in `tools/ch_mcp/tests/test_frida_attach.py` checks that every call in every agent is on its own file's list and that the kit's list matches its data file. No agent sets a game field directly today: the kit changes the game only through the setter methods on its list in `tools/ch_mcp/kit_methods.json`. The same test file still checks that no agent reads game memory by raw offset. A trace hook patches the start of the traced method in memory while it is attached; the user approved that on 2026-10-28. The launch agent, `tools/ch_mcp/agent/launch.ts`, is the one agent that changes what the game's own code does, and only by the one byte "Play stays offline" names. It holds no address or byte of its own: `tools/ch_mcp/launch_patch.json` rides in its arm message. It writes only when the loader's first bytes and the patch site both read as that file expects, and otherwise refuses with what it found. After the write it hooks the loader's entry, and that hook only counts the loader's runs and reads the patch site at the first one. `applyPatch` in `tools/ch_mcp/agent/launch_core.ts` owns that decision, and `tools/ch_mcp/tests/test_frida_attach.py` checks that the write can happen only from the call Frida makes when the game maps `GameAssembly.dll`, or from the deferred step that call schedules when the file's `defer` is true. The launch agent calls no game method. The state agent places one hook of the same kind while it is attached: on a per-frame method of the player screen, `watchPlayerScreens` in `tools/ch_mcp/agent/menu.ts`. That hook only records the object the method runs on, because the garbage collector's search cannot find the player screen; it reads no field and calls no game method. The method watch skips, in a class it hooks whole, any method whose code other classes share, and names each one it skipped in its start reply; `shared_rvas` in `tools/ch_mcp/method_watch.py` decides which.

Two facts about the menu driver matter for safety, and its code holds the details. The Online check refuses on more than an Online menu that reads as open: an error in place of the flag, or a read with no menu block, stops the run too. `online_refusal` in `tools/ch_mcp/menu_tools.py` says which reads count as closed. The step file presses no keys at all. Every item in it is a `kit:` item, and `item_problem` in the same file refuses a key name, a lane or typed text; `load_steps` runs that check on every step. So no step can press Space, which the manual's Keyboard and Gamepads page says opens the control mapper from the main menu.

Every wait has a cap and says so in its reply when the cap ends it. No tool retries on its own.

Nothing runs over the user's song library. Each tool takes one song folder or one chart folder.

## The shape of a live run

Each live run names its pass and fail lines before it starts, has a cap on how many times it runs, and ends with `ch_stop`'s restore lines. A typical run on the kit route goes like this:

1. `ch_start(song_folder, human=True)`. This is the direct route, the way to start a song for a kit run. The game starts paused and minimized, the launch agent attaches to it by process id and arms, the game is let go, and the agent changes the loader's one byte the moment the game maps `GameAssembly.dll`. `ch_start` returns once the agent says patched, and its reply shows the `settings.ini` line it set for the run, the module names the agent saw at the arm, and the bytes it found and wrote. A refusal or a passed cap kills the game and says why. `bot_run.launch_human` owns the order and the three caps. `ch_status` then prints the agent's status again, ending with "loader ran after patch:" and "yes", "no" or "not yet". The reply also names the machine recorder's pid and its `machine-<n>` folder under the session folder, and `ch_run_chart`'s reply, after the watch step's line, says how many samples it has written so far. A run on a game the server did not start has no recorder, and that reply says so in the same place. The default player is `bot_run.DEFAULT_PLAYER`; pass `player="ProDrums,Expert"` for a pro drums chart. The launch agent must be built first (`npm run build:launch`, see `tools/ch_mcp/README.md`). Every agent build writes a stamp beside its `.js`, and the loaders refuse an agent whose stamp is missing or stale; `tools/ch_mcp/build_stamp.py` owns that check. With a song folder and no `human`, the bot plays the song from the command line and needs no kit. With no song folder, the game opens at its menu, which only the menu walk of step 6 needs.
2. `ch_attach`, then `ch_state`, `ch_snapshot` or `ch_menu` to read the game.
3. `ch_kit_setup`. Its reply shows Rewired's keyboard and mouse switched off, every player's keyboard and mouse flags before and after, the kit, and the map and bindings it read back. The kit's map is loaded by category and layout, from `KIT_MAP_CATEGORY_ID` and `KIT_MAP_LAYOUT_ID` in `tools/ch_mcp/kit_tools.py`, on whichever player gets the kit. `player` names the Rewired player the kit goes to; left out, it goes to `KIT_PLAYER` in the same file. The command-line loader gives the song's player Rewired's System Player (IN-66 on page 07), so for a human launch the kit goes to `System`: pass `player="System"`. The user chose that in the direct-start plan's question 7. `KIT_PLAYER` stays `Player1`: LS-D1d passed on System, and the user ruled on 2026-11-06 to keep the default ("Keep Player1"), so the menu walk keeps the player its presses were proven on. `ch_kit_status` shows the frame rate, whether the game has focus and the foreground count. `ch_kit_watch` reads every player for a few seconds and says whether any key reached one.
4. For Star Power, `ch_sp_watch_start` as early as the run allows. The watcher waits for a moving engine clock and logs every change of the Star Power fields to a CSV. `ch_sp` prints its latest read, `ch_sp_watch_status` lists the activations and the rises of the meter and prints a line with the gaps over 50 ms between samples, inside the song, `ch_sp_between` answers a question about one stretch of the song, and `ch_sp_watch_stop` ends it. `ch_sp_compare(watch_csv, score_json, schedule_json, resolution)` checks the CSV against a `hydra_replay` score JSON. It needs `resolution`, the chart's Resolution from its `[Song]` section, and refuses without it. It takes the run's stop reason from the last play session and refuses while one is running; a run that stopped before the song's end gets a FAIL line ending with the run's stop message. After its checks it prints one line per activation of the schedule: Hydra's ready point (the schedule's `sp_ready_ms`) beside the first watch row where the game's meter had reached its own half (`sp_half_u64`, the game's field at engine `+0x1B8`) with the flag clear, or that the game was not ready before the activation's chord (`sp_tools.ready_lines` owns the line). `ch_sp` and `ch_sp_between` use the same half for "ready". It looks for each chord where the auto-player pressed it, and reads that from `schedule_json`, the same path's schedule that `ch_play_chart` plays (step 5). A schedule that refuses its path is refused with the schedule's words. A bot run cannot answer a Star Power question, because the game's bot never gains or spends Star Power (docs/clone-hero/live-checks.md). So a Star Power run needs a human player: a song started with `human=True`, or one started from the menus.
5. For the auto-player, `ch_play_chart` as early as the run allows, with `song_folder` so the run cap follows the song's length. With the kit set up and no route given, it presses each chord through the kit. `ch_kit_press` presses one chord by hand. A song launched with a bot is played by the bot, so the auto-player needs a human player, started the same two ways as in step 4. Every press comes from `schedule_json`, the file `hydra_replay schedule` wrote from the chart, the dump the score file came from and a path index (docs/development.md, "Developer tools", says what the file holds). The player works out no window, lead or Star Power end itself.

   The file says when each press should be judged, not when to send it. The judge time is the moment the game scores the press. Each press has a judge target (its chord's `ms` plus its `aim_ms`, `Press.at_ms` in `tools/ch_probe/experiments/play_chart.py`). It also has a band, the stretch of song time it may be judged in (`band`, with `from_ms`, `to_ms` and `from_strict`), and its chord's hit window (`window_from_ms` and `window_to_ms`). A plain press aims at its chord's own time, and its band is its window. A press that must beat a Star Power end has a band from its window's front edge to that end, and it aims at the band's middle. A squeeze-out's late gem has the other kind of band: from just after its own end to its window's back edge, again aimed at the middle. The file holds no frame length, lead, lag or gap of its own. A later order group of a chord names the group it `follows`, with no gap in milliseconds.

   The player reads the end the game stored after each chord the file names. It then moves the band of each later press timed from that read to that press's own end as the read moved it, and aims the press at the new band's middle (`retime_from_end` and `moved_band` in `play_chart.py`). The read end and the press's own end can sit at different tempos or time signatures, so the file gives each such press a `conversion`, and the player multiplies the read's error by it and works out no ratio itself. When the read leaves an end-band empty, because the press's own end now lies before its window's front edge, the press goes down on the window's first frame and its row's `agent_note` says `no_frame_in_band`. When the read crosses a press's fallback threshold, it takes the fallback the file wrote: a squeeze-out's late gem goes down with its chord's last inside group (its press row says `retimed=inside`), and a squeeze-in is pressed plain instead (`retimed=plain`). A late gem kept after the end says `retimed=late`. It refuses to start when the file holds a refusal, or a squeeze the game cannot make at 100% speed, and quotes the file's words; each such squeeze's line gives the file's safe sum. A fill the path passes over needs no argument: the schedule marks each such chord `declined` and lists the gems it sends in `kept_gems`, every gem but the fill's activation note, and the player sends that list. The schedule has one decline rule, so there is no `decline_mode` and `hydra_replay schedule` has no `--decline`. `path_index` (default 0) names the path of the dump you mean to play. The schedule records the path it was made from in its `path_source`, and a schedule made from another path, or with no `path_source`, is refused before anything starts; `path_index_refusal` in `tools/ch_mcp/game_tools.py` owns that check.

   The route says who times the presses, and there is no switch. On the kit route the whole schedule goes to the kit agent, which hooks `GameManager.Update` and picks the frame for each press (`tools/ch_mcp/agent/press_schedule.ts`). It measures the frame step as the median of every step of the song clock since play began, so one long frame does not move it. A press written on a frame is judged `JUDGE_FRAMES` (two) frame steps after that frame's clock, because the hook's clock is a frame old and the game reads the write a frame later (IN-93 on page 07). So on each frame the agent predicts that judge time. It puts the press down on the frame whose predicted judge time is nearest the target, among the frames inside both its band and its window. When the frames straddle the band, so no frame can land in it, the press goes down on the frame inside its window nearest the band, and its event says `no_frame_in_band`. A squeeze-in then aims at its chord's own time instead (`no_frame_aim_ms`). A press with no frame inside its window is not sent, and its row says DROPPED. A later order group goes down on a frame after the frame of the group it follows. Each press event reports the frame step it used, its predicted judge time and the judge time that really followed, and the press log keeps them as `step_ms`, `predicted_judge_ms` and `judged_ms` (`FRAME_PICK_PRESS_COLUMNS` in `overlay_logs.py`). Python then only listens for the agent's report of each press, writes the press log and reads the Star Power ends, and sends a `retime` when an end moves later presses. On the keys route the auto-player's own Python loop reads the clock and sends each press on the first read at or past its judge target. That loop adds no judge delay, because nobody has measured when the game judges a key press, so a keys press is judged later than its target by that unmeasured delay. It sends nothing for a press read past its window's back edge, and that row says DROPPED. A later order group goes on the first read after the group before it was sent. Neither `ch_play_chart` nor `ch_run_chart` takes a `timing` argument. A call that still passes `timing` is not refused: the server drops the argument without a word and runs the call as if it were left out (`test_a_leftover_timing_argument_is_dropped_without_a_word` in `tools/ch_mcp/tests/test_server.py`). The press log keeps all its columns, so every earlier log still reads: the seven step-timing columns are filled only on keys rows and stay empty on kit rows, and `frame_gap_ms`, `agent_note` and the three frame-pick columns are filled only on kit rows. `ch_kit_frame_probe(seconds)` checks the hook on its own inside a playing song, for at most `FRAME_PROBE_SECONDS`: it logs each frame, presses Green once, reads it back, and prints PASS or FAIL. The frame rate it prints never decides that (D341). What LS-G1's probe found is on page 07, IN-93.
   `ch_run_chart(song_folder, score_json, schedule_json, kit_player="System")` does steps 2 to 5 in one call, right after `ch_start`, because calls made one by one reach the first press too late. It attaches, checks the song, sets the kit up on `kit_player`, starts the Star Power watch and starts the auto-player, with one engine search shared by the watch and the player. It takes `schedule_json` and `path_index` as `ch_play_chart` does, and no `dump_json` or `decline_mode`. It also takes an optional `probes_json`, the same probes file `ch_edge_probe` reads (below). With it, each chord the file names is pressed at the lead the file gives, its press row carries the asked lead in the `probe` column, and the reply adds the "probes:" line right after the play's line. A probes file `ch_edge_probe` would refuse is refused before the builds record and the attach, in `edge_probe`'s own words, with nothing started. Without it, the run presses the schedule exactly as given. `tools/ch_probe/experiments/edge_probe.py` owns how a probe chord is moved, for both calls. The run is for the song folder that holds the schedule's `chart`. Before the attach, the call refuses when `song_folder` is not that folder, and when the schedule names no chart or names it by a relative path (`schedule_chart_folder` in the same file). After the attach, the "song check" step reads which song folder the game has loaded, and stops the run before any press unless it is that folder. Before the attach, the call also writes `builds-<n>.json` in the session folder: the build stamp of each agent the run loads and the schedule's `hydra_replay_build` (`build_stamp.builds_record` owns what it holds). It returns at the first press, with one line per part and how long that part took, the "builds record" line naming that file, the press log's line, then "first press chord index k at ms". It writes a press log, `press-<n>.csv` in the session folder, with one row added at each press as the run goes, and the reply names the file. The log's columns have one home, `PRESS_LOG_COLUMNS` in `tools/ch_probe/experiments/overlay_logs.py`; among them, the first row of each press message says how long each step of that press took, so a stall names the step it happened in, and `ch_play_status` shows those times on its rows too. `ch_play_status` names the file on its first line, and the file holds every row when the server cuts a long status reply. The agents now skip any `GameManager` the game has destroyed. Every Unity object holds a pointer to its native half in `m_CachedPtr`, a field of `UnityEngine.Object`, and Unity clears that pointer when it destroys the object. The object itself can stay in memory until the garbage collector runs, which is how a destroyed one can still be found. The lookup in `tools/ch_mcp/agent/gamemanager.ts` reads that field by name, and the state, clock and trace agents all go through it. Each `ch_state` reply carries `destroyed`, the number of destroyed `GameManager`s the read skipped.
