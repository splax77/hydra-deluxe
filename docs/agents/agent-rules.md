# Agent rules

This page holds the full text of the fifteen agent rules. `CLAUDE.md` keeps each rule as one short line under the same number and points here for the details. The numbers never change, because other pages cite the rules by number.

These hold for the main session and every agent it sends out. Hooks enforce a few of them (the hooks paragraph after rule 15 says which); the details live in `docs/agents/brief-preamble.md` (what every agent reads first) and the model-postures file (what the main session gets each prompt).

1. Agents never run the full test suite, and they run no test that needs a build; those are the main session's (rule 14). Any other test an agent runs is for its own change. When the main session merges a Hydra change, it runs what `build-cpp\Release\hydra_precheck.exe --repo <path> --tests <range>` prints on its `tests:` line. That tool decides what counts as shared code and when the whole suite runs, so nobody types the test list by hand. For hooks, the main session runs the whole suite only when the change touches shared code: `gates\common.py`, `gates\lib`, `settings.json`, `gates\tests\lib`. Untouched parts stay as they were, so re-running them proves nothing (the user's ruling, 2026-10-14). Three tests read the whole repo, so they also run at every merge to Hydra's `main`, docs-only ones included: the docs-vs-code check (`hydra_tests.exe "-tc=docs match code*"`), the single-owner scan (`hydra_tests.exe "-sf=*single_owner*"`) and the precheck self-test (`hydra_tests.exe "-sf=*test_precheck*"`). A change in one place can break any of them, and twice only CI caught it (the user's ruling, 2026-10-24). The precheck prints them as three `always:` lines, and each line is one command of its own.
2. Planning agents run on Fable. Code executors run on Opus. Code reviewers run on Sonnet. Read-only scouts run on Sonnet or Haiku. Bulk read-and-fill writers, such as the card writers, run on Haiku.
3. No work starts without the user's approval. Every plan and every build waits for the user's yes before it begins. In this rule a build means any piece of work: writing code, editing hooks, or launching agents to do either. A change that only touches code needs no approval of its design: pick the design and recommend it, but the build still waits for the yes. A change to a display in the app or a stored record also takes its design to the user first. When the user asks for one specific edit, the request is the approval. The main session's compiling and test runs inside approved work need no separate yes (rule 14).
4. Agents never stall or go quiet for long. When they hit a problem, they fail loudly: stop and say what broke.
5. One review per change, then done. One fresh reviewer agent reads the change's code and documents, fixes every finding itself, commits its fixes and signs off. Then the change merges. There is no separate fixer, no checker and no second round, and nothing goes back to the user (D107). There is one narrow exception (D314). A reviewer cannot compile, so its C++ fix can fail the main session's build or a test. That fix goes to a fresh executor, and a fresh reviewer reads only that fix. If that fix fails too, the main session stops and tells the user. A reviewer that runs out of time or tool calls signs off what it fixed and lists the rest in the Notes section of its review; the main session passes those Notes to the user, and the merge does not wait for them. No agent is woken up again after its turn ends.
6. Agents run in parallel, in workflows, while the main session merges. Waves of parallel agents are fine. Never queue independent tasks one after another.
7. Agents write a status line every 5 minutes; only time counts, not calls. At 100 tool calls an agent starts wrapping up: it commits what it has and hands the rest to a fresh agent. A reviewer hands nothing on: it signs off what it fixed and lists the rest in the Notes of its review (rule 5). 150 tool calls is a hard stop. Time works the same way. At 20 minutes of real time an agent starts wrapping up, and 30 minutes is a hard stop. Whichever limit comes first applies.
8. Nobody runs a full library test without the user's explicit permission, asked for in chat first. That covers the main session and every agent, and any run over the user's whole song library (for example `hydra_batch --whole-library`, or a whole-library compare or timing run). The user allows one run by sending exactly `allow library run`; each such message lets one command through. Ask only when nothing smaller can answer the question. Otherwise test on the checked-in chart corpus in `testdata/input` (about 115 charts) or on the few charts the change touches.
9. Never trust another agent's summary or the comments it left behind. The code and the source data are the source of truth. Check a claim against them before you repeat it or act on it. A handoff is another agent's summary. Before any new work starts from a handoff, every claim in it is checked against what actually exists: the code is the source of truth, and a handoff claim that does not match the code is wrong. `docs/agents/handoff.md` says what a handoff holds and how to check one.
10. After a push, report done and move on. Don't wait for CI or check it unless your change is to CI itself. CI runs on GitHub after the push, and nothing waits for it.
11. A question that changes what Hydra does lists what the user will see. Before the question goes out, find every screen and output that reads the changed value: search for its readers, not just the place it is decided. Write each one into the question under "You will see": the screen, what it shows before, and what it will show after, taken from a real chart in `testdata/input`. A question that changes nothing on screen says so in one line. A screen the list leaves out is a change the user did not approve, so it becomes its own question before anything ships, never a line in a later report. The user ruled this on 2026-10-31 ("Yes, require it"), after `docs/audit/2026-10-31-silent-changes.md` found four questions that asked about a rule and never showed what the screen would say: D13's squeeze-in sentence, the 96.2 ms readout, D229's fill lanes and the over-500 confirm.
12. A change the user can see that their words did not ask for is a question before it merges, never a line in a report. This covers an agent's extra, a reviewer's addition, a side effect of a refactor and a stray edit found in the working tree. Nothing merges while such a question is unanswered. Opt-out lines such as "I'm treating it as fine unless you say otherwise", "Say the word and I'll hide it", "it'll ride along" or "I recommend leaving it as is" never close one: silence is not a yes. The user ruled this on 2026-10-31 ("Yes, ban them (Recommended)"), after `docs/audit/2026-10-31-silent-changes.md` found five changes that stayed in Hydra because an opt-out line went unanswered (its cases 4 to 8). The reviewer backs this rule: step 9 of `docs/agents/derive-once-review.md` lists every visible change with the user's words for it, and one with none holds the merge.
13. A commit or release never holds an edit that nobody in the session made or was asked to make. Uncommitted edits found in the working tree are reported to the user and left out of every commit until the user says what they are, whether or not they change anything on screen. The user ruled this on 2026-10-31 ("Yes, add it (Recommended)"), after the silent-changes finding traced a hidden eff. figure to an edit of unknown origin that went into release 1.7.3 under "build to v1.7.3".
14. At most three builds run at once on this machine. In this rule a build means compiling, not rule 3's piece of work. Agents never build. A main session builds, one build at a time, through a pass from `hydra_build_pass`; `docs/development.md`, "Building under Claude Code", says how. Any test that needs a build is the main session's too, so an agent hands its branch back uncompiled. Agents may run `hydra_precheck.exe` from the main checkout, because it only reads a worktree and tests nothing. They may not run `hydra_tests.exe`, `hydra_uitest.exe` or `hydra_replay.exe`, because those test a branch's code and need that branch built. A build or test that fails before review goes to a fresh executor on the same branch, with the failure output, and the main session then builds again. The main session runs a test red only when a brief asks for it. Otherwise the reviewer reads the test and says what would make it fail. The user ruled this on 2026-11-07: "i want a limit of three builds at once, strictly enforced. agents are never allowed to start their own builds, only the main session, with a limit of one build per session." and "any tests that require a build are done by the main session, not agents." D314 in `docs/audit/2026-10-03-fix-decisions.md` holds the answers that followed.
15. Find the existing owner before you write one. This applies to plans and briefs as well as code. Before a plan step, a brief or a change answers a question, write the question in plain words ("which way is each note of this squeeze pressed"). Then search everywhere it might already be answered: `src/core`, `src/app`, `src/ui` and `tools`. Look for answers hidden in text and signs, not only in named functions. A sentence that picks "early" or "late" is an answer. So is a plus or minus sign on a press. If one place answers it, call that place. If several places answer it, merging them into one core owner is the first task, and only then does the new work start. If none does, the new owner goes in core, and the plan's Premise map names the search that found nothing. A rule copied from a tool, a test or a comment is a second owner, never a source. The Dynamic Hit Window row is why this rule exists. On 2026-11-13 the user found it called the same note "late" in the squeeze sentence and "early" in the row. "Which way is this note pressed" had three answers written by three sessions: the sentence (2026-10-03), the `hydra_replay` schedule tool (2026-11-08) and the row (2026-11-12), which copied the tool's answer into cases the tool never handled. The user asked for this rule on 2026-11-13: "add a rule so sessions find the existing owner before writing one".

    A display decides nothing about Star Power, scoring or the player; it reads what the engine computed. That covers every screen and every plan for one. Each value a screen shows maps to one engine value: a stored record field, or what the replay the screen already runs returns. When the engine works a value out during its search but keeps it nowhere a screen can read, the change carries that same value out, as a field the engine's own code fills. It never writes a new rule that decides the value, so "if none does, the new owner goes in core" above never applies to a display. A plan never offers its own reading of a gap, an edge or an exception, such as "the gauge stays empty until the chord" or "a chord on the end counts as inside". It never puts such a reading to the user as a question either. Rule 12 asks about changes the user's words did not ask for; it never turns a rule a plan made up into a question. A plan's reviewer checks every design choice and every question in it. If one is not a read of an engine value, that is a finding. The reviewer fixes it by naming the engine value instead, or by adding the task that carries that value out, and drops the question. The Preview's Star Power gauge is why this paragraph exists. On 2026-11-14 a plan asked the user four such questions about where the gauge refills and where a squeezed-out window ends. The user answered: "the correct rule is to use what hydra already knows. stop trying to invent new rules" and "anything that invents its own rule instead of reading what the engine already knows is a violation". The user approved adding this rule the same day: "Yes, add it".

    Two more habits back this up. A plan that changes what Hydra decides or shows is built from an owner map that a scout writes first, and a result that contradicts the user's words stops the work instead of being resolved inside a plan. `docs/agents/owner-map.md` says how both work. Under an owner map, "if none does, the new owner goes in core" above waits for the user: a question with no owner goes to the user first, and only a value the engine already works out and keeps unreadable is carried out. A brief for such a plan, or for its scout, gives the user's requirement in the user's own words and names the engine values it points at. It never adds the main session's own sentence about how to apply them, because an agent has to interpret such a sentence at its edges, and interpreting it invents a rule. The user asked for these after a third plan in a row invented a rule on 2026-11-14: "Yes, write them".

Hooks check four of these. The progress hook keeps rule 7's status lines and budgets. The whole-library guard keeps rule 8. The ref gate keeps rule 5's one review before `main`. A hook keeps rule 14's "agents never build" by refusing `hydra_build_pass` to every agent, and `build_cpp.ps1` then refuses any build with no pass; nothing checks rule 14's line on tests. The main session also gets a stall notice when an agent has made no call for 10 minutes, which helps with rule 4. The notice repeats at 20 and 30 minutes of the same silence, and the third says it is the last. The step is `STALL_SECONDS` in `stall.py`, and the cap is the progress hook's time limit, `MINUTES_STOP` in `progress.py`. An agent that has not handed back 30 minutes after its first call gets one more notice, saying it is past that limit. Under each agent's status lines, `stall.py` adds an evidence line of what the hooks and git recorded for it, and the main session checks the lines against it; the preamble's "Status lines" section says what that line holds. No hook checks the rest; follow them yourself. The hooks live in `C:\Users\Patrick\.claude\gates\`.

## Rulings and definitions

This rule has no number. `CLAUDE.md` keeps its short form under "Rulings and this machine".

Nothing is recorded as the user's ruling without the user's explicit approval. The user asked for this on 2026-11-13: "nothing should ever be recorded as a ruling without my explicit approval. so how do we prevent this?" A ruling is filed in `docs/agents/rulings/` only after the user clicks "File it" for that exact line in a question box. That folder's `README.md` holds the line shape and the approval step. Git's ref gate runs the hooks repo's ruling check, which that `README.md` names, on every branch a Claude Code session moves, and it refuses an added ruling line the user did not approve. Old lines get one narrow click-free route, the backfill route, which the same `README.md` describes. A ruling counts only once it is committed.

A line under `## Confirmed` is the user's words. Anyone may cite it for what it literally says.

A line under `## Unconfirmed` is not the user's ruling. Sessions keep following it as a working rule, but no plan, review or question may cite it as the user's ruling. A session that needs the user's words for it looks for the quote in a session card or asks the user.

A reading, a memory note, a handoff or a plan's "as ruled" never counts as the user's words.

`CONTEXT.md` decides what a project word means. A ruling that uses a word does not redefine it. A change that gives a `CONTEXT.md` word a second meaning is a finding at step 8 of `docs/agents/derive-once-review.md`, whatever a rulings line, a plan or a memory note says. Git checks only `docs/agents/rulings/`. The decision log, plans' "User decisions", `docs/adr/` and `CONTEXT.md` are held by the review instead: a decision entry there counts only when it quotes the user's words as found under `## Confirmed` or in a session card.

A change to what a `CONTEXT.md` term means is treated like a ruling: only the user approves one. A reviewer or executor never rewrites a definition, even to fix a finding. It writes the finding as a question for the user. Before any agent calls a project term wrong or unclear, it checks how the code already uses the term. The code's usage settles the meaning, not a guess drawn from one sentence of a doc. If a definition's text and the code's usage disagree, that is a question for the user, in game terms with both readings, and the agent changes neither the text nor the code to match the other. This part exists because a reviewer reworded "Backend squeeze" on its own (commit `fdf45d790a2e706be7a8f847af49080f59593728`), reasoning from the word "early" in its one-line definition without reading the code, and the main session reverted it (`e6d78af63ab119292c661419865630fa9d76b929`). The user's words: "why is the reviewer trying to invent its own rules? this is exactly the kind of bullshit i am trying to stop".
