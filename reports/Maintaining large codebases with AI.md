# Guardrails, not models, keep AI codebases clean

The "vibe coded slop" complaint has real data behind it. Across 2024 to 2026, independent studies and vendor reports agree that AI-assisted code brings more copy-pasted code, less refactoring, and more warnings that stay in the code long after the speed gains fade. But the same evidence shows the cause is missing discipline, not the AI itself. Google's DORA survey calls AI an "amplifier": teams with strong tests, small changes and good version control gain, and teams without them break more. The big companies all keep large codebases healthy the same way. They make the safe path the only easy path, and then let machines enforce it. Google uses one repository with one version of everything. Microsoft generates many artifacts from one spec. Amazon blocks unreviewed code in its deploy pipeline. Oracle's OpenJDK needs a named reviewer on every commit. Anthropic's own advice for Claude points the same way: give Claude a check it can run, keep instructions short, enforce must-always rules with hooks, and review with a fresh agent. Your "derive once" rule has a well-known name. It is DRY ("Don't Repeat Yourself") as its authors meant it, also called SPOT ("Single Point of Truth"), and in data systems the "system of record". No binding standard requires it, and no standard treats two disagreeing on-screen counts as a defect. Your setup already matches most of this precedent. The main gaps are a cheap clone detector, human sampling of agent-only reviews, and pruning the context your agents load every session. The recommendations section near the end turns these into ten ranked steps for this project.

## The slop charge holds up: copies rise, refactoring collapses

The clearest data comes from GitClear, which sells code-analytics tools, so treat it as a **vendor report**. Its three yearly reports all point the same way. The 2026 report covers 623M changes from 2023 to 2026. It found **refactoring fell from 21% of changed lines in 2022 to 3.8% in 2026**. Within-commit copy-paste rose from 9.4% to 15.7%. "Function connectivity" fell 35%, which means new code calls existing code less and writes its own version more ([GitClear 2026](https://www.gitclear.com/the_ai_code_quality_maintainability_gap)). That last number describes slop directly: the agent pastes a new helper beside the old one instead of reusing it. GitClear's data is correlational. It shows trends that line up with AI adoption, not proof that AI caused them. Its 2025 and 2026 reports also measure duplication differently, so the exact figures don't compare across years ([GitClear 2025 PDF](https://gitclear-public.s3.us-west-2.amazonaws.com/GitClear-AI-Copilot-Code-Quality-2025.pdf)).

Independent academic work backs up the direction with better study designs. A Carnegie Mellon study compared projects before and after they adopted coding agents, against matched projects that didn't (**arXiv preprint**, so not yet peer-reviewed). It found **static-analysis warnings rose about 18% and code complexity about 39%, and those costs stayed after the speed gains faded** ([Agarwal et al. 2026](https://arxiv.org/abs/2601.13597)). A second preprint checked 302,600 AI-written commits in 6,299 GitHub repos. More than 15% of commits from every assistant added at least one issue, and **22.7% of those issues still survive in the latest code** ([Liu et al. 2026](https://arxiv.org/abs/2603.28592)). A third found that after Copilot arrived in open-source projects, core developers wrote 19% less original code and reviewed 6.5% more ([Xu et al. 2025](https://arxiv.org/abs/2510.10165)). The cost moved onto the experts.

The most important result for an agent-built app is a **controlled experiment** (also a preprint). Four frontier agents solved **up to 13.1% fewer tasks when building on agent-written code than on human-written code**. Standard maintainability metrics did not explain the gap. Subtle changes to input checking and error handling did ([Patel et al. 2026](https://arxiv.org/abs/2606.21804)). In plain terms: debt left by one agent makes the next agent worse. Cleanup protects future agents, not just future humans.

Survey and trial data add context. Google's DORA reports are **large surveys**, so their numbers are correlations. In 2024, a 25% rise in AI adoption went with **a 7.2% drop in delivery stability** ([Google Cloud, DORA 2024](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)). By 2025, AI helped throughput but still hurt stability ([Google Cloud, DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). METR ran a **randomized controlled trial** in 2025. Experienced open-source developers were **19% slower with AI while believing they were 20% faster** ([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). METR's 2026 follow-up leans toward a speed-up, but its confidence ranges include zero and METR itself calls the new data unreliable ([METR 2026](https://metr.org/blog/2026-02-24-uplift-update/)). The lasting lesson is the perception gap: people trust AI output more than its measured quality earns. Vendor reports point the same way with bigger, looser numbers. CodeRabbit, which sells AI review, found AI co-authored pull requests had about 1.7x as many issues as human-only ones ([CodeRabbit 2025](https://www.coderabbit.ai/blog/state-of-ai-vs-human-code-generation-report)). Veracode found 45% of LLM outputs on security-targeted tasks had a flaw ([Veracode 2025](https://www.veracode.com/resources/analyst-reports/2025-genai-code-security-report/)).

The fair reading is this. AI speeds up writing code. Without guardrails, the extra volume turns into duplication, complexity and instability. With guardrails, the same tools work well. That second half is what the big companies show.

## Four giants make the safe path the only easy path

None of the four companies relies on engineers simply being careful. Each one picks a single owner for each thing, then makes tools enforce it. The table compares them. Evidence strength matters here, because many AI numbers are executive claims.

| Company | How it keeps the codebase healthy | What it does with AI code | Strength of the AI evidence |
|---|---|---|---|
| Google | One repository, one version of every library, every change reviewed, sweeping cleanups as routine | AI does migrations; humans still review every shard; output capped to fit reviewer time | Google's own papers, one small trial, CEO claims |
| Microsoft | One giant repo per product, shared tools from a central team, separate-person review required by the security process | Agent PRs get the same pipeline as human PRs; one instruction file nearly doubled success | Detailed team report from dotnet/runtime, one large internal study |
| Amazon | Each small team owns one service; review blocks deploy; slow, metric-watched rollouts with automatic rollback | Big Java-upgrade claim; after 2026 outages, more human sign-off | CEO claim, then press reports Amazon partly disputes |
| Oracle | OpenJDK: public proposal for big changes, warn-before-remove, tooling rejects commits without a reviewer | Mostly products for customers; no internal numbers | Press releases only |

### Google: one version of everything, and the changer fixes every caller

Google keeps nearly all its code in one repository called Piper. In 2015 it held about 2 billion lines of code and took 40,000 commits a workday. **Automated systems made more of those commits than people did** (about 24,000 versus 16,000) ([Potvin & Levenberg, CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/)). Machine-made maintenance was normal there long before LLMs. The key rule is the "one-version rule": nobody ever chooses which version of a library to use, because only one exists. Google states the debt logic plainly. In a monorepo, "the technical debt incurred by dependent systems is paid down immediately as changes are made," because whoever changes a library must update all its callers at once ([CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/)). Google's book calls workarounds for multiple versions "entirely lost labor" ([Software Engineering at Google, ch. 16](https://abseil.io/resources/swe-book/html/ch16.html)).

Review is small and fast. A 2018 study of about 9 million changes found **a median change of 24 lines and a median review under 4 hours** ([Sadowski et al., ICSE-SEIP 2018](https://sback.it/publications/icse2018seip.pdf)). That study also found Google reviews mainly to teach and keep norms, not mainly to find bugs. The public review guide sets the bar: approve a change once it "definitely improves the overall code health," even if it isn't perfect, because "codebases degrade through small decreases in code health over time" ([Google eng-practices](https://google.github.io/eng-practices/review/reviewer/standard.html)). Sweeping fixes have their own tooling. A tool called Rosie splits one huge patch into pieces by owner, tests each, and routes it for review ([CACM 2016](https://cacm.acm.org/research/why-google-stores-billions-of-lines-of-code-in-a-single-repository/)). Deprecation gets deadlines, funded owners, and compiler checks that block backsliding, because "code is a liability, not an asset" ([SWE book, ch. 15](https://abseil.io/resources/swe-book/html/ch15.html)).

On debt itself, Google's research has an awkward finding. Google tested 117 code metrics against what engineers reported. **No single metric predicted where engineers said debt was hurting them**, so Google measures debt mainly through quarterly engineer surveys. This comes from a secondary summary of a paywalled paper, so treat the details as unverified ([DX summary of Jaspan & Green 2023](https://newsletter.getdx.com/p/measuring-and-managing-tech-debt)).

With AI, Google aims at its oldest debt: unfinished migrations. Its own paper reports a JUnit3-to-JUnit4 migration of 5,359 files in three months, with about 87% of AI code committed unchanged. Engineers estimated a 50% time cut on a 32-to-64-bit ID migration. The paper is blunt about the limit: "The bottleneck in the process was the speed at which engineers could review the changes. We purposefully limited the number of changes we generate every week" ([Nikolov et al. 2025](https://arxiv.org/abs/2501.06972)). It also says plain syntax-tree tools are "always correct" and should be paired with the model to catch its mistakes. The headline numbers are weaker evidence. **CEO Sundar Pichai said in April 2026 that 75% of new Google code is AI-generated and approved by engineers** ([blog.google](https://blog.google/innovation-and-ai/infrastructure-and-cloud/google-cloud/cloud-next-2026-sundar-pichai/)). Semafor notes such figures are "pretty impossible to fact-check" ([Semafor](https://www.semafor.com/article/04/24/2026/google-ceo-says-75-of-companys-new-code-is-ai-generated)). Google has published no defect or rollback rates for AI code. The one **controlled trial**, with 96 Google engineers, found about 21% faster work on one task, with a wide margin of error ([Paradis et al. 2024](https://arxiv.org/abs/2410.12944)).

### Microsoft: same pipeline for agents, and one instruction file doubled success

Microsoft also chose one giant repo per product. In 2017 the Windows repo was about 300 GB and 3.5M files, with about 4,000 engineers ([Brian Harry 2017](https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/)). It changed Git itself so each developer loads only the files they touch. Its security process (the SDL, "Security Development Lifecycle") binds every team. It requires that "a manual review is conducted by a reviewer who isn't the engineer that developed the code," calling separation of duties "an important control" ([Microsoft Learn, SDL](https://learn.microsoft.com/en-us/compliance/assurance/assurance-microsoft-security-development-lifecycle)). Its Azure architecture guide says to track debt in the backlog beside features and reserve time every sprint to pay it down. Its 2026 text on AI says generated code is "untrusted until validated" and goes through the same reviews and tests "with the same rigor" as human code. It also names the cost: more generated output "shifts throughput pressure downstream" to review ([Azure Well-Architected Framework](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/maturity-model)). For API definitions, Microsoft writes the contract once in a language called TypeSpec and generates specs, SDKs and docs from it ([Microsoft Learn, TypeSpec](https://learn.microsoft.com/en-us/azure/developer/typespec/overview)). That is derive-once applied to interfaces.

The best Microsoft data on agents comes from a **detailed team report** on the .NET runtime repo. Over ten months the Copilot coding agent opened 878 pull requests. **67.9% merged and only 0.6% of merged ones were reverted.** But agent PRs drew more review comments than human ones (16.5 versus 12.4), and humans pushed their own commits to 45% of merged agent PRs. The most useful number: **"Our success rate jumped from 38% before our instruction file to 69% after."** That file spelled out build commands, test patterns and architectural boundaries ([Stephen Toub, .NET Blog 2026](https://devblogs.microsoft.com/dotnet/ten-months-with-cca-in-dotnet-runtime/)). The agent's limit in a mature codebase was project knowledge, not coding skill. A larger **internal study** of tens of thousands of engineers found command-line agents raised merged pull requests per engineer by about 24%. The authors warn they measured no quality, revert or rework outcome ([Murphy-Hill et al. 2026](https://arxiv.org/html/2607.01418v1)). Older Microsoft research also matters here. A 2013 study found review is "less about defects than expected"; its main payoff is shared understanding ([Bacchelli & Bird 2013](https://www.microsoft.com/en-us/research/publication/expectations-outcomes-and-challenges-of-modern-code-review/)). If nobody understood the code while writing it, review loses its main benefit, not just its bug-finding.

### Amazon: ownership, pipelines that refuse, and a 2026 course correction

Amazon gives each small team sole ownership of one service, from code to production ([AWS, two-pizza teams](https://aws.amazon.com/executive-insights/content/amazon-two-pizza-team/)). Its 2020 deployment write-up says every change must be approved by a teammate, and the pipeline "will block any unreviewed commits from being deployed." Code then rolls out slowly: one machine first, then one region wave at a time, with waits of an hour to half a day and automatic rollback when alarms fire ([Clare Liguori, Amazon Builders' Library 2020](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)). Shared safety settings live in one parent pipeline class that every service inherits. That is derive-once for process. After incidents, teams write a blameless "Correction of Error" report, and its action items feed back into readiness checklists ([AWS Well-Architected, COE](https://wa.aws.amazon.com/wellarchitected/2020-07-02T19-33-23/wat.concept.coe.en.html)).

Amazon's AI story has two halves. In 2024 CEO Andy Jassy claimed AI upgrades to Java 17 saved **4,500 developer-years**, and that developers shipped 79% of AI-generated code reviews without changes ([Andy Jassy on X](https://x.com/ajassy/status/1826608791741493281?lang=en)). That is a **CEO claim**. Amazon published no defect or rollback rate for the upgraded code. Then came trouble. After retail outages in March 2026, Amazon added "controlled friction" to changes in key systems, according to internal documents reviewed by the press. Amazon said none of the incidents involved AI-written code. It said one involved an engineer following "inaccurate advice that an agent inferred from an outdated internal wiki" ([Fortune, March 2026](https://fortune.com/2026/03/12/amazon-retail-site-outages-ai-agent-inaccurate-advice)). Several outlets report that junior and mid-level engineers now need senior sign-off on AI-assisted production changes ([Slashdot](https://slashdot.org/story/26/03/10/212214/after-outages-amazon-to-make-senior-engineers-sign-off-on-ai-assisted-changes)). Amazon also disputed a Financial Times report that its agent caused a 13-hour outage, blaming "misconfigured access controls—not AI" ([Amazon](https://www.aboutamazon.com/news/aws/aws-service-outage-ai-bot-kiro)). Whatever the cause, Amazon's fix was more human review, not less. The stale-wiki case also shows something new: once agents read your docs, outdated docs become a production risk.

### Oracle: a reviewer on every commit, and little else published

Oracle publishes almost nothing about how its database code is maintained. Its best-documented process is OpenJDK, which it leads. Any significant change needs a public proposal, called a JEP ([JEP 1](https://openjdk.org/jeps/1)). An API can't be removed unless an earlier release marked it for removal ([JEP 277](https://openjdk.org/jeps/277)). The repo's commit checker rejects any commit without at least one named reviewer ([openjdk/jdk .jcheck/conf](https://raw.githubusercontent.com/openjdk/jdk/master/.jcheck/conf)). Oracle's Java secure coding guide includes the rule "Avoid duplication," because copied code and data get changed inconsistently ([Oracle Secure Coding Guidelines](https://www.oracle.com/java/technologies/javase/seccodeguide.html)). The often-quoted story of Oracle Database as 25M lines of C held together by millions of slow tests is **an anonymous 2018 Hacker News comment**. No Oracle source confirms or denies it ([HN item 18442941](https://news.ycombinator.com/item?id=18442941)). On AI, Oracle's public work is customer products. By July 2026 it openly supports Claude Code and Codex for building on its Fusion platform, inside a framework that already enforces its security and approvals ([Oracle press release](https://www.oracle.com/news/announcement/oracle-introduces-ai-native-builder-experience-2026-07-14/)). Oracle has published no internal AI productivity or quality figures.

The common thread across all four is simple. Each company picks one owner for each thing: one library version, one spec, one pipeline, one reviewer of record. Then it makes the tooling refuse anything else. With AI, every one of them kept the human review gate and treated review capacity as the real limit.

## Anthropic says: give Claude a check, keep context small, review with fresh eyes

Anthropic's guidance rests on one constraint. "Claude's context window fills up fast, and performance degrades as it fills" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The context window is the model's working memory for one session. Everything else follows from protecting it and from giving Claude something to check against.

The first rule is verification. "Give Claude a check it can run: tests, a build, a screenshot to compare." Without one, "you become the verification loop." Anthropic lists four ways to stop Claude declaring done too early, in rising strength. You can ask in the prompt. You can set a goal that a separate evaluator re-checks. You can add a "Stop hook," a script that "blocks the turn from ending until it passes." Or you can use a verification subagent, so "the agent doing the work isn't the one grading it" ([best practices](https://code.claude.com/docs/en/best-practices)). Anthropic asks for evidence, not assertions, and says to fix root causes rather than suppress errors.

The recommended workflow is explore, plan, implement, commit. Planning matters most when many files change or the code is unfamiliar. To fight duplication, the guide says to point Claude at an existing example and follow its pattern, to use only libraries already in the codebase, and to ask a subagent whether there are "existing ... utilities I should reuse" ([best practices](https://code.claude.com/docs/en/best-practices)). Anthropic has no standalone "avoid duplication" guide. Its anti-duplication advice is spread across these lines plus the `/simplify` command, which runs four review agents checking "reuse of existing helpers, simplification, efficiency, and whether the change is at the right level of abstraction" ([Claude Code commands](https://code.claude.com/docs/en/commands)). `/simplify` does not hunt for bugs; `/code-review` does. A team worried about re-implemented helpers needs the reuse check, because a bug reviewer alone won't catch a working duplicate.

On instructions, Anthropic is firm that less is more. For each line in CLAUDE.md, ask: "Would removing this cause Claude to make mistakes?" If not, cut it. "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Leave out anything Claude can learn from the code, and use skills (instructions loaded only when needed) for occasional knowledge. Anything that must happen every time belongs in a hook, because "unlike CLAUDE.md instructions which are advisory, hooks are deterministic" ([best practices](https://code.claude.com/docs/en/best-practices)). If you've corrected Claude more than twice on the same thing, clear the session and start fresh with a better prompt.

On review, Anthropic recommends a writer/reviewer split: "A fresh context improves code review since Claude won't be biased toward code it just wrote." It also warns against overdoing it. "Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen." Reviewers should flag only gaps that affect correctness or stated requirements ([best practices](https://code.claude.com/docs/en/best-practices)). Its managed Code Review product follows the same idea. Its tuning file advice says to cap nits, require a file-and-line citation before any claim, and on re-review post only important findings so a fix doesn't reach "round seven on style alone" ([Code Review docs](https://code.claude.com/docs/en/code-review)).

For long autonomous runs, Anthropic's harness post sets a "clean state" standard. Each session should end with code "appropriate for merging to a main branch," so the next session doesn't start by cleaning "an unrelated mess." It keeps progress in a log file and a JSON feature list, and it forbids editing or removing tests ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). For big migrations, Anthropic's core idea is "you don't fix the code. You fix the process (loop) that produced the code," with "a built-in referee" such as tests or equivalence checks ([Claude blog, AI code migration](https://claude.com/blog/ai-code-migration)). That is the closest Anthropic gets to a single-source principle: when output is wrong, fix the rule, prompt or hook that made it, so the fix applies everywhere.

Anthropic also reports on its own use. By May 2026, **more than 80% of code merged at Anthropic was written by Claude**, and engineers merged about 8x as much code per day as in 2024. Anthropic itself calls the 8x "almost certainly an overstatement," and says Claude's code was "somewhat worse" than human code in late 2025 and is "roughly at parity today" ([Anthropic Institute](https://www.anthropic.com/institute/recursive-self-improvement)). This is a **company self-report**. Its safety net is several narrowly scoped review agents on every pull request, human approval tiered by risk, and **a logged reason for every automated approval, with a risk-weighted sample reviewed by humans** ([Claude blog, secure SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)). Anthropic says its automated reviewer would have caught "roughly a third of the bugs behind past incidents." That means two thirds would still get through.

## Users converge on guides plus sensors, and the sensors do the work

The community's answer has a clear shape. Birgitta Böckeler of Thoughtworks named it in April 2026 as "harness engineering." **Guides** steer the agent before it acts: instruction files, skills, specs. **Sensors** check its output afterward: tests, linters, duplicate detectors, architecture tests, AI review. Deterministic sensors catch duplicate code, complexity and architectural drift "reliably." AI reviewers are needed for code that does the same thing in different words, but they only catch it some of the time. Neither catches misunderstood requirements, which still need a person ([Böckeler, martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)). Thoughtworks' Technology Radar now rates "complacency with AI-generated code" as Hold (stop doing it). It also flags "codebase cognitive debt," the gap between what the code does and what the team understands, as Caution. Its suggested fixes are feedback sensors and architectural fitness functions, meaning automated tests of design rules ([Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/codebase-cognitive-debt)).

The guides side has become hugely popular but is weakly tested. GitHub's Spec Kit, a spec-first workflow tool, had about 140,000 stars by October 2026 ([github/spec-kit](https://github.com/github/spec-kit)). The skill collections obra/superpowers and Matt Pocock's skills, both in this project's toolset, had roughly 280,000 to 300,000 stars each. Both enforce design first, small planned tasks, test-first coding, fresh-agent review, and verification before claiming done ([obra/superpowers](https://github.com/obra/superpowers); [mattpocock/skills](https://github.com/mattpocock/skills)). No controlled evaluation of either exists. The best controlled evidence on instruction files is sobering. An ETH Zurich benchmark (**arXiv preprint**) found that AGENTS.md-style files **did not raise success rates on average and cost over 20% more** to run. Agents did follow specific instructions in them. Repository overviews didn't help ([Gloaguen et al. 2026](https://arxiv.org/abs/2602.11988)). Read together with Microsoft's 38%-to-69% jump, the lesson is that a short file of concrete build commands and boundaries helps, while a codebase tour mostly costs tokens.

Practitioner reports fill in the failure modes. These are **anecdotes**, but they match the data. On Hacker News one user said Claude built four separate registries when told to use one unified pattern, which took "half a day of shouting" to fix. Others said long constraint files get ignored, short "never do X" rules under about 50 lines work, and a pass/fail test makes the model "extremely reliable" ([HN thread](https://news.ycombinator.com/item?id=48144494)). One public repo's own Claude Code hook layer had four JSON escapers and five lock implementations ([mark-brannan/dotfiles #517](https://github.com/mark-brannan/dotfiles/issues/517)). The tooling that answers these failures is old and cheap. jscpd finds copy-paste in 220+ languages ([kucherenko/jscpd](https://github.com/kucherenko/jscpd)). ArchUnit turns architecture rules into unit tests ([TNG/ArchUnit](https://github.com/TNG/ArchUnit)). Mutation testing, which plants small bugs to see if tests notice, catches tests that were weakened.

Respected practitioners agree on the framing. Kent Beck contrasts "vibe coding," where you care only whether it works, with "augmented coding," where you still care about complexity, tests and coverage. His warning signs are loops, features nobody asked for, and agents cheating on tests ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)). Simon Willison's "vibe engineering" says agents reward existing good practice: with a solid test suite they "can fly" ([simonwillison.net](https://simonwillison.net/2025/Oct/7/vibe-engineering/)). Ranked by evidence, the fixes that work are: deterministic sensors the agent can't skip, then small batches with easy rollback, then short specific rules, then plan-first workflows, and last, AI review as a secondary net.

## Derive once has a name, a lineage, and no binding standard

Your rule is not new. It is one of the most cited principles in software, under several names. What doesn't exist is a formal standard that requires it.

The closest match is DRY as its authors meant it. The 20th Anniversary Edition of *The Pragmatic Programmer* defines it as: "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system." The authors admit the first edition was misread as "don't copy-paste code." They now say "DRY is about the duplication of knowledge, of intent" ([PragProg excerpt](https://media.pragprog.com/titles/tpp20/dry.pdf)). That clarification is exactly why two screens computing one count with different-looking code is still a violation. The same book gives a data example. A `Line` class that stores its length beside its start and end points is a DRY violation; length should be calculated. If you cache it for speed, only the owning class keeps it in sync. Eric Raymond restated the same sentence as SPOT, "Single Point Of Truth," at Brian Kernighan's suggestion ([Art of Unix Programming](https://www.linuxtopia.org/online_books/programming_books/art_of_unix_programming/ch04s02_2.html)).

| Name | Where it comes from | How close to "derive once" |
|---|---|---|
| DRY (20th anniversary edition) | Thomas & Hunt, 2020 | Same rule, same words; knowledge, not code |
| SPOT | Raymond, 2003, after Kernighan | Same sentence, renamed |
| System of record vs derived data | Kleppmann, *Designing Data-Intensive Applications*, 2017 | Same rule for data, plus the tie-break: the source is right |
| "Avoid redundant state" | React and Redux docs | Same rule at the display layer |
| Database normalization | Codd; Kent 1983 | Same rule for stored tables only |
| Once and Only Once | Kent Beck, Extreme Programming | Same instinct, aimed at code |
| Information hiding | Parnas, 1972 | Explains why one owner helps; not about duplicates |

Martin Kleppmann's "system of record" framing adds the tie-break your rule assumes. The system of record holds each fact once. Derived data can be rebuilt from it. If the two disagree, the system of record is right by definition ([O'Reilly, DDIA Part III](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/part03.html), wording from a search snippet). At the display layer, React says "avoid redundant state": if a value can be calculated during render, don't store it ([react.dev](https://react.dev/learn/choosing-the-state-structure)). Redux says to keep stored state minimal and compute values like counts in named selector functions, which gives each derived value one owner ([Redux Style Guide](https://redux.js.org/style-guide/)).

Your "missing facts get a stored field" rule fits once you split two kinds of value. A source fact that can't be recomputed from what's stored belongs in one stored place, as normalization and Kleppmann say. A derived value gets computed once, by one owner, as DRY's `Line` example says. Your rule says that if a display needs a fact the engine never recorded, add the field instead of guessing it again downstream. That is the system-of-record idea applied to an engine and its screens.

On formal standards, the answer is no. **ISO/IEC 5055:2021**, built from CISQ's code-quality measures, is the only standard found that measures duplication. It counts copy-pasted code under CWE-1041, "Use of Redundant Code," and lists "duplicated business logic" as a system-level weakness ([CWE-1041](https://cwe.mitre.org/data/definitions/1041.html); [CISQ](https://www.it-cisq.org/standards/code-quality-standards/)). But a clone detector can't find two different-looking functions that compute the same count, which is the case your reviews target. ISO/IEC 25010 names maintainability and modularity as qualities but sets no duplication rule ([arc42, ISO 25010](https://quality.arc42.org/standards/iso-25010)). MISRA C Rule 8.5 says a C declaration lives in one file only ([MathWorks, MISRA 8.5](https://www.mathworks.com/help/bugfinder/ref/misrac2012rule8.5.html)), which is single-source for declarations, not facts. The one partial "standard" adoption found is Oracle's Java guide rule "Avoid duplication."

There is also no standard name for "two screens show different counts for one thing." The nearest database term is an **update anomaly**: one fact stored in several places, and only some copies change. William Kent's classic example is a warehouse whose address differs between records ([Kent 1983](https://www.bkent.net/Doc/simple5.htm)). Nielsen's usability heuristic "Consistency and standards" is about words and conventions, not matching numbers ([NN/g](https://www.nngroup.com/articles/ten-usability-heuristics/)). The most precise description of your rule is: a visible update anomaly, or a derived view drifting from its system of record.

The main pushback doesn't apply to you. Sandi Metz argues "duplication is far cheaper than the wrong abstraction" ([Sandi Metz](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)), and the Rule of Three says wait for the third copy. Both are about merging code that merely looks alike. DRY's own authors draw the line: two identical validators for age and quantity are "a coincidence, not a duplication" ([PragProg excerpt](https://media.pragprog.com/titles/tpp20/dry.pdf)). Merge when two places answer the same question. Leave them alone when they only share a shape. Your rule sits on the first side.

Your setup is a C++ app built mostly by Claude agents. Every code merge needs a derive-once review from a fresh Sonnet agent, enforced by a hook. You have about two dozen ADRs (numbered decision records) in `docs/adr/`, source-scan tests such as `tests/test_long_paths.cpp` and `tests/test_single_owner.cpp`, a mechanical precheck script, and a one-round review rule. Your reviewer brief also does something the literature recommends but rarely makes concrete. It searches "by question, not by name" and compares answers as truth tables at the edges. That is the practical test for DRY's line between knowledge duplication and coincidence. Two functions with the same truth table answer the same question. Two that only look alike don't.

The research points to four gaps.

**First, you have no cheap clone detector.** A quick search of the repo turned up no jscpd, PMD CPD, semgrep or clang-tidy configuration. Your precheck finds kinds B to E mechanically, and kind A, a rule written twice, depends on an AI reviewer. Böckeler's point is that AI sensors catch things only some of the time. A token-based clone detector won't find two different-looking derivations. But it would catch the plain copy-paste that GitClear shows rising, for almost no cost, and leave the reviewer more time for kind A. Each kind-A finding can also become a new scan row, so the probabilistic catch turns into a deterministic one. You already do this for some rules, and the research supports doing it every time.

**Second, no human samples the agent-only reviews.** Microsoft's research says review's main payoff is shared understanding. Google's study found the same. Thoughtworks calls the loss of that understanding "codebase cognitive debt." Your fresh-agent reviewers clear the derive-once audit, but nobody builds a mental model from it. Anthropic itself, at 80% Claude-written code, logs the reason for every automated approval and has humans review a risk-weighted sample. Reading one merged review a week, picked from the riskiest areas, would match that precedent. Anthropic's reviewer catches only about a third of incident bugs, so a sample is a real safety net, not a formality.

**Third, the context you load every session is large.** Your CLAUDE.md is 67 lines, which is reasonable. But your memory index loads about a hundred entries into every session, many of them dated status notes. The ETH study found broad context files cost 20% more and don't raise success. Specific rules do help. Anthropic says to cut anything that wouldn't cause a mistake if removed. Amazon's stale-wiki outage shows the second risk: an agent acting on outdated notes. Moving finished-project notes out of the always-loaded index, and keeping only live rules there, would follow both lessons.

**Fourth, nothing checks that agent-written tests actually catch bugs.** Your kind-B check stops tests from recomputing production code, which is good. But Beck's warning sign is agents weakening tests, and Patel's study shows agent-written code makes later agent work harder. Mutation testing would show whether a test fails when the code it guards breaks. Running it occasionally on core engine files would be enough. This gap rests on practitioner advice (Böckeler), not controlled studies.

One caution cuts the other way. Anthropic warns that chasing every review finding breeds extra abstraction and defensive code. Your one-round rule and your "never call code wrong without ground truth" line already guard against that. Keep them. The literature's split between same-question and same-shape code is the right guard against your rule's own failure mode.

So these recommendations build on a strong base. They are ordered by value for effort. Each one says how strong its evidence is and whether it needs your decision first. "Code only" means it changes no display or stored record, so under your rules it can go ahead on recommendation.

### 1. Add a copy-paste detector with a baseline that only shrinks

GitClear's clearest finding is that copy-paste rises as refactoring collapses. Your review gate catches a rule written twice, but only when the AI reviewer notices. Böckeler's point is that deterministic tools catch plain copies every time, while AI review catches them some of the time. A clone detector won't find two different-looking derivations of one count. It finds the cheap kind for free, which leaves the reviewer more attention for the hard kind.

The best fit is the pattern you already use. `tests/test_single_owner.cpp` keeps a baseline that may only shrink, and your kind-E rule says every source scan lives in that file. So add the check there: normalize each line (strip whitespace and comments), hash every window of about eight lines across `src/` and `tools/`, and fail on any window that appears twice and isn't in the baseline. An external tool such as jscpd (needs Node) or PMD's CPD (needs Java) would do the same job but sits outside the one scan. Start with today's clones as the baseline so nothing breaks on day one.

### 2. Make every "rule written twice" fix end in a scan row

Anthropic's migration advice is "you don't fix the code. You fix the process (loop) that produced the code." When the reviewer finds a kind-A duplicate, the fix removes the copy. Nothing stops the next agent writing it a third time unless a scan row pins it. Some fixes already add a row. Make it the rule in `docs/agents/derive-once-review.md`: a kind-A fix is finished only when it adds a row to `tests/test_single_owner.cpp`, or says in one sentence why a text search can't catch it. Over time each probabilistic catch becomes a deterministic one, which is exactly the move the harness-engineering literature recommends.

### 3. Prune the memory index loaded every session

The memory index (`MEMORY.md`) is 98 lines pointing at 110 memory files, and every session loads it. Many lines are dated project status, such as finished phase plans and a line labelled "Historical/obsolete." The ETH Zurich study found broad context files cost over 20% more and don't raise success, while specific rules do help. Anthropic's test for each line is whether removing it would cause a mistake. Amazon's stale-wiki incident shows the second risk: an agent acting on a note that is no longer true.

Keep the index to live rules and active work. Move finished projects to an archive index that agents read only when a task points there. The same goes for `docs/handoffs/`, which holds 34 entries. Marking a handoff "superseded" when its work is done stops an agent following an old plan. The `consolidate-memory` skill is built for this pass. It's your call because it changes what every future session knows.

### 4. Keep one copy of the "How to explain things" rules

Your global `~/.claude/CLAUDE.md` and the project `CLAUDE.md` both carry the same "How to explain things" section, so every session in this repo loads it twice. That is a small derive-once break in the instructions themselves: edit one copy and the two drift. Keep the section in the global file and leave the project file with only what is unique to it, such as the BAD/GOOD example and the agent rules. The project `CLAUDE.md` has uncommitted edits right now, so this is yours to do or approve.

### 5. Read one merged review a week

Microsoft's and Google's research both found the main payoff of code review is shared understanding, not bug-finding. Your agent reviewers clear the derive-once audit, but you don't build a mental model of the code from their reports. Thoughtworks calls that gap "codebase cognitive debt." Anthropic, at 80% Claude-written code, still has humans read a risk-weighted sample of automated approvals. Its own reviewer would have caught only about a third of past incident bugs.

A light version fits here. Once a week, pick the merge that touched the engine or stored records and read its review report. To keep it near ten minutes, have the merge step put a three-sentence plain-English "what changed and why" at the top of each review report. It's your call because it costs your time.

### 6. Keep each reviewed change small

Google's median change is 24 lines. In Microsoft's .NET data, agent PRs under 50 lines succeeded 76–80% of the time, and success fell as size grew. DORA lists small batches among the capabilities that make AI pay off. Here, the last 15 merges into `main` changed a median of about 350 lines, and the largest changed about 1,700. A merge bundles several agent commits, so that isn't one agent's diff. But the merge is what the reviewer reads in one pass. A sensible start: the planner splits tasks so each reviewed diff stays under about 400 changed lines, and the reviewer flags anything larger as "split before review." Tune the number once you see how it feels; the research gives no exact threshold for agents.

### 7. Try mutation testing on the engine core

Your kind-B check stops tests from recomputing what production computes. It doesn't show that a test fails when the code it guards breaks. Kent Beck's warning sign is agents quietly weakening tests. Mutation testing checks for that directly: it makes a small deliberate bug, such as flipping `<` to `<=` or dropping a `+ 1`, and confirms some test fails. Mull, the main C++ tool, needs a clang build, and this project builds with MSVC. The cheaper route is a small script that applies a dozen such edits to one engine file at a time, rebuilds, and runs only that file's tests, which keeps within your "only your own tests" rule. Run it before a release on the scoring and path code, not on every merge. The evidence here is practitioner advice, not a controlled study.

### 8. Run the MSVC static analyzer on a schedule

The Carnegie Mellon study found static-analysis warnings rose about 18% after projects adopted agents. Your `/W4 /WX` build already blocks every compiler warning, which most projects don't manage. MSVC's `/analyze` mode finds a further class: possible null dereferences, buffer overruns and uninitialized reads. Add it as a separate build preset, run it weekly or before a release, keep a baseline of today's hits, and fail only on new ones. The first run may need a triage pass, which is why this is medium effort.

### 9. Track three health numbers over time

Google found that no single code metric predicts where debt hurts, so a dashboard isn't worth building. Three trends do tell you whether the gates work. First, derive-once findings per merge, split by kind A to E. A falling kind-A count means the scan rows are doing their job. Second, the size of the scan baselines, which should only shrink. Third, reverts and fix-up commits that touch a merge's files within a week of it. Your commits already carry `Task:` and `Agent:` trailers, so a small script over `git log` and the review reports can produce all three. Look at them once a month.

### 10. Add a CI build on push to `main`

The repo has no `.github/workflows`, so every gate lives in local hooks on one machine. A commit made outside those hooks skips them. That has happened: another session's edits were swept into a merge on 27 September. Amazon and OpenJDK both put the final gate on the server, where nothing local can skip it. A GitHub Actions Windows job that builds with `/W4 /WX` and runs the suite on each push to `main` would be that backstop. It doesn't break your "full suite once at merge" rule, because it runs on GitHub, not in an agent's session. It's your call: it uses Actions minutes if the repo is private, and the suite must run without local-only test data.

### Keep doing

Several of your rules already match the best evidence, and they should stay. The one-round review guards against the over-engineering Anthropic warns about. The "same question vs same shape" line is the exact distinction DRY's authors draw, and it keeps the rule from merging code that only looks alike. The `/W4 /WX` build, the 67-line `CLAUDE.md`, the headless `hydra_uitest` checks, and an ADR for every user decision all have direct precedent at the companies above.

## Conclusion

The evidence changes the shape of the "slop" argument. The problem isn't that AI writes worse code line by line; by Anthropic's own account it is now roughly at parity. The problem is that AI makes writing cheap and leaves reviewing just as expensive. Every large company that published real data hit the same wall. Google capped AI migrations to what reviewers could absorb. Microsoft saw agent PRs draw more comments. Amazon added senior sign-off after outages. Duplication is what fills that gap, because a pasted helper always passes review faster than a refactor. That makes derive-once more than a style preference in an agent-built codebase. It is the main defense against the one failure the data shows most clearly, and Patel's result suggests it is also what keeps the next agent effective.

The other takeaway is about where to spend effort. Instruction files and skills are the most popular answer online and the least proven. Deterministic checks the agent can't skip are the least glamorous answer and the best supported. Your setup already leans toward checks over prose. The next gains are probably in turning more AI review findings into source-scan rows, adding a cheap clone detector, and putting one human back in the loop as a sampler rather than a gatekeeper.
